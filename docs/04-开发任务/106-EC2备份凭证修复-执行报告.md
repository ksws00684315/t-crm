### 4.2 轮换不重启：归档请求带新令牌，postgres 未重启

- **确认方法**：pgBackRest 2.60 没有 HTTP 请求日志选项（`log-level-http` 不存在，见 §7），在验证网络里放了 socat TLS 终结侧车（`OPENSSL-LISTEN:443 → TCP:s3mock:9090`，`-v` 把每个字节转储进 `docker compose logs recorder`），从日志统计每个请求头的 `x-amz-security-token`。替身接受任意令牌，所以新令牌请求成功返回。
- 轮换前统计：`T106TOKEN-rot1` 共 1359 次（全部请求）。
- 以 rot2 再跑一次刷新脚本（原子替换生效，容器无需任何操作）→ `psql -c "select pg_switch_wal()"` 两次强制切段 → 8 秒后 `docker logs --since 60s recorder` 统计：`T106TOKEN-rot2` 3 次（即轮换后的新归档请求全部带新令牌）。
- `docker inspect postgres`：`RestartCount=0`，`StartedAt=2026-11-03T14:28:15.553553042Z` 轮换前后一致——postgres 没有重启。

### 4.3 原子性：连续 100 次刷新 + 持续写库触发归档，无半个文件、无解析失败

- 建测试表 `t106.atomic_probe`（独立 schema），后台循环 400 次 `insert + pg_switch_wal`（每次间隔 0.3 秒）持续触发归档。
- 同时在独立 Linux 容器（`--network none`，挂桩）连续快速执行刷新脚本 100 次：`refresh ok=100 fail=0`。
- 归档侧：并发窗口内 `pg_stat_archiver.failed_count` 全程保持 14 不增（那 14 次失败是 stanza 建立之前的初始归档尝试，时间戳 14:28:16–18，早于本项窗口）；`pgbackrest check` exit 0；postgres 日志在窗口内无 error/warning 新增；测试期间写库全部成功。
- 刷新侧：100 次全部成功，EXIT trap 保证无 `.tmp` 残留；每次都是同目录 `mv` 原子替换，归档进程读到的要么是完整旧文件要么是完整新文件。

### 4.4 刷新失败的三种情况：旧文件保留、非零退出、无凭证泄漏

桩的三种模式各跑一次，基线文件先取 sha256：

| 模式 | exit | stderr（原文） | 文件 | 泄漏扫描 |
|---|---|---|---|---|
| `fail`（桩自身报错） | 1 | `aws: simulated failure (NetworkError)` + `refresh-s3-credentials: aws configure export-credentials failed` | sha 不变 | 无命中 |
| `noexp`（无过期时间） | 1 | `refresh-s3-credentials: credentials have no expiration time (not from the instance role); refusing to write them` | sha 不变 | 无命中 |
| `shortexp`（15 分钟后过期） | 1 | `refresh-s3-credentials: credentials expire in 900s (< 1800s); not writing the file` | sha 不变 | 无命中 |

泄漏扫描：对三种情况的 stdout、stderr 和最终文件内容 `grep "T106AKIA\|T106wJalr\|T106TOKEN"`（桩里的假密钥串）均 0 命中。同一用例已固化为单元测试（`test-refresh-s3-credentials.sh`），macOS 本机（BSD date 路径）与 CI（GNU）都跑。

## 7. 专项结论（派发要求的四项）

1. **pgBackRest 2.60 的 config-include-path 默认值与 repo1-s3-token 支持**：镜像内（2.60.0）`pgbackrest help stanza-create` 明确输出 `--config-include-path … [default=/etc/pgbackrest/conf.d]`。conf.d 语义实测：目录内 **`.conf` 后缀**文件被读取（放含未知选项的片段立即报错），非 `.conf` 后缀被忽略；片段与主配置**重复设置同一选项会报错**（`option 'log-level-console' cannot be set multiple times`），不是覆盖——所以刷新片段只含主文件未设的四个凭证选项，pgbackrest.conf 头注释写明了这条约束。`repo1-s3-token` 支持：`--repo1-s3-token`（S3 repository security token）出现在 2.60 的选项列表，`repo1-s3-key-type=shared` + key/secret/token 组合可用。异步归档进程不构成停下条件：源码（release/2.60.0，`command/archive/push/push.c`）确认 `archive-push` 前台进程按需 fork 一次性的 `archive-push:async` 批处理进程，处理完当前队列即退出，每条 `archive_command` 都重新读配置，轮换令牌无需重启 postgres（§4.2 实测一致）。
2. **镜像内 postgres 用户的实际 uid**：`postgres:17.11`（`deploy/postgres/Dockerfile` 的基镜像，未改用户）内 `id -u postgres` = **999**。脚本常量 `POSTGRES_UID=999` 注明依据；容器内实测刷新产物 `owner=999 mode=600`，uid 999 可读（pgBackRest 在容器内以该用户运行）。
3. **轮换不重启时确认请求带新令牌的方法**：pgBackRest 2.60 没有 HTTP 请求日志选项（`log-level-http` 不存在，`pgbackrest help archive-push` 确认），所以把 TLS 终结点从替身前移到 socat 侧车（`alpine/socat:1.8.1.3`，`OPENSSL-LISTEN:443 → TCP:s3mock:9090`，`-v` 全量转储），pgBackRest 的每个 S3 请求头（含 `x-amz-security-token`）都落在 `docker compose logs recorder` 里。轮换前统计全部请求为 `T106TOKEN-rot1`（1359 次）；主机侧以 rot2 重跑刷新脚本 + 两次 `pg_switch_wal` 后，新请求 3 次全部带 `T106TOKEN-rot2`，且 postgres `RestartCount=0`、`StartedAt` 不变。生产等价手段：替身/真实 S3 侧的访问日志记录 token 后缀，或临时在替身上拒绝旧令牌。
4. **选用的 S3 替身及其许可证和版本**：`adobe/s3mock:5.2.3`（Docker Hub 官方镜像，Apache License 2.0，版本写死）。支持任意 access key/secret/token 组合（用于令牌观测）、path-style URI（验证用 `PGBACKREST_REPO1_S3_URI_STYLE=path`，仅写在 override；生产默认 host style 不受影响）。观测侧车 `alpine/socat:1.8.1.3` 不是 S3 替身（许可说明见 §8 第 5 条）。两者都只在验证环境，不进仓库，收尾时删除镜像。
