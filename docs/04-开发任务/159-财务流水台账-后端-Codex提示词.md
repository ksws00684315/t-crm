## 2. 已确认的业务规则（负责人 2026-11-22 会话）

事件与科目（「微店提现」即达人提现，同一付款事件记两笔）：

| 事件 | 记入科目 |
|---|---|
| 订单同步登记为未支付 | 预收入（订单级） |
| 订单支付 | 预收入转冻结中收入（订单级）、冻结中佣金支出（商品行级计提额） |
| 未支付订单关闭 | 预收入核销 |
| 订单退款成功 | 支出（订单级退款金额）、佣金扣回（商品行级）；退款中不记账（现行规则） |
| 订单结算确认 | 冻结中收入转可提现收入（订单级）、可结算佣金（商品行级释放额） |
| 达人提现付款成功 | 订单已提现（按 `crm_commission_withdrawal_allocation` 分摊记到商品行/订单）、佣金已提现（达人级付款额） |

- 金额基数、转账关系、恒等式、科目枚举命名以 158 规则文档为准；两者冲突时停下来报告。
- 订单已提现 = 该订单佣金被有效提现申请占用并完成付款。
- 多商品行：收入侧科目挂订单级；佣金计算与退款呈现以商品行为主；售后冻结维持整单判定。
- 结算周期维持现行规则（微店结算确认后释放，`CONFIRMED` 锚点）；计佣基数维持订单实付分摊、付款即计提。
- **唯一事实源**：佣金余额与状态仍以 `crm_commission_wallet`、`crm_commission_item_state` 为准；流水表只作口径记录与呈现，不参与余额计算，测试中断言两者金额一致。

## 3. 范围

改（后端 only）：

- **新迁移**：财务流水表（只追加）。至少含 `tenant_id`、科目、金额（`BigDecimal`，接口序列化为字符串）、业务发生时间（`Instant`）、关联 `order_id` / `order_item_id` / `kol_id`、来源类型与来源 ID、幂等键（唯一索引）、稳定流水号。表和字段全部注释（规范 04、flyway-migration skill）。
- **写入触发**（与现有触发点同事务、按幂等键防重）：
  1. 订单同步登记未支付订单：记预收入；
  2. 订单支付：预收入转冻结中收入，记冻结中佣金支出；
  3. 未支付订单关闭：记预收入核销；
  4. 退款成功：记支出、佣金扣回；
  5. 结算确认：冻结中收入转可提现收入，记可结算佣金（与 `CommissionReleaseService` 释放同触发）；
  6. 提现付款登记成功：按分配明细记订单已提现（行/订单级），记佣金已提现（达人级）。
- **模块边界**（规范 01）：order 不得依赖 commission。流水表归属与写入路径按 158 规则文档架构小节执行；拿不准先停下来报告。
- **接口**：`GET /admin-api/order/orders/{id}/chain` 财务流水板块改为科目化流水（收入侧订单级、佣金侧行级；同一商品行多笔提现分配拆行，含提现编号、付款时间、分配金额）。权限与可见性沿用任务 72 契约：`commission:view` 才返回财务字段，商务 `OWN` 混合归属隐藏金额。设计说明书 §6.2 同步。
- 既存注释与实现不一致（`crm_commission_item_state.basis_cny` 等）用新迁移修正注释，不改已合并脚本。

不做：前端（任务 160）；经营分析统计改造；预付相关科目（预付维持现状）。

- 多商品行分摊尾差归实付最大行；同一商品行多笔提现分配合计不重复。
