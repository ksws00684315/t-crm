# 138 复制任务提交上限改为系统配置：执行报告

- 分支：`task/138-convert-limit-config`
- 日期：2026-11-08
- 类型：功能调整（后端 + 管理端语言包，无迁移）

## 1. 背景

负责人 2026-11-08 要求：表格脚本提交复制任务时，「每次最多 500 个商品」是写死的，需要改为可配置。

修改前，上限写死在两处：

- `ProductLinkService.MAX_CONVERT_ITEMS = 500`；
- `ProductLinkController.ConvertRequest.items` 的 `@Size(max = 500)`。这一处在参数校验阶段就会拦截。

超过上限时只返回笼统的「请求参数无效」，客户看不出是数量超限。表格脚本把选区内的全部商品放在一次请求里提交，脚本本身没有上限，所以不用改。

负责人选择的方案：放进任务 34 的「系统配置」，默认 500，可设 1～5000，改完不用重启。

## 2. 改动

| 文件 | 改动 |
|---|---|
| `backend/.../system/model/SystemConfigDefinition.java` | 新增配置项 `product-links.max-convert-items`，分组为业务默认值与上限，整数，默认 500，范围 1～5000 |
| `backend/.../product/service/ProductLinkService.java` | `convert` 每次请求都通过 `SystemConfigApi.getInt` 读取上限，超出时报 `COMMON_VALIDATION_FAILED`，消息为「每次最多提交 N 个商品」。测试用构造器默认 500 |
| `backend/.../product/service/ProductLinkMessages.java` | 新增 `tooManyItems(max)` 中文消息（§6.5 对外接口用中文 `msg`） |
| `backend/.../product/controller/ProductLinkController.java` | `@Size(max = 500)` 改为 `5000`：与配置允许的最大值一致，作为请求体的硬上限；实际生效的上限在 service 中检查 |
| `admin-ui/src/locales/zh-CN.ts`、`en-US.ts` | 系统配置页新增该配置项的名称 |
| `deploy/README.md`、`docs/03-设计/系统详细设计说明书.md` | 系统配置表新增该项；`/convert` 接口说明改为按配置限制条数 |
| 测试 | `ProductLinkServiceTest`：上限配置为 2 时，提交 3 个被拒绝，返回中文消息，且不会验证令牌；上限配置为 1000 时，提交 501 个能通过数量检查。`SystemConfigValidationTest`：配置项总数 36，接受 1 和 5000，拒绝 5001 |

**为什么最大只开到 5000**：微店 QPS 默认是 5，每个商品要先在每个启用店铺各探测一次，再调用若干次接口完成复制。5000 个商品的任务要跑几个小时；任务越大，中途重启或失败的影响也越大。

## 6. 同时排查：订单同步是否有任务 137 的跨店问题（负责人 2026-11-08 提问）

结论：代码结构上没有。

- 任务 137 的问题出在 `vdian.item.get`：它接收外部传入的任意商品 ID，微店不校验商品是否属于当前令牌对应的店铺。
- 订单（`vdian.order.list.get` → `vdian.order.get`）、退款（`open.SellerQueryRefundList` → 详情）、结算流水（`shop.order.trade.detail`）和商品导入（`vdian.item.list.get`）都是用店铺自己的令牌列出本店数据，再对列表里的 ID 取详情。没有一处拿外部提供的 ID 去逐个店铺试探。订单详情还会比对返回的订单号。
- 全后端按外部 ID 调用微店接口的，只有商品复制探测一处，已在任务 137 修复。
- 残余风险：订单唯一键是 `(shop_id, weidian_order_id)`。如果微店列表接口返回了别家店的订单，同一订单会按两个店铺各存一份。按接口语义这不太可能发生。如需实证，可在正式库只读查询是否有同一个 `weidian_order_id` 出现在多个店铺下（需负责人同意，结果只看条数）。
