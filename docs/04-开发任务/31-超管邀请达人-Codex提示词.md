## 1. 背景与决定

现在「达人管理 → 达人列表」上的「邀请达人」入口只对商务显示，条件是：启用的子账号、数据范围为本人、有 `kol:edit` 和 `kol:register-link`（任务 28、30）。超级管理员看不到这个入口。

负责人 2026-10-20 决定：

- **超级管理员也能邀请达人**：超管有自己的商务邀请码（8 位）和注册链接。
- **用超管的邀请码注册的达人不绑定商务**：`bd_user_id` 为空，关系状态显示「待更新」，期间业绩归管理员（公司）。这与 1018 表第 14 行（04.02）一致：「若未绑定有效商务，达人状态则显示待更新，待更新期间产生的佣金归管理员所有」。之后由超管分配或转移给商务，可以用现有的认领和商务转移功能。
- 审核流程不变：这类达人注册后同样是「待审核」，可以由超管审核。
- 平台管理员、数据范围为「全部」的普通子账号，仍然**不能**取得邀请码。

## 3. 要做的事

### 3.1 后端

- `GET` / `POST /admin-api/kol/register-code`：
  - 当前公司的超级管理员可以调用。权限码 `kol:register-link` 保持不变，超管本来就拥有全部权限码；
  - 商务的判断条件保持不变；
  - 其他账号仍然返回 422 `KOL_INVALID_BD_USER`。
- `crm_kol_register_code.bd_user_id` 的含义改为「邀请码所属账号」：可以是商务，也可以是超管。
  - 用新迁移只更新这一列的注释（版本号 `V202610201000`），**不改**列名和约束；
  - 每个账号同一时间最多一条有效码（现有的部分唯一索引不变）。
- **注册时的归属**：
  - 邀请码所属账号是可用商务时，绑定该商务，与现在一样；
  - 是超管时，`bd_user_id` 为空，不写商务归属历史，或写一条「未分配」，与现有商务转移中「转为未分配」的写法保持一致；
  - 注册时如果邀请码所属的商务已不可用，按现有规则处理，在报告中写明现在的行为。
- **注册预览**：邀请码属于超管时，返回 `bdUserName = null`，`tenantName` 照常返回。
- 设计说明书：§4.2「自助注册」第 1 条、§6.2 的 `register-code` 行写明超管可以取得邀请码，以及用它注册的达人不绑定商务；在 ADR-025 末尾补一条「2026-10-20 补充」。

### 3.2 管理端

- `canRegisterLink`：当前公司的超级管理员，或者满足原来商务条件的账号，都可以使用。平台管理员不显示。
- 「邀请达人」弹窗：超管打开时，在邀请码和链接下方加一行提示：「通过此链接注册的达人不绑定商务，注册后显示为待更新，请通过认领或商务转移分配给商务。」中英文都要有。

### 3.3 达人端

- 注册页：`bdUserName` 为空时，显示「Invited by {tenantName}」；两者都为空时不显示这一行。

## 4. 测试要求

**先写测试，复现「超管调用 `register-code` 返回 422」**，再修改。

| 场景 | 期望 |
|---|---|
| 超管取得、重新生成邀请码 | 成功；8 位；同一时间只有一条有效码 |
| 平台管理员、数据范围为「全部」的子账号 | 仍然被拒绝 |
| 用超管的邀请码注册 | `bd_user_id` 为空；列表显示关系状态 `PENDING_UPDATE`；审核状态为 `PENDING` |
| 用商务的邀请码注册 | 行为不变 |
| 注册预览 | 超管的邀请码返回 `bdUserName = null` 和 `tenantName` |
| 认领与转移 | 超管邀请注册的达人能被商务认领，也能被转移给商务（集成测试） |
| 管理端 | 超管能看到入口和提示行；商务看不到提示行；平台管理员看不到入口 |
| 达人端 | `bdUserName` 为空时显示公司名 |
