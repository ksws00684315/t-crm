# 任务 86 执行报告：达人端列表表格高度修复

> 分支：`task/86-kol-table-height`（从合并 #163 后的 `main` `5f75ee18` 开出）
> 依据：架构师任务说明（遗留 L-043），规范 05、08、11、12、13（第 3.16 节）。
> 状态：kol-portal 六项检查全部通过，浏览器验收 72 组全部通过，等待审查。L-043 的状态按惯例由合并记录更新，本 PR 未改 `遗留问题清单.md`。

## 1. 根因（已在真实浏览器确认）

`DataTable.measureHeights` 用父容器 `clientHeight` 算表格上限，前提是页面高度固定。`.items-page`、`.orders-page` 和资金页的 `.el-card__body` 高度都跟内容走：表格一变矮，父容器跟着变矮，上限再也回不去，最后落到 `Math.max(160, ceiling)`，再按整行取整后只剩 1 行。

修复前在 Chrome 中逐页实测（3 行数据，模拟接口）：

| 页面 | 受影响 | 父容器 | 1440×900 表格高度 | 可见行数 | 说明 |
|---|---|---|---|---|---|
| `views/items` | 是 | `.items-page`（423px，跟内容走） | 121px | 1/3 | L-043 原始现象 |
| `views/orders` | 是 | `.orders-page`（451px） | 105px | 1/3 | |
| `views/funds` | 是 | `.el-card__body`（295px） | 105px | 视口内 0/3 | 根因相同，L-043 未确定 |
| `views/income/prepay` | 否 | `.prepay-results`（796px，`height: 100%`） | 220px | 3/3 | 作为正确做法的参照，未改 |

1280、2560 宽下表格高度相同（`funds` 在 2560 宽下可见 1/3 行）；修复前截图见 `assets/task-86/before-items-short-1440x900-zh.jpg`。

## 2. 改动

只改页面样式，**没有改 `DataTable`**，所以不产生与管理端版本的同步差异（规范 11 §12），也没有搬 `fill-available-height`（任务说明不要求，规范 13 第 3.16 节也只覆盖管理端）。

- **`items`、`orders`**：页面 `height: 100%`，沿用 `income/prepay` 已验证的做法；`min-height: 420px` 保证极矮窗口下至少能看到首行，放不下时由外层滚动；手机端重置为 `height: auto; min-height: 0`。
- **`funds`**：不能用页面剩余高度。汇总区在 1440×900 下占约 640px，下方还有「提现申请记录」卡，整页本来就由外层滚动。所以桌面端（`min-width: 768px`）把记录卡固定为 560px，`.el-card__body` 跟随卡高，`DataTable` 拿到稳定的上限；手机端不受影响。
- **测试**：新增 `views/__tests__/list-page-height.spec.ts`。jsdom 没有布局，只能校验 CSS 契约（`CopyText.spec` 等已有此做法），渲染结果以 §4 的浏览器实测为准。

未改：`DataTable`、`income/prepay`、手机卡片和分页模型、依赖、接口。

### 方案取舍

- **只在 `DataTable` 里判断「父容器不固定就不设上限」**：不选。这样长列表不再内部滚动，20 行时分页被推到一屏以外，不满足验收要求。
- **`funds` 高度随内容、由视口算上限**：不选。要给 `DataTable` 加属性，并与管理端版本产生差异；规范 13 也不主张用视口减法凑高度。
- **`items`、`orders` 用 `min-height: 100%` 代替 `height: 100%`**：不选。内容一旦超高，父容器就跟着变高，窗口缩小后上限回不来。

## 4. 浏览器验收

### 4.2 `funds` 的分页可见性

1440×900、1280×800 下，汇总区约占 640px，首屏放不下记录卡，这一点修复前后相同，要改只能压缩汇总区，属范围外。滚到记录卡后，整张卡在视口内，分页可见，长列表在卡内滚动。三种尺寸、中英文都已实测，分页底部分别在 681/900、623～662/800、969/1440。2560×1440 下首屏即可看到分页。

## 6. 需要审查人知晓

1. **`funds` 短列表卡内留白**：记录卡固定 560px，短列表和空列表时卡内下方有空白（3 行约 170px，见 `funds-short-2560x1440-zh.jpg`）。这是长列表稳定内部滚动的代价，与规范 13 第 3.16 节「短列表保留卡片空间」的方向一致，但该节只覆盖管理端。卡高若要调整，改 `.records-card` 的 `height` 和对应测试即可。
2. **`funds` 首屏看不到分页**：见 §4.2，属页面结构决定，未改。
3. **全屏模式上限未随卡片放大**：全屏时卡片占满视口，但 `measureHeights` 仍按页面算上限，1440×900 下 `items` 卡片 804px、表格 486px，卡内有空白。按代码判断这是原有逻辑，修复前和 `prepay` 也会如此（这两种情况未实测），不在本任务范围。
4. **顶栏公司名被挤成竖排**：截图右上角「t8 / 6 / Co」在修复前后相同，与本次改动无关。模拟数据缺部分资料字段，未确认真实数据下是否也如此，建议另查。
