## 4. 要做的事

### 4.1 订单明细唯一键只约束有效行（报告 P2-01）

新迁移 `V202610181000__order_item_identity_live_rows.sql`：

- 删除约束 `uk_crm_order_item_identity`，改建部分唯一索引 `(order_id, sub_order_id) WHERE is_deleted = FALSE`；
- 带中文注释（索引用 `COMMENT ON INDEX`），说明为什么只约束有效行；
- 在报告中评估锁表风险。

补集成测试复现原问题：导入订单（子订单号为空）→ 接口同步覆盖并逻辑删除导入明细 → 接口再次同步时出现与已删除明细相同的键 → 现在应正常插入。

### 4.2 请求格式错误不再返回 500（报告 P2-02，以及同类问题）

`GlobalExceptionHandler` 增加：

| 异常 | HTTP | 错误码 |
|---|---|---|
| `HttpMediaTypeNotSupportedException` | 415 | 新增 `COMMON_UNSUPPORTED_MEDIA_TYPE` |
| `HttpMessageNotReadableException`（JSON 格式错误、类型不符） | 400 | `COMMON_VALIDATION_FAILED` |
| `MissingServletRequestParameterException`、`MethodArgumentTypeMismatchException` | 400 | `COMMON_VALIDATION_FAILED` |

- 先确认这些异常现在确实落到 500（写复现测试），再修复；
- 新错误码登记在 `ErrorCode`，并在 `admin-ui`、`kol-portal` 的 `zh-CN`、`en-US` 语言包中补文案；
- 日志不得输出请求体内容。

### 4.3 导入模板的编号列设为文本格式（报告 P2-07）

Excel 会把长数字当数值处理，超过 15 位丢精度，并改成科学计数法。

- 扩展 `ExcelFiles` / `ImportTaskApi.template`：允许指定哪些列使用文本格式（单元格格式 `@`）；
- 各导入模板中所有编号类列都设为文本：
  - 订单导入：微店店铺 ID、订单号、子订单号、商品 ID、SKU ID；
  - 退款导入：微店店铺 ID、退款单号、订单号、子订单号；
  - 原商品、对应关系、达人导入中的微店店铺 ID、商品 ID 等编号列（逐个核对列定义）；
- 测试：用 POI 读取生成的模板，断言这些列的格式是文本。

### 4.4 集成测试去掉 `Thread.sleep`（报告 P2-05）

`backend/src/test` 中共 12 个文件使用 `Thread.sleep`。

- 在测试代码中写一个小的等待工具，例如 `TestWait.until(Duration timeout, BooleanSupplier condition)`，轮询间隔短，超时后给出明确的失败信息；
- 把「等异步结果」的 sleep 改为条件等待；
- 「必须等过某个时间点」的 sleep（例如验证码过期、限流窗口）如果不能改成条件等待，保留，但加注释说明原因；
- 不得放宽任何断言。

### 4.5 点击日志按公司查询的索引（报告 P2-09）

`crm_click_log` 是按时间分区的大表，现有索引 `(kol_id, product_id, click_time)` 不以 `tenant_id` 开头。

1. 先列出所有读 `crm_click_log` 的查询（看板尚未实现，以现有代码为准），判断哪些按公司过滤；
2. 在本地造一批数据（例如 2 家公司、各 100 万行，分布在多个分区），用 `EXPLAIN (ANALYZE, BUFFERS)` 对比有无新索引的计划；
3. **只有在现有查询确实受益时**才加索引（迁移 `V202610181010`，在分区父表上建，注意分区表建索引的写法与锁表影响），否则不加，把对比结果和「等看板实现时再定」写进报告。

### 4.6 鉴权声明与实际一致（报告 P3-05、P2-10）

- `NotificationController`：角色声明去掉 `PLATFORM_ADMIN`。平台管理员应由注解直接拒绝，返回 403；对应测试改为断言注解拒绝。
- `TaskController`：保持「公司账号可访问、服务层只返回提交者本人的任务（超管可看全部）」的现状，**不改代码**；在设计 §6.2 任务接口一行写明这条规则。

### 4.7 控制器层测试补齐（报告 P3-02）

`system.controller`（行覆盖约 23%）和 `order.controller`（约 29%）偏低。

- 为这两个包补 Web 层测试（沿用现有 controller 测试的写法）：每个接口至少覆盖鉴权失败、参数校验失败、成功三种情况；
- 目标：两个包行覆盖都达到 70% 以上；
- 在 `pom.xml` 中为这两个包加 JaCoCo 门槛（LINE 0.70），不得降低任何现有门槛。

### 4.8 接口清单防漂移（报告 P2-03、P2-11）

全量 OpenAPI 受工程差距 I6 限制，本任务不引入 springdoc。改为：

1. 把设计 §6.2（管理端）、§6.3（达人端）的接口表补全到与代码一致：
   - 每个接口一行：方法、完整路径、权限声明、说明；
   - 以任务 22 附件「接口鉴权清单」为起点，逐个核对代码。
2. 新增单元测试：用 Spring 的 `RequestMappingHandlerMapping`（或扫描 `@RequestMapping` 注解）取出所有接口的「方法 + 路径」，断言每一个都出现在设计说明书 §6.2 / §6.3 中，反之也成立。失败信息列出多出和缺失的接口。
3. `backend/openapi-order.yaml` 保留，在文件头注明「接口以设计 §6.2 为准，由测试保证与代码一致」。

## 5. 测试要求

| 场景 | 期望 |
|---|---|
| 订单明细 | 已逻辑删除的明细不阻止同键新明细插入；有效明细仍唯一 |
