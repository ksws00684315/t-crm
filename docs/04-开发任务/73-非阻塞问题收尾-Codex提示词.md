## 2. 范围

### 2.1 后端健壮性（#106）

**A. 库中出现代码不认识的枚举值时，列表不能整页 500**

- 现状：MyBatis 默认的枚举 TypeHandler 遇到未知取值时抛异常，整条查询失败。受影响的字段见 #106「影响面」表格。先全仓核对一遍枚举映射字段，表格之外的也要列出。
- 读取时容错：未知取值返回 `null`，并记一条 `WARN`，内容包含列名、原始值和目标枚举类型。日志不得输出个人信息或凭证。
- 写入时保持严格：Java 枚举类型本身已经限制了写入的取值，接口入参校验不变。
- **读到 `null` 之后**：逐个检查读这些字段并按取值分支的业务代码，比如状态机、权限判断、`switch`。确认 `null` 不会被当成某个默认状态，也不会引发空指针。需要处理的地方要显式按「未知」处理。在执行报告中列出检查过的调用点和结论。
- 前端：账号列表中，这些字段为 `null` 时要显示占位符，不能报错，也不能显示空白。只核对 #106 验收提到的页面，即账号管理（岗位、角色、数据范围）。

**B. 数据库版本比代码新时启动失败——只在部署环境启用**

- 负责人决定：**本机开发和共享库默认关闭**。原因是所有本机代理共用一个库，分支落后的代理也必须能启动。**预览环境（`docker-compose.preview.yml`）同样连共享库，也不得启用。**
- 只在生产部署模板 `deploy/docker-compose.prod.yml` 中通过环境变量开启，并在 `deploy/README.md` 中说明作用与回滚方法。
- 优先用 Flyway 现成的配置实现（例如 `ignore-migration-patterns`），不要自己写版本比较。失败时日志要能看出「库版本超前，请部署不低于该版本的镜像」。如果 Flyway 自带的报错做不到这一点，再补一条明确的提示。
- 测试只用 Testcontainers 集成测试：在容器库的 `flyway_schema_history` 中插入一条超前版本，断言开启后启动失败、关闭时正常启动。**严禁改动共享库的 `flyway_schema_history`。**

**C. 追踪号进日志**

- `RequestTraceFilter` 已把 `traceId` 写进 MDC，但日志格式没有输出它。优先用 Spring Boot 的 `logging.pattern.correlation` 一类配置项加上 `%X{traceId:-}`，非 Web 线程留空。只有配置项做不到时，才新增 `logback-spring.xml`，并在报告中说明原因。
- `GlobalExceptionHandler.unknown()` 已经把异常对象传给了日志，确认堆栈能完整输出即可。
- 逐个检查 `LOG.error` 中没有传异常对象的调用：该带堆栈的补上。可能把令牌、密钥或个人信息带进日志的（例如微店接口异常的消息），保持现状或做脱敏，并在执行报告中逐条写明结论。
- 测试：构造一个必现的未捕获异常，断言响应体里的 `traceId` 能在日志中找到，且该日志行带有根因异常的堆栈（可以用 `OutputCaptureExtension` 一类方式）。
