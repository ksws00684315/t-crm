## 2. 关键结论与截图对照

- **订单总额保留**：`order-detail-1440-zh.png` 中「商品金额」「单价」为「缺失历史售价」，「订单总额」为 `¥297.00`。根因是 `OrderService.detail` 曾把 `itemAmount` 同时传给商品金额与订单总额两个字段，现已按源订单 `crm_order.total_amount` 取值。
- **单价文案不再截断**：`order-detail-1440-en.png` 的 `Unit price` 列显示 `No price`，`order-detail-1440-zh.png` 的「单价」列显示「缺失历史售价」，两者均无省略号；上一版英文 `Historical price unavailable` 被截成 `Historical pric...`，本轮改短英文文案并把该列由 110 加宽到 140。
- **补录标注**：`order-chain-1440-zh.png` 中比例 `8.5%` 带橙色「补录」标签，同行单价为「缺失历史售价」，净达人佣金 `¥19.47`。
- **两类 409 语义不同**：`rate-supplement-conflict-*` 是「已有比例、不可覆盖」（写入被旧值挡住）；`rate-supplement-state-conflict-*` 是「订单不再满足补录前提」（付款/归属状态变化）。
- **角色维度**：`role-chain-staff-1440-zh.png` 证明商务账号能看到链路数据但看不到补录入口 —— 入口由前端 `isSuperAdmin` 控制，后端接口另有 `@SaCheckRole("SUPER_ADMIN")`。仅靠后端 403 无法证明界面入口被隐藏，故补此场景。

## 4. 复跑方式


脚本自包含：管理员与商务两个账号的登录、截图、断言与临时数据回写都在脚本内；输出 JSON 汇总（`checks` / `failed` / `screenshots` / `errors`）并写入 `.tmp/185-preview/browser-107/results.json`。

脚本涉及的两个临时写操作（清空 `pay_time`、改 `bd_user_id`）都包在 `try/finally` 中并带独立的回写断言，任一场景失败也会恢复数据。
