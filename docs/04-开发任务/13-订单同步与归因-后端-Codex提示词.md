## 1. 背景

客户确认的一期优先级是：注册 → 复制商品并生成链接 → **在达人开始推广前同步微店订单**（2026-10-14 会议）。规则已确认：

- 一笔订单只属于一位达人；
- 订单按支付时刻记录所属商务：商务转移之前的订单归原商务，之后的归新商务；
- 不能自动归因的订单由运营人工处理。

任务 09a 已经定义好微店订单、退款接口的类型化客户端（`integration.api.WeidianBusinessApi`），以及令牌中心、限流、重试，但还没有用真实账号跑通过。

佣金台账依赖「微店结算时间」这一待确认项（设计 §0.4 Q2），放在后续任务，**本任务不计算佣金**。

## 4. 已定的设计决定（不要自行改变）

### 4.1 迁移 `V202610171600__create_order.sql`

所有表都带 `tenant_id NOT NULL`、雪花主键（正值）和通用字段，表与字段都要有中文注释。

| 表 | 要点 |
|---|---|
| `crm_order` | 按设计 §5.2，另加 `kol_id`、`bd_user_id`、`settled_time`（本任务不写入，留给后续任务）、`attribution_status`（`PENDING` 未处理 / `ATTRIBUTED` 已归属达人 / `NON_KOL` 非达人订单 / `CONFLICT` 明细归到多位达人 / `UNMATCHED` 有未匹配明细）。唯一键 `(shop_id, weidian_order_id)`。索引 `(tenant_id, pay_time)`、`(kol_id, pay_time)`、`(bd_user_id, pay_time)`、`(tenant_id, attribution_status)` |
| `crm_order_item` | 按设计 §5.2。`sub_order_id`：微店有子订单号就用它，没有就用「商品 ID + SKU ID + 行号」生成稳定的键。唯一键 `(order_id, sub_order_id)`。`attribution_type`：0 未匹配 / 1 商品 ID / 2 人工 / 3 非达人 / 4 冲突 |
| `crm_refund` | `order_id`（必填）、`order_item_id`（可空：退款能对应到明细时才填）、`weidian_refund_no`（唯一）、`amount`、`raw_status`、`refund_time`、`finish_time` |
| `crm_order_sync_state` | 每个店铺一行：`shop_id`（唯一）、`order_cursor`、`refund_cursor`（上次成功同步到的更新时间）、`last_success_at`、`last_error`（英文，≤ 500） |

金额一律用 `NUMERIC(14,2)`，单位为元（微店退款接口中以分为单位的字段要换算）。时间一律 `TIMESTAMPTZ(3)`。

### 4.2 同步

1. **频率与范围**：定时任务每 5 分钟运行一次，按公司执行，只同步启用且授权状态为 `AUTHORIZED` 的店铺。
   - 每个店铺一把分布式锁 `order:sync:{shopId}`，不等待；
   - 不同店铺之间互不影响，一个店铺失败不影响其他店铺。
2. **订单窗口**：
   - 调用 `vdian.order.list.get`，按更新时间增量拉取：`update_start = order_cursor − 10 分钟`，`update_end = 现在`；
   - 首次同步从「现在 − 24 小时」开始；
   - 用 `has_more` / `after_key` 翻页；
   - 每个新增或有变化的订单调用 `vdian.order.get` 取明细。
3. **退款窗口**：用 `open.SellerQueryRefundList` 按更新时间增量拉取（同样回溯 10 分钟），逐笔调用 `open.sellerQueryRefundDetail`。退款对应的订单本地不存在时，先拉取该订单。
4. **游标**：整批成功后才前移，失败时不前移；接口失败写入 `last_error`，按 09a 的错误分类处理。
5. **手动同步**：`POST /admin-api/order/syncs`（`order:manage`），请求 `{shopId}`，立即返回 202，同步在后台执行。同一店铺正在同步时返回 409 `ORDER_SYNC_RUNNING`。
6. **幂等**：订单按 `(shop_id, weidian_order_id)`、明细按 `(order_id, sub_order_id)` 更新，不会重复写入。状态、金额、退款变化时更新，并记录 `last_sync_time`。
7. **数据最小化**：不解析、不保存买家姓名、电话、地址；`raw` JSON 不落库。买家 ID 存 `SHA-256(TCRM_IP_HASH_SALT + 买家 ID)`，盐值复用现有环境变量，在报告中说明。

### 4.3 状态标准化

1. 在一个类里集中维护「微店原始状态 → 标准状态」的映射（设计 §8.1）。依据 09a 的执行报告和微店文档 `vdian.order.get` 的状态说明。
2. 文档里查不到的原始状态映射为新增的标准状态 `UNKNOWN`（不算有效订单），记 `WARN`，不阻断同步。
3. 映射表写单元测试。报告中列出全部映射，并注明「M0 用真实订单核对」。

### 4.4 归因

1. **逐条明细匹配**：按 `(订单所在店铺, 明细商品 ID)` 查找**支付时刻有效**的对应关系（`valid_from ≤ pay_time`，且 `valid_to` 为空或晚于 `pay_time`）。
   - 匹配到：写入 `kol_id`、`product_id`、`kol_item_id`，`attribution_type = 1`；
   - 匹配不到：`attribution_type = 0`。
2. **订单级规则**（一笔订单只属于一位达人）：
   - 已匹配的明细都指向同一位达人，且没有未匹配的明细：`ATTRIBUTED`，订单的 `kol_id` 为该达人；
   - 已匹配的明细指向两位及以上达人：`CONFLICT`，所有已匹配明细改为 `attribution_type = 4`，订单 `kol_id` 为空，进入人工匹配池；
   - 存在未匹配的明细：`UNMATCHED`，进入人工匹配池；若已匹配部分只有一位达人，订单 `kol_id` 先写为该达人，人工处理时再确认。
3. **已归因的不自动改**：后续同步不改变已归因明细的归属（设计 §4.6）。
4. **未支付订单不归因**：没有支付时间的订单不归因，`attribution_status = PENDING`，支付后再归因。

### 4.5 所属商务快照

1. 订单得到 `kol_id` 时，按该达人的商务归属历史（`crm_kol_bd_history`）找出覆盖 `pay_time` 的那一条，写入 `crm_order.bd_user_id`。该时段没有商务（`bd_user_id` 为空）时订单的商务也为空，即归公司（设计 §3.2 第 3 条）。
2. **快照修正任务**：每 10 分钟运行一次，读取上次运行之后新增的归属历史记录（按 `create_time`），重新计算这些达人在对应时段（`pay_time ≥ start_time`，且 `end_time` 为空或 `pay_time < end_time`）内订单的 `bd_user_id`。
   - 这样无论任务 16 是立即转移，还是预约生效后由定时任务补写历史，订单都能得到正确的商务。
   - 检查点存 Redis `order:bd-snapshot:checkpoint`，Redis 中不存在时回溯 24 小时。
3. `kol` 模块需要在 `kol.api` 中提供两个按需读取的方法：
   - 按达人和时间点查商务；
   - 按 `create_time` 区间列出归属历史。

   这是本任务允许修改 `kol` 模块的唯一范围。

### 4.6 人工匹配

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /admin-api/order/unmatched` | `order:manage` | 人工匹配池：`attribution_status` 为 `CONFLICT` 或 `UNMATCHED` 的订单及其明细，分页，可按店铺、支付时间筛选 |
| `PUT /admin-api/order/orders/{id}/attribution` | `order:manage` | 请求 `{kolId}` 或 `{nonKol: true}`，加必填的 `reason`（≤ 255 字）。整单指定达人：全部明细 `attribution_type = 2`，订单 `ATTRIBUTED`，并按 4.5 写入所属商务；标记非达人：全部明细 `attribution_type = 3`，订单 `NON_KOL`。指定的达人必须属于本公司 |
| `POST /admin-api/order/orders/{id}/reattribution` | `order:manage` | 按 4.4 重新自动归因，用于运营补导对应关系之后 |

人工操作写入操作日志，参数包含原因。

### 4.7 订单查询

`GET /admin-api/order/orders`，权限 `order:view`，分页。

- 筛选：店铺、支付时间区间、达人编号、标准状态、归因状态。
- 每行带明细与退款合计。
- 数据范围 `OWN` 的账号只看到 `crm_order.bd_user_id = 本人` 的订单（按快照，与客户需求 6 中「商务只看自己名下时间段内的数据」一致）。
- 响应中不含买家信息。

## 6. 测试要求

微店接口用模拟服务器或桩实现，不连真实微店。

| 场景 | 期望 |
|---|---|
| 状态映射 | 映射表全部分支；未知状态映射为 `UNKNOWN` 并记 WARN |
| 增量同步 | 首次回溯 24 小时；之后从游标回溯 10 分钟；翻页；失败不前移游标；锁冲突跳过 |
| 幂等 | 同一订单重复同步不重复写入；状态与金额变化被更新 |
| 退款 | 退款写入并换算分到元；对应订单不存在时先拉取订单 |
| 归因 | 支付时刻有效的映射才匹配（映射在支付之后才生效、在支付之前已失效两种情况都要测）；单达人、冲突、未匹配三种订单；未支付订单不归因；已归因明细不被后续同步改写 |
| 所属商务 | 支付时刻在某条历史区间内取该商务；区间商务为空时订单商务为空；快照修正任务在新增历史后更新受影响的订单，且只改对应时段 |
| 人工匹配 | 指定达人、标记非达人、重新归因；原因必填；跨公司的达人 ID 返回 404 |
| 查询 | `OWN` 账号只看到快照商务为本人的订单；跨公司隔离 |
| 隐私 | 订单数据中没有买家姓名、电话、地址；日志中没有买家信息 |
