# 任务 09a：微店接入基础执行报告

## 执行结论

已按提示词第 4.0 节负责人核对的微店协议，完成后端凭证加密、两种店铺授权、集中令牌管理、管理接口、外部 API 客户端及 12 个业务 API 的类型定义和解析测试。没有新增依赖，也没有实现订单同步或商品复制业务。当前使用本地模拟 HTTP / 官方响应示例，不做真实账号联调。

订单详情 v2.0 的官方示例在 `expect_delivery_time` 和 `express` 之间漏了逗号，示例测试夹具仅修复此 JSON 语法错误。样例有 `fans1_id`、`fans1_money_total`，但结果字段表没有对应说明；不推断含义，字段留在 `raw`。退款列表把 `add_time` 标为字符串，示例值是 Unix 秒；退款详情 `refundFee` 字段单位为分；实现分别按其示例/说明解析。`vdian.item.add` 同版本文档有重复：选择通用 `vdian.item.add` 文档 231；另一个文档 10530 提到后续推荐 smart-store 的 `vdian.cloud.item.add`，但该接口不等同本任务指定的方法，本任务未替换接口，后续店铺类型与接口适配待产品确认。

未专门建模、保留在 `raw` 中的字段包括订单买家信息、备注、配送及发票对象、退款买家和展示字段、商品分类/SKU/属性等未结构化扩展字段，以及各 API 未列明或含义不清字段。买家姓名、电话、地址等不会被解析到业务字段，也不写日志。订单、商品、退款中有明示结构的字段以 Java record 建模；金额用 `BigDecimal`，文档北京时间格式用 `Asia/Shanghai` 解析为 `Instant`。Unix 秒/毫秒字段依各自官方示例与说明解析。

## 数据库迁移锁表评估

迁移只新建两张表并创建其约束和索引，不扫描或改写已有业务数据、不锁 `crm_shop` 行，也不修改已合并迁移。Flyway 在迁移期间持有 schema history 锁；PostgreSQL 只需短暂锁定新建对象以建表/索引，表为空且没有生产查询依赖，锁表风险低。迁移名高于当时 `main` 的现有迁移版本；推送前再次核对并行分支迁移版本。

## M0 真实账号冒烟测试步骤

1. 在微店开放平台分别准备可用的自用型与服务型测试应用；生产/测试域名必须一致登记。备份 `TCRM_SECRET_KEY` 后启动 CRM。
2. 建一家公司和测试店铺，把 CRM `weidian_shop_id` 记录为基准；仅通过超级管理员界面录入自用型 key/secret。确认应用取令牌、调用 `vdian.item.list.get(page_num=1,page_size=1)` 成功，DB 仅存 `v1:` 密文，接口与日志均不含凭证。
3. 用服务型应用配置公司 appkey/secret，发起授权并检查 `state` 只含 `[A-Za-z0-9]`；授权同一店铺后验证 callback 只消费一次、302 是相对路径、响应无令牌。对比 `openid` 与 CRM `weidian_shop_id`；再用另一个店铺验证不一致不会写入令牌。
4. 记录 `expire_in`、`refreshExpireTime` 原始值及实际令牌失效时刻，判定 `refreshExpireTime` 是绝对毫秒时间还是时长；确认代码 30 天上限合理。
5. 对比商品列表返回的 `seller_id` 与 CRM 店铺 ID。该值只产生 WARN，不影响授权；记录两者标识空间是否相同。
6. 在安全测试账号上验证 access token 过期后的主动续期、10013/10016 被动续期、10021/10026 重新授权状态、10023 刷新令牌过期与重新授权路径。

## 偏离与遗留事项

- 官方文档响应示例的订单详情 JSON 缺少逗号；测试夹具做了单字符语法修复。API 10530 提及替代 smart-store 方法，但按本任务指定的通用 API 保持方法名不变，需结合客户店铺类型确认。
- `refreshExpireTime` 单位语义、服务型 `openid` 与 CRM 店铺 ID 标识对应关系、商品 `seller_id` 与 CRM 店铺 ID 对应关系需按上方 M0 清单用真实账号确认。
- 没有真实微店账号，因此不能声称完成服务商实网联调。
