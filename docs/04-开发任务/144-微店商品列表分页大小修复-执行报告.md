# 任务 144：微店商品列表分页大小修复（执行报告）

## 1. 现象

- 2026-11-10 02:11:56 UTC（北京时间 10:11），crm-admin ERROR，traceId `b6eb3b5009984c3799e5a32699f53a66`。
- 日志（生产 v0.1.14，只读查询）：

  ```
  WARN  WeidianClient  : Weidian API failure method=vdian.item.list.get version=1.1
        shopId=2118624507729219585 statusCode=108
        reason=param is error, page_size param illegal!
        params={"update_end":null,"page_num":"1","update_start":null,"status":1,"orderby":null,"page_size":"100"}
  ERROR GlobalExceptionHandler : Unhandled request failure: WeidianApiException
  ```

- 触发入口：`sys_oper_log` 显示 02:11:55 `POST /admin-api/product/shops/2118624507729219585/capacity-refreshes` FAILURE（管理员点「刷新容量」）。该店铺 02:08 刚完成 OAuth 重新授权，之后第一次刷新容量即失败。

## 2. 总览快照（2026-11-10 02:28 UTC）

v0.1.14，五个容器全部 running/healthy；磁盘 5%，内存充足，load 0.23。非基础设施问题。

## 3. 根因

`WeidianIntegrationService.countOnSaleItems()` 调 `vdian.item.list.get` 时固定传 `page_size="100"`，微店以 statusCode=108 拒绝（`page_size param illegal!`）。微店该接口的合法上限未公开，生产与仓库均无记载；实测 `page_size=1`（连通性探测）与 `=5`（连通性测试）可行，`100` 被拒。代码自 2026-10-22（任务 37，#100）就这样写，此前无人点过该店铺的「刷新容量」，所以一直没有暴露。

`ItemListResponse.total_num` 有值时现有代码直接返回总数，分页大小只影响 `total_num` 缺失时的逐页累加路径，因此把每页降到安全值即可。

## 4. 修复

- `backend/.../WeidianIntegrationService.java`：`ON_SALE_PAGE_SIZE = 5`（审查后定为实测可行值，见 §8），`page_size` 改传 5，累加终止条件 `current < 5`；`total_num` 有值时短路返回的逻辑不变（上限 1000 页 × 5）。
- `backend/.../WeidianIntegrationIT.java`：假微店网关模拟真实行为——`vdian.item.list.get` 的 `page_size > 5`（与生产常量 `ON_SALE_PAGE_SIZE` 同口径）时返回 108 `page_size param illegal!`（5 是实测可行值，真实上限未知，不代表恰好 5）。现有容量刷新用例即复现用例。

## 5. 验证

- 复现：仅还原生产代码、保留新假网关跑 `WeidianIntegrationIT#shouldRefreshCapacityAndPreserveTheLastSuccessfulSnapshotOnApiFailure` → 失败（`Status expected:<200> but was:<500>`）。
- 修复后同一用例 → 通过（Tests run: 1, Failures: 0）。
