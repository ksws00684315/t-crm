## 1. 背景

预付抵扣在钱包记一笔负向台账 `PREPAY_DEDUCT`，之后每笔佣金正向入账 `COMMISSION_CREDIT` 按 FIFO 分配给未冲抵完的预付，结果写进 `crm_commission_recovery`。已释放佣金被扣回（`COMMISSION_ADJUSTMENT`，如归属改出、释放后退款）时，原实现只减钱包余额，不撤回该笔佣金当初做过的冲抵，导致「已抵扣」偏大、「待抵扣」偏小；同一行再次入账还会对其他预付重复冲抵。钱包余额本身正确，错的是冲抵记录。

## 5. 读取方核对（提示词 §2.2）

| 读取方 | SQL 形态 | 负数行后的行为 | 结论 |
|---|---|---|---|
| `CommissionWalletMapper.listOutstanding` | `HAVING -l.amount_cny > COALESCE(SUM(r.amount_cny), 0)` | `SUM` 含负数行后为净冲抵，`-l.amount_cny > 净冲抵` 正确表达「未冲抵完」，撤回后预付重新进入待抵扣列表并被后续入账 FIFO 冲抵 | 正确，无需修改 |
| `PrepayMapper.sumRecovered` | `SUM(amount_cny) WHERE deduction_ledger_id = ?` | 净冲抵额 | 正确，无需修改 |
| `CommissionFinanceQueryMapper.recoverySums` | `SUM(amount_cny) GROUP BY kol_id` | 净「已抵扣」 | 正确，无需修改 |
| `CommissionFinanceQueryMapper.pendingDeductions` | `SUM(-l.amount_cny - (SELECT SUM(r.amount_cny) ...))` | 净「待抵扣」 | 正确，无需修改 |

全仓搜索 `crm_commission_recovery`：主代码仅上述三处读取（`CommissionWalletMapper`、`PrepayMapper`、`CommissionFinanceQueryMapper`），均为 `SUM(amount_cny)` 汇总，没有逐行展示冲抵记录、也没有假定 `amount_cny > 0` 的地方。测试代码中的引用（`CommissionSettlementIT`、`WithdrawalIT`、`SystemIT`、`ChainWorld`）为清理与 `SUM` 断言，不受影响。服务层「已抵扣」（`CommissionIncomeService`、`KolCommissionService`）全部经 `recoverySums` 取数，自动变为净额口径。

## 6. 存量数据排查（提示词 §2.3，只读）

不做数据修复迁移，不改共享库与正式环境已有数据。以下 SQL 供负责人在正式环境**只读执行**（本任务未在任何环境执行过），找出「有扣回、且扣回所在行的入账做过冲抵」的达人及金额：

```sql
-- 找出已释放佣金被扣回（COMMISSION_ADJUSTMENT）、且该来源行的入账在扣回前做过预付冲抵的组合。
-- net_recovered_cny 为该来源行在扣回发生前的净冲抵合计（含更早的撤回），即本应被撤回的上限；
-- should_reversed_cny = min(|扣回金额|, 净冲抵合计)，即本应撤回的金额（目前库里没有这笔负数记录）。
-- 说明：以扣回台账 create_time 与冲抵记录 create_time 的先后判定“扣回前”，与实现使用的同一事务
-- 内时钟一致；结果供人工复核，不在正式环境之外执行任何写操作。
SELECT a.tenant_id,
       a.kol_id,
       a.source_id                         AS source_row,
       a.id                                AS adjustment_ledger_id,
       a.source_key                        AS adjustment_source_key,
       a.amount_cny                        AS clawback_cny,
       SUM(r.amount_cny)                   AS net_recovered_cny,
       LEAST(-a.amount_cny, SUM(r.amount_cny)) AS should_reversed_cny,
       a.create_time                       AS clawback_time
FROM crm_commission_ledger a
JOIN crm_commission_recovery r
  ON r.tenant_id = a.tenant_id
 AND r.kol_id = a.kol_id
 AND r.create_time < a.create_time
JOIN crm_commission_ledger c
  ON c.tenant_id = r.tenant_id
 AND c.id = r.credit_ledger_id
 AND c.kol_id = a.kol_id
 AND c.source_type = 'COMMISSION'
 AND c.source_id = a.source_id
WHERE a.entry_type = 'COMMISSION_ADJUSTMENT'
  AND a.source_type = 'COMMISSION'
GROUP BY a.tenant_id, a.kol_id, a.source_id, a.id, a.source_key, a.amount_cny, a.create_time
HAVING SUM(r.amount_cny) > 0
ORDER BY a.tenant_id, a.kol_id, a.create_time;
```

结果解读：每行代表一次受影响的扣回；`should_reversed_cny` 是该次扣回本应追加的负数冲抵合计。累计同一 `kol_id` 的 `should_reversed_cny` 即该达人「已抵扣」多计、「待抵扣」少计的金额上限（后续入账可能已部分自然纠偏，需按时间线人工核对）。

## 9. 口径与偏离

- 「已抵扣」「待抵扣」口径未变：仍是 `crm_commission_recovery` 的净额汇总（`recoverySums` / `pendingDeductions`），本任务只让扣回把净额修正回去，不涉及金额口径定稿冲突。
- 撤回额按提示词取 min(扣回绝对值, 来源行净冲抵合计)，LIFO 顺序为冲抵记录 `create_time` 倒序、同一时间按 ID 倒序，与提示词一致。
- 无范围外改动：不改 `CommissionSettlementRules`、不改订单链路取数、不改前端与接口出入参、不修改 `docs/04-开发任务/README.md` 与《遗留问题清单》。
