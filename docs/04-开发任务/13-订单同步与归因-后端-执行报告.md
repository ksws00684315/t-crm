## 3. 同步、退款、游标与隐私

- 调度每 5 分钟运行；系统范围只枚举启用公司 ID，随后 `TenantScope.runCompany`，筛选启用且 AUTHORIZED 的店铺；每店 `order:sync:{shopId}` 非等待 watchdog 锁。店铺/公司异常隔离，不输出异常载荷。
- 订单首次回溯 24 小时，后续 `order_cursor − 10 分钟`；退款按独立退款游标同样回溯。按北京时间字符串传给接口，内部使用 Instant UTC；超过 90 天的积压拆成至多 89 天的窗口。
- 订单使用 has_more 与官方 next_after_key；下一请求参数为 after_key。09a 类型访问器读取 after_key，官方下一页字段仍保存在 raw，因此本适配层仅对白名单 next_after_key 做兼容读取，没有修改或持久化 raw。
- 新增/更新的订单取详情；已处理且源更新时间未前移的订单跳过详情调用。订单、明细、退款按唯一键幂等更新；后续同步保留已归因明细的达人。
- 退款列表从第 0 页开始、每页 50；逐笔取详情，对应订单本地缺失时先拉取订单。refundFee 以分除以 100 转元，BigDecimal 保留两位、HALF_UP；状态 10 才计入退款合计。能按子订单或唯一商品/SKU 对应时填写 order_item_id；跨多明细或无法唯一识别时保持空，不猜测分摊。
- 所有订单和退款窗口完成后才同时更新两个游标及 last_success_at；API 失败或成功检查点写入失败时保留原游标/成功时间，写安全英文摘要。底层 09a 客户端继续负责限流、重试、被动刷新、过期标记等分类处理，order 不复制其协议策略。
- 手动同步后台线程先取得同一店铺锁再返回 202，因此并发请求可以可靠得到 409 `ORDER_SYNC_RUNNING`；后台线程显式恢复公司范围。
- 不解密、读取或保存买家姓名/电话/地址，不保存原始 JSON；只取 buyer_id 并计算 `SHA-256(TCRM_IP_HASH_SALT + buyerId)`，缺失 ID 时哈希为空。订单响应连哈希也不返回。

## 4. 状态与归因

依据 [微店官方详情接口 1064](https://thor.weidian.com/openweb/api.getById/1.0?param=%7B%22id%22%3A%221064%22%7D) 的 status 说明集中映射在 `OrderStatus`，**待 M0 用真实订单核对**：

| 原始详情状态 | 标准状态 | 有效订单 |
|---|---|---|
| unpay / part_pay | UNPAID | 否 |
| pay | PAID | 是 |
| ship / split_deliver | SHIPPED | 是 |
| accept | RECEIVED | 是 |
| finish | COMPLETED | 是 |
| close | CLOSED | 否 |
| 其他（含误用列表数字状态） | UNKNOWN | 否，记固定 WARN，不把不可信原值写日志 |

订单列表数字状态不能套用详情状态。09a 的精简详情测试样例带数字 20；本任务不据此推断详情状态定义，而按官方文本说明实现。

归因按支付时刻的 `[valid_from,valid_to)` 查店铺、当前店铺商品 ID；供货分销优先 cur_shop_item_id / cur_shop_sku_id，避免使用其他店铺的商品标识。无支付时间 PENDING；全部同一达人 ATTRIBUTED；多达人 CONFLICT、所有已匹配明细类型 4、订单达人为空；有未匹配明细 UNMATCHED，只有一个已知达人时暂存该达人。

人工指定整单达人或 NON_KOL，必填原因、记录操作日志；人工处理清除旧的对应关系 ID。显式重新归因清理旧结果再查映射；普通同步不自动修改已有归属。跨公司达人/订单 404，OWN 根据订单已有商务快照限制读写，不依赖达人当前商务。

商务快照按支付时刻覆盖的历史区间取 BD，空 BD/无历史归公司。修正任务每 10 分钟持全局锁，按各公司新历史创建时间重算对应达人、对应支付区间；Redis 检查点 `order:bd-snapshot:checkpoint`，首次回溯 24 小时，后续保留 10 分钟重叠以覆盖迟提交；失败不前移。只改商务快照，不改达人归属。
