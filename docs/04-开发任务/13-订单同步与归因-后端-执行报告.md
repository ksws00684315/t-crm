## 3. 阻塞二：跨模块只读 API 缺口与修改范围

任务开头第 6 行规定 `order` 只读取 `kol`、`product`、`integration` 的 `api` 包；工程规范 01 §3 禁止跨模块访问 service、mapper、model。任务 §4.5 已明确允许补充 `kol.api` 的两项历史读取能力。本轮还发现以下两项读取能力未暴露。

### 3.1 历史有效对应关系

- `backend/src/main/java/com/tcrm/admin/product/api/KolItemApi.java:8` 说明 `*CurrentLink*` 方法只返回 `valid_to IS NULL` 的当前映射。
- `getCurrentLink`（第 63 行）按达人、原商品查当前映射，不支持按店铺、微店商品、时间点查找。
- `listRefsByIds`（第 90 行）虽然能读取已关闭映射，但要求调用者已知对应关系 ID。订单同步只知道店铺和微店商品 ID，不能凭现有接口先得到历史对应关系 ID。
- `KolItemLinkDTO`、`KolItemRefDTO` 均不包含 `valid_from`、`valid_to`，不能在 `order` 内自行恢复历史有效区间。

因此，使用当前映射不能满足支付之前已失效、支付之后才生效等边界场景；直接访问 product 的 mapper/service 或在 order SQL 中读取 product 所属业务表，会绕开本任务要求的模块 API 边界。

需要明确允许的补充范围：在 `product.api` 及其实现中增加**按当前公司内的店铺、微店商品 ID 和确认后的归因时间点查询有效对应关系**的只读接口，返回归因必需的达人、原商品、对应关系 ID；保持公司隔离，不调整现有当前映射接口语义。

### 3.2 已授权店铺状态

- `product.api.ShopAccessApi` 可以列出店铺，`ShopAccessDTO` 含启停状态，但没有授权状态。
- `integration.api.WeidianShopView` 含 `status`，它是 DTO，没有可调用的读取接口。
- 实际枚举店铺接入状态的方法是 `integration.service.WeidianIntegrationService.shops()`（第 121 行），未通过 `integration.api` 暴露。
- `integration.api.WeidianBusinessApi` 的现有方法只覆盖订单、退款和商品业务调用，没有列举已授权店铺或读取授权状态的方法。

任务 §4.2 要求同步前仅选择启用且 `AUTHORIZED` 的店铺，不能用“对全部店铺尝试调用订单接口”代替授权状态筛选。

需要明确允许的补充范围：在 `integration.api` 及其实现中增加当前公司范围的**店铺授权状态读取**能力，不回传凭证、不暴露 integration 内部模型。随后由 order 结合店铺启停状态筛选。

以上列为需要确认的接口范围，不将其伪装成已完成的实现，也不宣称现有 API 本身有缺陷；这些 API 原本用于其他任务，尚未承诺订单同步所需能力。
