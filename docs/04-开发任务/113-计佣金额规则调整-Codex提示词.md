## 1. 背景与负责人决定

负责人 2026-11-05 确认了《金额名词与口径定义》（下称「定稿」）。其中 §2.1 改变了退款中订单的计佣方式：

| 情况 | 现在 | 定稿 |
|---|---|---|
| 退款中（未完结退款 `PROCESSING` / `UNKNOWN`），佣金**还没释放** | 照常计提，只阻断释放和新的提现占用（`AFTER_SALES`） | **计佣金额、计提暂为 0**；退款被拒绝或关闭后恢复 |
| 退款中，佣金**已释放**到达人账户 | 同上 | **不扣回**：已释放部分保持不变，冻结不可提现（占用它的待付申请暂停）；退款被拒绝或关闭后解除 |
| 退款成功（部分或全额） | 按支付金额 − 成功退款重算，少于已释放时产生负向差额，余额可为负 | 不变（负责人 2026-11-05 再次确认：退款成功时才扣，不论是否已提现，余额不足显示负数） |
| 付款后关闭 | 0 | 不变 |
| 已结算 | 仍按支付金额（结算只作确认） | 改为结算金额，**待 M0 核实流水格式，本任务不做** |

**为什么已释放的不扣回**（执行方 2026-11-05 停止报告与只读核实）：如果退款中先扣回、被拒后再补发，补发时要等释放任务（最多 5 分钟），暂停的提现申请不会自动解除；而且负向扣回不会撤回预付冲抵记录，补发后同一笔佣金会被记成冲抵两次，「已抵扣 / 待抵扣」统计出错（现有缺陷，登记为 L-118，本任务不修）。退款成功时才扣，就不会出现「先扣再补」。

「计佣基数」已由任务 112 在页面上改称「计佣金额」。本任务的代码注释和设计说明书按新名称写，类名、字段名不改。

**业务前提**：一单只对应一个达人，所以「退款中」按整单判断。

## 2. 要求

### 2.1 退款中：未释放的计为 0，已释放的冻结不扣回

1. 订单任一商品行有未完结退款（`PROCESSING` 或 `UNKNOWN`）时，**整单各行**都按退款中处理：
   - 释放依据为 `AFTER_SALES`（整单，包括没有退款的那一行）。阻断释放和新提现占用的规则不变；只占用另一行的待付申请也随之暂停。
   - 每行计提改为 **min(原计提, 该行已释放)**：还没释放的行为 `0.00`，已释放的行保持已释放金额。**不得产生负向台账差额**。
   - 订单仍算已核实，不进待核实，不写 `commission_basis_reason`。
2. 退款完结后按现有规则重算，不另写恢复逻辑：
   - 被拒绝、撤销、关闭：恢复为（支付金额 − 成功退款）× 比例，冻结解除，之后按原释放依据释放；
   - 退款成功：按部分退款或全额退款规则计算。结果低于已释放时，按设计 §4.7 第 2 条产生负向差额（`COMMISSION_ADJUSTMENT`），余额可以为负。这是现有行为，不改。
3. 计提变化都经现有快照修订路径（`applyRevision`）写入，订单同步、退款同步、退款导入、结算重算四条路径都要生效，不新增旁路。
4. **提现暂停**：占用该订单的待付申请，在退款中按 §4.8.6 暂停。退款被拒绝或关闭后，已释放不变，占用 ≤ 已释放，应由 `applyRevision` 中现有的 `resumeForItem` 自动解除。先在代码里确认这一点；如果解除不了，停下报告。
5. 在执行报告用一张时间线表写清以下三种情况下，冻结中、可提现、提现中、累计佣金、钱包余额各自怎么变，并验证五层恒等式：
   - 付款 → 进入退款中（未释放）→ 退款被拒；
   - 付款 → 释放 → 有待付申请 → 进入退款中 → 退款被拒；
   - 付款 → 释放 → 已提现 → 进入退款中 → 部分退款成功（余额变负）。
6. 计佣的订单状态范围不变：已付款、已发货、已签收、交易成功（`PAID` / `SHIPPED` / `RECEIVED` / `COMPLETED`）计入，付款后关闭为 0。`UNKNOWN` 订单状态维持现有处理，在报告里写明现有处理是什么。

## 6. 停下来报告

- 「计提不低于已释放」在现有修订机制里做不到，或者会产生台账记录；
- 退款被拒后，待付申请不能经 `applyRevision` 自动解除暂停（§2.1 第 4 条）；
- 退款中整单置 0 会让某条路径（同步、导入、结算重算）的结果与其他路径不一致，或者需要绕开 `applyRevision`；
- 「退款被拒绝或关闭」在微店退款状态里没有对应取值，无法判断恢复时机；
- 需要改台账类型、预付冲抵逻辑（L-118 不在本任务范围）；
- 需要迁移或新增依赖。
