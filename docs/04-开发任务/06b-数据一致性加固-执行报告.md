## 3. 每个问题的复现与修复

### A、B、C、I：事务内登记与后台同步

- **A**：全量重建在持有达人锁 `link:index:kol:{kolId}` 期间重读数据库，再写临时 key 并 `RENAME`。`LinkIT.shouldKeepMappingCommittedDuringRebuild` 固定“重建读完、映射随后提交、重建再替换”的顺序，最终 Redis 是新映射。
- **B**：Redis 写入失败时 outbox 行保留，`attempts` 增加，`next_attempt_at` 按 10 秒、30 秒、1 分钟、5 分钟、10 分钟退避，之后固定 10 分钟，行不丢弃。恢复后处理并删除。业务事务回滚不插入 outbox 行。对应 `LinkIT.shouldRetryOutboxRow_whenRedisWriteFails_andApplyItAfterRecovery`、`shouldNotInsertOutboxRow_whenBusinessTransactionRollsBack`。
- **C**：停用店铺只在事务内登记 outbox，请求线程不写 Redis。工人处理后该店链接 `status=0`。对应 `LinkIT.shouldDisableShopWithoutWritingRedisUntilTheWorkerRuns`。
- **I**：`TransactionalEvents.publish` 在没有活动事务时抛出 `IllegalStateException`。`ArchitectureTest` 禁止除该工具外直接调用 `ApplicationEventPublisher.publishEvent`。
- 工人空闲每 2 秒（锁 `link:index-sync`，等待 0、看门狗续期），有到期行时在同一把锁内按 200 行排空。监控锁 `link:index-outbox-monitor`：最早一行的等待严格超过 1 分钟记 WARN，严格超过 10 分钟记 ERROR（等于阈值仍算较低一档）；`attempts >= 5` 记 ERROR，并带上 scope 与 id。
- **复现记录**：A、B、C 的修复与对应用例写在同一次提交里，**没有单独观察到修改前集成测试失败**。I 的单元测试与架构规则随实现一起提交，修改前的失败也没有单独跑到。

决定记在 `docs/06-架构决策/ADR-013-链接索引采用事务内登记与后台同步.md`。ADR-012 的“影响”只加了一句：索引遗漏或陈旧由 ADR-013 在数秒到数分钟内修正，不再依赖每日重建。ADR-012 的决定部分没有改。

### D：原商品与专属商品互斥

两条写入路径在事务内先取同一把咨询锁 `pg_advisory_xact_lock(hashtextextended(键, 0))`，键为 `crm:shop-item:{shopId}:{weidianItemId}`（`ProductRules.shopItemLockKey`，注释里同时登记了 `crm_shop:create`），然后在锁内复查对方表。事务外的检查仍作快速失败。

- **修改前**：`ProductIT.shouldRejectOneClaim_whenOriginalAndExclusiveImportsOverlap` 失败。店铺微店 `1005`、商品 `9001` 的原商品导入与对应关系导入都是 `SUCCESS`（断言期望其中一个 `FAILED`，实际 `["SUCCESS","SUCCESS"]`，当时在 `ProductIT.java:292`）。
- **修改后**：同一次运行中原商品导入 `SUCCESS`、对应关系导入 `FAILED`。`weidian_item_id = '9001'` 的未删除原商品与当前专属商品合计为 1。哪一方赢不固定。

### E：重复点击回查

规则不变：同一 `kol_item_id` + `ip_hash`，事件时间差的绝对值小于 10 秒即为重复。Redis `click:last:*`（TTL 60 秒）只作加速。本批里缓存未命中的键，用一条查询取 `[本批最早 − 10 秒, 本批最晚]` 内每个键的最近 `click_time`，条件按 `kol_id`、`product_id`、`click_time` 写成 OR，以便走 `idx_crm_click_log_kol_product_time`，再按 `kol_item_id`、`ip_hash` 过滤。Redis 已命中的键不查库。

- **修改前（单元测试）**：`ClickConsumerTest.shouldMarkDup_whenRedisMissesButTheClickLogHasThePreviousClick` 失败，第二条点击没有被标成重复（`Expecting value to be true but was false`，当时在 `ClickConsumerTest.java:121`）。
- **修改后**：该单元测试通过。`LinkIT.shouldMarkDupFromTheClickLog_whenTheRedisKeyIsGone` 分两批消费、中间删掉 `click:last:*`，第二条仍为重复。**这条集成测试在修改前没有单独跑过**，只观察到了单元测试的失败。

### F：操作日志保留 180 天

`OperLogRetentionJob` 每天 03:45（UTC），锁 `system:oper-log-retention`（等待 0、看门狗续期）。删除 `oper_time` 严格早于 `now − 180` 天的行，每批最多 10,000 行，每批 `REQUIRES_NEW`，直到一批不足 10,000。删除总数记 INFO，包括 0。保留天数是常量 `RETENTION_DAYS = 180`，不是配置。正好等于截止时间的行保留。

`SystemIT.shouldDeleteOperationLogsOlderThan180Days_andKeepTheBoundary` 插入截止时间前 1 毫秒、正好截止、截止后 1 毫秒三条，只删第一条。该次运行日志为删除 1 条，测试 1 个、失败 0。

### G：`/t/` 限速

`deploy/nginx/templates/default.conf.template` 增加 zone `tcrm_redirect`（`rate=30r/s`）。`location /t/` 使用 `burst=60 nodelay`，`limit_req_status 429`。`location = /healthz` 不限速。`deploy/README.md` 写明 Cloudflare 是主要防线，Nginx 是兜底，阈值可按实际流量调整（CGNAT）。没有为 Nginx 配置写自动化测试。

### H：IP 哈希盐至少 32 字符

跳转服务先检查回退地址，再检查 `TCRM_IP_HASH_SALT`。短于 32 个字符（含空）时启动失败，异常信息包含变量名和 `openssl rand -hex 32`。`deploy/.env.example` 的注释已同步。哈希算法不变，仍是 `SHA-256(salt + ip)`，中间没有分隔符。

`RedirectServiceTest` 覆盖空盐和 9 字符盐。`RedirectIT` 使用 32 字符测试盐，6 个测试、失败 0（含故意拒绝 `XADD` 的用例，日志里的 `NOPERM` 是这条用例，不是失败）。**没有单独跑过修改前的启动失败**：长度检查和测试是一起提交的。

## 4. 性能（提示词第 6 节）

测量机是本机，不是单独的验证机。Docker Desktop 29.8.1（引擎内存 7934 MB），PostgreSQL 17.11，Redis 7.4.5，JDK 21.0.12.1。时间是 2026-10-07 12:37（+08）。

做法（临时集成测试，测完已删除，不进入 CI）：经接口建 1 个店铺、1 位达人；用 JDBC 插入 2 万条原商品（编码 `X00001`–`X20000`，微店商品 ID 与专属商品 ID 不重叠）；再用 FastExcel 生成 364,237 字节的 xlsx，`POST /admin-api/product/kol-item-imports`。`LinkIndexSyncJob` 的定时任务保持开启。点击消费线程在这次测量里关掉了，它不跑在调度线程上，不影响索引工人。

| 项目 | 结果 |
|---|---|
| 原商品播种（不计入导入） | 548 毫秒 |
| 任务自身 `startedAt` → `finishedAt` | 2026-10-07T04:37:06.499Z → 2026-10-07T04:37:36.808Z，**30,309 毫秒** |
| 从接口接受文件到测试观察到 `SUCCESS` | 31,508 毫秒（轮询间隔 1 秒，最多比任务结束晚约 1 秒） |
| 任务结果 | `SUCCESS`，20,000 行，0 行失败 |
| 任务刚成功时 | outbox 还剩 587 行，Redis `HLEN link:{kolCode}` 为 19,413 |
| 导入完成到索引全部可用 | **616 毫秒**（outbox 为 0，`HLEN` 为 20,000，2 万个 field 的值都含 `"status":1`） |

导入过程中工人一直在排空：约 15.4 秒时已处理 9,400 行、索引里已有 9,087 个 field；约 30.5 秒时已处理 19,900 行、索引里已有 19,413 个 field。追上时间远小于 1 分钟。

写入延迟与设计说明书 §7.4 一致：请求线程不写 Redis，索引在提交后数秒内更新。这次大批导入里，大部分 field 在导入结束前已经写上，收尾不到 1 秒。
