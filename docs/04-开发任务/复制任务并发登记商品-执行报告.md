## 1. 现象

2026-11-10 14:28（北京时间），客户反馈「最新的同步任务，有 100 多条失败」。对应表格脚本复制任务在正式环境 v0.1.14 的数据：

| 任务编号 | 创建（UTC） | 结束（UTC） | 总数 | 成功 | 失败 | 状态 |
|---|---|---|---|---|---|---|
| `y5sGJhThv_jVp6atwF_lfw`（最新） | 05:41:38 | 05:48:16 | 2206 | 2086 | **120** | `partial_failed` |
| `trTTwnMAEBTsazCPDbLrtg`（前一条） | 04:37:09 | 05:48:16 | 2206 | 2109 | **97** | `partial_failed` |

两条任务属于同一公司、同一达人（`kol_id=2119784017517916162`）、同一目标店铺（`2118624507729219585`）、同一复制令牌，调用方都是 `google_sheet_plugin`，明细来源商品完全相同。也就是说，第一条任务还在跑时，客户又用同一批 2206 个商品提交了一次。

97 + 120 = 217 条失败明细的 `error_message` 完全相同：

```
微店复制失败：
### Error updating database.  Cause: org.postgresql.util.PSQLException: ERROR: duplicate key
value violates unique constraint "uk_crm_product_shop_item"
```

`crm-admin` 日志同一时段（05:47:09–05:48:16 UTC）在 `copy-job-1` 与 `copy-job-2` 两个工作线程上交替出现：

```
Copy job item ... failed: DuplicateKeyException
```

## 2. 总览快照（2026-11-10 06:29 UTC）

- 版本：`v0.1.14`（`crm-admin`、`crm-redirect`、`postgres`、`redis` 均 healthy，已运行 15 小时）
- 磁盘 `/` 使用 5%，内存可用 5768 MB，负载 0.20，无重启、无发布
- 属单条业务失败，不是整站或基础设施问题

## 3. 根因

1. **重复提交**：客户在第一条任务仍在处理时又提交了同一批商品。`CopyJobWorker` 的线程池是 2 个线程，两条任务各占一个，从 05:41 起并行处理重叠的来源商品。
2. **商品自动登记存在并发竞态**：来源商品未登记时，`CopyJobWorker.findSource` 会经微店 `item.get` 探测，再由 `ensureProduct` 先 `SELECT` 再 `INSERT` 到 `crm_product`。该路径**没有**加商品导入、推广表映射已经在用的店铺商品事务锁（`ProductRules.shopItemLockKey` + `ProductMapper.lockShopItem`，`pg_advisory_xact_lock`）。两个任务同时探测同一商品时都查到「不存在」，都尝试插入，后插入的事务撞上唯一索引 `uk_crm_product_shop_item`，PostgreSQL 将事务置为中止，明细被写成失败，并把 JDBC 原始报错暴露给了表格脚本。
3. **失败是「假失败」**：只读 SQL 核对最新任务的 120 条失败明细，`source_product_id` 在同批其他任务里都有成功记录，且不存在「哪条任务都没复制成功」的商品（`never_copied = 0`）。商品与专属商品映射均由另一条任务完成，客户不需要重做这 120 条。
4. **同一竞态还可能复制两份**：对于已登记商品，两条任务都会先查「当前达人是否已有该原商品的专属商品」，两边都查到空时会各自调用微店 `item.add`，产生两个新商品 ID，后登记的明细会报「微店已创建商品 … 系统登记失败」。本次两条任务的失败信息里没有出现该文案，说明这次没有实际产生重复副本，但窗口客观存在。

补充：10:21、10:30（北京时间）两条各 2206 条失败的任务，失败原因全部是「该商品是其他达人的专属商品」，属于另一件事（负责人已决定用数据库方式处理归属关系，相关 PR 已关闭），与本次 120 条无关。

## 4. 改动

| 文件 | 改动 |
|---|---|
| `backend/.../product/service/CopyJobWorker.java` | `ensureProduct` 在重新查询、插入前获取 `ProductRules.shopItemLockKey(shopId, weidianItemId)` 事务级咨询锁，与商品导入、推广表映射共用同一把锁；`processOne` 解析出原商品后、查询当前达人映射前再次获取同一把锁（未登记路径是同一事务内的重入），使另一条任务在本事务提交后才继续，直接复用已登记商品和已复制结果，避免重复复制 |
| `CopyJobWorkerTest` | 新增 2 个用例：登记探测商品前必须先拿锁；已登记商品复用映射前先拿锁 |
| `ProductLinkIT` | 新增并发复现用例：同一未登记商品、两条任务同时探测（`CyclicBarrier` 卡住两个探测），断言两条任务都完成、`crm_product` 只有 1 行、`crm_kol_item` 只有 1 行、微店 `copy` 只调用 1 次 |

为什么用咨询锁而不是「捕获唯一键异常后重查」：PostgreSQL 在唯一键冲突后事务已中止，同事务内无法继续查询；重试整个事务又会再次探测微店并放大重复复制窗口。项目已有店铺商品咨询锁，扩到复制链路即可同时解决登记冲突与重复复制。

## 6. 影响与遗留

- 已失败的两条任务不会自动重跑；本次 120 条经核对已由另一条任务复制成功，无需重新提交。以后遇到「部分失败」先在管理端「商品任务」看明细原因，不要立刻整批重交。
- 重复提交仍会重复消耗复制额度并多跑一遍微店探测。是否在 `convert` 层拒绝/合并「同达人、同目标店铺、仍有处理中任务」的提交属于产品口径，需负责人决定；本次未改。
- 失败信息仍可能暴露 JDBC 原文（其他路径的 `DuplicateKeyException` 也可能走到 `failMessage`）。本次只修并发根因，未改文案。
- 发版后建议观察一次重复提交场景：两条任务都应完成，且目标店铺只有一份新商品。
