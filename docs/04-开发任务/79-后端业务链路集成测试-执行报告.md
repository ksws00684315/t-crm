### 手算（链路 A，费率 0.1000）

行实付 40.00 与 20.00，运费 5.00，订单实付 65.00。货款收入 6500 分 = 65.00，手续费 −20 分 = −0.20，分润 −10 分 = −0.10。基数 64.70。按行实付分摊：64.70×40/60 = 43.1333… → 43.13；64.70×20/60 = 21.5666… → 21.57；四舍五入后已等于 64.70，尾差 0。佣金 4.31 与 2.16，合计 6.47，等于 round(64.70×0.10, 2)。`release_at` 等于货款收入的 `tradeTime`。

手续费和分润的 `tradeTime` 比货款收入晚 30 秒和 60 秒。`release_at` 仍等于货款收入的时刻，不是手续费的时刻。

部分退款再减 100 分（−1.00），基数 63.70。行基数 42.47 与 21.23，佣金 4.25 与 2.12，合计 6.37。已释放部分产生 `COMMISSION_ADJUSTMENT` −0.06 与 −0.04，可提现 6.47 → 6.37。每个商品行追加一条修订。

这组两行金额四舍五入后之和恰好等于基数，尾差是 0.00，看不出尾差落在哪一行。非零尾差落在实付最大行（相等时落在较小的订单行 id）已由 `SettlementBasisCalculatorTest` 覆盖。本链路选这组数，是为了让钱包、提现和退款调整同时闭合。

结算前全额退款只有 `PRE_SETTLE_REFUND`（−6500 分），基数 0.00、已核实、`release_basis` 为 `UNSETTLED`，钱包无入账。

货款收入按元返回 65 时，换算成 0.65，不等于实付 65.00，原因 `INCOME_MISMATCH`，两行未核实。

## 待 M0 验证

假微店不能代替第 11 步。2026-10-28 的实测记录写明：近 12 个月结算明细和 `PRE_SETTLE_REFUND` 都是 0 条，没有真实结算样本。下列项仍以那一步复测为准：

1. 金额单位常量 `SettlementBasisCalculator.AMOUNT_IN_MINOR_UNITS`（现按分；订单详情金额实测为元，测试里订单用元、结算流水用分）。
2. 已知流水类型是否就是「收入 / 支出」和「货款收入 / 交易手续费 / 分润 / 退款」。
3. `orderId` 能否与本库订单号完全匹配、会不会带后缀。
4. `tradeTime` 是否就是货款收入的结算时点，从而等于 `release_at`。
5. 一单「货款收入」是否等于订单实付（含运费）。不等则订单会停在 `INCOME_MISMATCH`。

订单状态用文本 `pay`。M0 实测记录里真实订单的原始状态就是 `pay`，系统记为 `PAID`。样本文件里的数字状态 `20` 会被 `OrderStatus` 收成 `UNKNOWN`，所以测试替换成 `pay`，与实测记录一致，不是另造一种状态。

## 偏离与原因

- 数据前缀是 `t79-` 而不是提示词写的 `t79_`。租户编码只允许 `[a-z0-9-]{2,32}`，下划线无法开公司。账号、店铺和达人名称沿用同一前缀，只存在于 Testcontainers 里。
- 商品走 Excel 导入，不从商品列表接口落库。原因见「主要改动」。
- 结算拉取调用 `OrderSettlementFlowService.pull`，不调用按日盖章的调度入口。原因见「主要改动」。
- 订单详情断言 `orderNo`。列表接口另有同值字段 `weidianOrderId`。详情 DTO 没有 `weidianOrderId`，也没有行上的 `attributionType`；归属类型在列表行上断言。
- 收款账户审核读取管理端详情里的 `lastSubmittedAt`。该列是 `TIMESTAMPTZ(3)`，创建响应里的内存时间戳纳秒对不上库里的毫秒，会得到 `PAYOUT_ACCOUNT_NOT_PENDING`。这与 `PayoutAccountIT` 的审阅方式一致。
- 失败的结算轮次之后，订单同步仍会调用 `vdian.order.list.get`。订单更新时间没有变化时，生产代码不重复调用 `vdian.order.get`。测试断言列表调用增加，并断言订单仍是 `PAID`。
- 订单同步在没有结算流水时就会写入未核实的佣金行（原因 `NO_SETTLEMENT`）。失败轮次跳过重算，这两行保持未核实、台账为空；下一轮成功后才核实并只入账一次。
- 建数、样本和邮件截获放在 `ChainWorld`、`ChainSamples`、`ChainMailCapture`、`ChainScheduler`。它们与测试类同包，不被继承，也没有被其他测试使用。两个 IT 若各写一份，会复制同一套开公司和假微店协议。提示词禁止的是抽取测试基类和改造 `CompanySessions`。
- 隔离链路的类名是 `GuardChainIT`。`*ChainIT` 只匹配以 `ChainIT` 结尾的类，原先的 `ChainGuardIT` 不会被稳定性命令选中。
- 两行分摊的尾差为 0。非零尾差的落点留在已有的 `SettlementBasisCalculatorTest`，不在这条金额闭合的链路上再造一组数。

未发现需要停下来另开任务的生产缺陷。覆盖率门槛没有降低。没有新增依赖。
