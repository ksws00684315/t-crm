## 1. 背景

#122 已把订单链路页重排为「资金信息、订单信息、财务流水」三个板块，缺数据的地方显示「开发中」。现在的 `GET /admin-api/order/orders/{id}/chain` 中，商品行的 `ledger`、`withdrawals` 始终为 `null`（任务 40 留下的占位）。任务 62、63 已经实现了计佣、释放、提现占用和付款，本任务把这些数据接到链路接口上。

## 2. 已确认的业务规则（负责人）

- 每位达人统一一个比例；历史商品行返回支付时刻的比例快照，不能用当前比例反算（ADR-032 第 3 条，2026-10-25 修订）。
- **店铺获利 = 微店结算净额 − 净达人佣金**，不扣商品成本。微店结算净额在 M0 核实前没有数据，店铺获利一律返回 `null`（待核实），与任务 68 的 `retained` 一致。
- 未知或未核实的金额返回 `null`，不得用 0 代替。

## 3. 范围

### 3.1 契约（作为本 PR 的第一个提交）

在设计说明书 §6.2 中重写 `GET /admin-api/order/orders/{id}/chain` 的响应结构，并同步机读目录。用正式结构取代 `ledger`、`withdrawals` 两个 `Object` 占位。至少包含：

- **订单级资金（B07）**：订单实付、成功退款合计、净达人佣金、店铺获利（M0 前为 `null`）、账务状态（`POSTED`/`UNVERIFIED`，口径同结算明细）。
  - 同一笔退款关联多个商品行时，整单退款合计不得重复累加。
- **商品行级（B07、B09）**：比例快照、净达人佣金、店铺获利（`null`）、释放依据、提现占用合计，以及 `withdrawals[]`。`withdrawals[]` 每条包含提现 ID、提现编号、占用金额、状态、付款时间（未付为 `null`）。
  - 已付、在途、驳回或撤回后释放的占用，按任务 63 的状态机区分；不能把历史申请金额全部算作当前占用。
- **财务流水（B08）**：一个列表。每行包含流水编号、店铺名、类型（店铺应收 / 达人佣金）、方向（增加 / 减少）、金额、业务发生时间、金额流转时间、关联结算单号。
  - 金额的正负与方向的约定在契约中写明。

### 3.2 后端

- **依赖方向**：链路接口在 order 模块，但佣金和提现数据在 commission 模块，而 order 不能依赖 commission（已有 commission → notification → order 的链路）。请沿用任务 62 的做法，在 `order.api` 中定义只读端口，由 commission 实现，可以扩展已有的 `CommissionOrderStateApi`。
- **达人佣金流水**：
  - 来自计佣修订（`crm_commission_item_revision`）和钱包台账（`crm_commission_ledger`）。退款冲减、归属修正产生的负向差额要体现为「减少」，不能因为类型是「达人佣金」就固定为增加。
  - 「业务发生时间」取产生这笔流水的业务事实时间（例如支付、退款、修正的时间），不得统一替换成读取时间或同步时间。
  - 「金额流转时间」取财务付款登记中，对应提现的付款时间（`crm_commission_withdrawal_payment.paid_at`）。没有付款时为 `null`。不得用冻结到期、入账或申请时间代替。
  - 「关联结算单号」取对应的提现编号；尚未关联提现时为 `null`（前端显示「－」）。
  - 同一商品行有多次或部分提现时，要能看出每笔金额对应哪个提现编号和付款时间：按提现分配（`crm_commission_withdrawal_allocation`）拆成多行，不能只取第一笔，也不能把整笔佣金重复计入。
  - 流水编号要稳定、可追溯，例如用修订或分配记录的 ID 加前缀。
- **店铺应收流水**：依赖微店结算净额和微店「可提现时间」，这两项都要等 M0 核实，本任务**不生成**店铺应收流水。在契约和代码中注明待 M0 接入，返回结构中保留这个类型。
- **权限**：链路接口现在只需要 `order:view`。资金板块、商品行佣金和财务流水属于财务数据，只有同时持有 `commission:view` 的用户才返回；否则这些字段为 `null`，前端显示无权限或隐藏。商务按 `OWN` 范围只看名下达人的行，混合归属的订单对商务隐藏金额，口径同结算明细。如果与现有页面权限设计冲突，先停下来报告。
- 跨模块只经 `api` 包，金额用 `BigDecimal` 并序列化为字符串，时间用 `Instant`。
