## 3. 主要改动

### 3.1 退款类型与状态（行 39，08.02）

- `crm_refund` 新增 `refund_type`（REFUND_ONLY / RETURN_REFUND / UNKNOWN）、`refund_status`（PROCESSING / SUCCESS / CLOSED / UNKNOWN），迁移 `V202610221300__refund_type_and_status.sql`（含 CHECK、回填：`raw_status='10'` → SUCCESS、索引 `(tenant_id, refund_status)`）。
- 映射集中在一个类 `order/service/RefundDictionary`（唯一位置，单元测试覆盖已知值/未知值/空值）；无法识别记 UNKNOWN 且 `raw_status` 保留原值。
- `OrderWriter.saveRefund`（接口同步）按 `refundBasicInfo.status` / `refund_type`（兼容 `refundType` 键）映射；`saveImportedRefund`（Excel 导入，模板只有已完成退款）固定 SUCCESS、类型 UNKNOWN。
- 订单级退款状态不落库，由 `OrderRefundStatuses` 每次展示时推导：NONE（无退款）/ PROCESSING（退款中，任一行退款中优先）/ PARTIAL_SUCCESS / FULL_SUCCESS（成功金额之和与实付比较）；只有 SUCCESS 计入成功退款金额，成功统计时间为 `finish_time`。列表与详情的 `refundStatus` 均为该值。
- `crm_refund.refund_time` 即申请时间，接口 `applyTime` 直接取该列（见第 8 节偏离说明 1）。

### 3.2 订单查询与详情（行 43，09.04）

- `GET /admin-api/order/orders` 扩展：筛选新增 `orderNo`（精确）、`channel`（当前仅 `WEIDIAN`，未知渠道返回空页）、已有 `shopId`；每项新增 `channel`、`orderNo`、`shopCode`（暂 null，待任务 37）、订单级 `refundStatus`、`freight`、`createTime`，`shopName`/`kolCode`/`kolName`/`payAmount`/`payTime` 原有。新增索引 `(tenant_id, weidian_order_id)`（`V202610221304`）。
- 新增 `GET /admin-api/order/orders/{id}`（`order:view`，OWN 按商务快照）：`merchantNo`（店铺微店标识）、`itemAmount`（商品行金额之和）、`freight`、`totalAmount`、`payAmount`、下单/支付时间、来源（API/IMPORT）、`lastSyncTime`；商品行 `imageUrl`（行达人商品 → 原商品 `image_url`，取不到为 null）、`weidianItemId`、`skuName`、`kolCode`/`kolName`、`quantity`、`unitPrice`（实付÷数量，HALF_UP 2 位）、`payAmount`、`refundAmount`、`status`（订单状态）。

### 3.3 退款查询与详情（行 43，09.04）

- 新增 `GET /admin-api/order/refunds`（`order:view`）：筛选 `refundNo`/`orderNo`（精确）、`channel`、`refundStatus`、`refundType`；分页按申请时间倒序；每项含 `orderId`/`orderNo`、店铺、达人（行达人优先、回退订单达人）、类型/状态、金额、申请/成功时间。商务（OWN）通过 EXISTS 子查询只看自己负责的达人，未归属订单不可见。
- 新增 `GET /admin-api/order/refunds/{id}`：基础信息 + `merchantNo` + 退款商品行（`imageUrl`、名称、商品 ID、SKU、达人、数量、退款金额），行与 `order_item_id` 关联。现表结构一笔退款至多关联一行；微店一笔退款多商品行的结构待 M0（见第 9 节）。

### 3.4 订单链路（行 43，09.04）

- 新增 `GET /admin-api/order/orders/{id}/chain`（`order:view`）：按商品行返回复制任务（`crm_copy_job.job_code` + 创建时间，经 `crm_copy_job_item.target_item_id` = 达人商品微店商品 ID 关联，找不到为 null，走新 API `product/api/CopyJobLookupApi`）、达人商品链接（`kolItemId`、`linkCode`（暂 null，待任务 39）、来源/目标商品 ID、达人）、数量与实付、该行退款（单号、类型、状态、金额、成功时间）；`ledger`、`withdrawals` 恒为 null（佣金未建，前端显示「开发中」）。

### 3.5 同步监控与导入截止时间（行 42、43，09.03/09.04）

- `GET /admin-api/order/sync-states` 扩展（原 6 字段保留，管理端旧页面不受影响）：新增 `orders` / `refunds` 两类 `{source（API/IMPORT，取该店铺此类最新一条记录来源）、lastSuccessAt、lastError、failures24h、missingFields}` 与 `lastImport {kind, dataCutoffTime, taskId}`。缺字段字典（8 个键，`payTime`/`orderTime`/`payAmount`/`totalAmount`/`itemItemId`/`itemPayAmount`/`orderItemId`/`finishTime`）写进设计说明书 §4.6a，按店铺 SQL 聚合（`SUM(CASE WHEN …)`，兼容租户拦截器的 JSqlParser 重写）。
- 失败记录用新表 `crm_order_sync_failure`（迁移 `V202610221302`，只追加）：接口同步失败按失败阶段记 `ORDER_SYNC` / `REFUND_SYNC`（`OrderSync` 带店铺）；导入任务结束 FAILED/PARTIAL 时经 `ImportRowProcessor.onFinish`（task 模块新增 default 钩子，任务完成后回调）记一条 `ORDER_IMPORT` / `REFUND_IMPORT`（跨店铺、`task_id` 关联任务，逐行错误仍在任务错误文件）。
- 新增 `GET /admin-api/order/sync-failures`（`order:view`）：最近 100 条失败（店铺、类型、时间、错误、关联任务）。
- 订单 / 退款导入新增必填参数 `dataCutoffTime`（ISO-8601）：随任务保存到 `crm_task.params`（JSONB，迁移 `V202610221303`，`ImportTaskApi` 新增带 params 的 submit 重载）；导入处理器按文件中出现的每个店铺把它记入 `crm_order_sync_state.last_import_*`（新列，迁移 `V202610221301`），同步监控据此展示每个店铺最近一次导入的截至时间。缺参返回 400 `COMMON_VALIDATION_FAILED`。

### 3.6 人工匹配池证据（行 44，10.01）

- 新增 `GET /admin-api/order/unmatched/{orderItemId}/evidence`（`order:manage`，只读，OWN 同人工池）：商品行微店商品 ID、所在店铺与 `merchantNo`；该商品 ID 在本公司的全部对应关系（达人、`linkCode`（暂 null）、生效起止、是否覆盖支付时间，走新 API `KolItemApi.listMappingsByShopItem`）；对应的原商品（新 API `product/api/ProductAccessApi`）；未匹配原因 `PENDING` / `NO_MAPPING`（缺规则）/ `MAPPING_EXPIRED`（映射不覆盖支付时间）/ `CONFLICT`（证据冲突）/ `MATCHED`（字典在设计说明书 §8.5）；现有人工处理记录（`attributionType`、`manualReason`、`attributionTime`）。

## 9. 偏离与原因

1. **未新增 `apply_time` 列**：`crm_refund.refund_time` 本就是申请时间（接口同步取 `addTime`、导入取「发起退款时间」列），新增同义列会引入两列不一致的风险；接口字段 `applyTime` 直接映射 `refund_time`（设计说明书 §5.2 已注明）。
2. **`linkCode`、`shopCode` 暂为 null**：按任务提示词第 2 节，链接编码（任务 39）、店铺编码（任务 37）在并行开发，本任务先按 ID 实现；两任务合并 main 后本分支再合并 main 补上这两个字段，PR 再转 Ready。
