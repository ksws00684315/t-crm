## 4. 主要改动

### 4.1 L-032:暂停联动(后端,按架构审查返工)

- **阻断判定(一处)**:商品行「阻断」= 售后中(`after_sales`),或该行占用合计(含 `PAID`,与行剩余同口径)超过其 `released_commission_cny`(超占)。SQL 收在 `WithdrawalMapper.isItemBlocked` / `countBlockedItems`(同一谓词);付款校验、暂停解除、快照联动共用。
- 新增 `commission/service/WithdrawalPauseService`:
  - `pauseForItem(itemStateId)`:占用该行且 `PENDING_REVIEW`/`PENDING_PAYMENT`、未暂停的申请置 `paused=true`、写 `pause_reason`(英文机器原因,页面文案仍走 `finance.refundPause`)并写 `PAUSED` 历史(操作人为空、角色 `SYSTEM`)。
  - `resumeForItem(itemStateId)`:`countBlockedItems=0`(全部占用行都不再阻断)才解除并写 `RESUMED` 历史。
  - `prelockItem(itemStateId)`:按 ID 升序锁下占用该行的活跃申请(两侧)。
- **负责人 2026-11-01 决定:阻断的申请保持暂停、只能驳回。** 退款完结但占用超出已释放(钱不够付)时申请不解除、不能付款,财务驳回后达人按最新余额重新申请;解除只发生在全部占用行都不再阻断(如部分退款后占用仍放得下)。驳回与撤回清除 `paused`/`pause_reason`(`decide` 的 REJECTED 分支与 `withdraw` 的 UPDATE 内联,不写 `RESUMED`——已有终态历史)。
- `CommissionItemSnapshotService.applyRevision`:修订前读该行阻断状态(`isItemBlocked`),落库后再读一次,翻转才应用暂停/解除——判定走共享 SQL 谓词,不在 Java 侧预估(触发条件自然覆盖 `after_sales` 与已释放金额变化,归属扣回也经过这里)。订单同步、退款同步、退款导入、结算重算四条路径共用这一个写入点;行被整单同步剔除(逻辑删除)时同样解除。
- **预锁(复审二轮重写)**:`syncOrderItems` 事务**开头一次**查出该订单全部行(含将被剔除的行)上的活跃申请 ID,去重后按全局升序一次锁完(`prelockForItems`),任何钱包写入都在其后。上一轮「`applyRevision` 逐行预锁」在多行订单上仍是「第 1 行已写钱包、第 2 行才锁申请」,复审实测死锁;按审查指定方案改为按订单一次预锁(`recomputeOne` 与 `OrderWriter` 都是一单一事务,这样即够)。配套删除了逐行预锁、`released` 预计算与行级占用查询。
- **谓词括号修复(返工中实证)**:`BLOCKED_LINE` 初版缺外层括号,`WHERE withdrawal_id = ? AND (售后) OR (超占)` 中超占半边不受申请约束,会把无关申请也判为阻断(实测:另一行已付并退款后,本行正常的待付申请付款得到 409 而非 422)。加外层括号后行为正确。
- **付款现查**:`payInCompany` 在申请锁内除 `paused` 标志外,现查一次 `countBlockedItems`——同步与申请并发时同步可能看不到未提交的占用而漏置标志,现查保证超额申请永远付不出去(不给占用查询加行锁,避免新的锁序倒置)。
- **付款拦截余额不足(负责人 2026-11-01 第二个决定,复审时给出)**:`CommissionWalletService.postWithdrawalDebit` 在钱包锁内、幂等判断之后校验余额——余额小于付款金额即拒绝(复用 `WITHDRAWAL_INSUFFICIENT_AVAILABLE` 422),等于付款金额允许;失败整个付款事务回滚,申请保持 `PENDING_PAYMENT`、不写 `paused`。付款不再把钱包付成负数;负余额只能来自付款后的扣回或预付扣减。
- `WithdrawalMapper` 新增 `findActiveIdsByItemState` / `pause` / `resume` / `countBlockedItems` / `isItemBlocked` / `sumOccupiedByItemState`;`CommissionItemStateMapper` 新增 `findStaleIdsByOrder`。
- 审核不受 `paused` 限制(设计 §4.8.4/§4.8.6 只约束付款),代码未改审核路径;已在设计说明书 §4.8.6 补充说明。
- 存量回补:共享库无符合条件数据(§3),未做迁移。
- 边界说明:释放定时任务只增加 `released_commission_cny`(向解除方向),不触发联动;由此产生的滞后解除会被付款现查拦住,资金方向安全,该行下次修订自然纠正。

### 4.2 L-033:可提现收口(后端)

- `WithdrawalFundingSource` 新增唯一算法:`allocatableByKol`(行级可分配合计,SQL 与 `listReleasedRows` 同过滤:已核实、未售后阻断、`CONFIRMED/FALLBACK`、到期、剩余 = 释放 − 占用,负剩余按 0 计)+ 默认方法 `availableCny(kolId, balance, occupied)` = min(钱包余额 − 活跃占用, 行级可分配)、`availableByKol`(列表页批量)。
- 四个调用方全部改调它:`WithdrawalService.conditions`(含 `canApply`)、`WithdrawalService.requireFunding`(申请校验,与展示同值)、`KolCommissionService.overview`(达人端概览)、`CommissionIncomeService`(管理端收入页,行级批量)。售后中已释放的金额不再出现在「可提现」里,展示值恒等于实际可申请上限。
- **冻结展示等式(审查返工)**:`frozenShortfallCny` = max(0, 钱包余额 − 占用 − 可分配合计),即被阻断行的已释放未占用金额;conditions/概览/收入页的冻结展示统一加上它,保持「预估 = 冻结 + 可提现 + 占用 + 已付」(无预付时)恒等,落实设计 §4.8.1「阻断期间该行一律显示冻结」。达人端 `totalCommissionCny = commissionPaid + occupied + frozen` 的合成不含 `available`,不受影响。
- 删除 `CommissionWalletService.balance/withdrawalEligibility/Balance`(生产无调用方的第二套门槛算法,任务 89 删预付接口后的残留),同步删除其测试。
