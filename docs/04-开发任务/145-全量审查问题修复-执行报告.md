## 8. 架构审查意见处理（PR #264，2026-11-10）

审查结论：1 项必改——整店性错误识别不全，微店故障（传输失败、5xx 退避用尽、10021/10026 授权过期、10013/10016 令牌刷新后仍无效）抛的是 `WeidianApiException`，不在 `OrderSync.SHOP_WIDE_ERRORS` 里，会按单订单跳过：每个订单各写一条失败记录、第 3 次失败各发一条通知，绕开「成功→失败转换只通知一次」的口径。

**选择的修法**：按异常类型区分，并在 integration 的 api 边界转换（审查给出的边界要求），不走「每店每轮聚合」也暂不加「连续 N 单失败」阈值。理由：这些错误本身就是整店性的，按类型判定不会把真正只坏一个订单的失败误判成整店故障；聚合方案在停摆窗口内仍会把整店订单全部塞进重试表，游标照常前移。

- `integration/service/WeidianBusinessApiClient`：`WeidianBusinessApiClient.call` 捕获 `WeidianApiException` 后转换——
  - `statusCode < 0`（传输失败 / 5xx 退避用尽）与 10000/10001/10002/10004/10005（可重试业务码用尽）→ `BusinessException(WEIDIAN_API_FAILED)`；
  - 10013/10016/10021/10023/10026（令牌或授权不可用）→ `BusinessException(WEIDIAN_SHOP_NOT_AUTHORIZED)`；
  - 其余业务码（如 200056）保持 `WeidianApiException`，仍按单订单跳过。
  这样 `order` 模块只依赖 `integration.api` 与 `shared`，不引用 `integration.service.WeidianApiException`。
- `order/service/OrderSync`：`SHOP_WIDE_ERRORS` 增加 `WEIDIAN_API_FAILED`；命中即抛出走原整店失败路径——游标不前移、只写一条失败记录、只在成功→失败转换时通知一次。
- 复现测试：`OrderSyncNotificationTest.shouldFailTheShopOnce_whenEveryOrderDetailHitsAShopWideFailure`（3 个订单详情连续整店失败 → 返回 false、游标保留、失败记录 1 条、通知 1 次、重试表 0 行、详情只拉 1 次）；`WeidianBusinessApiClientTest` 新增 2 个用例（整店码转换、单订单码保持原类型）；`OrderIT.shouldFailTheShopAndQueueNoRetries_whenOrderDetailsHitAShopWideFailure` 断言库中重试 0 行、失败记录 1 条、`last_error` 为 `WEIDIAN_API_FAILED`。
- 验证：临时回退两处实现后两条新用例失败（`shouldFailTheShopOnce…`、`shouldConvertShopWideFailuresIntoBusinessErrors`）；恢复后通过。`mvn verify`（JDK 21）：Spotless、Checkstyle、单测与覆盖率门槛全部通过；`mvn verify -Pdocker-it -Dit.test=OrderIT#shouldFailTheShopAndQueueNoRetries_whenOrderDetailsHitAShopWideFailure` 通过。
- 非阻塞项（永久失败订单 `fail_count` 无上限、退款阶段单笔失败仍整店失败 L-158）知悉，不在本返工内处理。

### 8.1 复审必改（`9628e2b1` 的回归）

复审指出：`WeidianResponseParser.resultOrThrow` 对「传输失败」和「成功但缺 result」都抛 `statusCode = -1`，而 `shopWide()` 按 `code < 0` 转换，于是单个订单详情返回空 result 也会让整店同步失败、游标回退——B-5 要解决的「一条坏订单卡住整店」换了个触发条件。

修法：

- `WeidianApiException` 增加两个常量：`NO_USABLE_RESPONSE = -1`（传输失败、令牌响应不完整、令牌时长非法，整店性）与 `MISSING_RESULT = -2`（`status_code = 0` 但没有 `result`，只影响本次调用）；
- `WeidianResponseParser.resultOrThrow` 缺 result 改抛 `MISSING_RESULT`；`WeidianClient` 与 `WeidianTokenCenter` 的 `-1` 改用 `NO_USABLE_RESPONSE`；
- `WeidianBusinessApiClient.shopWide()` 只转换 `NO_USABLE_RESPONSE` 与可重试码用尽，`MISSING_RESULT` 保持 `WeidianApiException`，订单同步按单订单跳过。

测试与验证：

- `WeidianBusinessApiEnvelopeTest.shouldKeepMissingResultAsAPerCallFailure`：走真实 `WeidianClient` + `WeidianBusinessApiClient` 链路，`status_code=0` 无 result → `WeidianApiException(-2)`，未被转换成 `BusinessException`；
- `OrderIT.shouldSkipOnlyTheOrderWithoutResult_whenOtherOrdersSucceed`：2001 缺 result、2002 正常 → 返回 true、只落 2002、重试表 1 行（2001、fail_count 1）、失败记录 1 条、游标前移；
- 复现：把缺 result 临时改回 `-1`，`WeidianBusinessApiEnvelopeTest` 该用例失败；恢复后通过。

### 8.2 转换的影响面（复审非阻塞意见）

转换发生在 `WeidianBusinessApiClient`，`WeidianBusinessApi` 的所有调用方都受影响，不只是订单同步：

- `WeidianItemCopyService.deleteItem`：命中转换的状态码后改走 `RuntimeException` 分支，删除失败原因从「微店删除失败（错误码 N）」变成「微店删除失败」，丢了错误码；
- `probe` / 复制：传输类失败提示变为通用 `WEIDIAN_CALL_FAILED` 文案，授权类失败变为 `WEIDIAN_SHOP_NOT_AUTHORIZED`；语义更准确，但用户可见文案有变化；
- `countOnSaleItems`（#260 / L-163）：传输类与授权类失败不再是未处理的 500，但 108 这类参数错误仍是 500，L-163 仍然有效。
