## 1. 背景

计佣基数一直没有接入：`OrderCommissionSync` 把 `basisCny` 固定传 `null`，所有商品行都是「未核实」，佣金为 0，达人永远无法提现。订单的 `settled_time` 也从未从微店写入，所以即使有基数也不会释放。

计佣引擎本身（任务 62：`CommissionItemSnapshotService`、`CommissionSettlementRules`、`CommissionReleaseJob`、钱包与台账）已经完成。只要 `OrderItemsCommissionEvent.ItemFacts` 带上正确的基数和结算时间，核实、计提、释放、预付冲抵都会按 ADR-032 自动走通。**本任务的工作是把微店结算明细接进来，把这些事实填对，不改计佣引擎的规则。**

**难点**：任务 75 已证实 `shop.order.trade.detail` 可以调用，但店铺还没有任何已结算订单，所以以下几点都**没有真实样本**：金额单位（分还是元）、`tradeType`/`tradeSubType` 的实际取值、`orderId` 的格式、`tradeTime` 的含义。本任务要在没有样本的前提下把代码写成**「拿不准就不核实」**：任何一项对不上，该订单保持未核实、不计提，并留下可查的原因。等 M0 第 5～7 步产生真实结算后，由审查人复测确认，必要时只改常量。

## 2. 已确认的业务规则（负责人 2026-10-28）

| 项 | 规则 |
|---|---|
| 计佣口径 | 佣金 = 微店回传的**可提现金额** × 达人佣金比例（R15，ADR-032 2026-10-28 修订）。比例仍按支付时刻的推广配置，引擎已实现 |
| 可提现金额 | 同一订单在 `shop.order.trade.detail`（`INCOME_DETAIL`）中**所有流水 `amount` 的合计**（货款收入、手续费、分润、退款等，带符号相加） |
| 运费 | **照样计佣**，不从可提现金额中扣除 |
| 一单多个商品行 | **同一笔订单不会出现两个达人的商品**。可提现金额只给整单一个数，系统内部按「商品行实付 ÷ 订单各商品行实付之和」比例分摊到各商品行，用于记账，尾差（四舍五入到分后的差额）计入实付最大的那一行（相同时取商品行 ID 最小的）。达人和界面看到的是汇总数 |
| 防御：一单出现多个达人 | 负责人说明不会发生。万一出现（归属达人去重后多于 1 个），该订单所有商品行保持未核实，原因写 `MULTIPLE_KOLS`，记一条 WARN（只记订单 ID，不记个人信息） |
| 释放 | **不设兜底**，只按结算时间释放。结算时间 = 该订单「货款收入」那一笔流水的 `tradeTime`。没有结算流水的订单一直不释放（`UNSETTLED`），`completedTime` 继续为 `null` |
| 拉取频率 | 默认**每小时增量 + 每天回扫**，频率放进**平台「系统配置」**，平台管理员可在界面修改、不用重启（见 §3.4） |

## 3. 范围

### 3.1 契约与文档（作为第一个提交）

- ADR-032 修订记录追加 2026-10-28 一条，记录 §2 表中的决定（运费照计、单达人订单按行实付比例记账、不兜底只按结算时间、频率进系统配置、金额单位常量 + 校验），并说明 ADR 修订记录中「留给后续开发任务决定」的四点已按此落地。
- 设计说明书：§5 增加结算流水表（§3.2）的表结构说明；§4.8 / §8.3 写明基数来源、核实条件和未核实原因代码；§9 增加结算明细拉取任务。

### 3.2 结算流水入库

- 新增结算流水表（命名自定，例如 `crm_order_settlement_flow`），**必须有 `tenant_id`、表与字段注释**（规范 04）。至少保存：
  - 店铺、微店订单号原值（`orderId`）、匹配到的本库订单 ID（匹配不上为空）、`refundId`、`tradeType`、`tradeSubType`、`tradeTime`、`remark`；
  - `amount` **原始值**（接口返回的数字，不做换算），以及换算后的人民币金额；
  - `queryType`（`INCOME_DETAIL` / `PRE_SETTLE_REFUND`）、首次拉取时间、最后一次拉取时间。
- 接口没有流水 ID。幂等键用「店铺 + `queryType` + `orderId` + `refundId` + `tradeType` + `tradeSubType` + `tradeTime` + `amount` 原值 + `remark`」的指纹，加唯一约束。重复拉取不产生重复行。在设计说明书里写明这个指纹的已知局限（两笔各字段完全相同的流水会被合并），并记入执行报告。
- **订单号只做完全匹配**：`orderId` 与 `crm_order.weidian_order_id` 完全相等才算匹配。不要猜测后缀（如 `_refund`）去截断。匹配不上的流水照样保存，标记为未匹配，不参与计佣。
- 只读接口：在 `integration` 模块的 `WeidianBusinessApi` 中新增 `shop.order.trade.detail` 调用与解析，写法照现有的 `orderList`、`refundList`。分页（`pageSize` ≤ 100），时间窗口按 **≤ 89 天** 切分（任务 75 实测：整 3 个月会被拒绝），遵守 `weidian.qps` 限流。不传 `ctx`。日志与异常不得输出令牌。

### 3.3 计佣事实（`OrderCommissionSync`）

按订单计算后传给 `ItemFacts`，规则如下。

**金额单位**：用一个常量表示结算明细 `amount` 的单位，默认按**分**（任务 75 审查注的判断，未证实），在常量旁写明「待 M0 第 11 步确认」。换算时元保留两位小数，不得有精度损失（用 `BigDecimal`）。

**核实条件**：一个订单同时满足下面全部条件，才给出基数；任何一条不满足，`basisCny` 传 `null`（保持未核实），并记录原因代码：

| 条件 | 不满足时的原因代码（示例，可调整命名） |
|---|---|
| 该订单有已匹配的结算流水（`INCOME_DETAIL`），或出现在 `PRE_SETTLE_REFUND` 列表中 | `NO_SETTLEMENT` |
| 所有流水的 `tradeType`/`tradeSubType` 都在已知集合内。已知集合按开放平台文档示例（货款收入、交易手续费、分润、退款等）写成常量，文档原文以开放平台为准。出现集合外的取值，整单不核实 | `UNKNOWN_FLOW_TYPE` |
| 恰好有一笔「货款收入」，换算后的金额**等于**该订单库内实付 `pay_amount`（订单实付含运费） | `INCOME_MISMATCH`（单位错误、字段理解错误都会落到这里，从而防止佣金差 100 倍） |
| 订单的归属达人不超过 1 个 | `MULTIPLE_KOLS` |

**PRE_SETTLE_REFUND**：结算前全额退款的订单，基数为 `0.00`，视为已核实（金额确定为 0，不会产生佣金）。

**满足条件时**：
- `basisCny` = 订单可提现金额（§2）按商品行实付比例分摊后的该行金额；
- `basisIncludesRefund = TRUE`：流水合计已含退款，引擎不再重复扣成功退款；
- `settlementState = CONFIRMED`；
- `settlementTime` = 「货款收入」的 `tradeTime`。同时把它写入 `crm_order.settled_time`，`OrderWriter` 已有保留逻辑。

**未核实原因要可查**：持久化在订单级（字段或结算流水汇总，自行设计），并在执行报告中说明从哪里查。`CommissionItemSnapshotService` 现有的日志原因（`pending M0`）要能区分上表的几种情况。改动只限于让原因文本正确，不改核实与计佣规则。

**重算触发**：结算流水有变化（新增、或回扫发现新流水）时，对受影响的订单重新调用 `OrderCommissionSync.sync`。计佣引擎按来源版本指纹判断，已有变化才追加修订，重复调用不会重复入账（ADR-032 第 10 条）。

**模块依赖**：结算流水属于订单数据，放在 `order` 模块；微店调用经 `integration.api`。跨模块只经 `api` 包（规范 01），不新增 `commission` 到 `order` 的反向依赖。

### 3.4 拉取任务与系统配置

- 在 `SystemConfigDefinition` 中新增两个平台系统配置项，补中英文名称（平台「系统配置」页按 `nameKey` 显示），并同步 `deploy/README.md` 的系统配置表：
  - `weidian.settlement.sync-interval-minutes`：增量拉取间隔，默认 `60`，范围 `15`～`1440`。每次增量拉取最近 3 天的流水。
  - `weidian.settlement.backfill-hour`：每日回扫的北京时间整点，默认 `3`，范围 `0`～`23`。回扫最近 89 天，补迟到与修正的流水。
- 改配置后不用重启就生效。做法：固定的短周期调度，例如每 5 分钟检查一次，按配置判断各店铺是否到期；每个店铺的上次增量和上次回扫时间要持久化，重启不丢、不重复狂拉。不要为此引入新依赖。
- 按公司执行，跳过停用公司和未授权店铺，用分布式锁防止多实例重复执行（照 `OrderSyncCoordinator` 的写法）。
- 调用失败只记日志并在下一轮重试，不影响订单同步；日志带店铺 ID 和异常堆栈，不带令牌。

## 4. 测试

先写测试再实现（规范 05）。测试数据按开放平台文档示例构造（货款收入、手续费、分润、退款多笔），注释写清手算过程。

- **单元测试**：
  - 解析器：分页、`result.list`/`total`、字段缺失；
  - 单位换算：分转元，不丢精度；
  - 核实条件：上表四种原因各一例，以及全部满足的一例；
  - 金额：多笔流水带符号合计、部分退款流水使基数下降；
  - 分摊：两行、三行订单，尾差落在实付最大的行，各行之和等于整单；
  - `PRE_SETTLE_REFUND` 基数为 0；
  - 指纹幂等；
  - 窗口按 89 天切分；
  - 到期判断：间隔与回扫整点，含北京时间零点前后。
- **集成测试**（Testcontainers，命名 `*IT`、`@Tag("docker")`），微店接口用现有集成测试的桩方式模拟：
  - 端到端：订单同步 → 拉到结算流水 → 商品行已核实、计提金额正确（手算）→ `release_at` = 货款收入时间 → 到期后 `CommissionReleaseJob` 入账 → 达人提现条件可用金额正确；
  - 单位故意设错（流水按元返回），所有行保持未核实，原因 `INCOME_MISMATCH`，钱包无入账；
  - 回扫拉到新的退款流水：基数下降，追加修订，已释放部分产生负向 `COMMISSION_ADJUSTMENT`；
  - 重复拉取：流水不重复，修订不重复，钱包不重复入账；
  - 未匹配订单号的流水只保存、不计佣；
  - 公司隔离、停用公司跳过；
  - 改系统配置后下一轮按新间隔执行。
- 不改、不弱化已有测试的断言；覆盖率门槛不降低。
