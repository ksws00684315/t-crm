## 1. 设计决定落实情况

### 4.1 请求语言

| 决定 | 落实 |
|---|---|
| 只支持 `zh-CN` 与 `en-US` | `shared.AppLocale`（枚举：`ZH_CN` = `Locale.SIMPLIFIED_CHINESE`、`EN_US` = `Locale.ENGLISH`，含 BCP 47 tag `zh-CN` / `en-US`） |
| 从 `Accept-Language` 解析；缺失/无法识别/其他语言一律英文 | `shared.SupportedLocaleResolver`（实现 Spring `LocaleResolver`）：用 `Locale.lookup` 匹配候选（`zh-CN`、`zh`、`en`），命中后折叠回两种语言之一，未命中或解析异常返回英文；**从不读取服务器默认 `Locale`** |
| 支持 `zh-CN`、`zh`、`en-US`、`en` 等写法；带权列表取第一个受支持的语言 | 同上。语言前缀匹配：`zh` / `zh-TW` → `zh-CN`，`en` / `en-US` / `en-GB` → `en-US`；`zh,en;q=0.8` 取 `zh-CN`，`en-GB,zh-CN;q=0.9` 取英文（`en-GB` 前缀命中英文优先于列表后部的 `zh-CN`，符合 RFC 4647 lookup） |
| 使用 Spring `LocaleResolver`，结果不受服务器默认 `Locale` 影响 | `shared.CommonConfiguration#localeResolver` 注册该 bean（Spring Boot 检测到后不再装配默认的）；`SupportedLocaleResolverTest` 在 `Locale.setDefault(zh)` 下验证缺失请求头仍为英文。**未用 `AcceptHeaderLocaleResolver` 的原因**：Spring 7.0.9 中它对裸 `zh`（语言标签无地区）会退到默认语言而非 `zh-CN`，不满足"支持 `zh` 等常见写法"的要求 |
| `MessageSource`：`messages_zh_CN.properties` + `messages_en.properties`，`fallbackToSystemLocale=false`，键一致由测试检查 | 两个文件在 `backend/src/main/resources/`；配置在 `application.yml`（`spring.messages.fallback-to-system-locale: false`、`encoding: UTF-8`）；键一致由 `shared.MessageBundlesTest` 检查 |
| 是否需要与英文相同的 `messages.properties` 基准文件 | **加了**，内容与 `messages_en.properties` 完全相同（测试断言逐字节一致）。作用：兜底两种支持语言之外的任何语言（仍应英文）；`fallbackToSystemLocale=false` 只关掉系统语言回退，没有基准文件时异常语言会抛 `NoSuchMessageException`，有基准文件则安全回英文 |

另有一处与校验相关的资源包（见 4.2）。

### 4.2 参数校验提示

| 决定 | 落实 |
|---|---|
| 消息插值按当前请求语言，只允许两种语言 | `CommonConfiguration#localeAwareValidationMessages`（替代原 `englishValidationMessages`）：把 Hibernate Validator 的默认插值器包进 `RequestLocaleMessageInterpolator`，两个 `interpolate` 重载都用 `AppLocale.current()`（请求语言，无请求上下文时英文），传入的 `Locale` 参数被忽略。原因：HV 9 的 `DefaultLocaleResolver` 只认 JVM 默认语言（不再桥接 Spring 的 `LocaleContextHolder`），Spring 的 `LocaleContextMessageInterpolator` 只在两参重载里生效而 HV 只调三参重载，均不可用 |
| Hibernate Validator 自带中英文提示可直接使用 | 未改动 HV 内置约束；中文来自 hibernate-validator 9.1.3 自带的 `ValidationMessages_zh_CN` |
| 自定义校验注解中英文两份 | `CountryCode` / `CompanyRole` 的 `message()` 改为 `{tcrm.constraint.*}` 模板，文案放 classpath 根的 `ValidationMessages.properties` / `ValidationMessages_en.properties` / `ValidationMessages_zh_CN.properties`（HV 贡献者资源包机制，三个文件键一致由测试检查）。**`ValidationMessages_en.properties` 必须显式存在**：JDK `ResourceBundle` 在请求 `en` 找不到 `_en` 文件时会回退到 JVM 默认语言（中文服务器上会给出中文），显式 `_en` 文件阻断该回退 |
| 返回结构不变：`FieldErrorVO.message` 随语言，信封 `msg` 仍英文 | `GlobalExceptionHandler` 未改动；`ValidationMessagesTest` 断言两种语言下信封 `msg` 均为 ASCII 英文 |
| `ValidationMessagesTest` 改写（ADR-015 有意行为变化） | 见第 3 节 |

### 4.3 导入模板

| 决定 | 落实 |
|---|---|
| 列定义改为语言包键 | `KolImportColumn` / `ProductImportColumn` / `MappingImportColumn` 常量改为 `import.{kol|product|mapping}.header.*` 键，`headers()` → `headerKeys()` |
| 表头与文件名使用请求语言；原有中文文件名不变 | 模板：`ImportTaskService.template(keys)` 用 `AppLocale.current()` 渲染。文件名：三个控制器（`KolImportController`、`ProductImportController`、`KolItemImportController`）注入 `MessageSource`，按 `import.{type}.template-name` 键解析（英文沿用原有 `kol-import-template.xlsx` 等；中文为 `达人导入模板.xlsx`、`原商品导入模板.xlsx`、`对应关系导入模板.xlsx`） |

### 4.4 导入错误文件

| 决定 | 落实 |
|---|---|
| `crm_task.locale VARCHAR(8) NOT NULL` + `CHECK (locale IN ('zh-CN','en-US'))`；存量行 `zh-CN`；迁移后无默认值；表/字段注释 | `V202610121000__add_task_locale.sql`：`ADD COLUMN ... NOT NULL DEFAULT 'zh-CN'` → 存量行取默认 → `ALTER COLUMN locale DROP DEFAULT` → `ADD CONSTRAINT ck_crm_task_locale` → `COMMENT` |
| 处理器返回"消息键 + 参数"；生成错误文件按任务 `locale` 渲染 | `task.api.ImportReason(key, args)`；`ImportRowProcessor.process` 返回 `List<ImportReason>`。三个处理器（`KolImportProcessor`、`ProductImportProcessor`、`MappingImportProcessor`）的中文句子常量改为 `import.{type}.error.*` 键；带动态内容的"专属商品已被占用"改为 `{0}`/`{1}` 参数。`ImportTaskService` 渲染错误列头（`import.error.column`）、分隔符（`import.error.reason-separator`，中文 `；` / 英文 `; `，英文尾随空格在 properties 里用 `\u0020` 转义防止被编辑器裁剪）、系统错误整行提示（`import.error.row-error`）与每条原因，全部 `getMessage(key, args, taskLocale)` |

| 存量任务迁移后 `zh-CN` | `TaskLocaleMigrationIT`：先迁移到 06d 之前 → 插入任务行 → 再迁移 → 断言 `locale='zh-CN'`、默认值已删、两种取值都能插入 |

## 3. `ValidationMessagesTest` 改写说明

原测试断言"校验提示不受请求语言影响、固定英文"——这是 ADR-015 之前的行为，任务提示词 4.2 第 4 条明确该行为**有意改变**，并要求改写断言（不属于弱化）。改写后：

1. `shouldInterpolateChineseFieldErrors_whenRequestAsksForChinese`：`Accept-Language: zh-CN` 的非法创建用户请求返回中文字段提示（精确断言 `不能为空`、`个数必须在10和72之间`、`不是一个合法的电子邮件地址`、`不能为null`），字段仍按稳定顺序排序，信封 `msg` 仍为英文。
2. `shouldInterpolateEnglishFieldErrors_whenRequestAsksForEnglishOrOmitsTheHeader`：`en-US`、`en`、`fr-FR`、缺失请求头（服务器默认语言为中文，`@BeforeEach` 设定）四种情况都返回英文字段提示。
3. `shouldLocalizeCustomConstraintMessages_inBothLanguages`：`@CountryCode` 与 `@CompanyRole` 两种语言下都有文案。

配套：`PlatformRequestValidationTest`（裸 Jakarta 校验器，无请求上下文）改为在构建校验器工厂前固定 JVM 默认语言为英文——HV 9 在工厂构建时捕获 JVM 默认语言，裸工厂与请求语言无关，固定英文后原有英文断言在任何机器上稳定（不改被测行为）。`GlobalExceptionHandlerOrderTest` 的断言与消息文本无关，未改。

## 4. 迁移锁表评估

`V202610121000__add_task_locale.sql` 只涉及 `crm_task`：

- `ADD COLUMN ... NOT NULL DEFAULT 'zh-CN'`：PostgreSQL 11+ 对常量默认值只写目录，**不重写表、不长时间锁**，瞬时 `ACCESS EXCLUSIVE`；
- `DROP DEFAULT`、`ADD CONSTRAINT ... CHECK (IN ('zh-CN','en-US'))`：`ACCESS EXCLUSIVE`，`crm_task` 是批量任务表（合同规模下每天数百行以内），CHECK 在小表上瞬时完成；
- 前提：迁移在事务内执行（Flyway 默认）。若线上有正在执行的导入任务写入 `crm_task`，该事务会短暂等待锁（毫秒级），不影响数据。

## 7. 偏离与遗留事项

- **实现选择（非偏离，供审阅）**：
  1. 未用 `AcceptHeaderLocaleResolver`（Spring 7.0.9 对裸 `zh` 解析不符合要求），改为实现 `LocaleResolver` 的小类 `SupportedLocaleResolver`，属提示词"例如"之外的等价实现；
  2. 校验插值未新增依赖：HV 9 的 locale 机制与 Spring 桥接脱节，用自写 `MessageInterpolator` 装饰器解决（见 4.2 表）；
  3. 新增 `messages.properties`（=英文）与 `ValidationMessages_en.properties`（=英文），理由见 4.1/4.2 表；
  4. `en-GB,zh-CN;q=0.9` 解析为英文（语言前缀命中优先于列表顺序），`zh-TW` 解析为 `zh-CN`——按 RFC 4647 lookup 语义。
- **遗留**：
  1. 达人登录与邀请邮件的双语模板（后续任务）；
  2. `spring-messages` 相关：达人端/管理端请求头 `Accept-Language` 由前端任务负责携带；
  3. 导入模板英文表头与错误文案的翻译质量请项目负责人与客户审阅（本报告第 2 节全表）。
