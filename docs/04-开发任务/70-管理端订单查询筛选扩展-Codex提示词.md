## 1. 背景

#122 已把管理端订单页的筛选改成：订单号、店铺、达人编号/姓名、订单状态、平台下单时间。后端还不支持的部分，前端显示「开发中」并禁用：

- 按达人姓名查询；
- 订单状态下拉中的「退款中」「退款成功」「异常订单」三项。

本任务补齐后端，并把前端这几处接上。**需求以对接清单原文为准**，负责人已确认其中的业务语义。

## 2. 范围

### 2.1 契约（作为本 PR 的第一个提交）

在设计说明书 §6.2 的 `GET /admin-api/order/orders` 一行中写明新增参数的名称、类型、时区与边界、匹配规则，并同步机读目录。建议的参数（可以调整命名，但要在契约中写清楚）：
- `orderTimeFrom`、`orderTimeTo`：平台下单时间 `crm_order.order_time`，UTC，含头不含尾，与 `payFrom`/`payTo` 的写法一致；
- `kolKeyword`：达人业务编号或姓名；
- `refundState`：`REFUNDING`（退款中）/ `REFUNDED`（退款成功，包含部分退款成功和整单退款成功）；
- `abnormal`：`true` 时表示异常订单。

### 2.2 后端（order 模块）

- **B01 下单时间**：按 `order_time` 过滤，不得用付款时间或入库时间 `create_time` 代替。原有 `payFrom`/`payTo` 的语义保持不变，两组参数可以同时使用。
- **B02 达人编号或姓名**：一个输入框同时支持业务编号和姓名。编号精确匹配（兼容原 `kolCode`），姓名不区分大小写、包含匹配（转义 `%`、`_`）。经 `kol.api` 把关键词解析为达人 ID 集合，再在订单查询中过滤；order 已经依赖 `kol.api`，不会形成循环。命中范围与原 `kolCode` 一致；如果原有逻辑只按主单达人过滤，而多达人订单需要按商品行达人匹配，先停下来报告。原 `kolCode` 参数保留兼容。
- **B03 退款状态**：根据 `crm_refund` 的实际退款记录判断，用 `EXISTS` 子查询，同一订单有多条退款记录时不得重复计数。
  - `REFUNDING`：存在进行中的退款；
  - `REFUNDED`：存在退款成功的记录（部分或整单）。
  - 同一订单可能同时满足两者，两个筛选分别都能查到它。
  - 退款状态的取值以现有 `refund_status` 枚举为准，并在契约中写明映射关系。
  - **不得**把退款状态塞进原有的 `orderStatus` 枚举。
- **B04 异常订单**：`order_status = 'UNKNOWN' OR attribution_status IN ('UNMATCHED','CONFLICT')`，三个条件作为一个整体（并集），再与店铺、时间、达人、公司隔离和本人数据范围取交集。
- 所有筛选都在服务端、分页之前执行，`total` 与结果集用同一组条件。

### 2.3 前端（admin-ui，只改接线，不改 #122 的布局）

- 平台下单时间、达人编号/姓名、退款中、退款成功、异常订单，去掉「开发中」和禁用状态，改为调用新参数。
- 订单状态下拉中，原有 7 种状态仍走 `orderStatus`；「退款中」「退款成功」走 `refundState`；「异常订单」走 `abnormal=true`。
- 同步更新 `admin-ui/src/api/order/order.ts` 的类型与中英文文案，补前端测试。
