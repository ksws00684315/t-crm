## 3. 计佣数字口径（手算，供复核）

单位默认按分。桩数据：货款收入 60000 分（=600.00 元，等于订单实付）、交易手续费 −400 分、分润 −30000 分 → 可提现金额 **296.00** 元。商品行实付 400.00 / 200.00（和 600.00）→ 分摊 296×400/600=197.33、296×200/600=98.67（和恰为 296.00）。达人比例 10% → 计提 **19.73 + 9.87 = 29.60**；结算时间 = 货款收入 `tradeTime`，释放后钱包 29.60、可提现 29.60。

## 7. 待 M0 验证（有真实结算样本后，M0 清单第 11 步）

1. **金额单位常量**（`SettlementBasisCalculator.AMOUNT_IN_MINOR_UNITS`，默认分）：用能匹配本库订单的「货款收入」与订单实付比对；证实为元则只改此常量。
2. **已知流水类型集合**（`KNOWN_TRADE_TYPES` / `KNOWN_TRADE_SUB_TYPES` / `TRADE_SUB_TYPE_GOODS_INCOME`）：按实测 `tradeType × tradeSubType` 取值修正；集合外取值整单不核实（`UNKNOWN_FLOW_TYPE`）。
3. **`orderId` 完全匹配**：结算明细回传的 `orderId` 是否与 `crm_order.weidian_order_id` 完全相等（不截断 `_refund` 等后缀）；匹配不上的流水只保存不计佣。
4. **`tradeTime` 含义**：「货款收入」一笔的 `tradeTime` 是否即结算时点（对应 `settled_time` 与释放）。
5. **一单的「货款收入」= 订单实付**（含运费）：不等则单位或口径有误，订单停在 `INCOME_MISMATCH` 不核实——这是防佣金差 100 倍的校验，复测时重点确认。

## 8. 偏离与原因

1. **已知流水类型常量的取值依据**：开放平台文档需登录，无法在任务内重读原文；常量按任务 75 提示词中审查人记录的文档示例（`tradeType`＝收入/支出；子类型＝货款收入、交易手续费、分润、退款）写成中文字面值集合。任何集合外取值整单不核实（fail-safe），M0 复测后必要时只改常量——与提示词「必要时只改常量」一致。
2. **新增第 5 个原因代码 `ALLOCATION_FAILED`**：提示词原因代码为「示例，可调整命名」；各行实付全为 0 而整单基数非 0 时无法分摊，单列为独立代码（归并进 `INCOME_MISMATCH` 会掩盖数据问题），已写入设计说明书 §4.8.1。
3. **达人端资金页**：任务只分配了后端 18761 与管理端 Vite 8876 两个端口，未给 kol-portal 端口（规范：只用分配端口），达人端资金页未单独起服务；「可提现金额」通过管理端「财务 → 收入 → 达人详情」验证（ADR-032：一份后端两个前端，同一接口数据）。如需 kol-portal 截图，请负责人补派端口后补做。
4. **翻页上限**：每窗每查询类型最多 200 页（2 万条）防御失控翻页；触限时保留已拉流水但**不触发**该窗订单重算（数据可能不完整，宁可不算），记 ERROR 等下一轮完整拉取，避免按不完整流水算出错误基数。
5. **重算失败的恢复**：单订单重算失败只记 ERROR；该订单在下次自身流水变化或订单/退款同步触及时自然重算（`OrderCommissionSync.sync` 每次都从流水表现算）。
