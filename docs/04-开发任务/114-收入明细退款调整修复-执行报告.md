## 3. 主要改动

1. `CommissionSettlementRules` 新增三个共用方法（`backend/src/main/java/com/tcrm/admin/commission/service/CommissionSettlementRules.java:113-131`）：
   - `refundAdjustment(accruedCny, releasedCny)`：`min(已计提 − 已释放, 0)`，`released` 为 null 按 0 处理；
   - `adjustmentDirection(adjustment)`：负数 `DEBIT`，否则 `CREDIT`（与结算明细任务 81 起的原判断一致）；
   - `commissionableText(row)`：`commissionable(row)` 的文本化（null 时返回 null）。
2. `CommissionIncomeService`：删除私有 `commissionableText`，「退款调整」改调 `refundAdjustment`，方向改调 `adjustmentDirection`（原 `released − accrued` 缺陷即在此）。
3. `CommissionSettlementDetailService`：同样接入三个共用方法，删除本地的内联公式与私有 `commissionableText`；取值与任务 81 的实现完全一致（同一输入同一输出）。

### 3.1 关于提示词 §2.3「合并 commissionableText」（派发说明的回应）

任务 113（#206）已把计佣金额取值统一为 `CommissionSettlementRules.commissionable(CommissionItemStateDO)` 一个入口，链路 `OrderChainCommissionService.commissionable(state)` 已委托该入口（并带 verified/null 语义），本次未动。仍然逐字重复的是收入明细、结算明细两个服务里的私有 `commissionableText(row)`（文本化渲染），本次把它合并为 `CommissionSettlementRules.commissionableText(row)`，两服务改调共用方法。L-114 第 ① 项至此处理完毕（清单本身由架构负责人改）。

### 3.2 方向判断（提示词 §2.2）

两处原判断完全相同（`adjustment.signum() < 0 ? "DEBIT" : "CREDIT"`），收入明细照结算明细改后共用 `adjustmentDirection`。调整为 0 时方向为 `CREDIT`（冻结中的行、已释放无退款的行均显示 `CREDIT 0.00`）——这是结算明细的现有行为，按提示词未顺手改；语义上 0 调整记 CREDIT（该列描述调整分录方向）合理。
