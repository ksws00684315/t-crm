## 2. 后端补充（限任务 §4.1 两项）

### 2.1 订单列表补显示字段

`OrderDTO` 增加 `shopName`、`kolCode`、`kolName`、`bdUserName`；`OrderItemDTO` 增加 `kolCode`。组装在 `OrderService.decorate`：

- 店铺名来自 `product.api.ShopAccessApi.listShops()`（每页一次，含停用店铺，已删除店铺为空）；
- 达人编号/姓名来自 `kol.api.KolApi.listByIds`（订单达人与全部明细达人合并去重后一次查询）；
- 商务显示名来自 `system.api.BdUserApi.listByIds`，昵称优先、无昵称用用户名，`bd_user_id` 为空（归公司）时为 `null`；
- `orders` 与 `unmatched` 两个查询共用该逻辑，每页对上述三个 API 各调用一次，查询次数不随行数变化；无数据页不触发。

### 2.2 店铺同步状态

新增 `GET /admin-api/order/sync-states`（`order:view`），返回 `[{shopId, shopName, enabled, authorized, lastSuccessAt, lastError}]`：店铺与启用状态来自 `listShops()`，授权来自 `integration.api.WeidianAuthorizationApi.authorizedShopIds()`，同步时间与错误来自 `crm_order_sync_state`（按租户过滤）；无同步记录的店铺照常出现，两个时间为空。订单页与匹配池的店铺筛选下拉均使用该接口，无 `product:view` 的账号也能选店铺。

未改动第 4.1 节之外的任何后端类；错误码无新增。

| 页面/入口 | 路由 | 权限 | 说明 |

- **订单列表**：筛选为店铺（来自 sync-states）、支付时间区间（`el-date-picker` 本地时区选择，`payRangeToQuery` 转 UTC ISO，`payTo` 原值传递、后端不含）、达人编号、订单状态、归因状态；列为订单号（`CopyText`）、店铺、支付时间、订单状态、实付、退款合计、达人（编号·姓名）、所属商务（空显示「公司」）、归因状态（已归属/非达人/冲突/未匹配/待支付彩色标签）；展开行显示明细九列（商品 ID、名称、型号、数量、明细实付、退款、归属达人编号、归因方式、人工原因）。
- **同步状态对话框**：列出全部店铺的启用/授权状态、最近成功时间、最近错误；仅「启用且已授权」的店铺有「立即同步」（`POST /order/syncs`），202 提示「已开始同步」，409 `ORDER_SYNC_RUNNING` 经 `notifyError` 映射语言包文案。「最近错误」按审查建议改为本地化的「同步失败」标签，鼠标悬停显示后端的英文摘要原文；无错误显示「-」。
- **导入入口**：`ImportDialog` 按任务 18 的接口约定（`/order/order-imports`、`/order/refund-imports` 及模板下载），模板文件名「订单导入模板.xlsx」「退款导入模板.xlsx」（语言包键），完成后刷新列表。
- **人工匹配池**：店铺+支付区间筛选，列同订单列表，默认展开全部明细；三种操作——指定达人（远程搜索 `GET /kol/kols`，原因必填 ≤255）、标为非达人订单（原因必填）、重新匹配（确认后 `POST .../reattribution`）；成功后刷新，处理完的订单自然离开匹配池。
- 公共组件 `DataTable` 增加 `expandable` / `defaultExpandAll` 与 `expand` 作用域插槽（选中等原有行为不变）；`TaskType` 增加 `ORDER_IMPORT`、`REFUND_IMPORT`。界面文字全部来自语言包，两份语言包键一致（`messages.spec` 校验通过）。

### 5.1 导入上传的端到端验证（审查修订）

审查指出管理端的 `FormData` 上传会被 axios 序列化成 JSON（`{"file":{}}`）。该缺陷已由 main 上的 #66 在 `utils/http` 的请求拦截器统一修复（`FormData` 时清掉 JSON `Content-Type`），本分支合并 main 后沿用同一实现，不再重复改动；`request.spec.ts` 中 #66 的两项测试（FormData 原样到达适配器且无 JSON 头、普通对象仍为 JSON）在本分支通过。本地按规范先写过复现测试确认到达适配器的 `data` 为字符串 `'{"file":{}}'`，与审查实测一致，随后以 main 的版本替换。

浏览器实测（#58 尚未合并，用其分支 `8b0c87f` 的后端提供导入接口）：

- 环境：PostgreSQL/Redis（Compose `tcrm-19a`），`origin/task/18-order-import` 的 `backend/` 提取到临时目录运行于 18191，本分支管理端 8891；店铺「19a 演示总店」微店店铺 ID `12345678`。导入文件由 Python 标准库生成（中文表头 + 同一订单两行明细）。
- 自动化运行时不能驱动系统文件选择器，文件通过 `DataTransfer` 放入对话框真实的 `<input type="file">` 并触发 `change`，之后走的都是组件原有逻辑：校验、`uploadOrderImport` → `http.request` → 浏览器 XHR → 后端 `POST /admin-api/order/order-imports`（该端点 `consumes = multipart/form-data`，JSON 请求体会被 415 拒绝）→ 202 `{taskId}` → `ImportDialog` 轮询任务。
- 第一次上传：请求被后端接受并创建 `ORDER_IMPORT` 任务，两行因业务校验失败（订单号须为 1～32 位数字，我的样例带字母前缀）；对话框显示「导入失败：2 行全部未导入」，错误文件经 `GET /task/tasks/{id}/error-file` 下载为 200 的 xlsx，末列「错误原因」为中文。这一步已证明 multipart 链路正确（否则不会有任务）。
- 第二次上传（对话框「继续导入」）：修正订单号后「导入完成：成功 2 行」（截图 18）；关闭对话框触发 `@finished` 刷新，列表出现该订单（截图 19，归因「未匹配」属预期，未录对应关系）。
- 说明：截图 19 的「店铺」列为空，因为 #58 分支的后端不含本 PR 的 `shopName` 等补充字段（它从 `7ed6691` 分出）；显示字段已在截图 01/02 用本分支后端验证。#58 合并后两边字段自然齐全，不需要再改。
