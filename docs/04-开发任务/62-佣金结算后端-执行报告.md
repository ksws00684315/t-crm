### 3.2 计佣引擎（commission 模块）

- `CommissionSettlementRules`（纯函数，设计 §8.3）：核实条件（有效金额语义 + 归因类型 1/2 + 支付时刻比例）、有效金额（来源未扣退款时减成功退款、下限 0）、`round_half_up(有效金额 × 比例, 2)`、释放依据矩阵（`CONFIRMED` / `FALLBACK`+冻结天数默认 7 / `UNSETTLED` / `AFTER_SALES` / `UNVERIFIED`）。
- `CommissionItemSnapshotService`（实现 `commission.api.CommissionItemApi`）：来源版本指纹（MD5，含比例与规则版本推导项）变化才追加修订；比例解析商品级优先 [D7]，否则取 `crm_kol_promotion_record` 支付时刻生效的 `defaultRate`（`KolApi.rateEffectiveAt`）；规则版本取支付时刻生效的 `crm_commission_rule_version`；归属变更先对原达人 `postCommissionAdjustment(−已释放)` 并重置释放基数；同归属下调产生负向差额；正向冻结差额留给释放任务。同步后清理被替换删除商品行的快照（逻辑删除）。
- `CommissionWalletService.postCommissionAdjustment`（新增）：负向记账，同一事务更新钱包，余额可为负，不参与 FIFO；`source_key` 上限放宽到 160。
- `CommissionReleaseService` + `CommissionReleaseJob`：每 5 分钟（UTC）持 `commission:release` 分布式锁遍历启用公司，把 `release_at ≤ now` 的已核实行差额经 `postCommissionCredit` 入钱包（预付 FIFO 冲抵自动发生），行锁重读防并发；整批无进展即停，防打转；同键金额冲突时以台账为准对齐行。
- `CommissionRuleConfigService`：结算配置读取（无版本时返回默认 version 0 / 200.00 / 7 天）与保存（`expectedVersion` 乐观锁，不匹配 409 `COMMISSION_CONFIG_VERSION_CONFLICT`；minimum ≥ 0 两位小数、days 0～365；写 `sys_oper_log` 业务审计）。

### 3.3 订单侧接入（order 模块）

- `OrderItemsCommissionEvent`（`order/api`）+ `OrderCommissionSync`：订单保存（同步与导入都汇入 `OrderWriter.save`）、退款保存（`saveRefund` / `saveImportedRefund` 的完成退款合计刷新）、人工归因与重新归因（`OrderService.persist`）在事务内发布事件；`CommissionSnapshotListener` 以 `BEFORE_COMMIT` 在同一事务登记快照——**见 §8 偏离 1（ArchUnit 禁止模块循环，用规范 01 的事件方案替代 order→commission.api 直调）**。微店同步目前不提供可提现金额，来源事实传 `basisCny = null`，全部行落「未核实」（Q-1017-1/2 待 M0）。

## 8. 偏离与原因

1. **订单侧经 Spring 事件而非直调 `commission.api`**（ADR-032 §2「order 模块通过 commission 模块的 api 登记」的字面方向）：ArchUnit 强制「模块禁止循环依赖」——既有 commission→notification（预付 outbox）与 notification→order（同步失败通知）已构成链，再加 order→commission 即成环。按规范 01「需要反向通知时使用 Spring 应用事件」：`order.api.OrderItemsCommissionEvent` 在订单事务内发布，`CommissionSnapshotListener` 以 `BEFORE_COMMIT` 在**同一事务**登记快照，原子性与契约语义不变；`commission.api.CommissionItemApi` 保留为模块公开契约（集成测试直驱）。若负责人要求字面方向，需要先解除 commission→notification 或 notification→order 依赖，属跨任务结构调整。
2. **归属变更回冲的台账 source_key 追加 `:K{原达人ID}` 后缀**（ADR-032 §1 仅给出 `COMMISSION_ITEM:{item_state_id}:{source_version}`）：同一版本可能需对原达人回冲、又对新达人释放，两个钱包不能共用幂等键；后缀仅用于跨钱包回冲一种场景，幂等与审计不受影响。
3. **11.02「设置流水、记预付金额入口」「13.05 重置/刷新/复制」等界面交互**：本任务为后端任务，接口与数据已备，交互归管理端前端（PR #112 页面）任务。
4. **收入列表 `lines`/`payments` 不分页**（契约即不分页）与 **`fund-records` 内存分页**：当前数据量（每达人流水/每公司活跃达人）在管理规模内；若后续量级变化再引入游标分页（规范 04 推荐）。
