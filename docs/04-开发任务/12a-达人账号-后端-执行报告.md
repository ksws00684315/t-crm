## 1. 数据库迁移

`backend/src/main/resources/db/migration/V202610171200__kol_account.sql`：

1. `crm_kol` 新增列（均有中文注释）：
   - `password_hash VARCHAR(100) NULL`（BCrypt）；
   - `account_status SMALLINT NOT NULL DEFAULT 0`（0 未激活 / 1 已激活）；
   - `credential_version INT NOT NULL DEFAULT 0`；
   - `last_login_time TIMESTAMPTZ(3) NULL`；
   - 约束 `ck_crm_kol_account_password CHECK (account_status = 0 OR password_hash IS NOT NULL)` 与 `ck_crm_kol_account_status CHECK (account_status IN (0, 1))`。
2. 新表 `crm_kol_auth_token`（只追加，使用后置 `used_at`，无修改类字段与逻辑删除，表注释已说明）：`id`、`tenant_id`、`kol_id`、`purpose VARCHAR(8)`（`INVITE`/`RESET`，CHECK 约束）、`token_hash CHAR(64)`、`expires_at`、`used_at`、`create_time`；唯一索引 `uk_crm_kol_auth_token_token_hash(token_hash)`，普通索引 `idx_crm_kol_auth_token_kol(kol_id, purpose)`。

**索引说明**（规范 04 第 3 节）：登录按 `lower(email)` 跨公司查询（`WHERE lower(email) = ? AND is_deleted = FALSE`）。现有唯一索引 `uk_crm_kol_email` 以 `tenant_id` 开头（多公司改版后为公司内唯一），该查询无法命中；`crm_kol` 为小表（合同规模百级），且任务提示词已固定迁移内容不含新索引，故未额外加索引——如达人数量显著增长，建议新增 `ON crm_kol (lower(email)) WHERE is_deleted = FALSE` 部分索引。`crm_kol_auth_token` 的两个查询（按哈希、按达人+用途）分别命中上述索引。

**锁表风险**：`crm_kol` 加列均为带常量默认值或不带默认值，PostgreSQL 17 仅改元数据；新表新建。无 `CONCURRENTLY` 需求。

## 2. 达人令牌体系

- `StpKolUtil`（`security.api`）持有独立 `StpLogic("kol")` 与静态委托方法；`SecurityConfiguration.kolStpLogic()` 用 `SaTokenConfig.setConfig` 为其配置独立参数并注册进 `SaManager`，`@SaCheckLogin(type = "kol")` 与拦截器共用同一实例：
  - 令牌名 `X-Kol-Token`（配置 `crm.kol-auth.token-name`，默认 `X-Kol-Token`），只读请求头；
  - 绝对有效期 7 天（`crm.kol-auth.timeout`，默认 604800 秒），空闲 3 天失效（`crm.kol-auth.active-timeout`，默认 259200 秒），每次请求续期；
  - 多端登录允许（`is-concurrent=true`、`is-share=false`），每达人最多 10 个令牌（`crm.kol-auth.max-login-count`，默认 10），超出时最早的失效；
  - 不受 `sa-token.*` 全局配置影响；`application.yml` 中 `sa-token` 段注释已改为"仅管理端账号体系"，设计说明书 §3.3 增加达人端令牌说明。
- `CurrentKolContext`（`security.api`）每次请求按达人 ID 重读达人状态、账号状态、`credential_version` 与所属公司状态（按请求缓存一次）；达人停用、公司停用或版本不一致时注销令牌并返回 401（`AUTH_ACCOUNT_DISABLED` / `AUTH_UNAUTHORIZED`），与管理端 `CurrentUserContext` 对称。
- `KolApiInterceptor`（`security.config`）拦截 `/kol-api/**`，排除 5 个公开接口：先 `StpKolUtil.checkLogin()` + 账号校验，再用 `TenantScope.openCompany` 打开该达人所属公司的范围，`afterCompletion` 关闭；因此达人端每条 SQL 自动限定在本公司。第二个 `SaInterceptor` 处理 `@SaCheckLogin(type = "kol")` 注解。
- 令牌隔离：两个账号体系的 Redis 键均含各自令牌名与 loginType（`X-Admin-Token:admin:*` vs `X-Kol-Token:kol:*`），互不可见；集成测试覆盖"达人令牌访问 /admin-api 401、管理员令牌访问 /kol-api 401"。
- `ArchitectureTest.shouldDeclareAccess` 扩展：公开接口 `@PublicEndpoint`，达人接口可声明 `@SaCheckLogin(type = StpKolUtil.TYPE)`。

## 3. 接口与实际响应示例（供 12b 核对，均为统一信封）

登录成功 `POST /kol-api/auth/login`：

```json
{"code":0,"msg":"Success","data":{"tokenName":"X-Kol-Token","token":"6f1c…uuid","expiresIn":604800,
 "kol":{"kolCode":"KOL0003","name":"Alice","email":"alice@example.com","country":"US","tenantName":"默认公司"}},
 "errorCode":null,"traceId":"…"}
```

多家公司匹配时同一接口返回：

```json
{"code":0,"msg":"Success","data":{"selectionToken":"43位随机串",
 "companies":[{"tenantId":"1","tenantName":"默认公司"},{"tenantId":"雪花ID字符串","tenantName":"第二公司"}]},
 "errorCode":null,"traceId":"…"}
```

`POST /kol-api/auth/login/select`（`{selectionToken, tenantId}` 字符串）与 `POST /kol-api/auth/activate`、`PUT /kol-api/me/password` 返回与"登录成功"相同的结构；`POST /kol-api/auth/logout`、`/forgot`、`/reset` 返回 `"data": null`。`GET /kol-api/me` 返回 `data` 即上面 `kol` 对象。

错误码与 4.8 一致：`AUTH_INVALID_CREDENTIALS` 401、`AUTH_ACCOUNT_LOCKED` 429、`AUTH_ACCOUNT_DISABLED` 401、`AUTH_UNAUTHORIZED` 401、`KOL_AUTH_TOKEN_INVALID` 400、`AUTH_OLD_PASSWORD_INCORRECT` 422、`KOL_LOGIN_SELECTION_INVALID` 400。新登记于 `shared.ErrorCode`；前端文案映射按任务划分留给 12b（本任务禁止修改 `kol-portal/`，见偏离说明）。

管理端新增 `POST /admin-api/kol/kols/{id}/invite`（权限与达人编辑相同：`@SaCheckRole SUPER_ADMIN/OPERATOR`，10a 合并后随编辑接口一起改为 `kol:edit`）；已激活返回 409 `KOL_ALREADY_ACTIVATED`。

## 4. 规则实现要点

1. 密码 10–72 位可打印 ASCII（与管理端相同的校验注解），BCrypt（强度 12 的共用编码器）。
2. 失败计数：`LoginFailures` 增加键前缀参数，达人实例为 `@Bean kolLoginFailures`（前缀 `kol:auth`，键 `kol:auth:fail:*`），阈值与管理端一致（5/20/50、15 分钟窗口）；账号不存在或未激活也执行一次 BCrypt（启动随机 `timingHash`）。
3. 无图形验证码（§3.4 已写明，ADR-017 只约束管理端）。
4. 未激活账号无密码，按密码错误处理；密码正确但达人或公司停用返回 `AUTH_ACCOUNT_DISABLED`（不计数失败）。停用的达人/公司不能激活或重置（令牌按无效处理，见偏离说明第 4 条）。
5. 邀请/重置令牌：32 字节随机数 Base64URL（43 字符），库中只存 SHA-256 十六进制；邀请 72 小时、重置 30 分钟、均一次性（`markUsed` 的 UPDATE 带条件防并发双用）；重置成功后同达人其余未使用重置令牌一并作废；改密/重置 `credential_version + 1` 使旧令牌全部失效。
6. 选择凭据：32 字节随机串，Redis 键 `kol:auth:selection:{token}`，值为已通过密码校验的达人 ID 列表（JSON 字符串数组），5 分钟 TTL，读取用 `GETDEL` 保证一次性；只能换取列表内账号。
7. 自动邀请：仅 `KolService.create`（后台单个新建，行已提交）触发 `KolInvites.issueAndSend`；Excel 导入走 `KolImportProcessor → KolWriter`，不触发。发送在 `@Async` 线程，失败只 `WARN`。
8. 找回限流：IP 每小时 20 次（每次请求计数）、邮箱 10 分钟 3 封（仅在实际发信时计数），超出仍返回成功但不发送；键为 SHA-256 摘要，不含明文。
9. 审计：激活 / 改密 / 重置经 `ExternalAuditApi.recordKolOperation` 写 `sys_oper_log`（module=`KolAuth`，username=达人邮箱，params 只含 `kolId`）；管理端重发邀请走 `@AuditLog(module="KOL", action="Resend invite")`。密码、令牌、链接不出现在任何日志/审计/响应中（`LoggingMailSender` 在 `log-links=false` 时也只记收件人、模板、主题）。

## 5. 邮件

- `shared` 新增 `MailSender` / `MailMessage`（说明见偏离第 2 条），`integration` 模块提供实现与选择：
  - `ResendMailSender`：JDK `HttpClient` POST `https://api.resend.com/emails`，`Authorization: Bearer`；每请求 10 秒超时，失败重试 2 次（退避 1、3 秒），仍失败抛异常由调用方 `WARN`；不新增依赖。构造参数含 baseUrl 仅为单测注入本地服务器。
  - `LoggingMailSender`：未配置 Key 时使用，仅记录收件人 + 模板名 + 主题；`crm.mail.log-links=true`（默认 false）才额外记录正文与链接，代码与配置注释均写明「生产禁止开启」。
  - `MailConfiguration`：有 Key 无 `TCRM_MAIL_FROM` 时启动失败。
- 模板（`KolMailTemplates`，`kol` 模块）：英文在前、中文在后，写明公司名称，纯文本 + 简单 HTML（公司名做 HTML 转义）；链接 `https://{TCRM_KOL_PORTAL_BASE_URL}/activate?token=…`、`/reset?token=…`；多公司找回为一封邮件、按公司各一条链接。
- 邀请邮件全文（`{company}` = 公司名称，`{url}` = 激活链接）：

  主题：`[{company}] Set up your creator account / 设置您的达人账号`

  ```text
  Hello,

  {company} invites you to join its creator program on T-CRM.

  Set up your account password (the link is valid for 72 hours and can be used once):
  {url}

  If you were not expecting this email, you can ignore it.

  ----
  您好，

  {company} 邀请您加入其达人合作计划（T-CRM）。

  请设置您的账号密码（链接 72 小时内有效，仅可使用一次）：
  {url}

  如果您没有预期收到这封邮件，请忽略它。
  ```

  HTML 版为同样的内容以段落与 `<a href="{url}">` 链接呈现。

- 重置邮件主题：`[{company}] Reset your password / 重置密码`；正文同样式，每个公司一段「Reset the account of {company} (the link is valid for 30 minutes and can be used once): {url} / 重置 {company} 的账号密码（链接 30 分钟内有效，仅可使用一次）：{url}」。多公司时主题取第一家公司（按达人 ID 升序）名称。

## 9. 偏离与遗留

1. **admin-ui 语言包补 3 条错误文案**：规范 03 第 4 节要求新增错误码同步前端文案，且 admin-ui 的 CI 测试直接扫描后端 `ErrorCode` 枚举强制全覆盖（`error-codes.spec.ts`），不补则 CI 无法通过（任务要求等 CI 通过）。先例：任务 04（`a1fa2e5`）、任务 09a（`35b971a`）新增错误码时都在同一提交更新了 `admin-ui/src/locales/{zh-CN,en-US}.ts`。本任务同样只加了 3 条文案（`KOL_ALREADY_ACTIVATED` 等），未改任何 admin-ui 功能代码；`kol-portal/` 未动，达人端文案由 12b 登记。
2. **`MailSender`/`MailMessage` 位于 `shared` 而非 `integration.api`**：提示词 4.5 要求接口放 integration 模块；但既有依赖链 integration → product（ShopAccessApi）→ kol（KolApi）与新增 kol → integration 会构成 `ArchitectureTest` 的切片循环（规范禁止弱化）。契约放 `shared`（与 `R`、`ErrorCode` 同类的基础契约），Resend/Logging 实现仍在 integration 模块，行为与提示词一致。
3. **`ExternalAuditApi` 增加 `recordKolOperation`**：达人自助操作（激活/改密/重置）的操作者是 `crm_kol` 而非 `sys_user`，复用 `@AuditLog` 切面会把 user_id 留空且无法归属公司，故在 system 模块 api 上加最小方法（username 存达人邮箱、tenant_id 显式、ip 记录、params 只含 kolId）。
4. **停用的达人/公司不能激活或重置**（令牌按 `KOL_AUTH_TOKEN_INVALID` 处理）：提示词未明确规定该场景；停用账号本就无法登录，激活/重置只会设置一个用不上的密码，按无效处理最简单且安全。达人重新启用后可让商务重发邀请。
5. **多公司找回邮件的主题**取第一家公司名（按 ID 升序）：提示词只给了单一 `[{公司名}]` 格式，多公司场景无唯一公司名。
6. **达人登录按邮箱跨公司查询未命中索引**（见第 1 节说明）：表规模小 + 迁移内容已定稿，未加索引，报告留档。
7. 遗留（后续任务）：自助注册与注册链接（12c）；`/me` 的 `whatsapp`、`sheetUrl`（任务 11 合并后补充）；达人端页面（12b）。
