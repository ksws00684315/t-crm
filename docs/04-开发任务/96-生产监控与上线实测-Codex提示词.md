## 2. 要求

### 2.1 主机检查脚本

新增 `deploy/scripts/ops-check.sh`，host cron 每 5 分钟运行。检查项：

| 检查 | 告警条件 |
|---|---|
| 磁盘 | 使用率 ≥ 70%，≥ 85% 标记严重 |
| 内存 | 可用内存 < 10% |
| 容器 | 任一服务非 running 或 unhealthy；5 分钟内重启过 |
| 公开证书 | `public.pem` 剩余 ≤ 20 天 |
| pgBackRest | 最新备份早于 26 小时，或 WAL 归档最近 15 分钟无进展 |
| 逻辑备份 | 最新 `.dump.gpg` 早于 26 小时 |
| 应用日志 | 上次检查以来 crm-admin、crm-redirect 出现 ERROR |
| 容量告警 | 日志里出现 Redis 内存、点击积压的 WARN |

1. 告警发往 `TCRM_ALERT_WEBHOOK_URL`（飞书自定义机器人格式），为空时只输出到标准输出。
2. 同一告警状态不变时最多每小时重复一次，恢复时发一条恢复通知。状态文件放 `TCRM_OPS_STATE_DIR`。
3. **日志内容不外发**：只发级别、logger 名、次数和 traceId，不发消息正文，避免个人信息流向第三方。
4. 每次运行结束 ping `TCRM_HEARTBEAT_URL`（可为空），脚本自身或主机挂了由外部服务发现。
5. 判定逻辑写成可 source 的函数，补 `deploy/scripts/test-ops-check.sh`，并加入 `deploy.yml` 的检查。

### 2.2 300 MB 推广表实测

现有实现落临时文件后解析，但没有在生产内存限制下测过。

1. 用脚本生成接近 300 MB、结构合规的 xlsx（生成脚本放 `.tmp/`，不提交），行数和图片比例贴近 `docs/00-需求` 的真实样例。
2. 在 `tcrm-t96-verify` 的生产内存限制下（crm-admin `2g`）经 `upload.` 上传，走完预览和确认。
3. 记录耗时、crm-admin 内存峰值、是否 OOM 或超过 `proxy_read_timeout 300s`。

本任务只测量。发现问题写进报告并停下来，不改后端。

## 4. 验证

用仓库外的 override（放工作树 `.tmp/`，不提交）启动项目 `tcrm-t96-verify`，只允许删除该项目自己的容器和卷。Webhook 指向本地临时 HTTP 监听，逐项触发：

1. 停容器、人为缩短阈值触发磁盘告警、用短期证书触发证书告警、把备份文件时间改旧；
2. 写入一条带 `t96_` 测试邮箱的 ERROR，确认告警内容不含该邮箱；
3. 告警去重、恢复通知、Webhook 不可用时脚本不崩溃；
4. 心跳每次运行都发出。
