## 4. 迁移与归属规则

新增 `V202610171800__create_kol_bd_transfer.sql`，没有修改已合并迁移。新表带 `tenant_id NOT NULL`、全部通用字段和中文表/字段注释，保存来源、目标、约定生效时间、状态、实际执行时间和最多 255 字的取消原因。发起原因写操作日志，不占用取消原因。

索引共六个（含主键）：主键、每达人一条预约的部分唯一索引、预约到期部分索引、公司+来源商务+生效时间+ID、公司+目标商务+生效时间+ID、达人+生效时间+ID。按编号先用达人全局唯一编号索引取 ID；转移列表按达人索引或来源/目标索引过滤。默认公司列表使用来源/目标索引的公司前缀过滤后排序，最后以 ID 兜底。新表创建不存在既有大表加列或重建索引的锁表风险。

立即转移在一个事务内按达人 ID 升序锁行，重新读取当前商务，获得锁后取当前时间；当前与目标相同则跳过，实际变更关闭当前历史并新增历史、记录 `DONE`、取消原预约（「被立即转移取代」）。目标为空就是归公司。新接口与旧 PUT 共用该路径。

预约保存当前来源商务。先锁住整批达人并检查全部预约冲突，再写任何记录；冲突返回 `KOL_TRANSFER_EXISTS` 和所有冲突编号，整批回滚。一个请求不能同时提供达人列表和来源商务；列表 1～500 个，预约时间最多未来一个日历年，过去或当前时间按立即执行。

目标商务通过 `system.api.BdUserApi` 复用同公司、启用、STAFF、OWN、`kol:edit` 规则。目标用户行锁先于达人行锁，避免停用与转移并发时把达人重新分配给已停用账号。不可用的同公司账号返回 422 `KOL_INVALID_BD_USER`；不存在或跨公司 ID 返回 404。所有业务 Mapper 查询由租户插件限定公司。

## 5. 接口与示例

| 方法与路径 | 权限 | 行为 |
|---|---|---|
| `POST /admin-api/kol/bd-transfers` | SUPER_ADMIN | 立即或预约；返回 `{immediate,scheduled,skipped}` |
| `GET /admin-api/kol/bd-transfers` | SUPER_ADMIN | `page`/`size`，按 `status`、`kolCode`、`fromBdUserId`、`toBdUserId` 筛选，生效时间与 ID 倒序 |
| `DELETE /admin-api/kol/bd-transfers/{id}` | SUPER_ADMIN | 仅 SCHEDULED 可取消；「手动取消」；其他状态 409 `KOL_TRANSFER_NOT_SCHEDULED` |
| `PUT /admin-api/kol/kols/{id}/bd-user` | SUPER_ADMIN | 保留为单达人立即转移入口；原响应不变 |

立即转移（ID 为示例，目标为空也合法）：

```json
{"kolIds":["123","124"],"toBdUserId":"456","reason":"商务交接"}
```

预约来源商务名下全部达人：

```json
{"fromBdUserId":"456","toBdUserId":"789","effectiveAt":"2026-11-01T00:00:00Z","reason":"预约交接"}
```

预约冲突响应使用统一信封，HTTP 409，`errorCode="KOL_TRANSFER_EXISTS"`，`data=["KOL0001","KOL0002"]`。列表 ID/总数序列化为字符串，时间为 ISO 8601 UTC，计数为整数。新增两个错误码均已补管理端中英文文案。

## 6. 预约任务与停用兜底

`BdTransferJob` 每分钟运行，持 `kol:bd-transfer` 分布式锁，不等待，watchdog 续租至结束。逐个启用公司打开明确公司作用域，每公司按生效时间和 ID 领取最多 200 条。每条使用独立事务，锁住达人行并重读状态；已完成/取消不会再次执行。

当前商务与来源不一致时取消（「执行时归属已变化」）；目标不再可用时取消（「目标商务不可用」）并记 WARN；成功时以 `effective_at` 关闭和新增历史，`executed_at` 单独记录实际执行时刻。若历史当前开始时间晚于约定生效时间，使用历史开始时间并记 WARN，不把时间告警写进取消原因。单条异常回滚、保留待重试，继续处理本批其余记录。

`UserService.updateStatus` 在同一事务内发布 `system.api.StaffDisabledEvent(tenantId,userId)`；`kol` 通过 BEFORE_COMMIT 监听，按事件明确的公司处理：锁住其名下达人并改为未分配，关闭历史并新增空商务历史；来源预约的 `from_bd_user_id` 改为空、保持预约；目标预约取消（「目标商务已停用」）。重新启用不恢复归属。事件失败会阻止账号状态事务提交。

发起、取消、停用兜底均通过 `system.api.ExternalAuditApi` 在业务事务中写操作日志；包括数量、来源与目标、生效时间及原因，或停用商务及未分配人数。保留原有旧 PUT 与用户状态接口的接口级审计。为复用原审计能力增加明确 HTTP 方法的写操作入口，原 OAuth 回调接口保持兼容。
