### C. L-052 已有行与重算（返工重写）

1. **冻结天数规则的生效历史**：合并前的 main 上，`OrderCommissionSync` 传给规则的 `completedTime` 一直是 `null`，`FALLBACK` 从未触发。本 PR 初版曾把订单 `receive_time`（确认收货时间）当作交易完成时间传入，使该规则第一次变得可达——但「确认收货」与「交易完成」是两个状态，且返工核查确认微店接口根本不提供交易完成时间字段（证据见 §1 差别 1）。按负责人口径与设计 §5「接口未提供时不推断」，返工将传参回退为 `null`：**本 PR 合并后冻结天数规则仍不生效**，等数据来源确认后按 ADR-032 修订启用。
2. **已释放金额不会被收回**：即便未来接入完成时间来源、已有行按新规则改判，`applyRevision` 只在计提减少或归属变化时扣回；已按旧依据释放的金额不会因 `release_basis` 改判被倒扣。
3. **改判时机**：`CommissionItemSnapshotService` 每次同步/重算按现行规则重算并写回 `release_basis` / 释放时间。接入完成时间来源后，已有订单在下一次同步/重算自动按新规则改判，不需要数据迁移。

## 8. 返工中发现的缺陷（E2E 复测发现，已修复，提交 `0ec89aa7`）

**`release.sh` 在 macOS bash 3.2 + UTF-8 locale 下，`$var` 紧跟全角字符会被解析成更长的变量名，`set -u` 报 unbound variable 中止；且展开错误进 EXIT trap 时 trap 内 `$?` 为 0，`on_exit` 照抄该值 `exit 0`——发布中途静默死亡、退出码 0。** 端到端复测场景 1 实测复现：`deploy 1.0.1` 只写入 pin 即死亡，无任何部署动作，`RELEASE_RC=0`（证据：`.tmp/verify/logs/t1-deploy-1.0.1.crash-unbound-var.log`、四 locale 对照、bash 3.2/5.2 对照、最小复现脚本 `l070-074-bug-*`）。生产 Linux（bash 5.2）不受影响，但脚本文件头声明兼容 bash 3.2，本机（维护者开发机）正是该覆盖范围。

处理与披露：

- **修复 7 处**（`$service：`×2、`$PREVIOUS_VERSION（`、`$rc）`、`$UPDATE_POSTGRES_VERSION（`、`$pin（`、`$version（`）：变量加花括号，行为零变化。其中 590/626/677 三处是**本 PR 新增代码**；209/211/253/282 四处是 **main 上任务 95 的存量代码**——按规范本应只报告不顺手改，但返工要求的复测路径（失败报告、回滚首行）必经这四行，不修则返工清单第 4 条无法验收，故按最小侵入一并修复。**如不接受存量修复：revert 提交 `0ec89aa7` 后保留 590/626/677 三处即可**（端到端复测场景 3/6 会因此受阻，报告附录 G 的相应证据随之失效）。
- `test-release-lock.sh` 新增**静态回归检查**：perl 扫描「`$var` 后紧跟非 ASCII 字节」模式（BSD grep 无 `-P`；CI 的 Linux bash 5 无法复现运行时行为）。修复前捕获 7 行（红），修复后通过（绿）。
- **未动** `on_exit` 的 trap 兜底语义（`$?=0` 吞掉 fatal 的机制在修完 7 行后暂无触发路径；根治需重设计 trap 入口状态捕获）。建议负责人后续任务评估。
- 其他部署脚本（`pg-backup.sh`、`ops-check.sh` 等）扫描 0 命中。
- 修复后的 7 行在端到端复测的真实路径全部覆盖（626=场景 1、590=场景 4、677=场景 3、209/211=场景 6 失败报告），四个非 0 退出全部干净，无 rc=0 吞错复现。
