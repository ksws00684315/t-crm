## 1. 背景

这是资金问题，优先级最高。

- **L-032**：设计写明「存在未核实完结退款期间，占用该行的待付申请置 `paused`，恢复后自动解除并写历史」，但主代码从未写入 `paused`，只有读取和付款时的校验（`WithdrawalService` 第 711 行）。结果是：退款中的行已被提现占用时，财务仍可付款，退款成功后钱包变负。
- **L-033**：已释放但售后中的行，明细显示冻结，钱包「可提现」却包含这笔金额。申请时会被 `WITHDRAWAL_INSUFFICIENT_AVAILABLE` 拦下，不会多提，但显示和实际可申请金额不一致。

## 2. 要求

### 2.1 L-032：真正写入和解除 `paused`

1. 先读清楚 `commission/service/CommissionItemSnapshotService`、`CommissionSnapshotListener`、`order/service/OrderCommissionSync.afterSalesItems`、提现占用明细的写入与查询，写一段现状说明放进报告，再动手。
2. 商品行进入未核实完结退款（`PROCESSING` / `UNKNOWN`，即 `AFTER_SALES`）时，把占用该行的、尚未付款的提现申请置 `paused=true`，写 `pause_reason`。
3. 退款转为完结且该行不再阻断时自动解除，并写提现历史（§4.8.6）。一个申请占用多行时，**全部行都不再阻断才解除**。
4. 触发点要覆盖：订单同步、退款同步、退款导入、结算重算。写在所有路径都会经过的地方，不要逐个入口复制。
5. 付款校验（第 711 行）保留。还要处理并发：付款事务和置暂停事务不能互相穿透，锁的顺序与现有 `FOR UPDATE` 一致，避免死锁。
6. 审核：`paused` 的申请能否审核，按设计 §4.8.4、§4.8.6 执行。设计没写清楚时停下来报告。
7. 现有暂停中的存量：上线时已处于退款中且被占用的行是否需要回补？查共享库现状并写进报告；需要回补时用迁移做，迁移要可重复、只动符合条件的行。
8. 通知：设计要求发通知时才加，不新增未要求的通知。

### 2.2 L-033：钱包可提现金额与可申请金额一致

1. 确认现状：`CommissionWalletService.balance` 只看钱包余额；`WithdrawalService.requireFunding` 减了 `sumActiveOccupied`；真正分配时（第 1570～1585 行）按可用行分配，售后中的行不可分配，这才是拦截点。
2. 达人端概览（`GET /kol-api/commissions/overview`）和管理端收入页展示的「可提现」，要扣掉「已释放但售后中」的金额，让展示值等于实际可申请的上限。
3. 门槛判断（`Balance` 的可提现标记、最低提现额）用同一个值，不留两套算法。把计算收在一处，接口和申请校验都调它。
4. 文案里的「冻结」金额如果因此需要调整，保证「总额 = 已提现 + 提现中 + 冻结 + 可提现」这类等式仍成立；等式依据查 ADR-032 附录 B。

### 2.3 L-016：补提现页面真实联调

不改代码，只补验收。用 `t90_` 数据把提现详情、审核、付款登记跑一遍（管理端），并验证 §2.1 的暂停效果。

- 优先通过接口造数据。
- 共享库造不出可提现数据时（要有已确认结算的行），不要直接写钱包或台账表。写明证据边界，L-016 保持「待处理」，并说明缺什么。

## 4. 测试

- 修缺陷先写复现测试。必须覆盖：
  - 待审核、待付款的申请在退款中被暂停，付款返回 `WITHDRAWAL_PAUSED`；
  - 退款完结后自动解除，写了历史；
  - 占用多行时只解除一行不解除申请；
  - 已付款的申请不受影响；
  - 重复同步幂等，不重复写历史；
  - 售后中的金额不进可提现，展示值等于可申请上限。
- 集成测试放 `*IT`，标注 `@Tag("docker")`。任务 79 的 `BusinessChainIT` 可作为主链参照，建议补一条「提现占用后退款」的链路。
