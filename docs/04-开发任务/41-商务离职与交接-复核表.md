## 不适用与不做

1. **07.02 推广表商务名同步——不适用**。任务 26 的推广表上传只做解析入库（`crm_kol_item` 的来源、商品快照、店铺/商品映射），表结构和商品模块都没有商务字段，商务关系只存在于 `crm_kol.bd_user_id` 与归属历史；因此「表格内的商务名」在系统里既没有存储也没有来源，不存在可同步的对象。这也符合原文档「建议推广表格内不放」的倾向。
2. **07.05 提现、预付待办——不做**。提现与预付属于佣金结算链路，提示词第 5 节明确排除；当前迁移中也没有提现/预付表，无法在本任务内转交。
3. **业绩统计与看板——不做**。07.03 的「扣减业绩」、07.04 的「业绩计算在管理员账号下」都属于统计口径，按提示词归任务 42 起处理；本任务只保证订单/退款归属与快照正确。
4. **达人停用后的兜底——沿用既有实现**。没有继承人时，计划执行走既有 `StaffDisabledEvent` → `unassignDisabled`，达人变为「待更新」，与直接停用商务的效果一致。

## 偏差与风险

1. **本人提交时不能指定继承人**。`submitOwn` 固定 `heirUserId = null`（`system/service/DepartureService.java:154`），只给超管发一条提醒消息；若超管在生效前没有补继承人，执行结果是 `UNASSIGNED`，达人在生效时直接转为未分配。这是提示词的规定，但交接实际依赖超管及时介入。
2. **停用只影响本公司的成员关系**。`disableMembership` 只改当前公司的 `sys_user_tenant` 一行并结束该公司会话（`system/service/UserService.java:226-252`）；同一自然人若还属于其他公司，其其他公司身份与名下达人不受任何影响，仍可登录其他公司。与「账号离职/禁用」的字面语义不完全等价。
3. **07.05 没有「转交给指定人」**。计划继承人必须是可用商务，收款待审核只能随达人归属移动；无继承人时达人先转未分配，待审核账户随之变成无人负责（仅超管可见），原商务已被停用，无法继续审核。原文「转交新商务或指定人」的「或指定人」这半边没有落地。
4. **无主业绩缺一个落点**。订单 `bd_user_id` 为空只表示「谁都不属于」，没有「计入管理员账号」的字段、视图或统计；OWN 范围订单列表按 `bd_user_id = 自己` 过滤（`order/service/OrderService.java:81`），无主订单对所有商务不可见，只对全量范围角色可见。判定「无主」可以，但要出数必须等任务 42。
5. **`PUT /{id}/departure-plan` 是整体替换**。请求里不带 `heirUserId` 会把已有继承人清空（`DepartureService.java:227`、`:235`），与「修改某一项」的直觉不同；当前管理端对话框每次提交完整表单，暂未暴露问题，但直接调接口时容易误清继承人。
6. **执行时按「是否仍是商务」再判一次**。复核时曾担心执行路径不校验角色、可能绕过「最后一个超管」保护；现已补上：执行前若成员关系已不是 `STAFF` + `OWN`，计划作废为 `CANCELLED` 并写明「账号已不是商务，计划作废」，不停用也不交接（`DepartureService.execute`，`DepartureServiceTest.shouldVoidThePlan_whenTheAccountIsNoLongerABd`）。计划创建时目标仍必须是商务，因此本项已闭合。
7. **测试执行情况**。本表最初为只读复核；其后已跑通 `mvn -o verify`（单测 1431 条，含本任务 DepartureServiceTest 17 条）、`mvn -o verify -Pdocker-it -Dit.test=DeparturePlanIT`（12 条）与 `-Dit.test=SystemIT`、管理端 `pnpm lint` / `pnpm typecheck` / `pnpm test`。复核结论与这些结果一致；07.04、07.05 的偏差属于提示词明确排除或归属任务 42 的范围，不是回归。
