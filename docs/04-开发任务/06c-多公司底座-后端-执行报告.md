## 3. 设计决定的落实

### 4.1 迁移

`V202610111800__add_multi_company.sql`。

- `sys_tenant`：无 `tenant_id`，无外键，`ck_sys_tenant_id`（`id > 0`），编码 `^[a-z0-9-]{2,32}$`，`uk_sys_tenant_tenant_code`，状态 0/1。插入默认公司 `id=1`、`tenant_code=default`、`name=默认公司`、`status=1`。
- `sys_user.tenant_id` 可空，现有行设为 1。`ck_sys_user_role` 增加 `PLATFORM_ADMIN`。`ck_sys_user_tenant`：`(role = 'PLATFORM_ADMIN') = (tenant_id IS NULL)`。`ck_sys_user_own` 未改，平台管理员 `data_scope=ALL` 仍合法。`uk_sys_user_username` 仍是全局 `lower(username)`，含已删除行。
- `sys_oper_log.tenant_id` 可空，现有行设为 1，新增 `idx_sys_oper_log_tenant_time`，保留 `idx_sys_oper_log_time`。
- `crm_kol`、`crm_kol_bd_history`、`crm_shop`、`crm_product`、`crm_kol_item`、`crm_task`、`crm_task_file`、`crm_click_log`：`NOT NULL DEFAULT 1` 后 `DROP DEFAULT`。
- `crm_link_index_outbox` 不加 `tenant_id`。
- 邮箱唯一改为 `(tenant_id, lower(email)) WHERE is_deleted = FALSE`。达人列表索引带 `tenant_id`（`bd_user` 索引除外）。原商品编码唯一改为 `(tenant_id, product_code)`。达人编号、微店店铺 ID 仍全局唯一。
- `SystemIT.shouldRequireTenantIdOnBusinessTables_whenMigrationsRun` 查 `information_schema`，分区子表经 `pg_inherits` 按父表判断。

### 4.2 公司范围与自动过滤

- `TenantScope`：显式公司范围或系统范围，可嵌套，后开的先关，关错顺序抛异常且不丢掉内层。线程池任务不继承范围（`ThreadLocal` 不继承）。`TenantScopeTest`。
- `CompanyTenantLineHandler` + `TenantLineInnerInterceptor`，注册在分页插件之前（`CommonConfiguration.pagination`）。未设置范围且没有登录态时 `getTenantId` 抛 `MissingTenantException`（不是 `BusinessException`，全局处理返回 500）。显式范围优先于登录公司。系统范围 `ignoreTable` 为真，不再取公司 ID。`sys_tenant` 与 `crm_link_index_outbox` 始终忽略。
- `tenant_id` 在各 DO 上 `updateStrategy = NEVER`，更新不改所属公司。没有放进 `BaseEntity`，`AuditFieldHandler` 不填公司。
- 登录公司由 `LoginTenantResolver` 经 `CurrentUserContext.account` 读取。该方法和 `user()` 共用请求内账号缓存，所以预检查和同一请求里的多条业务 SQL 只查一次账号。没有 HTTP 请求时每次读库。账号查询自己开系统范围，内层查询表被忽略，不会再取公司 ID，没有循环调用。

### 4.3 登录、会话与公司状态

- `AccountDTO` 增加 `tenantId`、`tenantName`、`tenantEnabled`。公司缺失或 `status != 1` 时 `tenantEnabled=false`。平台管理员 `tenantId` 为空，`tenantEnabled=true`。
- 登录：公司停用与账号停用一样拒绝，响应与密码错误相同，只做一次 BCrypt。`AuthServiceTest.shouldRejectLogin_whenCompanyIsDisabled`。
- 已登录请求：`SecurityConfiguration` 在 `SaInterceptor` 之前再挂一个拦截器，先 `checkLogin()` 再 `current.user()`。公司停用因此是 401 `AUTH_ACCOUNT_DISABLED`，而不是角色列表为空时的 403。`CurrentUserContextTest.shouldKickOut_whenCompanyIsDisabled`。这是拦截顺序，不是改错误码约定。
- `GET /admin-api/auth/me` 的 `UserVO` 与登录返回的 `user` 增加 `tenantId`、`tenantName`。平台管理员为 JSON `null`。
- 操作日志的公司在请求线程由 `AuditAspect` 决定，再交给 `AuditWriter`。失败登录若用户名能对上，记该公司（公司已停用也记）。平台管理员的空公司不被改成默认公司。注销前先记下公司。

### 4.4 平台管理员与平台接口

- 角色 `PLATFORM_ADMIN`（14 字符，`VARCHAR(16)` 够用）。`BootstrapAdmin` 在没有启用且未删除的平台管理员时，用 `TCRM_BOOTSTRAP_ADMIN_USERNAME` / `TCRM_BOOTSTRAP_ADMIN_PASSWORD` 创建：角色平台管理员、数据范围 ALL、状态 1、`tenant_id` 空。已有启用平台管理员时这两个变量不是必填。用户名已被任何人占用时启动失败，文案为 `该用户名已被占用，请为平台管理员设置另一个 TCRM_BOOTSTRAP_ADMIN_USERNAME`。`BootstrapAdminTest`。
- `PlatformController` 只允许 `PLATFORM_ADMIN`。路径与第 4.8 节一致：列表按创建时间、再按 id，不分页；创建重复编码 `TENANT_CODE_EXISTS` 409；名称去空白；空白备注存空；编码创建后不可改；停用复用 `StatusRequest`；为公司创建超管时角色固定 `SUPER_ADMIN`、范围 ALL、状态 1，并显式写入路径中的公司 ID；用户名全局冲突 `USER_USERNAME_EXISTS`；重置密码在系统范围内按 id + 公司 + 超管更新，0 行返回 404，不区分原因，凭据版本加 1 并 `StpUtil.logout`。停用公司仍可为其创建超管。不提供删除公司，也不提供停用或降级平台管理员的接口，因此“平台管理员同样至少保留一个”由没有该接口保证。
- 公司内用户接口仍自动过滤。`@CompanyRole` 拒绝 `PLATFORM_ADMIN`，字段 `role`，英文 “must be a company role”。空角色交给 `@NotNull`。`PlatformRequestValidationTest`。
- `PLATFORM_ADMIN` 只出现在登录后的 `logout` / `me` / `password`，以及 `PlatformController`。链接全量重建仍只有 `SUPER_ADMIN`，且重建全系统。
- “至少保留一个启用超管”按公司判断。`lockEnabledSuperAdmins` 经自动过滤只锁本公司。`TenantIsolationIT.shouldKeepLastSuperAdminInsideTheCompany`：B 公司有超管时，A 公司两名超管并发降级仍只留下一名，B 的超管角色不变。

### 4.5 唯一性

| 规则 | 位置 |
|---|---|
| 邮箱公司内唯一 | 部分唯一索引 `(tenant_id, lower(email))`；应用层查重走自动过滤 |
| 原商品编码公司内唯一 | `ProductMapper.existsCode` 走自动过滤，含已删除行；编码序列仍全局 |

| 微店店铺 ID 全局唯一 | `ShopService.create` 在系统范围 `countByWeidianId`（含已删除）；冲突仍是 `SHOP_WEIDIAN_ID_EXISTS` |
| 用户名全局唯一 | `UserService.create` 与 `PlatformService.createAdmin` 在系统范围 `countByUsername`；冲突仍是 `USER_USERNAME_EXISTS` |
| 每家公司最多 3 个店 | 锁键 `crm_shop:create:{tenantId}`，`countAlive` 经自动过滤 |
| 按 ID 跨公司 | 自动过滤后与不存在相同，返回 404，不返回 403 |

## 4. 系统范围的全部位置

系统范围表示这条 SQL 不自动加 `tenant_id`。需要按公司限制时，调用方自己写上公司 ID。

| 位置 | 理由 |
|---|---|
| `AccountStoreService` 的按用户名、按 ID、更新登录时间、更新密码，以及公司快照 | 登录与会话要找到任意公司的账号；平台管理员没有公司 |
| `BootstrapAdmin.run` | 启动时没有登录态，要查全表有没有平台管理员 |
| `AuditWriter.write` | 公司已在请求线程由 `AuditAspect` 写入记录；插入若被过滤，空公司的平台操作写不进去 |
| `OperLogRetentionJob.cleanup` 每一批 | 外层 DELETE 若被过滤，内层选出的其他公司 ID 会删 0 行，循环会提前停 |
| `TaskFileRetentionJob.cleanup` | 清理所有公司的过期任务文件 |
| `InterruptedTaskCleaner.run` | 启动时把所有公司中断的任务标失败 |
| `ClickPartitionJob.maintain` | 分区是全表的；目录 SQL 另外见下一节的 `@InterceptorIgnore` |
| `LinkIndexSyncJob.drain` | outbox 表本身被忽略，但应用变更要读各公司的达人、商品、店铺 |
| `LinkRebuildService.runLocked` | 跑在 `link-rebuild` 线程，没有请求登录态；重建全系统索引 |
| `LinkIndexOutboxMonitor.check`、`ClickStreamMonitor.check` | 只读 Redis 或 outbox，仍包在系统范围里，避免以后加查询时漏范围 |
| `ClickConsumer.process` | 一批点击可能属于多家公司；行上的 `tenant_id` 来自对应关系 |
| `ImportTaskService.run` | 工人线程没有登录态。先在系统范围读任务，任务没有公司或不是等待中则直接返回；否则 `TenantScope.runCompany(task.tenantId, …)`。这是提示词清单之外多开的一处 |
| `KolCodeGenerator.next`、`KolImportProcessor` 的 `existsCode` | 达人编号全局唯一，公司过滤会漏掉其他公司 |
| `ShopService.create` 的 `countByWeidianId` | 微店店铺 ID 全局唯一。创建锁本身是函数调用，插件不加条件；锁键已含公司 ID |
| `UserService.create`、`PlatformService.createAdmin` 的 `countByUsername` | 用户名全局唯一 |
| `PlatformService` 的列超管、建超管、重置密码 | 调用者是平台管理员，没有公司。条件或写入值显式使用路径中的公司 ID |

## 5. 手写 SQL 核对

插件是 MyBatis-Plus `TenantLineInnerInterceptor`（JSqlParser）。公司 ID 在单测里是字面量 8。系统范围下语句保持原样。`@InterceptorIgnore(tenantLine = "true")` 在解析之前返回，不是全局关闭插件。

| 语句 | 结果 |
|---|---|
| `nextval(...)` | 无表，不改 |
| `EXISTS` 子查询（达人编号、用户名、微店 ID、原商品编码） | 公司范围内加 `AND tenant_id = ?`。达人编号、用户名、微店 ID 的调用在系统范围，所以不加；原商品编码保持公司范围 |
| `SELECT … FOR UPDATE`（达人行锁、`lockEnabledSuperAdmins`） | WHERE 加 `tenant_id`，`ORDER BY` 与 `FOR UPDATE` 保留 |
| `pg_advisory_xact_lock(hashtextextended(...))` | FROM 项是函数，不加条件 |
| `countAlive` | `COUNT(*)` 加 `tenant_id` |
| `closeCurrent` 的 UPDATE | SET 不动，WHERE 加 `tenant_id` |
| `crm_kol_item` 的 SELECT / EXISTS | WHERE 加 `tenant_id`。`SELECT *` 未改（规范不鼓励，本任务不顺手改） |
| 三表 INNER JOIN（对应关系 + 原商品 + 店铺） | 右表条件在 ON 上，左表在 WHERE |
| 按达人 id 的 keyset 分页 | 追加 `tenant_id`，`LIMIT` 保留 |
| 点击 INSERT 未列 `tenant_id` | 补上列和值，`ON CONFLICT` 保留 |
| `ClickLogMapper.insertIgnore` 已列 `tenant_id` | 不重复追加 |
| 点击分区 `listPartitions` / `CREATE` / `COMMENT` / `DETACH` / `DROP` | 解析会失败，或给 `pg_inherits` 加上不存在的列。这些方法 `@InterceptorIgnore(tenantLine = "true")`，调用仍在系统范围 |
| outbox 的 SELECT / DELETE | 表始终忽略 |
| 操作日志按时间删除 | 必须在系统范围，内外两层都不加公司条件 |
| OR 连接的 WHERE（点击去重查询） | 插件先给 OR 加括号再 AND 公司条件，语义仍是“这些键之一，且属于本公司” |

没有乐观锁插件。分页插件在租户插件之后，页内计数先被公司条件限制。

## 6. 迁移锁与测试中修过的问题

表都很小。PostgreSQL 17 对常量默认值加列只改元数据，不重写表。重建邮箱、达人列表、原商品编码和原商品列表索引会短暂锁表。`crm_kol_item` 与 `crm_click_log` 只加列，不重建索引。不加外键。

验证过程中修过、且先看到失败的问题：

- 租户拦截器在创建 `SqlSessionFactory` 时就要账号存储，而账号查询又要 Mapper，上下文起不来。`LoginTenantResolver` 对 `CurrentUserContext` 使用 `@Lazy`。第一次按登录态取公司时才解析。
- 上下文里有两个 `RequestMappingHandlerMapping`（业务接口与 Actuator）。隔离测试只注入 `requestMappingHandlerMapping`。
- 对应关系列表必须带达人编号、原商品编码或微店商品 ID。隔离测试按 B 公司的微店商品 ID 查询。
- 登录响应的 `tenantId` 在 `data.user`，`GET /auth/me` 在 `data`。
- 导入接口声明 `multipart/form-data`。不带该类型时请求到不了 `@SaCheckRole`，返回 500。遍历业务接口时带上映射声明的 Content-Type，角色校验返回 403。
- `UserService.page` 在用户名为空时仍计算 `escapeLike(null)`，列表 500。改为与达人、原商品列表一样，空关键字不拼 `ILIKE`。`UserServiceTest.shouldListEveryUserInTheCompany_whenUsernameIsOmitted`。
