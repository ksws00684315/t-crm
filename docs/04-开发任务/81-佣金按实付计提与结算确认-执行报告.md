## 1. 改动概要

- **计提基数**：付款后按订单实付 `pay_amount`（含运费）分摊到商品行（`SettlementBasisCalculator.compute` → `accrueUnconfirmed`），付款即计提，释放依据 `UNSETTLED`（冻结中）。
- **结算确认**：`INCOME_DETAIL` 中恰好一笔「货款收入」、带 `tradeTime`、金额等于实付，才设结算时间（`CONFIRMED`）并写 `settled_time`；基数改为货款收入金额（数值与实付相同）。
- **不参与计算**：手续费、分润、退款与其他子类型流水只入库、只展示。`UNKNOWN_FLOW_TYPE` 原因码、分支与 `KNOWN_TRADE_TYPES` / `KNOWN_TRADE_SUB_TYPES` 常量已删除。
- **事件**：`OrderCommissionSync` 对有基数的行发 `basisIncludesRefund = FALSE`（成功退款由引擎扣减）。
- **结算明细（L-024）**：「净增减」改为「微店可提现金额」（该单 `INCOME_DETAIL` 流水合计，只展示，无结算流水为 null，前端显示「-」）；「店铺获利」删除（后端 `retained`、前端列与抽屉、文案）；支付金额改为订单实付；行状态为 `UNVERIFIED` / `FROZEN` / `POSTED`。
- **订单链路**：资金卡片与商品行删除「店铺获利」（`OrderChainDTO` 的 `shopProfit` 字段删除）。
- **order.api**：`OrderRefDTO` 增加 `payAmount`；新增 `weidianWithdrawableByOrderIds`。
- **未改**：`CommissionSettlementRules`、快照、释放、提现分配、预付冲抵、钱包台账、结算流水拉取、达人端状态映射（`CommissionOrderStateService` 原映射已覆盖「已核实、计提>0、未释放 → FROZEN」，只补了测试）。**无新迁移，无新依赖。**

## 8. 已知残留与后续

- **Flyway 已合并迁移 `V202610281001` 的列注释**仍提及 `UNKNOWN_FLOW_TYPE`。按规范不改已合并脚本，仅记录。
- **item 级 evidence** 不再写 `INCOME_MISMATCH`，订单级 `commission_basis_reason` 仍保留该原因。若业务上需要在 item 上也能看到，需改 `CommissionItemSnapshotService.evidence()`，本任务未做。
- **`FALLBACK` 分支**在 `CommissionSettlementRules.evaluate` 与 `CommissionItemStateMapper.listReleasedForWithdrawal` 中仍在，实际不可达（`completedTime` 恒为 null）。按 §8 不改 `CommissionSettlementRules`，仅记录。
- **`CommissionItemSnapshotService.evidence`、`CommissionSettlementRules` 注释**中仍有「pending M0」旧文案，未改。
- **`weidianWithdrawableByOrderIds`** 对每单单独查询流水（列表页 N+1），可后续改为批量查询，非阻断。
- **`accountStatus`**（订单链路资金卡）在已付款未结算时仍为 `POSTED`，管理端未渲染，无可见错误。
- **历史执行报告与 1024 对接清单**中的旧术语未改（历史记录）。
- **运费是否计入佣金基数**：是负责人 2026-10-29 决定的口径（基数 = 订单实付，含运费），不是缺陷；结算明细与订单链路的文案均按此口径。
- **造数据的支付时间**必须晚于推广比例的生效时间，否则结算为「待核实」、佣金 0。这是设计行为，但容易被误判为缺陷。
- **spotless** 作用于整个 backend 目录，格式化了本分支的其它未提交改动；这些改动都属于本任务，无额外范围影响。
