### 第 3 步：点击采集 `feat(backend): consume click stream into partitioned click log`

- **消费**：`ClickConsumerRunner`（`SmartLifecycle` 常驻线程，不占用共享的 `@Scheduled` 线程池）持有分布式锁 `link:click-consumer`（看门狗续期）时消费，拿不到锁每 10 秒重试；异常时释放锁、记 `ERROR`、10 秒后重试。`ClickStream` 在 `stream:click` 上创建消费组 `crm-admin`（`ReadOffset 0`，忽略 `BUSYGROUP`，读到 `NOGROUP` 时重建），固定消费者名；`ClickConsumer.pollOnce()` 先读本消费者的 PEL，空则 `XREADGROUP >`（500 条、阻塞 2 秒）。
- **一批的顺序**：解析 → 批内去重查询 `kol_id`/`product_id` → 按 Stream 顺序做重复判定 → `INSERT … ON CONFLICT (id, click_time) DO NOTHING`（一条语句）→ 写 `click:last:*`（PX 60000，pipeline）→ `XACK` 全部消息。写库或写 Redis 失败则整批不 ACK，下次从 PEL 重读；`id` 确定性生成，重放不产生重复行。格式错误的消息、查不到对应关系的 `kolItemId`：记 `WARN`、ACK、不写库。
- **规则**（`ClickRules`，纯函数）：`id = 毫秒 × 1,000,000 + 序号`（序号 ≥ 1,000,000、为 0、溢出时视为格式错误）；机器人关键字常量 16 个（空 UA 也算）；重复 = 与上一次点击（含批内前一条）的事件时间差的绝对值 < 10,000 毫秒，上一次时间取两者较大值后写回。
- **分区维护** `ClickPartitionJob`：每天 00:10 UTC，锁 `link:click-partitions`；保证当月及之后两个月分区存在（`CREATE TABLE IF NOT EXISTS … PARTITION OF`，带注释）；上界 ≤ 当天 − 13 个月的分区先 `DETACH` 再 `DROP`。分区名只接受 `crm_click_log_yyyymm`（正则白名单后才拼进 DDL）。纯计算在 `ClickPartitions`，含跨年测试。
- **监控** `ClickStreamMonitor`：每分钟，锁 `link:click-monitor`。积压取 `XINFO GROUPS` 的 `lag`（经 Redisson 原生 API 读取，因为 Spring Data 经 Redisson 返回的 `XInfoGroups` 不含 `lag`）；Redis 无法计算时返回 nil，Redisson 解码为 0，因此"lag 为 0 但最后投递 ID ≠ 最后生成 ID"视为未知，按 max(`XLEN`, 待处理数) 保守估算。超过 `TCRM_CLICK_STREAM_MAXLEN` 的 50% 记 `WARN`、80% 记 `ERROR`。同时读 `INFO memory`：`used_memory` 超过 `maxmemory` 的 70% / 85% 记 `WARN` / `ERROR`，`maxmemory` 为 0 时跳过。
- **链接列表** `GET /admin-api/link/links`：`kolCode` 必填（`@NotBlank`，缺失 400），可选 `productCode`（精确匹配）与分页，按原商品编码升序；角色 SUPER_ADMIN / OPERATOR / FINANCE，商务（OPERATOR + OWN）只能看本人负责的达人（403），达人不存在 404。点击数只统计当前页：`kol_item_id IN (...) AND click_time >= now − 30 天`，返回全部与有效（排除 `is_bot`、`is_dup`）。
- 配置 `crm.link.click-stream-max-len: ${TCRM_CLICK_STREAM_MAXLEN:1000000}`；`@MapperScan` 增加 `com.tcrm.admin.link`。
- 验证：`ClickRulesTest`（含 9,999 / 10,000 毫秒边界、ID 转换）、`ClickEventTest`、`ClickPartitionsTest`（含跨年）、`ClickPartitionJobTest`、`ClickConsumerTest`、`ClickConsumerRunnerTest`、`ClickStreamTest`、`ClickStreamMonitorTest`（含 `maxmemory` 为 0）、`LinkServiceTest`、`LinkControllerTest`（权限表每格、400、403、409）通过。另在本机临时开启后台消费线程连真实 Redis 验证：锁获取、建组、阻塞读取、写库与 ACK 均正常，`ClickStreamMonitor` 能经 Redisson 读到消费组信息（临时测试未提交）。

## 6. 偏离与说明

1. **`crm_click_log` 增加 `create_by`、`create_time`**：提示词字段列表没有，但规范 04 要求公共字段；只追加表省略修改字段与逻辑删除，表注释写明。`create_by` 恒为空（由消费写入）。

3. **格式错误的消息也 ACK 并跳过**：提示词只规定了"查不到对应关系"的处理；格式错误（缺字段、ID 无法转换）同样不可能重试成功，按同样方式处理，避免卡住 PEL。
4. **内部开关** `crm.link.click-consumer.enabled`（默认 true）与 `crm.link.click-consumer.retry`（默认 10s）：只用于测试关闭后台消费线程，不作为环境变量对外文档化。
5. **积压 `lag` 的读取方式**：Spring Data 经 Redisson 的 `XINFO GROUPS` 结果不含 `lag`，改用 Redisson 原生 `RStream.listGroups()`（已有依赖，未新增依赖）；nil lag 的判定与估算见第 3 节。
6. **设计说明书 §8.2**：不在提示词第 2 节的同步清单中，但 §4.4 第 1 步不再生成 `track_id`，为免前后矛盾在 §8.2 加了"暂不实现，待 M0"一句。

## 7. 实现中的取舍（默认采用，审查时可调整）

- 店铺状态取专属商品所在店铺（`crm_kol_item.shop_id`）；已删除的原商品 / 店铺不产生链接（全量重建会删除其 field）。
- 链接列表的 `productCode` 为精确匹配（不区分大小写）。
- 分区保留规则：上界 ≤ 当天 − 13 个月即删除（例：2026-10-06 删除 2025-08 及更早，保留 2025-09）。
- 消费组从 `0` 创建，首次启动会消费建组前已写入的点击；固定一个消费者名（同一时间只有一个实例消费，PEL 跨重启保留）。
- 增量更新在事务提交后同步执行（达人启停最多 2 万个 field，pipeline）；全量重建与并发增量之间存在很小的竞争窗口（重建读到旧状态后、`RENAME` 前发生的变更可能被覆盖），由下一次增量或下一次重建修正。
- 重复判定以"上一次点击"为准，被判为重复的点击也会刷新上一次时间（连续每 5 秒点击一次时，第 2 次起都算重复）。
- 手动重建接口立即返回 202，重建在独立线程执行；同时检查本实例标志与分布式锁，任一在用即 409。
