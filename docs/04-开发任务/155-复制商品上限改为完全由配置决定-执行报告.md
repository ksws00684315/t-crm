## 1. 背景与定位

负责人说的「同步商品」在本系统指管理端「商品任务 / 复制任务」：客户表格脚本经公开接口 `POST /admin-api/external/product-links/convert` 提交商品，后台逐条调用微店 `vdian.item.add`。涉及三个上限：

| 上限 | 位置 | 现状 |
|---|---|---|
| 每家公司每日复制条数 | 系统配置 `copy.daily-limit-per-company`（默认 5000，1～1000000） | 已完全由配置决定；计数在 Redis（`CopyDailyQuota`），**没有 SQL** |
| 每次提交商品数 | 系统配置 `product-links.max-convert-items`（任务 138 引入） | 服务层按配置值校验；但配置允许范围写死 `1～5000`，控制器还有 `@Size(max = 5000)` |
| 单任务明细条数 | 数据库 `crm_copy_job.total_count` | 迁移 `V202611091500` 把 CHECK 写死为 `total_count <= 5000`（任务 141 从 500 放宽到 5000） |

因此「代码中的 SQL 写死的最大记录条数」是 `crm_copy_job` 的 `ck_crm_copy_job_total` 约束。只改配置（把每日额度或每次提交上限调大）时，单任务明细超过 5000 会被数据库拒绝：应用接受了请求，插入 `crm_copy_job` 时报 `violates check constraint ck_crm_copy_job_total`（与任务 141 记录的正式环境事故同一根因）。另外，配置允许范围本身也停在 5000，导致「调大」在管理端无法保存。

## 3. 口径说明

- **上限来源**：每次提交商品数的唯一上限是系统配置 `product-links.max-convert-items`；单任务明细条数（`crm_copy_job.total_count`）不再有数据库硬上限，数据库只保留 `>= 0` 的不变量。
- **每日额度不变**：`copy.daily-limit-per-company`（默认 5000，1～1000000）仍按公司、北京时间在 Redis 计数，本次不改变其计日与计数口径；调大每日额度只需改配置。
- **配置范围**：`product-links.max-convert-items` 的范围放宽到 1～1000000，与每日额度上限一致；具体值由平台管理员在系统配置页设置，修改后下一次提交即生效，无需重启。
- **未改前端**：系统配置弹窗的范围提示（`systemConfig.rangeHint`）由接口返回的 `min` / `max` 渲染，因此页面上该项会显示「1～1000000」，不需要改前端代码。
- **传输层兜底**：去掉 `@Size` 后，超大 JSON 请求体由 Nginx `/admin-api/external/` 所在 server 的 `client_max_body_size 21m` 拦截；应用在落库前仍先按配置值拒绝超限请求。

## 6. 风险与遗留

- **单任务过大**：上限放开到 1000000 后，平台管理员可配置出非常大的单任务；复制逐条调用微店接口，耗时与数据库写入量都会相应增加。这是负责人「以配置为准」的直接结果，容量与队列仍由 `weidian.qps` 与复制 worker 决定，本次不调整。
- **计数口径**：L-127（每日额度按每家公司合计、微店官方口径未知）不因本次改动变化。
- **发版后动作**：负责人需要按实际需求把系统配置 `product-links.max-convert-items` 与 `copy.daily-limit-per-company` 调到目标值（默认值不变：500 / 5000）。
