## 1. 背景与负责人决定

现行口径（任务 76，负责人 2026-10-28）有三个特点：
- 计佣基数等于微店结算流水合计，货款收入、手续费、分润、退款都计入；
- 结算流水回来之前，订单商品行「未核实」，佣金为 0；
- 达人端把这类订单显示为「Invalid order」，即 L-031。

全流程模拟中，一笔实付 65.00 的订单在结算前显示无效、预计佣金 0.00。结算后，佣金按 64.70 计算，也就是扣掉了手续费和分润。

**负责人决定（2026-10-29，已确认）：**

1. **计佣基数 = 订单实付金额**，即 `crm_order.pay_amount`，含运费。运费按商品金额比例分摊到各商品行，即沿用现有「按商品行实付比例分摊、尾差归实付最大行」的规则，分摊对象从「结算流水合计」改为「订单实付」。佣金 = 基数 × 支付时佣金比例。
   - 例：模拟那单 65.00 → 43.33 + 21.67 → 按 10% 得 4.33 + 2.17 = 6.50。
2. **订单已付款，就立即计提**。佣金状态为「冻结中」，并显示这一单的具体佣金金额。
3. **结算时，计佣基数只按「货款收入」计算。** 手续费、分润（平台服务费）等扣减与佣金的计算和结算无关；流水合计（「净增减」）只记录展示。
4. **只有微店结算流水确认、系统把该订单佣金更新为「可提现」之后，才能提现。** 否则佣金保持「冻结中」。订单关闭和退款单独处理。
5. （L-024，负责人 2026-10-29）结算明细的「净增减」改为「微店可提现金额」；「店铺获利」不展示。
   - 「微店可提现金额」显示结算流水合计，**只展示，不再等于计佣基数**。
   - 「店铺获利」在结算明细列表、抽屉、订单链路资金卡片和商品行都去掉。

## 3. 计佣规则（后端）

### 3.1 付款后计提

1. 订单有 `pay_time`，即已付款时，按订单 `pay_amount` 分摊到各商品行，作为该行的计佣基数 `basisCny`。分摊方法用 `SettlementBasisCalculator` 现有的 `allocate`：按行实付比例分摊、保留两位小数、尾差归实付最大的行。
   - 核实条件不变：有基数、归属为达人（归因类型 1/2）、支付时有生效比例。三项都满足即核实，计提冻结。
   - 释放依据为 `UNSETTLED`，不释放，也不能被提现占用。
2. 未付款的订单 `basisCny = null`，保持未核实，与现状一致。
3. 订单归属多个达人（`MULTIPLE_KOLS`），或各行实付全为 0 而实付不为 0（`ALLOCATION_FAILED`）时，保持未核实，原因代码照旧写入 `crm_order.commission_basis_reason`。
4. 退款按现有规则单独处理，引擎已有对应逻辑，事件里 `basisIncludesRefund = FALSE`：
   - 成功退款金额从该行基数中扣除，不低于 0；
   - 有未完结的退款时阻断释放（`AFTER_SALES`）；
   - 已释放后再退款，走负向调整（`COMMISSION_ADJUSTMENT`）。
   结算流水里的「退款」行不再参与计算。

### 3.2 结算确认

1. 订单的 `INCOME_DETAIL` 流水里**恰好有一笔「货款收入」**，且满足以下两条时，视为微店已结算：
   - `tradeTime` 有值；
   - 换算后金额等于订单 `pay_amount`。这一条保留为单位错误的保护。
2. 结算后：
   - 计佣基数改为「货款收入」金额，按同一规则分摊；正常情况下数值与实付相同；
   - 结算状态 `CONFIRMED`，释放时间 =「货款收入」的 `tradeTime`，并写入 `crm_order.settled_time`；
   - 到时间后由现有释放任务转为可提现，提现资金来源只取已释放行，这部分现有逻辑不改。
3. 手续费、分润、退款以及其他子类型的流水只入库、只展示，**不参与计算，也不阻断确认**。`UNKNOWN_FLOW_TYPE` 不再使用：
   - 删除这个原因代码和对应分支；
   - 只为这个检查服务的常量（如 `KNOWN_TRADE_TYPES` / `KNOWN_TRADE_SUB_TYPES`）一并删除；
   - 「货款收入」这个子类型名称仍保留常量，待 M0 第 11 步确认。
4. 下列情况保持付款时的计提，不转可提现，原因代码写入 `crm_order.commission_basis_reason`：
   - 还没有结算流水：`NO_SETTLEMENT`；
   - 「货款收入」不唯一、缺 `tradeTime`、金额不等于实付，或金额无法解析：`INCOME_MISMATCH`。
   确认之后，原因清空为 null。
5. 结算前全额退款（`PRE_SETTLE_REFUND`），或退款成功后基数降为 0：计提为 0，与现状一致。
6. 结算流水变化后重算、检查点和幂等的机制都不变（§4.8.1 第 4 条后半段）。来源版本指纹会因为基数和结算状态变化而变化，自然产生新修订，不会重复入账。

### 3.3 达人端状态（L-031）

`CommissionOrderStateService` 的映射逻辑不用改：已核实、计提大于 0、未释放 → `FROZEN`。新口径下，已付款未结算的订单会显示「冻结中 / Frozen」和佣金金额。

`INVALID` 只剩以下几种情况：
- 未付款；
- 多达人或分摊失败；
- 没有比例；
- 计提为 0（例如全额退款）。

用测试证明：已付款未结算的订单不再返回 `INVALID`。

### 3.4 结算明细与订单链路（L-024）

1. 结算明细每单：
   - 「支付金额」改为订单 `pay_amount`，含运费，与订单链路的实付一致。现在是商品行实付之和，不含运费。
   - 「净增减」改名「微店可提现金额 / Weidian withdrawable」，值为该订单 `INCOME_DETAIL` 流水的带符号合计，换算规则与 `SettlementBasisCalculator.toCny` 一致；没有结算流水时为 null，前端显示「-」。数据经 `order.api` 取，不得跨模块读 mapper。
   - 删除「店铺获利」：后端 `retained` 字段、前端列和抽屉项、相关提示文案都去掉。ADR-032 附录 A 的字段对照同步修改。
   - 行状态现在只有 `UNVERIFIED` / `POSTED` 两种，新口径下付款即核实，会把未释放的单误显示为「已入账」。改为三种：
     - 任一行未核实 → `UNVERIFIED`；
     - 否则，任一行计提大于已释放 → `FROZEN`，显示「冻结中 / Frozen」；
     - 其余 → `POSTED`。
     管理端状态文案和筛选（如果有）同步修改。
2. 订单链路：资金卡片和商品行去掉「店铺获利」。其他字段不变。
