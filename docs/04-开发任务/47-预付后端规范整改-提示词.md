## 2. 数据访问分层（规范 01：controller → service → mapper）

- `commission/controller/KolPrepayController` 注入了 `JdbcTemplate` 并直接查库。controller 不能访问数据，请把查询移到 service。
- `PrepayService`、`CommissionWalletService`、`notification/service/PrepayOutboxJob` 都在用 `JdbcTemplate` 手写 SQL，绕过了 MyBatis-Plus 的公司过滤插件。请改为 `commission/mapper/` 下的 MyBatis-Plus Mapper：
  - 简单的增删改查用 `BaseMapper` 加 `*DO`；
  - 复杂查询、行锁（`FOR UPDATE`）、`ON CONFLICT`、条件更新（`WHERE status = ?`，用于并发保护）可以用注解或 XML SQL，但公司隔离交给插件，不要再手写 `tenant_id = ?`。确实需要跨公司处理的（例如定时任务），按规范 06 显式声明，参照现有定时任务的写法；
  - 并发语义保持不变：幂等 UUID、状态条件更新、付款重放、按先进先出冲抵、钱包负余额。现有的单元测试和 `CommissionWalletIT`、`PrepayMigrationIT` 必须继续通过，必要时改用 Mapper 的桩，但不得删减断言。
- `*DO` 不出现在接口入参出参（规范 01）。

## 3. 跨模块访问（规范 01：模块之间只能依赖对方的 `api` 包）

- `PrepayService` 直接 JOIN `crm_kol`、`sys_user`（取达人编号、名称、申请人姓名）。请改为通过 kol 模块、system 模块的 `api` 批量取数，在 service 中组装。如果对方 `api` 缺少方法，在对方 `api` 包中新增，并由对方的 service 实现。
- `notification` 模块的 `PrepayOutboxJob` 直接读写 `crm_prepay`、`crm_prepay_outbox`。outbox 属于 commission 模块：投递任务移到 commission 模块，通过 `notification` 的 `api`（现有的 `PrepayNotificationApi` 或 `NotificationApi`）发送；notification 模块中不再出现预付表。
- 检查本 PR 新增的其他代码有无同类问题，一并处理。
