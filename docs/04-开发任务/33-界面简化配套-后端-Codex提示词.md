## 1. 背景

负责人 2026-10-20 认为现在的管理端太繁琐，要求参照原系统（`docs/00-需求/原系统截图/`）简化：菜单按原系统的 7 个一级菜单重排，达人列表照原系统的版式（1018 表 I12 单元格中的图片），并且：

1. 管理员（超级管理员）拥有所有权限；
2. 不需要「清理记录」功能（界面去掉）；
3. 转移记录改在「操作日志」里查询；
4. 系统名称 T-CRM 改为 **SparkTrack**。

前端改造在任务 32。本任务提供它需要的后端能力。

## 2. 负责人已定的决定（不要自行改变）

| 项 | 决定 |
|---|---|

## 3. 接口与数据约定（前后端契约）

### 3.1 超管邀请达人（原任务 31 的 3.1 节）

- `GET` / `POST /admin-api/kol/register-code`：当前公司的超级管理员可以调用，商务的判断条件不变，其他账号仍然返回 422 `KOL_INVALID_BD_USER`。
- `crm_kol_register_code.bd_user_id` 的含义改为「邀请码所属账号」：用迁移只改列注释，不改列名和约束。
- 注册归属：
  - 邀请码属于可用商务时，绑定该商务；
  - 属于超管时，`bd_user_id` 为空，商务归属历史的写法与「转为未分配」一致。
- 注册预览：邀请码属于超管时返回 `{bdUserName: null, tenantName}`。

### 3.2 按达人设置自动清理

- `crm_kol` 新增 `auto_cleanup_days INTEGER`，可空：为空表示关闭，取值 1～365。
- `PUT /admin-api/kol/kols/{id}/auto-cleanup`，请求体 `{days}`（`null` 表示关闭），权限 `kol:edit`，数据范围与编辑相同；写推广记录，类型新增 `AUTO_CLEANUP`。
- `KolVO` 增加 `autoCleanupDays`。
- 自动清理任务改为：对每个设置了天数、状态为推广中、且最近 N 天没有出单的达人执行清理。清理效果不变：逻辑删除达人，结束商品对应关系，生成清理明细，由后台删除微店商品。
- 删除公司级的 `GET` / `PUT /admin-api/kol/cleanup-config` 和 `GET /admin-api/kol/cleanup-preview`。公司级配置表用新迁移删除，或者停止使用并在报告中说明理由。
- 删除 `GET /admin-api/kol/cleanup-items` 和 `POST /admin-api/kol/cleanup-items/{id}/retry`。明细表与后台工人保留。
- 手动清理 `POST /admin-api/kol/kols/{id}/cleanup` 保留。

### 3.3 操作日志查询（含转移记录）

- `GET /admin-api/system/oper-logs` 增加筛选参数：
  - `module`（如 `KOL`、`Product`、`Order`、`System`）；
  - `keyword`：匹配操作名称与参数摘要；
  - `operator`：用户名或姓名，精确匹配；
  - `from` / `to`：`Instant`，按操作时间筛选；
  - 以及原有的分页。
- 每行返回：`id`、`module`、`action`、`operatorName`、`method`、`path`、`summary`、`success`、`operTime`、`ip`（按现有的脱敏规则）。`summary` 是给人看的中文摘要，下面的转移操作必须有。
- **转移达人**的日志 `summary` 要写出：
  - 达人编号（最多列 20 个，超出写「等 N 位」）；
  - 原商务和新商务的姓名，「未分配」时写「未分配」；
  - 生效时间（立即或预约时间）、原因。
- 预约转移的执行、取消也各记一条。
- 数据范围：超管看全部；其他账号是否能看操作日志保持现状。

### 3.4 岗位模板（权限设置）

- 新表 `sys_post_template`：`tenant_id`、`post_template`（`BD` / `OPERATOR`）、`data_scope`、`permissions`（权限码数组）、`update_by`、`update_time`。表和字段都有注释。各公司没有记录时，使用代码中 `PostTemplate` 的默认值。
- 接口，仅超级管理员可用：
  - `GET /admin-api/system/post-templates` → `[{postTemplate, dataScope, permissions, isDefault}]`；
  - `PUT /admin-api/system/post-templates/{postTemplate}`，请求体 `{dataScope, permissions}`，权限码必须属于现有目录；
  - `POST /admin-api/system/post-templates/{postTemplate}/reset`：恢复默认。
- 新建账号时，按本公司的岗位模板预填权限和数据范围（取代直接读枚举）。已有账号不受影响。
- 每次修改写操作日志。

### 3.5 导入任务列表（上传文件）

- `GET /admin-api/task/tasks?type&status&page&size`：
  - 每行字段：`id`、`type`（如 `PRODUCT_IMPORT`、`MAPPING_IMPORT`、`ORDER_IMPORT`、`REFUND_IMPORT`、`KOL_IMPORT`）、`fileName`、`status`、`totalRows`、`successRows`、`failedRows`、`createTime`、`finishTime`、`operatorName`、`hasErrorFile`；
  - 超管看本公司全部，其他账号只看自己提交的。
- 现有的 `GET /{id}` 和错误文件下载接口保持不变。

### 3.6 改名 SparkTrack

- 邮件模板（达人邀请、注册验证码、找回密码等）中的 T-CRM 改为 SparkTrack。
- 发件显示名的默认值、`messages*.properties` 中面向用户的系统名、OpenAPI 标题（如果有）一并修改。
- 设计说明书和部署说明中「对外显示的系统名称」写成 SparkTrack，内部名称不改。

### 3.7 超管拥有所有权限

逐一检查：在当前公司，超管能通过所有权限码检查，数据范围为全部。列出仍然拒绝超管的接口：

- 设计上就只属于商务本人的操作，例如「认领达人」（认领即绑定给自己），保持拒绝，并在报告中写明；
- 其他拒绝超管的地方一律改为允许，并补测试。
