## 1. 背景

负责人 2026-10-20 认为现在的管理端太繁琐，要求参照原系统（`docs/00-需求/原系统截图/`）简化：菜单按原系统的 7 个一级菜单重排，达人列表照原系统的版式（1018 表 I12 单元格中的图片），并且：

1. 管理员（超级管理员）拥有所有权限；
2. 不需要「清理记录」功能（界面去掉）；
3. 转移记录改在「操作日志」里查询；
4. 系统名称 T-CRM 改为 **SparkTrack**。

前端改造在任务 32。本任务提供它需要的后端能力。

必读：`AGENTS.md`、`docs/05-工程规范/`；ADR-022、ADR-023、ADR-025；设计说明书 §3（账号与权限）、§4.2、§6.2；`docs/04-开发任务/31-超管邀请达人-Codex提示词.md`（3.1 节并入本任务）。

## 2. 负责人已定的决定（不要自行改变）

| 项 | 决定 |
|---|---|
| 超管邀请 | 超管有自己的 8 位邀请码；用它注册的达人不绑定商务，关系状态显示「待更新」，之后由认领或转移分给商务。平台管理员、数据范围为「全部」的普通子账号仍然不能取得邀请码 |
| 清理配置 | 原系统是**按单个达人**设置「自动清理：关闭 / N 天」。改为按达人设置，取代公司统一的清理开关和天数；手动清理保留 |
| 清理记录 | 界面不再提供。后台仍然生成清理明细，删除微店商品的后台工人保留；查询和重试接口删除 |
| 转移记录 | 在操作日志中查询，日志要能看出转移了哪些达人、从谁到谁、何时生效、原因 |
| 权限设置 | 指「岗位模板」：各公司可以维护「商务」「运营」两个岗位模板默认勾选哪些权限、默认数据范围；只影响之后新建的账号，不改已有账号的权限 |
| 上传文件 | 指导入任务：集中查看各类 Excel / CSV 导入任务的进度、结果和错误文件 |
| 认领 | **取消认领功能**（负责人 2026-10-20 第二轮）。没有绑定商务的达人由超管通过转移分给商务；商务可以按达人ID或邮箱精确搜索到未绑定的达人，并对其做资料编辑和审核（1018 表 03.02） |
| 关系状态 | 由系统自动决定，不再手动修改：推广配置齐全并保存后为「推广中」，否则为「待推广」；没有可用商务时显示「待更新」；账号冻结时显示「无效」（参照原系统：冻结的达人关系状态为无效） |
| 推广配置 | 字段按 1018 表 04.03：佣金比例、达人邀请码、代购平台（多选）及每个平台的地址、备注、达人推广表格，**全部必填**；不再要求前端选择跳转平台，默认取第一个平台 |
| 注册 | 字段按 1018 表 02.01：商务邀请码、账户名、邮箱、密码必填；手机号、WhatsApp、核心社媒平台、核心社媒ID 选填。**取消邮箱验证码**（02.01 没有列出）；邮箱唯一（02.02）与找回密码（02.03）不变 |
| 改名 | 用户看得到的地方从 T-CRM 改为 SparkTrack，包括邮件标题、正文和发件显示名的默认值；代码里的包名、环境变量（`TCRM_*`）、表名等内部名称**不改** |

## 3. 接口与数据约定（前后端契约）

### 3.1 超管邀请达人（原任务 31 的 3.1 节）

- `GET` / `POST /admin-api/kol/register-code`：当前公司的超级管理员可以调用，商务的判断条件不变，其他账号仍然返回 422 `KOL_INVALID_BD_USER`。
- `crm_kol_register_code.bd_user_id` 的含义改为「邀请码所属账号」：用迁移只改列注释，不改列名和约束。
- 注册归属：
  - 邀请码属于可用商务时，绑定该商务；
  - 属于超管时，`bd_user_id` 为空，商务归属历史的写法与「转为未分配」一致。
- 注册预览：邀请码属于超管时返回 `{bdUserName: null, tenantName}`。

### 3.2 按达人设置自动清理

- `crm_kol` 新增 `auto_cleanup_days INTEGER`，可空：为空表示关闭，取值 1～365。
- `PUT /admin-api/kol/kols/{id}/auto-cleanup`，请求体 `{days}`（`null` 表示关闭），权限 `kol:edit`，数据范围与编辑相同；写推广记录，类型新增 `AUTO_CLEANUP`。
- `KolVO` 增加 `autoCleanupDays`。
- 自动清理任务改为：对每个设置了天数、状态为推广中、且最近 N 天没有出单的达人执行清理。清理效果不变：逻辑删除达人，结束商品对应关系，生成清理明细，由后台删除微店商品。
- 删除公司级的 `GET` / `PUT /admin-api/kol/cleanup-config` 和 `GET /admin-api/kol/cleanup-preview`。公司级配置表用新迁移删除，或者停止使用并在报告中说明理由。
- 删除 `GET /admin-api/kol/cleanup-items` 和 `POST /admin-api/kol/cleanup-items/{id}/retry`。明细表与后台工人保留。
- 手动清理 `POST /admin-api/kol/kols/{id}/cleanup` 保留。

### 3.3 操作日志查询（含转移记录）

- `GET /admin-api/system/oper-logs` 增加筛选参数：
  - `module`（如 `KOL`、`Product`、`Order`、`System`）；
  - `keyword`：匹配操作名称与参数摘要；
  - `operator`：用户名或姓名，精确匹配；
  - `from` / `to`：`Instant`，按操作时间筛选；
  - 以及原有的分页。
- 每行返回：`id`、`module`、`action`、`operatorName`、`method`、`path`、`summary`、`success`、`operTime`、`ip`（按现有的脱敏规则）。`summary` 是给人看的中文摘要，下面的转移操作必须有。
- **转移达人**的日志 `summary` 要写出：
  - 达人编号（最多列 20 个，超出写「等 N 位」）；
  - 原商务和新商务的姓名，「未分配」时写「未分配」；
  - 生效时间（立即或预约时间）、原因。
- 预约转移的执行、取消也各记一条。
- 数据范围：超管看全部；其他账号是否能看操作日志保持现状。

### 3.4 岗位模板（权限设置）

- 新表 `sys_post_template`：`tenant_id`、`post_template`（`BD` / `OPERATOR`）、`data_scope`、`permissions`（权限码数组）、`update_by`、`update_time`。表和字段都有注释。各公司没有记录时，使用代码中 `PostTemplate` 的默认值。
- 接口，仅超级管理员可用：
  - `GET /admin-api/system/post-templates` → `[{postTemplate, dataScope, permissions, isDefault}]`；
  - `PUT /admin-api/system/post-templates/{postTemplate}`，请求体 `{dataScope, permissions}`，权限码必须属于现有目录；
  - `POST /admin-api/system/post-templates/{postTemplate}/reset`：恢复默认。
- 新建账号时，按本公司的岗位模板预填权限和数据范围（取代直接读枚举）。已有账号不受影响。
- 每次修改写操作日志。

### 3.5 导入任务列表（上传文件）

- `GET /admin-api/task/tasks?type&status&page&size`：
  - 每行字段：`id`、`type`（如 `PRODUCT_IMPORT`、`MAPPING_IMPORT`、`ORDER_IMPORT`、`REFUND_IMPORT`、`KOL_IMPORT`）、`fileName`、`status`、`totalRows`、`successRows`、`failedRows`、`createTime`、`finishTime`、`operatorName`、`hasErrorFile`；
  - 超管看本公司全部，其他账号只看自己提交的。
- 现有的 `GET /{id}` 和错误文件下载接口保持不变。

### 3.6 改名 SparkTrack

- 邮件模板（达人邀请、注册验证码、找回密码等）中的 T-CRM 改为 SparkTrack。
- 发件显示名的默认值、`messages*.properties` 中面向用户的系统名、OpenAPI 标题（如果有）一并修改。
- 设计说明书和部署说明中「对外显示的系统名称」写成 SparkTrack，内部名称不改。

### 3.7 超管拥有所有权限

逐一检查：在当前公司，超管能通过所有权限码检查，数据范围为全部。列出仍然拒绝超管的接口：

- 设计上就只属于商务本人的操作，例如「认领达人」（认领即绑定给自己），保持拒绝，并在报告中写明；
- 其他拒绝超管的地方一律改为允许，并补测试。

### 3.8 取消认领，商务可精确查找未绑定达人（03.02）

- 删除 `GET /admin-api/kol/claimable` 和 `POST /admin-api/kol/kols/{id}/claim`，以及对应的服务、错误码（如不再使用）和测试。
- 数据范围为「本人」的商务：
  - 列表默认只返回名下达人；
  - 当 `keyword` 与某个**未绑定商务**的达人编号或邮箱**完全相同**（不区分大小写）时，结果中加入该达人；
  - 商务可以查看该未绑定达人的详情，并调用资料编辑 `PUT /kol/kols/{id}` 和审核 `POST /review`。这两个操作**不会**把达人绑定给该商务；
  - 推广配置、清理、冻结等其他操作仍然只允许操作名下达人。
- 补测试：商务精确搜索到、编辑、审核未绑定达人；模糊搜索搜不到未绑定达人；其他公司的未绑定达人不可见。

### 3.9 关系状态改为自动

- 删除 `PUT /admin-api/kol/kols/{id}/relation-status`。
- 保存推广配置：要求审核已通过（409 `KOL_REVIEW_REQUIRED`）、必填项齐全（缺项时按现有方式返回校验错误）。保存成功后，存储的 `relation_status` 设为 `PROMOTING`，写推广记录。
- 存储值只剩 `PENDING_PROMOTION`、`PROMOTING`。用迁移把现有的 `INVALID` 改为 `PENDING_PROMOTION`；配置齐全的改为 `PROMOTING`。同时更新 CHECK 约束。
- 显示用关系状态 `displayRelationStatus` 的优先级：账号冻结（`status = 0`）→ `INVALID`；否则没有可用商务 → `PENDING_UPDATE`；否则 → 存储值。列表的 `relationStatus` 筛选按这个规则实现。
- 清理任务原来只处理「推广中」的达人，规则不变。

### 3.10 推广配置调整（04.03）

- `jumpTemplateId` 改为可选；不传时，取 `platforms` 中的第一个平台。
- `remark` 改为必填，长度上限沿用现有规则。
- 其余规则（版本号、生效时间、平台地址 https、刷新链接索引）不变。

### 3.11 注册取消邮箱验证码（02.01）

- `POST /kol-api/register` 不再需要 `emailCode`；删除 `POST /kol-api/register/email-codes` 及其限流计数、邮件模板（如不再使用）和测试。
- 必填：`code`、`name`、`email`、`password`；选填：`phone`、`whatsapp`、`primaryPlatform`、`primaryHandle`。`country`、`primaryUrl` 可以保留为可选字段，前端不再发送。
- 注册接口和预览接口按 IP 限流，保持现状。
- 邮箱已存在时，仍然返回 409 `KOL_EMAIL_EXISTS`（02.02）。
- 在执行报告中写明安全影响：不再验证邮箱归属；登录与找回密码仍以邮箱为准。
