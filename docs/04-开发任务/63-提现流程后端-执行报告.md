## 0.1 任务 62（#124）合并后的衔接实施（2026-10-25）

按负责人复查意见完成四项衔接（HEAD 含 merge commit c7ca012b）：

1. **合并 main（含 #124）**：设计说明书目录冲突保留双方行（提现 + 结算配置/结算明细/资金流水），`GET /admin-api/files/{id}` 权限补 `withdrawal:pay` 路由说明。
2. **资金来源真实现**：新增 `ItemStateWithdrawalFundingSource`，直读任务 62 的 `crm_commission_item_state`——已释放行（`verified`、未删、非售后阻断、`release_basis ∈ CONFIRMED/FALLBACK`、`release_at ≤ now`、`released > 0`）按 `release_at, order_item_id` FIFO 返回**扣除既有占用后的剩余**；冻结金额 = `accrued − released`（mapper 聚合）；`estimated`/`unverifiedCount` 同源；占用与剩余快照的 `item_state_id` 由资金源回填（迁移列 `V202610251100` 预留，部分索引 `WHERE item_state_id IS NOT NULL`）。**删除** `UnsettledWithdrawalFundingSource` 占位与桩；`WithdrawalIT` 改为插入真实 item_state 行（`releaseItems` helper），完整流程直接走生产路径。查询用参数化 `now`（PostgreSQL 的 `CURRENT_TIMESTAMP` 是事务开始时间，会漏掉同事务内释放的行）。最低提现额改为结算配置版本优先（`CommissionRuleConfigService.current()`），无版本时回退系统配置默认 200（ADR-032 §4）。
3. **订单行结算状态与工作台数字**：`CommissionOrderStateService` 接入提现占用——被在途申请（待审核/待支付）占用的行 = `WITHDRAWING`，被已支付申请占用的行 = `WITHDRAWN`（优先于释放阶梯判定）；`KolAnalyticsService` 工作台的 `withdrawnCny`/`withdrawingCny` 由这两个状态聚合（原为占位 0）。
4. **钱包核对任务**：新增 `CommissionWalletReconcileJob`（每日 02:30 UTC，分布式锁，逐启用公司）：钱包余额 = 台账合计（§4.8 每日核对），并比对**提现占用**——在途+已付申请金额合计不得超过钱包余额（负余额+在途提现需人工介入），不一致记 ERROR 日志。
5. **达人端接入**：`KolCommissionService.overview` 的 `occupied` 改为真实在途占用（原占位 0）；`fundRecords` 合并已支付佣金提现（`COMMISSION`）与预付付款（`PREPAY`）统一倒序分页，达人可见脱敏收款账户与 PAID 状态。

测试影响：`WithdrawalIT` 删除桩配置改用真实数据（含租户 2 隔离行、`item_state_id` 回填断言）；`WithdrawalServiceTest` 的分配用例按「资金源返回已扣占用后的剩余」新契约调整；`CommissionOrderStateServiceTest`/`KolCommissionServiceTest` 适配新构造参数并补占用状态查询桩。

## 6. 偏离与契约决策（供任务 61 契约对账）

1. **任务 61 未合并**：见前置说明。契约级决策登记在设计说明书「63 提现流程实现契约（2026-10-24）」。
2. **审核为单段**（`PENDING_REVIEW`→`PENDING_PAYMENT`），未采用 #112 期望的 `PENDING_FINANCE_REVIEW` 两段制——依据进度表 13.02 原文「状态包括待审核、已驳回、待支付、已支付」与设计 §4.8。
3. **付款权限复用 `prepay:pay`**（未新增权限码）——13.01 将佣金提现与达人预付统一为财务任务，「授权人员」登记付款为同一动作；超管隐含全部权限。未新增 `withdrawal:pay`。
4. **OWN 商务始终只见本人达人**（提现列表与财务任务列表），未沿用预付的「持审权即全公司」规则——依据 §4.8「所属商务审核」与 §3.2「提现的审核待办按其既定范围」。
5. **收款信息展示**：详情默认脱敏；`recipient` 端点对 `withdrawal:review`（12.02 审核人查看收款信息）与 `prepay:pay`（13.04 付款权限）开放并记审计；`commission:view` 只读用户仅见遮罩。
6. **#112 两个只读接口被取代**：`GET /withdrawals/{id}` 与 `GET /withdrawals/{id}/orders` 由本任务实现（提示词明示取代）；响应按 13.04 原文按**订单商品行**返回（#112 的订单分组+products 结构与其详情 `allocations=[]`、`paused` 字段、`PENDING_FINANCE_REVIEW` 状态不采用，前端 PR 需按本契约调整）。
7. **订单链路集成方式**：commission 依赖 order.api（分配快照需要商品行展示信息），为避免模块成环，链路「提现占用」由 `GET /admin-api/commission/withdrawal-occupations` 独立提供，`OrderChainDTO.withdrawals` 仍为 null（管理端链路页改调新端点，前端接线属前端契约任务）。
8. **资金来源接口**：`WithdrawalFundingSource`（62 未合并时空实现）——合并前线上所有申请会被 `WITHDRAWAL_INSUFFICIENT_AVAILABLE` 拦截（无已核实释放来源），符合「未核实不计提、不释放」原则。
9. **付款登记的说明规则**：非 CNY 必填折算说明；CNY 实付≠结算金额必填财务备注；外币金额不做汇率折算（系统不折汇，记账以 CNY 为准，与预付一致）。
10. **付款前驳回**：`PENDING_PAYMENT` 阶段由 `prepay:pay` 持有者驳回（设计 §4.8 第 4 条「打款前驳回」；#116 同规则）。
11. **提现凭证沿用 `PREPAY_FILE_INVALID`/`FILE_TOO_LARGE` 内容校验**（PNG/JPEG/PDF；≤2MB 由 crm_file CHECK 保证并显式校验），错误码名称沿用现有预付命名，未另设提现专用码。
12. **通知收件人**：提交→当前商务+启用超管；通过/驳回/付款→当前商务。达人端无站内信（现有通知体系面向管理端账号）。
13. **财务任务列表状态映射**：统一 `PENDING_REVIEW/PENDING_PAYMENT/PAID/REJECTED/CANCELLED`，预付 `WAITING_DETAILS`/两段审核均归 `PENDING_REVIEW`，`APPROVED`→`PENDING_PAYMENT`；响应同时带 `sourceStatus` 原始状态。
14. **列表筛选用 `kolCode`（精确）**，未实现 #112 的 `bdName` 筛选（跨模块账号名检索无既有 api；达人编号/名称/商务名在行内展示）。
15. **幂等的并发验证**：以达人行锁 + 唯一约束 + 钱包行锁串行化保证「并发只成功一笔」，测试为串行重放（含 ON CONFLICT 分支），未写真多线程用例。
