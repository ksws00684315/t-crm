## 1. 结论

§2 全部要求已实现，§4 的 6 项验证全部在本机真实运行并通过，§5 的浏览器验收已做。需要负责人知道的差别有三类：

1. **验证平台不是 Linux**：本机是 macOS arm64 的 Docker Desktop，不是发布目标 linux/amd64。镜像全部按本机架构（arm64）构建，没有验证 amd64 构建；发布工作流本身只过了 `actionlint`，没有在 GitHub 上运行过。
2. **Docker Desktop 的文件共享会让容器里看到的软链接过期**（见 §4.2 的说明）。这不是 Linux 行为：在 Linux 内核的卷上，用同一份 `switch_current`（GNU `mv -T`）连续切换 150 次，同时每秒数千次请求，66,793 次请求零失败。端到端流程验证时在 Nginx 容器里放了一个每 100 ms 列目录的替身刷新，已如实标注。该问题不满足「停下来报告」的条件（Nginx 读得到文件，切换时没有失败请求），但请负责人知道，上线后第一次发布要在服务器上确认。
3. **范围外的小改动 1 处**：生产 Compose 的 `TCRM_FLYWAY_IGNORE_MIGRATION_PATTERNS` 原来写死为 `""`，README 第 9 项的应急方法「临时设置该变量」按字面无法生效。本任务要求发布脚本在 Flyway 拒绝时打印应急方法，所以改为 `${TCRM_FLYWAY_IGNORE_MIGRATION_PATTERNS:-}`（默认仍是空，即严格模式，行为不变），应急方法才可执行，并已实测（§4.5）。见 §8 偏离。

## 4. 验证（提示词 §4 的 6 项，全部真实运行）

### 4.1 `deploy 1.0.0` 全流程

空环境（无容器、无卷）执行 `release.sh deploy 1.0.0`，退出码 0，用时 37.6 秒。日志（`.tmp/verify/logs/t1-deploy-1.0.0.log`）要点：拉取四个镜像 → 解出静态文件 → 「首次部署（没有 postgres 容器），跳过备份」→ 启动 postgres、redis 并等待健康 → crm-admin 健康 → crm-redirect 启动 → 建立 `current` 并启动 Nginx → 写 `.env` 与记录。`status`：

```
current -> releases/1.0.0
crm-admin     localhost:19581/tcrm/crm-admin:1.0.0      running/healthy
crm-redirect  localhost:19581/tcrm/crm-redirect:1.0.0   running/healthy
postgres      localhost:19581/tcrm/crm-postgres:1.0.0   running/healthy（RestartCount 0，HostConfig.Init=true）
```

`https://admin.t95.localhost:19580/build.txt` 与 `kol.` 返回 `1.0.0`，`t.` 的 `/healthz` 返回 200。

遗留 L-061（全新数据卷首次启动 postgres 退出一次）：两次空卷首次部署（一次 S3 端点拒绝连接，一次端点为黑洞地址 `10.255.255.1`）都**没有复现**，RestartCount 为 0。为验证等待逻辑，用 `docker exec … kill -9 <postmaster>` 让 postgres 崩溃一次，同时调用 `wait_healthy postgres lenient`：容器重启一次后返回健康，`rc=0`（`t9b-lenient-wait-after-crash.txt`）。基础设施（postgres、redis）的等待只以超时为失败条件，容忍重启；应用（crm-admin、crm-redirect）的等待在 `unhealthy` 或重启 2 次以上时立即失败。这是对重启的模拟，不是 L-061 本身，待任务 96 上线实测时一并确认。

### 4.2 `deploy 1.0.1`：持续请求，前端切换无失败，Nginx 未重启，跳转容器不变

发布期间用 `probe.py` 以约 20 次/秒分别持续请求 `t.` 的 `/healthz`、`admin.` 与 `kol.` 的 `/build.txt`、`admin.` 的 SPA 深层路由（均走 HTTPS 19580）：

```
admin-index: {'200 1.0.0': 285, '200 1.0.1': 130}
kol-index:   {'200 1.0.0': 286, '200 1.0.1': 130}
admin-spa:   {'200': 414}
t-healthz:   {'200': 405}
failures: 0
```

发布前后 `docker inspect`：Nginx 容器 ID、`StartedAt`、`RestartCount`（0）完全相同；crm-redirect 容器 ID 与 `StartedAt` 完全相同（脚本输出「crm-redirect 镜像摘要未变化（48daf85bd1d5），不重启」）。发布过程包含一次真实 `pg-backup.sh`（备份文件 79,948 字节的 `.dump.gpg`）。

**注意（返工更正）**：本节原始验证里「跳转服务不重启」用的是同一个镜像打多个标签，没有经过工作流的构建步骤，因而没有发现工作流给每个镜像加的 `revision`、`version` 标签会让镜像 ID 逐版本不同。该问题已在 §13.1 修复并用工作流的标签配置重新实测。

跳转服务镜像变化的分支也验证了：1.0.4 的跳转镜像带不同标签，`deploy 1.0.4` 输出「crm-redirect 镜像变化：48daf85bd1d5 -> 7eda749bd18f，更新」并重建容器。

**平台说明（重要）**：Docker Desktop 的文件共享会让容器内对替换后的符号链接保持旧视图——宿主机上 `current` 已指向新版本，容器内 `readlink` 仍返回旧版本两分钟以上，直到有进程列出父目录。本机首次手工切换时就出现了这个现象。端到端验证因此在 Nginx 容器里运行了一个替身（`.tmp/verify/crutch.sh`，每 100 ms 执行 `ls /usr/share/nginx/sites`），上面 0 失败的结果是带着这个替身得到的。为证明 Linux 行为，单独做了一个对照实验：Docker 命名卷（Linux 内核自己的文件系统，等价于 Linux 主机的绑定挂载）放 `releases/A`、`releases/B` 和 `current`，Nginx 容器以只读方式挂载**父目录**，另一个 `ubuntu:24.04` 容器（GNU coreutils 9.4）`source` 本任务的 `release.sh`，调用其中真实的 `switch_current` 在 A、B 之间切换 150 次（间隔 20 ms），同时 3 个循环在 Nginx 容器内持续请求：

```
52919 A
13874 B       （共 66,793 次，0 次失败，两个版本都被命中，没有过期视图）
```

结论：软链接加父目录挂载的方案在 Linux 上读得到文件、切换原子、无失败请求。「挂载 `current` 本身会钉死第一个版本」这一点按 Docker 文档设计，没有单独实验。

### 4.5 `rollback`

- **无新迁移**：1.0.1 → `rollback 1.0.0`，退出码 0，用时 14.7 秒，`current` 切回 `releases/1.0.0`，`build.txt` 返回 1.0.0，crm-redirect 摘要未变不重启。
- **有新迁移**：`deploy 1.0.4` 带迁移成功（`flyway_schema_history` 出现 `209901010000`）；`rollback 1.0.1` 时 crm-admin 启动失败，日志为 `Detected applied migration not resolved locally: 209901010000`。脚本退出码 1（7 秒），打印：

  ```
  原因：数据库结构比 1.0.1 的镜像新，Flyway 严格模式拒绝启动 …
    - 恢复服务：重新发布较新的版本，release.sh deploy 1.0.4
    - 确需用旧镜像：按 deploy/README.md「发布与回滚」的应急方法处理 …
  本脚本没有修改 TCRM_FLYWAY_IGNORE_MIGRATION_PATTERNS，也没有改动数据库。
  ```

  执行前后 `.env`、`compose.verify.yml`、`docker-compose.prod.yml` 的 `shasum`、`.env` 中 FLYWAY 行数（0）、`current` 指向全部一致（`t5c-before.txt` 与 `t5c-after.txt` 无差异）；crm-admin 容器环境里该变量为空。
- **应急方法实测**：在 `.env` 加 `TCRM_FLYWAY_IGNORE_MIGRATION_PATTERNS='*:future'`，重新执行 `rollback 1.0.1`，crm-admin 以旧镜像启动成功并完成切换；删除该行后 `deploy 1.0.4` 重建 crm-admin，容器环境里该变量回到空（严格模式）。

## 8. 偏离与原因

1. **拉取与解出静态产物放在备份之前**（提示词顺序是备份、拉取、解出）。这两步不改动线上；先做能让拉取失败时不产生任何变更，并且把备份放到更新前一刻，缩短备份与更新之间的数据窗口。备份失败仍然中止，且静态目录里多出的 `releases/<版本>/` 只是未使用的目录，会被保留策略清理。
2. **镜像标签用不带 `v` 的版本号**（git 标签 `v1.0.1`，镜像标签 `1.0.1`）。提示词「标签与 git 标签一致」的字面是否包含 `v` 有歧义；`TCRM_VERSION`、`release.sh deploy <版本>`、`releases/{版本}` 在提示词中都是不带 `v` 的版本号，所以镜像标签采用同一字符串。`release.sh` 也接受带 `v` 的参数并去掉。需要带 `v` 时改工作流的两处即可。
3. **`TCRM_FLYWAY_IGNORE_MIGRATION_PATTERNS` 在生产 Compose 中改为 `.env` 透传**（默认空，严格模式不变）。原来写死的字面量使 README 的应急方法无法执行。属于范围外的小改动，已实测；若负责人不同意，可还原该行并把应急方法改为「编辑 Compose 文件」。
4. **工作流增加「标签提交是 `main` 祖先」的检查**（需要 `fetch-depth: 0`）。提示词只要求把前提写进 README；这是一个不跑测试的廉价检查，能防止对未合并的提交打标签。
5. **`release.sh` 未实现提示词外的自动回退**：crm-admin 替换后失败时线上管理端接口不可用，需要按提示执行 `deploy <上一个版本>`（提示词要求停止并给出建议，不自动处理）。
6. **返工改动**（审查指出的三处，不含「不阻塞」项和 `crm-postgres` 独立版本变量，均未动）：见 §13。
7. **验证替身**：见 §2（Docker Desktop 文件共享刷新替身、`gpg`/`date` 替身、浏览器验收用明文监听、本机 arm64）。

## 13. 审查返工（PR #178 审查结论的三处）

范围只含下面三处。审查里「不阻塞」的几项（`.env` 留着 `*:future` 时无提示、回滚时多拉 `crm-postgres`、无并发锁、迁移超过健康检查窗口、L-061）和「需要负责人决定」的 `crm-postgres` 独立版本变量都没有动。`origin/main` 没有新提交（`git merge origin/main` 为 Already up to date），所以没有合并提交。

### 13.1 crm-redirect 每次发布都重启

**原因**：工作流给四个镜像都加了 `org.opencontainers.image.revision`、`version` 标签，值每次发布都不同，标签在镜像配置里，镜像 ID 随之改变；`release.sh` 比较的正是镜像 ID。原验证用同一个镜像打两个标签，没有覆盖工作流这一步，所以没有发现。

**改动**：`.github/workflows/release.yml` 的 crm-redirect、crm-postgres 构建步骤去掉这两个标签，只保留固定的 `source`；crm-admin、crm-static 不动（它们每次发布本来就变）。「provenance/sbom 关闭」的注释改写：镜像 ID 相同需要同时满足 provenance、sbom 关闭，**且**镜像配置里没有逐版本变化的标签，并说明为何只有这两个镜像去掉。

**实测**（`docker buildx build --provenance=false --sbom=false --load`，本机 arm64，内容相同的源码；标签配置与工作流一致）：

| 构建 | 镜像 ID |
|---|---|
| crm-redirect，只有固定 `source` 标签，两次 | `f7f8616b0cd2…` 与 `f7f8616b0cd2…` 相同 |
| crm-redirect，`revision`、`version` 每次不同，两次（返工前的工作流配置） | `7c12887a3461…` 与 `9398fbf36da6…` 不同 |
| crm-postgres，只有固定 `source` 标签，两次 | `ad0f7e32366f…` 与 `ad0f7e32366f…` 相同 |

端到端：1.0.0、1.0.1 的 crm-redirect 镜像取自上述两次独立构建（ID 相同），`deploy 1.0.1` 输出「crm-redirect 镜像摘要未变化（f7f8616b0cd2），不重启」，Nginx 与 crm-redirect 容器 ID、`StartedAt` 前后不变，也不再打印「crm-postgres 镜像不同」的提示（`grep` 计数 0）。

局限：这是本机构建，不是 GitHub 流水线（无注册表缓存、amd64）；真实流水线上两个连续标签是否得到相同镜像 ID 仍列在 §7 待上线验证。

### 13.2 `compose down` 之后发布不能跳过备份

**原因**：`FIRST_DEPLOY` 只看有没有 postgres 容器。已上线的主机执行过 `docker compose down` 后容器全无，脚本会打印「首次部署，跳过备份」，清空 `PREVIOUS_VERSION` 并继续发布。

**改动**（`deploy/scripts/release.sh`）：新增 `has_release_trace`（`current` 链接存在，或发布记录里有 `result=ok`）和 `is_first_deploy`（没有 postgres 容器**且**没有发布痕迹）。`check_backup_prerequisites`、`cmd_deploy` 都改用它。有发布痕迹而 postgres 没运行时，在拉取镜像之前报错退出，提示先启动 postgres 再发布，不跳过备份；`PREVIOUS_VERSION` 保留（脚本在报错前已读到，且不再被清空）。

**实测**（项目 `tcrm-t95-verify`，先 `deploy 1.0.0` 成功，再 `docker compose down`，容器全无）：

| 状态 | 结果 |
|---|---|
| A：`current` 链接 + 发布记录，无容器 | `deploy 1.0.1` 退出码 1，输出「这台主机已经发布过，但 postgres 没有运行：没有备份不能发布。先启动数据库（…up -d --no-deps postgres redis）…环境未改动」；前后对比 `.env` 的 shasum、`current`、`releases/` 目录、发布记录行数、备份文件数、容器数全部相同 |
| B：只有发布记录（`current` 临时移走） | 同样退出码 1、同样报错，环境未改动 |

之后按提示启动 postgres、redis（及应用）继续主线。

### 13.3 `.env` 写入不是原子的

**原因**：`cat "$tmp" > "$ENV_FILE"` 会先清空 `.env`，磁盘满或进程被杀时所有密钥丢失；临时文件放在 `/tmp` 并带着全部密钥，异常退出不清理。

**改动**（`env_set_version`）：用 `mktemp "$ENV_FILE.XXXXXX"` 在 `.env` 同目录创建临时文件，`cp -p` 复制权限（root 执行时同时复制属主），写入新内容后 `mv -f` 替换，同一文件系统内是一次原子重命名。每个失败路径都删除临时文件，`on_exit` 也清理（`ENV_TMP`），不会留在 `/tmp`。

**实测**（`.tmp/envtest-*`，`.env` 权限 640，含 `$` 的内容）：

| 场景 | 结果 |
|---|---|
| 替换已有 `TCRM_VERSION` | 内容正确，`$secret` 原样保留，权限仍为 640，属主不变，目录里没有残留临时文件 |
| `.env` 里没有 `TCRM_VERSION` 行 | 追加到末尾，权限 640，无残留 |
| 写入中途失败（`awk` 替身先输出一行再退出 1） | 原 `.env` 与失败前逐字节相同（`cmp`），权限 640，同目录和 `/tmp` 都没有临时文件 |
| 同上，在 `set -e` 与 `on_exit` 下 | 退出码 1，原 `.env` 完好，无残留 |

没有以非 root 与 root 两种身份比较属主复制：本机只有当前用户，`cp -p` 保留属主只在 root 下生效，这一点靠 `cp -p` 的语义，没有实测。
