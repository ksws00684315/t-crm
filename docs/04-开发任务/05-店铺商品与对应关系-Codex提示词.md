## 4. 已定的设计决定（不要自行改变）

### 4.1 店铺

- 表 `crm_shop`：`shop_name`（1～64）、`weidian_shop_id`（微店店铺 ID，数字字符串，1～32 位，全表唯一）、`status`（0 停用 / 1 启用）、`remark` 及通用字段。
- 店铺最多 3 个（设计 §1.2）；新增第 4 个时返回 422。
- 停用的店铺不能再导入商品或对应关系，已有数据不受影响。

### 4.2 原商品

- 表 `crm_product`：`product_code`、`shop_id`、`weidian_item_id`、`name`（1～200）、`category`（≤ 64，可空）、`image_url`（≤ 512，可空，填写时必须是 https）、`price NUMERIC(14,2)`（必填，≥ 0）、`rate NUMERIC(6,4)`（商品级佣金比例，0～1，可空，空表示使用达人默认比例）、`status`（1 在售 / 0 下架）及通用字段。
- **原商品编码**：`^[A-Z0-9_-]{1,16}$`，存大写（导入时转大写）。导入时填写则沿用（须未被占用），不填则系统生成 `P` + 6 位顺序号（序列 `crm_product_code_seq`，超过 999999 自动扩位，跳过已占用的编号，做法与达人编号相同）。编号创建后不可修改，全表唯一、永不复用。编码会出现在中转链接路径里，与跳转服务的校验 `^[A-Za-z0-9_-]{1,32}$` 兼容。
- 业务唯一键：`(shop_id, weidian_item_id)`，在未删除的商品中唯一。
- **导入为"新增或更新"**（§4.9"导入更新"）：
  - 按 `(店铺, 微店商品 ID)` 查找：不存在则新增；存在则更新。
  - 更新时，若该行填写了原商品编码且与已有编码不同，该行报错（编码不可修改）。
  - 更新时，**空单元格表示不修改**该字段（导入不能清空字段，清空在页面编辑中完成）。
  - 导入不修改 `status`；新增的商品为"在售"。
  - 新增时，若 `(店铺, 微店商品 ID)` 已是某条有效对应关系的专属商品，该行报错（专属商品不能再登记为原商品，与 4.3 第 2 条对应）。

### 4.3 专属商品对应关系

- 表 `crm_kol_item`：`kol_id`、`product_id`、`shop_id`（专属商品所在店铺）、`weidian_item_id`（专属商品微店 ID，数字字符串 1～32 位）、`valid_from`、`valid_to`（空表示当前有效）及 `create_by`、`create_time`、`update_by`、`update_time`。**不建 `is_deleted`**：对应关系只会被置失效，永不删除（表注释写明）。
- 约束：
  - 部分唯一索引 `(shop_id, weidian_item_id) WHERE valid_to IS NULL`：同一专属商品同一时间只有一条有效映射；
  - 部分唯一索引 `(kol_id, product_id) WHERE valid_to IS NULL`：同一达人同一原商品只有一条有效映射；
  - 普通索引 `(shop_id, weidian_item_id, valid_from)`：后续订单归因按"下单时有效"查历史映射。
- **导入逐行处理**（§4.3 第 2、3 步），每行一个事务：
  1. 店铺存在且启用；达人编号存在且启用；原商品编码存在（下架的商品也可以建立映射）。
  2. 专属商品不能是任何原商品本身：`(店铺, 专属商品 ID)` 与某个未删除原商品的 `(shop_id, weidian_item_id)` 相同时报错（否则原商品的订单会全部归给达人）。
  3. 若已存在**完全相同**的有效映射（同达人、同原商品、同店铺、同专属商品 ID）：视为成功，不做修改（重复导入幂等）。
  4. 若该专属商品已被**其他**有效映射占用：报错，写明占用它的达人编号和原商品编码。
  5. 若该达人对该原商品已有有效映射但专属商品不同（"更换专属商品"，§4.9）：把旧映射的 `valid_to` 置为当前时间，再新增一条；两步在同一事务内。
  6. 否则新增一条，`valid_from` 为当前时间。
  - 并发冲突（唯一索引报错）时，该行报错"数据已被其他操作修改，请重新导入该行"，不重试。
- **导入文件内的规则**：同一专属商品（店铺 + 专属商品 ID）或同一"达人 + 原商品"在文件中出现多次时，第二次及以后的行报错。
- **跨模块**：`product` 通过 `kol` 模块新增的 `api` 门面按编号查达人（返回 ID、编号、姓名、是否启用）、按 ID 批量取编号与姓名；`kol` 不得依赖 `product`。

### 4.4 权限（§3.1）

| 操作 | SUPER_ADMIN | OPERATOR + ALL | OPERATOR + OWN（商务） | FINANCE |
|---|:-:|:-:|:-:|:-:|
| 店铺：列表 | ✓ | ✓ | ✓ | ✓ |
| 店铺：新增、编辑、启停 | ✓ | — | — | — |
| 原商品：列表、详情 | ✓ | ✓ | ✓ | ✓ |
| 原商品：编辑、上下架、导入 | ✓ | ✓ | — | — |
| 对应关系：查询 | ✓ | ✓ | — | ✓ |
| 对应关系：导入 | ✓ | ✓ | — | — |

- 原商品不是个人数据，所有管理员都可查看；对应关系涉及达人归属，商务（`OWN`）本任务不开放，返回 403。
- 每个接口都有越权测试。

### 4.5 批量任务框架的调整（`task` 模块）

1. **每种任务各自的行数上限**：`ImportTaskApi.submitImport` 增加行数上限参数，取代全局常量。达人导入保持 2,000；原商品导入、对应关系导入均为 **20,000**（一个文件可以导入全部 2 万条原商品，或一位达人的全部对应关系）。文件大小上限仍为 20MB。
2. `TaskType` 与 `crm_task.task_type` 的 `CHECK` 增加 `PRODUCT_IMPORT`、`MAPPING_IMPORT`（新迁移，不修改任务 04 的脚本）。
3. **任务文件保留 30 天**（任务 04 审查决定）：
   - `task` 模块新增定时任务，每天 03:30（UTC）运行，删除 `create_time` 早于 30 天前的 `crm_task_file` 行；任务记录本身保留。
   - 按规范 02 通过 `shared.DistributedLocks` 执行；保留天数写为常量，不做成配置项。
   - 文件被清理后，下载错误文件返回 404，`errorCode` 为新增的 `TASK_FILE_EXPIRED`；任务详情的"是否有错误文件"随之为 false。管理端对该错误码显示"错误文件已超过 30 天，已被清理"。
4. **性能**：2 万行的原商品导入、2 万行的对应关系导入，在验证机上应在 5 分钟内完成。若逐行事务达不到，先在报告中给出实测数据和原因，**不要自行改为批量提交**（会改变"每行独立"的语义），停下来报告。

### 4.6 导入模板（列名与顺序；列定义各自集中在一处）

**原商品导入**

| 列 | 必填 | 规则 |
|---|---|---|
| 原商品编码 | 否 | 见 4.2 |
| 店铺 ID | 是 | 已存在且启用的店铺的微店店铺 ID |
| 微店商品 ID | 是 | 数字，1～32 位 |
| 商品名称 | 新增时是 | 1～200 字符 |
| 分类 | 否 | ≤ 64 字符 |
| 图片地址 | 否 | https，≤ 512 字符 |
| 价格 | 新增时是 | ≥ 0，最多 2 位小数；允许千分位逗号 |
| 商品佣金比例(%) | 否 | 0～100，最多 2 位小数，存为小数（与达人导入相同） |

**对应关系导入**

| 列 | 必填 | 规则 |
|---|---|---|
| 店铺 ID | 是 | 专属商品所在店铺（微店店铺 ID），已存在且启用 |
| 专属商品 ID | 是 | 数字，1～32 位 |
| 达人编号 | 是 | 已存在且启用的达人，不区分大小写 |
| 原商品编码 | 是 | 已存在的原商品，不区分大小写 |

## 5. 接口

全部在 `/admin-api` 下，遵循规范 03；写操作加 `@AuditLog`；每个接口显式声明角色。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/product/shops` | 店铺列表（不分页，最多 3 个） |
| POST | `/product/shops` | 新增店铺 |
| PUT | `/product/shops/{id}` | 编辑名称、备注（微店店铺 ID 不可修改） |
| PUT | `/product/shops/{id}/status` | 启用 / 停用 |
| GET | `/product/products` | 列表：`keyword`（编码、名称、微店商品 ID；转义 `%`、`_`、`\`）、`shopId`、`status`、`category`、分页；按 `product_code` 升序 |
| GET | `/product/products/{id}` | 详情 |
| PUT | `/product/products/{id}` | 编辑名称、分类、图片、价格、商品佣金比例（可清空）；只写这些列 |
| PUT | `/product/products/{id}/status` | 在售 / 下架；只写状态列 |
| GET | `/product/product-imports/template` | 下载原商品导入模板 |
| POST | `/product/product-imports` | 上传原商品 Excel，202 + `{taskId}` |
| GET | `/product/kol-items` | 对应关系查询：`kolCode`、`productCode`、`shopId`、`weidianItemId`、`current`（默认 `true` 只查有效映射，`false` 含历史）、分页；按 `valid_from` 倒序、`id` 兜底；返回达人编号与姓名、原商品编码与名称、店铺、专属商品 ID、生效区间 |
| GET | `/product/kol-item-imports/template` | 下载对应关系导入模板 |
| POST | `/product/kol-item-imports` | 上传对应关系 Excel，202 + `{taskId}` |

商品 VO 的 `price`、`rate` 按规范 03 以字符串返回（`price` 2 位小数，`rate` 4 位小数）。错误码按 `{模块}_{原因}` 新增（如 `SHOP_LIMIT_REACHED`、`SHOP_WEIDIAN_ID_EXISTS`、`PRODUCT_NOT_FOUND`、`TASK_FILE_EXPIRED`），并同步管理端的错误码文案。

**查询性能**：`crm_kol_item` 按 200 万行设计。对应关系查询的每种筛选组合都要能用上索引；在 PR 中附上用 20 万行以上合成数据执行 `EXPLAIN (ANALYZE)` 的结果（规范 04 第 3 节）。单表索引不超过 6 个。
