## 1. 类型与登录态

| 项 | 落实 |
|---|---|
| `Role` | `"PLATFORM_ADMIN" \| "SUPER_ADMIN" \| "STAFF"`。公司内可分配的是 `SUPER_ADMIN` 与 `STAFF` |
| `PostTemplate` | `"OPERATOR" \| "BD"`，只用于预填，不是角色 |
| `PermissionCode` | 4.5 的 18 个码，供路由 `meta` 与 `can()` 使用 |
| `UserVO.permissions` | `string[]`，不是 `PermissionCode[]`。接口以后多出来的码要能显示原码，不能在类型上被丢掉 |
| `UserVO.postTemplate` | `PostTemplate \| null`。超管与平台管理员为 null |
| 会话 | `/auth/me` 的 `permissions` 随 `UserVO` 进会话。`can(code)` 对超管恒为真；`isOwnScope` 为 `STAFF` 且 `OWN`；`isSuperAdmin`、`isPlatformAdmin` 由角色得出 |
| 页面判断 | 菜单、守卫和按钮走 `accessOf` / `can` / `isSuperAdmin`。列表行是否子账号用 `isStaff` / `isSuperAdminAccount`，比较只留在 `permission.ts` |
| 页头 | 子账号有岗位时显示岗位名（运营 / 商务），否则显示账号类型 |

旧会话只校验 token、过期时间和用户名、角色。缺 `permissions` 时按空数组处理，下次 `refreshProfile`（进布局时已有）再对齐。

## 4. 用户管理

列表增加账号类型（超级管理员 / 子账号）、岗位（运营 / 商务 / —）、权限数。子账号显示「n 项」，悬停为权限名称；未知码显示原码。超管显示「全部」，不用数组长度，避免空数组看起来像 0 项。子账号行有「权限设置」。

新建先选账号类型，默认子账号。

- 子账号必须选岗位模板。选中后按 `GET /system/permissions` 返回的模板勾选权限并设置数据范围，之后可以逐项改、也可以改数据范围。权限区按接口清单分组渲染，不写死 18 个码。每组有全选。每个码显示语言包里的名称和一句说明。未知码、未知分组显示原值。
- 超管隐藏权限区和数据范围，提示「拥有全部权限」。创建请求只带 `username`、`password`、`nickname`、`email`、`role`。

权限区下方注明不可授予的六项：用户与权限、系统配置、操作日志、审批预付、标记打款、转移达人。设计说明书 §3.1 还列了「链接索引手动重建」。任务 4.4 只要求这六项，重建仍是超管按钮，不放进可勾选清单。

编辑把基本信息和权限分开：

- 基本信息 `PUT /system/users/{id}`，字段为 `nickname`、`email`、`role`、`postTemplate`。不传 `dataScope`，也不传权限，避免改岗位时覆盖已有权限和数据范围。改岗位模板只改这一处显示。
- 权限用单独对话框。打开时 `GET /system/users/{id}/permissions`，勾选以该结果为准，不用模板覆盖。「按模板重置」使用**已保存**的岗位模板。保存 `PUT /system/users/{id}/permissions`，整表替换 `{permissions, dataScope}`。没有岗位模板时重置按钮禁用。超管不显示数据范围，也不提供该对话框。

数据范围单选：全部数据 / 仅本人负责的达人。

下列断言因角色模型变化而改写，没有删掉原来要守住的行为：

1. `hasAnyRole` 的用例删除。函数已不存在。访问判断改由 `accessOf`、`canAccessRoute` 覆盖。
2. `buildMenu` 的入参从角色数组改为 `AccessProfile`。超管仍看到全部公司菜单；平台管理员仍只看到公司管理。原先「运营 / 财务看到除用户和日志外的全部菜单」改为：只有 `kol:view` 的子账号只看到首页和达人；有 `product:view` 且不是 `OWN` 才看到对应关系。
3. `kolAbilities` 不再返回 `canManageBd`。超管仍可写、可换商务、可指定、可筛选。有 `kol:edit` 且数据范围为全部的子账号可写、可指定、可筛选，不能更换商务（4.3 把更换收成超管）。`OWN` 的编辑者可写，不能筛选、指定或更换。只有 `kol:view` 且不是 `OWN` 的账号可以筛选商务，不能写。这最后一条与旧「财务不能管商务」不同，按 4.3 改。
4. `productAbilities` 不再返回 `canWriteProduct`。店铺管理仍只有超管。原商品编辑与上下架分开测。`OWN` 不再连带关掉 `product:edit`；关掉的是对应关系查看。
5. `linkAbilities` 不再让每个公司角色都看链接，改为要有 `product:view`。重建索引仍只有超管。
6. `canAccessRoute` 的入参从角色数组改为 `AccessProfile`。路由表断言从 `meta.roles` 列表改为 `permission` / `superAdmin` / `platformAdmin` / `hideForOwn`。首页不再声明三个角色。
7. 守卫夹具里的 `OPERATOR`、`FINANCE` 改为带权限码的 `STAFF`。无权限、超管页面、`OWN` 对应关系、平台管理员首页重定向这些结果保留。
8. `setup.spec` 不再读 `store.roles`，改为 `isSuperAdmin` 与 `access.can("kol:view")`。守卫入参改为会话上的 `access`。
9. 错误码条数从「与后端枚举长度相等」改为「多出来的键只能是后端还没有的 `USER_PERMISSION_INVALID`」。每条后端错误码仍必须有中英文文案。
10. 菜单搜索里不能看到「用户管理」的账号从 `FINANCE` 改为只有 `kol:view` 的子账号。超管仍能搜到。
11. 重新认证里的另一个账号从 `OPERATOR` 改为 `STAFF`。该测试用的本地路由没有守卫，去掉了已经不存在的 `meta.roles`。换账号回首页的行为不变。
12. 登录测试里的 `OPERATOR` 用户改为带 `kol:view` 的 `STAFF`。站外重定向断言不变。
13. 布局里「旧响应没有 tenantName」的夹具从 `OPERATOR` 改为 `STAFF`。仍断言页面不出现 `undefined` / `null` 字样。
14. 用户列表行从角色「运营」改为子账号、岗位运营、一项权限。中文期望增加「子账号」「1 项」「权限设置」，英文增加 “Staff”“1 items”“Permissions”；「运营 / Operator」「仅本人 / Own only」仍在。可选角色从三个改为 `SUPER_ADMIN`、`STAFF`。
15. 达人列表的四行角色矩阵拆成按权限码命名的用例，并补上指定商务、链接和导出。分页用例的登录夹具从运营改为只有 `kol:view` 的子账号。`OWN` 不把商务筛选项传给接口的断言保留。
