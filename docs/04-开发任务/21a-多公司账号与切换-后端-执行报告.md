# 任务 21a：多公司账号与切换（后端）执行报告

## 1. 结论

按提示词与 ADR-022（本任务新建）实现了 P2 模式：账号与公司之间建成员关系 `sys_user_tenant`，角色、岗位模板、数据范围、启停与权限码按公司授予；当前公司保存在 Sa-Token 令牌会话里，登录时选定、可切换；`X-Company-Id` 只用于核对；公司超管的账号管理、商务判定、停用事件按成员关系；平台管理员新增账号查找、加入成员、改姓名邮箱、重置密码、整个账号启停。达人端与平台管理员的业务隔离未改。

本地 `mvn spotless:apply`、`mvn verify`、`mvn verify -Pdocker-it` 全部通过（数字见第 9 节），并在一个由 main 版本写入数据的本地库上验证了迁移与旧令牌兼容。最终以 CI 与审查结论为准，不自行合并。

| 对象 | 变化 |

**锁表风险**：`ALTER TABLE … DROP/ADD CONSTRAINT / DROP COLUMN / RENAME` 与重建唯一索引都会对 `sys_user`、`sys_user_permission` 取 `ACCESS EXCLUSIVE` 锁。两表行数为个位到两位数（账号数），在一个 Flyway 事务中完成，锁持有时间为毫秒级；`DROP COLUMN` 只改元数据。部署时应用尚未启动，不影响在线请求。

## 4. 会话与当前公司

- `CurrentUserContext.CURRENT_TENANT = "currentTenantId"`，与 `credentialVersion` 同在令牌会话。每个请求读一次令牌会话（同时取当前公司和凭据版本），按「账号 + 当前公司」加载 `AccountDTO` 并缓存于请求范围。
- `AccountStore` 改为：`getByUsername`、`getById(id)`（上次公司，仅用于旧令牌与平台管理员）、`getById(id, tenantId)`、`companies(id)`、`recordLogin(id, tenantId, time)`、`recordSwitch(id, tenantId, time)`、`updatePassword`。`AccountDTO` 形状不变，字段含义改为「当前公司中的身份」：`role/dataScope/postTemplate/permissions` 来自成员关系与该公司的权限码；`tenantEnabled` 表示「成员关系与公司都启用」；`status` 是整个账号的启停。
- 每次请求校验账号、成员关系、公司都启用；不满足时只 `logoutByTokenValue` 当前令牌（原来是 `kickout` 整个账号），返回 401 `AUTH_ACCOUNT_DISABLED`。
- `LoginTenantResolver` 改为取 `CurrentUserContext.currentTenantId()`（同一请求缓存）。`StpInterface` 的角色与权限码来自同一缓存，即当前公司。
- 旧令牌（会话里没有 `currentTenantId`）：按账号 `last_tenant_id` 加载并写回令牌会话，不需重新登录。
- `/me`、登录响应的 `UserVO` 增加 `companies:[{tenantId, tenantName, role}]`（按公司名称排序，平台管理员为 `[]`）。`companies` 放在响应 VO 而不放进每次请求加载的 `AccountDTO`，避免每个请求多一次查询（见第 11 节偏离 1）。

## 5. 登录与切换

- 登录流程（验证码 → 锁定检查 → 密码）不变。平台管理员没有当前公司。公司账号：`last_tenant_id` 对应的成员关系仍可用就进入它，否则进入可用公司中名称第一的；都不可用时 401 `AUTH_ACCOUNT_DISABLED`、不签发令牌，并**计入一次登录失败**（见第 11 节偏离 2）。成功后写 `sys_user.last_login_time/last_tenant_id` 与成员关系 `last_login_time`。
- `POST /admin-api/auth/company {tenantId}`：`@SaCheckRole` 只允许 `SUPER_ADMIN`/`STAFF`，平台管理员在角色检查处即 403 `AUTH_FORBIDDEN`（服务层另有同样的检查）；校验目标在本人可用公司中（否则 403 `AUTH_COMPANY_NOT_MEMBER`）→ 更新令牌会话并清掉请求缓存 → 写 `last_tenant_id` 与成员关系 `last_login_time` → 经 `CompanySwitchAudit`（`@AuditLog(module="Auth", action="Switch company")`，参数 `{fromTenantId}`）在**目标公司**记操作日志 → 返回与 `/me` 相同结构。审计采用独立 bean，是因为 `security` 不能依赖 `system.api`（ArchUnit 禁止模块环）。

## 6. `X-Company-Id` 校验

`security.config.CompanyHeaderInterceptor`：注册在「登录与状态检查」拦截器之后、Sa-Token 注解拦截器之前，覆盖 `/admin-api/**`，排除 `/admin-api/auth/**`、`/admin-api/platform/**`、微店 OAuth 公开回调。请求头存在且与会话当前公司不同（含非数字、平台管理员）时抛 409 `AUTH_COMPANY_SWITCHED`，handler 不执行；没带或为空时不校验。头只做比较，绝不参与决定公司。对外复制接口（ADR-019）目前没有 `/admin-api` 下的实现，不受影响。CORS 允许的请求头增加 `X-Company-Id`。

## 7. 账号管理（`/admin-api/system/users/**`）与商务、事件

- 列表：`sys_user_tenant` join `sys_user`，只列本公司成员，排序为成员关系创建时间倒序；每行 `companyCount` 由系统范围的计数查询得到（只返回计数，不返回其他公司数据）。`status`、`lastLoginTime`、`createTime` 为成员关系的值。
- 新建：仍新建账号（`role=MEMBER`、`last_tenant_id=本公司`）+ 本公司成员关系 + 本公司权限码；用户名已存在（包括其他公司的账号）409。
- 修改：角色/模板/范围只改本公司成员关系；姓名或邮箱**与原值不同**且 `companyCount > 1` 时 422 `USER_MULTI_COMPANY_LOCKED`；原值不变时允许改角色（否则多公司账号无法通过该接口改角色）。重置密码在 `companyCount > 1` 时 422。
- 启停：只改本公司成员关系；锁本公司成员关系行；「至少保留一个启用超管」锁本公司启用的超管成员关系；停用 STAFF 发 `StaffDisabledEvent(本公司, userId)`；`CurrentUserContext.logoutCompany` 只结束当前公司是本公司的令牌。
- 权限码读写（`UserPermissionService`、`PermissionChangeApplier`）都带 `tenant_id` 条件。
- `BdUserService`：所有查询经成员关系限定公司，「可用商务」= 成员关系启用 + `STAFF` + `OWN` + 本公司 `kol:edit` + 账号启用；公司取显式公司范围（后台任务、达人自助注册）或登录会话。`lockById` 锁成员关系行。

## 11. 偏离、取舍与遗留

1. **`companies` 不在 `AccountDTO` 里**：提示词写「`AccountDTO` 形状尽量不变，另加 `companies`」。为避免每个请求多一次查询，`companies` 只在 `/me`、登录、切换的响应 `UserVO` 中按需查询；接口约定（4.8）不受影响。
2. **所有公司不可用时的登录**：按 4.3 返回 401 `AUTH_ACCOUNT_DISABLED`（原行为是与密码错误相同的 `AUTH_INVALID_CREDENTIALS`）。这让知道正确密码的人能区分「账号存在但无可用公司」；为不增加试探速度，该结果仍计入登录失败次数。`TenantIsolationIT` 原断言「停用公司后登录与密码错误响应相同」随之改为断言 `AUTH_ACCOUNT_DISABLED` 且无令牌。
3. **迁移时重置公司账号的账号状态**：提示词只要求成员关系的 `status` 取自原 `sys_user`。若保留原 `sys_user.status`，迁移前被公司停用的人会同时变成「整个账号停用」，公司超管重新启用成员关系后仍无法登录。迁移前不存在账号级停用，所以公司账号统一置为启用；平台管理员不变。
4. **停用账号的令牌处理**：原来停用（含公司停用）时 `kickout` 整个账号；现在只结束当前令牌（4.2.3），其他公司的令牌在各自下一次请求时按各自公司判断。
5. **列表中的 `status`**：公司超管看到的是本公司成员关系的状态；整个账号被平台停用时成员关系仍显示启用，但该账号无法登录。「至少保留一个启用超管」也只按成员关系计算，不考虑账号级停用（账号级停用只有平台能做）。
6. **`companyCount`**：统计未删除的成员关系（含已停用的），即「这个人属于几家公司」。
7. **超管列表（任务 20）尚未改写**：20 未合并，`EnabledSuperAdminService` 不在本分支。合入含 20 的 main 后，应改为 `SysUserTenantMapper.listByRole(tenantId, SUPER_ADMIN)` 并过滤成员关系与账号均启用（提示词 4.6.6）。同时检查 20 的 `SystemIT` 改动与本分支的冲突。
8. **范围外发现**（未改）：
   - 规范 04 第 22 行把 `sys_user` 列为「`tenant_id` 可为空」的例外，现在 `sys_user` 已没有 `tenant_id`，措辞可在规范维护时更新；
   - `docs/04-开发任务/README.md` 中 21a 的状态未更新（不在本任务可改文件内）；
   - 部署 Nginx 是否需要放行 `X-Company-Id`：同源部署无需 CORS，未改 `deploy/`。
9. 设计说明书除 4.9 列出的章节外，同步更新了 §2.2 的当前接口表两行，避免与 §6.2 矛盾。
