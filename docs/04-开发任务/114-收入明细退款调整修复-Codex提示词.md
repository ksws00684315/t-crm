## 1. 背景

管理端「达人收入」详情的计佣明细里有一列「退款调整」，说明写的是「退款导致的佣金扣减」。

但收入明细（`CommissionIncomeService` 第 408 行附近）的算法是：

```java
BigDecimal adjustment = released.subtract(row.getAccruedCommissionCny());   // 已释放 − 已计提
```

还没释放的行（冻结中），已释放为 0，所以「退款调整」显示成负的已计提金额。例如一行计提 15.00、还没释放，就显示 −15.00，看起来像被退款扣了 15 元，其实一分钱都没退。任务 112 浏览器验收时发现了这个问题（订单 A 行显示 −¥15.00）。

结算明细在任务 81 已经改成「只有释放后的扣减才算调整」：

```java
// Only a reduction after release is an adjustment (refund or attribution change). The frozen
// remainder (accrued minus released) is not an adjustment (task 81).
BigDecimal adjustment =
    row.getAccruedCommissionCny().subtract(released).min(BigDecimal.ZERO.setScale(2));
```

收入明细没有跟着改。这是任务 112 之前就有的缺陷。

## 2. 要求

1. **先写复现测试**（规范 05「修复缺陷先写复现测试」）：在 `CommissionIncomeServiceTest` 中加一条用例，计提 15.00、已释放 0（冻结中），断言「退款调整」为 0.00。先确认它在现有代码下失败，再改代码。
2. **统一算法**：「退款调整」= min(已计提 − 已释放, 0)，与结算明细一致。
   - 把这段计算提到 commission 模块的一个共用方法里，收入明细和结算明细都调用它（例如放进 `CommissionSettlementRules`），不再各写一遍。
   - 方向 `CREDIT` / `DEBIT` 的判断两处保持一致：先看结算明细现在怎么判断，收入明细照它改。如果发现结算明细在调整为 0 时的方向本身不合理，写进报告，不要顺手改。
3. **顺带处理 L-114 第 ① 项**：两个服务里逐字相同的 `commissionableText(row)` 和链路的 `commissionable(state)`，合并成同一个共用方法。只做合并，取值不变。
4. 用例至少覆盖以下几种，收入明细和结算明细同一组输入、同一组结果：

   | 已计提 | 已释放 | 退款调整 |
   |---|---|---|
   | 15.00 | 0.00 | 0.00 |
   | 15.00 | 15.00 | 0.00 |
   | 12.00 | 15.00（释放后发生退款） | −3.00 |
   | 0.00 | 15.00（释放后全额退款） | −15.00 |

5. **文档**：
