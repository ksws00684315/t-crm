# 任务 152：复制件来源一律从副本复制 — 执行报告

## 1. 结论

任务 151 上线当天发现缺口：客户实际操作模型是「原商品店 A 复制出店 B 的副本后停用店 A，之后都用店 B 的副本作为复制来源」。151 的回溯口径会把来源回溯到店 A 的原商品，被「只从启用店铺取源」规则挡住（`shopUnavailable` → SOURCE_NOT_IN_SHOPS），复制仍然失败。负责人同日决定改为**一律从副本本身复制**：来源是其他达人的登记专属商品时，物理复制源就是该副本（副本所在店铺 + 副本商品 ID），原始商品店铺状态不再影响；新映射 `product_id` 仍指向回溯到的原始商品行。已在 v0.1.17 修复（本任务）。

## 2. 与任务 151 的关系

151 解决「别人的副本链接整批被拒」；152 解决「回溯到的原商品店铺停用时仍复制不了」。同日两次口径修订，均为负责人确认（AskUserQuestion 记录：方案选「一律从副本复制」，推广表无原商品映射选「继续失败」）。

## 3. 主要改动

### 3.1 后端（`product` 模块）

- `CopyJobWorker.processOne` 专属分支重写：其他达人的专属 ID → `product_id` 为空或原商品已删除仍失败（EXCLUSIVE_UNTRACEABLE，负责人决定不放开）；副本所在店铺 `shopUnavailable` 时失败（新文案 EXCLUSIVE_SHOP_DISABLED「该复制件所在店铺已停用，无法作为复制来源」）；否则 `copyFor(job, row, 副本店铺, 副本商品ID, 原商品id)`——物理源为副本本身，登记 `product_id` = 原商品。
- `copyFor` 签名改为 `(job, row, sourceShopId, sourceItemId, productId)`：findSource 路径传原商品三要素，行为逐行不变；shop-item 锁、幂等短路、扣额度、容量计数、链接索引事件全部保留，物理锁键改为副本店铺+副本 ID；专属分支另补拿原商品键锁（先原商品键后副本键，固定顺序无死锁），使「同一原商品的多个物理源」并发转换互斥（审查 P1，见 §6）。
- 删除 151 引入的 `resolveExclusiveSource`（回溯仅剩一次 `selectById`，内联）；`shopUnavailable` 语义改为校验副本所在店铺。
- 不变：同达人幂等分支、convert 入口、额度语义（预扣不返还）、resolve 契约、直连原始链接路径、admin-ui。

### 3.2 测试

- `CopyJobWorkerTest`：U1/U2/U6 重写为从副本复制断言（copy 收到副本店铺+副本 ID、insert 收到原商品 ID、落库 sourceShopId=副本店铺、锁键=副本店铺+副本 ID）；新增 `shouldCopyFromTheCopy_whenOriginalShopDisabled`（店 A 停用仍成功，店 A 行不参与）；新增 `shouldFail_whenTheCopysOwnShopIsDisabled`（EXCLUSIVE_SHOP_DISABLED）；U3/U4（无法追溯）与既有回归保留。
- `ProductLinkIT`：I1 重写断言 `copy(poolShop, "90001", poolShop)`、`source_shop_id=poolShop`；I5 并发用例同步调整；新增 `shouldConvertCopiedLink_whenOriginalShopIsDisabled`（端到端复现店 A 停用场景：UPDATE crm_shop status=0 后转换成功）；I2/I3/I4 保留。

## 6. 子代理审查（2026-11-13，code-reviewer 深度审查）

结论：**修复 1 条 P1 后合并**。防回归清单 6 项（151 的 4 项 + 152 新增 2 项）逐项核实通过；copyFor 三参数化对 findSource 路径逐字段等价；边界（shop_id/kol_id 非空约束、product_id 空检查先于店铺校验、软删过滤、文案与 ADR/D-31 逐字一致）全部核实。

**P1（已修复）**：锁键从原商品键改为副本键后，同一达人的两个并发任务分别提交「副本 ID」与「同一原商品的原始 ID」时不再互斥——双方都通过映射检查、各扣 1 额度、各调一次微店复制，后提交者撞 `uk_crm_kol_item_kol_product` 假失败并留下一个未登记的微店复制件（与生产 2026-11-10 事故、#266 同形）。修复：专属分支在物理锁之外补拿原商品的 shop-item 锁（原商品键先于副本键，顺序固定无死锁），两个并发任务在锁上串行，后到者在锁内命中幂等短路。新增并发回归 IT 固化（`shouldSerializeConvertingCopyAndOriginalOfTheSameProduct`：同达人两令牌分别转换副本与原始 ID，断言两任务完成、恰一条映射、微店复制只调一次）。修复后 `mvn verify` 与 `ProductLinkIT` 22/22 重验通过。

**P2（既有问题，登记不修）**：`findCurrentByWeidianItem` 对同一微店商品 ID 在多家店铺各有当前有效行（异常数据）时 `LIMIT 1` 无排序、取行不确定——151 审查的 L-172 同源问题，已登记 L-172 备注，本任务未扩大范围。

## 7. 已知代价（负责人知情选择）

- 原店启用时也从副本复制，多复制一代；上游副本被清理/删除后，以它为源的后续复制会失败（微店删除错误），已有映射与归因不受影响。
- `product_id` 为空的推广表映射继续失败，客户需先补原商品关联（或重新走复制）才能让这类副本参与转换。
