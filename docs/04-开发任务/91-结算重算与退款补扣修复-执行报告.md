## 3. 现状说明（动手前调查）

- **L-023**：`OrderSettlementFlowService.pull` 原先在任何一笔订单重算失败时返回 false，`OrderSettlementSyncCoordinator.pullIfDue` 只有 `ok` 才前移检查点——一个持续失败的订单让该店检查点永不前移：每 5 分钟重新增量拉取，过了回扫整点每 5 分钟做一次 89 天回扫，重算集合（`first_pulled_at` 晚于检查点的订单）逐轮变大。
- **L-035**：`SettlementBasisCalculator` 原先对 F > C 的差额直接按实付比例 `allocate`，无每行上限；已被 CRM 退满的行分到的份额被佣金引擎按 0 截断，这一部分少扣。
- **L-038**：`OrderCommissionSync.persistOutcome` 原先只在 `settledChange`（新结算时间非空且变化）时写 `settled_time`，从不写 null——确认后变成 `INCOME_MISMATCH` 时旧时间保留。
- **现有字段够不够用（提示词 §2.1 第 5 条）**：`crm_order_sync_failure` 是只追加日志、无订单键，表达不了「待重算」；`crm_order.commission_basis_reason` 是枚举 VARCHAR，不是计数器；`crm_order` 无可复用字段，故新增一列（结论与 ADR-032 修订记录一致）。采用订单列而非新表：`crm_order` 已有 `tenant_id`；该列不进 `OrderDO`，订单同步的整行更新不会覆盖它。

## 4. 主要改动

### 4.1 L-023：失败订单不阻塞检查点

- 迁移 `V202611031000__order_settlement_recompute_failures.sql`：`crm_order` 增列 `settlement_recompute_failures INTEGER NOT NULL DEFAULT 0`，CHECK `>= 0`，列注释写明语义（0 = 无待重算标记；大于 0 = 最近一次结算重算失败，下一轮只重试该订单，成功清零，不参与计佣）。不新增索引：`crm_order` 已有 6 个普通索引（规范 04 上限），按店铺查待重算订单走唯一约束 `uk_crm_order_identity (shop_id, weidian_order_id)` 的 `shop_id` 前缀，每店每个拉取周期一次。
- `OrderMapper` 新增 `listSettlementRecomputePending`（按 shop_id 查带标记订单，`is_deleted = FALSE`，租户条件走拦截器，写法与既有 `listMatchedOrderIdsSince` 一致）、`markSettlementRecomputeFailed`（+1）、`settlementRecomputeFailures`（读计数）、`clearSettlementRecomputeFailed`（清零，带 `> 0` 守卫）。
- `OrderSettlementFlowService.recomputeSince`：重算集合 = 带标记订单 ∪ 新流水订单（`first_pulled_at` 晚于检查点，任务 76 规则不变）。每单独立事务重算；失败在新事务（失败事务已回滚，外层无事务，`TransactionTemplate` 新开）写标记并读回失败次数；成功且带标记的订单在同一事务清零。
- **日志**：首次失败 ERROR 带店铺、本地订单 ID、微店订单号、失败次数与完整堆栈；之后每轮一行（异常只记类名），不再刷屏；不输出个人信息。标记本身写不进去（如数据库不可用）时 pull 返回 false，检查点保留，由持久化流水恢复重算集合（任务 76 兜底不变）。
- `pull` 的返回语义改为「拉取完成且每个失败重算都记上了标记」：微店拉取失败仍抛异常（检查点不动、不重算），翻页上限中止仍抛异常；只有标记写不进去才返回 false。
- `OrderSettlementSyncCoordinator`：`pullIfDue` 逻辑不变，注释同步（检查点在拉取完整成功后前移；单订单重算失败不再挡住它）。

### 4.2 L-035：补扣不被 0 截断

- `SettlementBasisCalculator.allocateRefundGap`（新）：F − C 先按实付比例分摊（复用 `allocate`，尾差给实付最大行、相同取商品行 ID 最小）；每行最多再扣「行基数 − 该行 CRM 成功退款」（下限 0），装不下的部分再按同一比例分给仍有剩余基数的行，循环到分完——补扣总额等于 F − C（到分）。没有截断时每行 take = 首轮份额，与任务 81 的结果逐位相同。
- 全部行扣到 0 仍有剩余（流水退款超过订单实付，数据异常）时：每行恰好扣到 0、不产生负基数，剩余记入 `BasisOutcome.refundGapUnallocated`，由 `OrderCommissionSync` 记 WARN（订单 ID 与未扣金额），不入账不分摊——沿用任务 81「各行有效金额仍不低于 0」与 WARN 的既有规则，未新增台账或状态（ADR-032 2026-11-01 条目已确认该处理）。
- 分摊结果只取决于行的实付、基数与 CRM 退款，`LinkedHashMap` + 稳定排序保证重复计算逐位一致 → 来源指纹与修订号稳定（任务 83 规则），不产生新修订。
- `OrderCommissionSync` 对 `refundGapUnallocated > 0` 记 WARN（订单 ID 与未扣金额）。

### 4.3 L-038：确认失效清空结算时间

- `OrderCommissionSync.persistOutcome`：原因为 `INCOME_MISMATCH`（已有收入明细流水但不再确认）且订单已有 `settled_time` 时置空（SQL `set(null)` + 内存对象同步置空，后续事实行的结算时间一致）。
- 不清空的情况（这些轮次说明不了确认是否有效）：`NO_SETTLEMENT`（本轮没有任何 `INCOME_DETAIL` 流水）、`MULTIPLE_KOLS` / `ALLOCATION_FAILED`（基数算不出）、零基数快捷路径（付款后关闭 `CLOSED`、结算前全额退款 `PRE_SETTLE_REFUND`）、未付款订单。
- 只改订单展示字段；行上结算状态（`UNSETTLED` / `CONFIRMED`）本来就由同一 `BasisOutcome` 得出，计佣与释放不受影响。
