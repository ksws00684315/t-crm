## 1. 背景

客户需求补充 6（2026-10-15）与 10-14 会议确认：

- 商务离职时，超级管理员把他名下的达人转给其他商务，可以**预设生效时间**，例如「几月几号几点生效」；
- 从生效那一刻起，达人的订单和佣金归新商务；之前的仍归原商务，不迁移；
- 商务离职到转移之间产生的数据**归公司**（任何商务都不算）；系统兜底：商务停用时其名下达人自动改为「未分配」；
- 达人对此无感知。

现有实现：`PUT /admin-api/kol/kols/{id}/bd-user` 只能立即更换单个达人的商务（10a 之后为超管专属），并写入商务归属历史 `crm_kol_bd_history`。

## 4. 已定的设计决定（不要自行改变）

### 4.1 迁移 `V202610171800__create_kol_bd_transfer.sql`

新表 `crm_kol_bd_transfer`，字段按设计 §5.2：

- 必有字段：`tenant_id`、`kol_id`、`from_bd_user_id`（可空）、`to_bd_user_id`（可空：转为「未分配」）、`effective_at`、`status`（`SCHEDULED` / `DONE` / `CANCELLED`）、`executed_at`、`cancel_reason`（≤ 255）；
- 加上通用字段；
- 部分唯一索引 `(kol_id) WHERE status = 'SCHEDULED'`：每位达人最多一条预约；
- 索引 `(effective_at) WHERE status = 'SCHEDULED'`。

表与字段都要有中文注释。

### 4.2 发起转移

`POST /admin-api/kol/bd-transfers`，超管专属，请求体：

```json
{
  "kolIds": ["..."],
  "fromBdUserId": "...",
  "toBdUserId": "...",
  "effectiveAt": "2026-11-01T00:00:00Z",
  "reason": "..."
}
```

1. **对象**：`kolIds` 与 `fromBdUserId` 二选一。
   - `kolIds`：最多 500 个；
   - `fromBdUserId`：该商务名下的**全部**达人。
2. **目标**：
   - `toBdUserId` 必须「可作为商务」（与 `BdUserService` 同一规则：同公司、启用、`STAFF`、`OWN`、有 `kol:edit`），否则返回 422 `KOL_INVALID_BD_USER`；
   - `toBdUserId` 为空表示转为「未分配」，即归公司。
3. **生效时间**：`effectiveAt` 可空。
   - 为空或不晚于当前时间：**立即生效**；
   - 晚于当前时间：**预约生效**，最晚一年以内，否则返回 400。
4. **立即生效**：逐个达人在一个事务内锁住达人行。
   - 当前商务与目标相同时跳过；
   - 否则更新 `bd_user_id`，关闭当前归属历史并新增一条，开始时间为当前时间（沿用 `changeBd` 的写法，提取为一个共用方法，`changeBd` 也改为调用它）；
   - 同时写一条 `DONE` 的转移记录；
   - 该达人如有 `SCHEDULED` 的预约，置为 `CANCELLED`，原因为「被立即转移取代」。
5. **预约生效**：为每个达人写一条 `SCHEDULED` 记录，`from_bd_user_id` 取当前商务。
   - 已有预约的达人返回 409 `KOL_TRANSFER_EXISTS`，并列出这些达人的编号；
   - 整批不写入。
6. **响应**：`{immediate: 数量, scheduled: 数量, skipped: 数量}`。
7. **审计**：写入操作日志，参数中包含达人数量、来源、目标、生效时间与原因。

### 4.3 查询与取消

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /admin-api/kol/bd-transfers` | 超管 | 分页；按状态、达人编号、来源商务、目标商务筛选；默认按 `effective_at` 倒序 |
| `DELETE /admin-api/kol/bd-transfers/{id}` | 超管 | 只能取消 `SCHEDULED` 的记录，置为 `CANCELLED`，原因为「手动取消」；其他状态返回 409 `KOL_TRANSFER_NOT_SCHEDULED` |

### 4.4 执行预约

1. 定时任务每分钟运行，按公司执行，持分布式锁 `kol:bd-transfer`（不等待），领取 `effective_at ≤ 现在` 的 `SCHEDULED` 记录，每批 200 条。
2. 逐条在事务内锁住达人行：
   - **当前商务不等于 `from_bd_user_id`**（期间被其他操作改过）：置为 `CANCELLED`，原因为「执行时归属已变化」；
   - **目标商务已不再「可作为商务」**：置为 `CANCELLED`，原因为「目标商务不可用」，记 `WARN`；
   - **否则**：更新 `bd_user_id`；关闭当前归属历史、新增一条，**开始时间为 `effective_at`，不是执行时间**；记录置为 `DONE`，写入 `executed_at`。
3. 时间要合法：如果当前归属历史的开始时间晚于 `effective_at`，则以当前历史的开始时间为准，并在 `cancel_reason` 之外记 `WARN`，保证历史区间不重叠。
4. 订单的所属商务由任务 13 的快照修正任务根据新写入的归属历史更新，本任务不调用订单模块。

### 4.5 商务停用兜底

1. `UserService.updateStatus` 把一个 `STAFF` 账号停用时，在同一事务中发布 `system.api.StaffDisabledEvent(tenantId, userId)`（新增）。
2. `kol` 模块监听该事件（事务提交前），把 `bd_user_id = 该账号` 的全部达人改为未分配：`bd_user_id` 置空，关闭当前归属历史、新增一条 `bd_user_id` 为空的历史，开始时间为当前时间。
3. 来源是该商务的 `SCHEDULED` 预约保留：生效时它们的 `from_bd_user_id` 与达人当前的「未分配」不一致，会按 4.4 第 2 条被取消，所以停用时把这些预约的 `from_bd_user_id` 一并改为空，使其仍能按时把达人转给目标商务。
4. 目标是该商务的 `SCHEDULED` 预约置为 `CANCELLED`，原因为「目标商务已停用」。
5. 账号重新启用时不自动恢复任何达人。
6. 写入操作日志：停用了谁、多少位达人改为未分配。

### 4.6 不在本任务范围

- 管理端的转移界面（以后任务；现有「更换商务」按钮继续调用 `PUT /bd-user`，即立即转移）。
- 订单与佣金的归属（任务 13 的快照与修正；佣金在后续任务）。
- 「进行中的流程转交」：收款账户、提现的审核待办按达人**当前**的商务计算，转移后自然出现在新商务那里，不需要额外处理（设计 §4.13 第 7 条）。在报告中说明已核对。

## 6. 测试要求

| 场景 | 期望 |
|---|---|
| 立即转移 | 按达人列表、按来源商务全部；跳过已是目标的达人；归属历史连续、不重叠；有预约的被取消 |
| 预约 | 写入 SCHEDULED；重复预约整批 409 并列出编号；超过一年 400；未分配为目标 |
| 执行 | 到期执行后，历史的开始时间等于 `effective_at`；执行时归属已变化则取消；目标不可用则取消；锁冲突跳过；同一条不会执行两次 |
| 停用兜底 | 停用商务后其达人全部未分配、历史正确；来源是他的预约之后仍能执行；目标是他的预约被取消；重新启用不恢复 |
| 权限 | 子账号（即使拥有全部权限码）调用转移接口返回 403；跨公司的达人或商务 ID 返回 404 |
| 并发 | 两个请求同时转移同一位达人，结果一致、历史不重叠 |
| 审计 | 发起、取消、停用兜底都有记录 |
