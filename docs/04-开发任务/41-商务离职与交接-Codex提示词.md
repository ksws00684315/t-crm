## 2. 要做的事

### 2.1 后端

- 新增「离职 / 停用计划」（每个账号最多一条未执行的计划）：账号、类型（`RESIGN` 离职 / `DISABLE` 停用）、生效时间、继承商务（可空）、发起人、发起方式（本人 / 管理员）、原因、状态（`SCHEDULED` / `DONE` / `CANCELLED`）、执行时间、执行结果。表结构与命名由你决定，写进设计说明书。
- **本人标记离职**：`POST /admin-api/auth/resignation`、`DELETE /admin-api/auth/resignation`（登录用户本人，与现有 `PUT /admin-api/auth/password` 同属本人操作；仅商务岗位可用），填写预计离职时间（不早于当前时间）与原因；本人只能提交和撤销自己的计划，不能指定继承人。提交后给公司超级管理员发站内消息（任务 20 的通知模块），提醒指定继承商务。
- **管理员标记**（`SUPER_ADMIN`，写审计日志）：
  - 为某个商务账号创建离职或停用计划：生效时间可以是「立即」或未来时间；可选继承商务；
  - 修改继承人、修改生效时间、撤销计划；
  - 列表与用户详情中显示计划。
- **继承商务校验**：同一公司、账号启用、本身没有未执行的离职 / 停用计划、具有接收达人所需的权限（`kol:edit`，数据范围包含本人负责的达人）、不是被离职的本人。不满足时返回明确的错误码。
- **到期执行**（复用现有每分钟运行的定时任务机制，按现有方式加分布式锁）：
  1. 有继承商务：把该商务名下全部达人转移给继承人，**复用任务 16 的转移逻辑**，生效时间为计划生效时间，写归属历史；
  2. 停用账号（与现有「停用」效果相同：退出登录、不能再登录）；
  3. 没有继承商务时，名下达人按现有规则变为无归属（「待更新」）；
  4. 记录执行结果，失败可重试且不重复转移；给超级管理员发站内消息。
  执行时继承人已不满足校验条件的，不转移达人，账号照常停用，消息中说明原因。
- 立即生效的计划在请求内同步执行同样的步骤。

### 2.2 管理端

- 账号菜单增加「申请离职」（只对商务岗位显示）：预计离职时间、原因；已提交时显示计划和「撤销」。
- 用户管理（系统管理—账号）：
  - 列表增加「离职计划」列：无 / 「离职 2026-10-30 18:00（继承：xxx）」/「已离职」；
  - 行操作「更多」中增加「标记离职 / 停用」：类型、生效时间（立即 / 指定时间）、继承商务（下拉只列出符合条件的商务）、原因；已有计划时改为「修改计划」「撤销计划」；
  - 本人提交的离职计划未指定继承人时，在列表中提示「待指定继承人」。
- 文字进语言包；时间按分钟显示。

## 3. 测试重点

- 本人提交 / 撤销、非商务不能提交、管理员创建 / 修改 / 撤销；
- 继承人校验的每个条件；
- 到期执行：有继承人（达人全部转移、归属历史按生效时间）、无继承人（达人变无归属）、继承人失效、执行失败重试不重复转移；立即生效；
- 停用后旧会话失效、不能登录；
- 收款账户待审核在转交后归新商务可见、原商务不可见（07.05）；
- 站内消息发送；公司隔离与权限码。
