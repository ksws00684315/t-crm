# 任务 69 执行报告：提现接口与契约对齐（任务 63 的接口逐字段复核）

## 1. 结论

任务范围内完成。把任务 63 提供的全部提现接口逐字段对照 ADR-032 附录 A/B 与设计说明书 §6.2/§6.3 复核了一遍，后端改为与契约一致（下述改动均经独立复核子代理逐项核实）：

- `finance-tasks` 行字段改为契约的 `applicationNo`/`type`/`amount`（原 `taskNo`/`taskType`/`amountCny`），`bdId`/`bdName` 按提示词允许保留为额外字段；
- 提现行与详情的 `amountCny` 改为契约的 `amount`，`type` 取值由 `COMMISSION_WITHDRAWAL` 改为附录 A 的 `COMMISSION`；
- 列表与详情的收款脱敏快照由平铺 `accountType`/`accountMasked` 改为嵌套 `account`（`AccountSnapshot` 形状，补 `id`、`qrFileId`）；完整收款快照接口同样补 `id`、`qrFileId`；
- 状态历史按附录 A 改为 `{action,at,actor,note}`：`actorName` 改名 `actor`，`actorId` 按契约不再返回（`actorRole` 保留为额外字段）；
- 付款对象按 `PaymentRegistration` 形状把 `voucherFileId` 改名 `voucher`（管理端与达人端详情一致）；
- 详情 `allocations[].orderItemId` 改为附录 A `Allocation.id`；
- 达人端提现列表/详情 `amountCny`→`amount`、`account.accountId`→`account.id`，列表补 §6.3 要求的审核意见 `reviewNote`，详情删除「财务备注」字段（§6.3：财务备注不返回；原实现返回 `"financeNote":null`）；
- 提现条件 `version`、`unverifiedCount` 改为 JSON 数字（与 §6.2 结算配置的 `version` 数字一致；计数不是字符串）；
- 四个分页响应（`finance-tasks`、管理端提现列表、订单级快照分页、达人端提现列表）的 `total` 改为 JSON 数字（`int`），不再被全站 long→字符串序列化。

文档只改了任务提示词第 2 节第 2 条已确认的一处：ADR-032 附录 A `SettlementQuery` 的 `shop` 改为 `shopId`（#112 已按 `shopId` 实现），并在修订记录登记；接口未动。无迁移、无错误码变更、无前端改动。

发现一个跨团队协调事项（不阻塞本任务，见 §9.4）：#116 达人端在 2026-10-26 凌晨的提交里加了一个按任务 63 旧线格式（`amountCny`、`account.accountId`、`version` 字符串）写的临时适配层，与本 ADR 附录 B 相反；本任务按提示词「后端改为与契约一致」执行，#116 合入前应去掉该适配层、直接消费契约字段。

## 9. 偏离与原因

1. **`conditions.version` 与 `unverifiedCount` 改为 JSON 数字。** 契约未定 `version` 的类型；取与 §6.2 结算配置 `version`（任务 67 复核为 JSON 数字）同源同型。`unverifiedCount` 是计数，按提示词「计数为 JSON 数字」。#116 当前类型写的是 `version: string`，其页面直接展示文本，数字不破坏运行时渲染；TS 类型应由前端随契约调整。
2. **列表收款快照改为嵌套 `account` 并补 `id`/`qrFileId`。** §6.2 列表行只写「收款脱敏快照」未定层级；按附录 A `AccountSnapshot`（详情 `account`）对齐列表与详情、管理端与达人端的形状。#112 已不再调用管理端列表接口（其提现页用 `finance-tasks` + 详情），无前端受影响。
3. **`history.actorRole`、`payment.operatorName/operatorRole`、行上 `bdId/bdName` 等额外字段保留。** 附录未列但任务 67 已有「附录未列、保留不删」的先例（`lines[].kolId` 等）；`actorId` 因契约明言「不返回」而删除，与额外字段的取舍不同。
4. **#116 达人端的临时适配层（跨团队协调事项，不阻塞）。** `origin/task/60-kol-portal` @ `f5d400ca`（2026-10-26 01:44）把达人端提现列表/详情的线格式适配成任务 63 旧实现（读 `amountCny`、`account.accountId`，`version: string`），注释自述「Task 63 wire fields differ from the portal presentation model」；这正是提示词 §3 所说「前端已经按另一种写法实现」的过渡态。契约文本（附录 B `WithdrawalRecord.amount` 等）没有因此改变的依据，按提示词「产品方的前端是按契约写的，需要后端改为与契约一致」执行后端对齐；**#116 在合入前应移除该适配层、直接消费契约字段（`amount`、`account.id`、数字 `version`）**，请负责人与产品方确认。
5. **#112 的 `FinanceTask.paused?`/`history?` 为可选字段，后端不返回。** §6.2 的行定义没有这两个字段，操作入口由前端按状态推导；如前端需要，应由负责人修订契约后再加，本任务未擅自扩 API。
6. **#112 `exportWithdrawals` 疑似缺陷（范围外，未改）。** 其非预览分支把列表查询参数 `kolId` 改名成 `kol` 再发导出请求（`{ kol: kolId.trim() }`），契约导出参数是 `kolId`，照此实现导出会丢失达人筛选。属 #112 前端问题，请产品方修正。
7. **#112 `WithdrawalQuery` 在 `6f7cdebd` 中删除了 `bdName` 且未见 `bdUserId`。** 附录 A 的契约参数（`bdUserId`、`kolKeyword`）后端保持不变；前端商务筛选如需恢复按附录 A 传 `bdUserId` 即可，后端无需改动。
