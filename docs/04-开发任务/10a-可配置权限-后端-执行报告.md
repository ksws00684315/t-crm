# 任务 10a：可配置权限（后端）执行报告

## 执行结论

已按 ADR-018 与任务提示词，把公司账号从 `OPERATOR` / `FINANCE` 改为超级管理员加可配置权限的子账号 `STAFF`。平台管理员与超级管理员保留。业务接口改为声明权限码，超管专属接口仍声明 `SUPER_ADMIN`。没有新增依赖。仓库没有 OpenAPI 描述，本任务不补。

## 迁移做法与转换结果

脚本 `backend/src/main/resources/db/migration/V202610171000__configurable_permissions.sql`。已合并脚本未改。

新表 `sys_user_permission` 只追加和删除：`id`、`tenant_id`、`user_id`、`permission_code`、`create_by`、`create_time`。不扩展 `BaseEntity`，没有修改字段和逻辑删除。`sys_user` 增加可空 `post_template`，`CHECK (post_template IN ('OPERATOR','BD'))`。

主键不用序列。三条来源放进同一个 `INSERT ... SELECT`，用 `row_number() OVER (ORDER BY user_id, permission_code)` 从 1 连续编号。空表上不会和之后的雪花 ID（约 10^18）冲突，脚本结束也不留下序列。`ConfigurablePermissionsMigrationIT` 在停在 `202610121800` 的库里插入旧角色后再迁到最新，确认编号为 1 至 43，且 `pg_class` 中没有名称含 `permission` 的序列。

转换包含已逻辑删除的行：

| 原账号 | 转换后 |
|---|---|
| `OPERATOR` + `ALL` | `STAFF`，`post_template=OPERATOR`，运营模板 9 个权限码 |
| `OPERATOR` + `OWN` | `STAFF`，`post_template=BD`，商务模板 13 个权限码 |
| `FINANCE` | `STAFF`，`post_template` 为空，`data_scope=ALL`，财务只读 8 个权限码 |
| `SUPER_ADMIN`、`PLATFORM_ADMIN` | 角色与数据范围不变，不写权限行 |

先按旧角色发权限，再删除 `ck_sys_user_own`、`ck_sys_user_role`，更新角色，然后加上新检查：角色只允许 `PLATFORM_ADMIN` / `SUPER_ADMIN` / `STAFF`；`data_scope = 'ALL' OR role = 'STAFF'`。

唯一索引是 `(user_id, permission_code)`，没有 `tenant_id`。用户 ID 全局唯一，同一用户不会跨公司。另有非唯一索引 `idx_sys_user_permission_tenant_code (tenant_id, permission_code)`，供「谁有 `kol:edit`」查询。

## 接口与权限码对照

| 接口 | 实际声明 |
|---|---|
| `GET /admin-api/kol/kols`、`GET /admin-api/kol/kols/{id}` | `kol:view` |
| 达人新建、编辑、启停；导入模板与导入 | `kol:edit` |
| `PUT /admin-api/kol/kols/{id}/bd-user` | `SUPER_ADMIN` |
| `GET /admin-api/system/bd-users` | `kol:view` |
| `GET /admin-api/product/shops` | `product:view` |
| 店铺新建、编辑、启停 | `SUPER_ADMIN` |
| 原商品列表、详情 | `product:view` |
| 原商品编辑；原商品导入模板与导入 | `product:edit` |
| `PUT /admin-api/product/products/{id}/status` | `product:status` |
| `GET /admin-api/product/kol-items` | `product:view`；服务层对本人范围仍返回 403 |
| 对应关系导入模板与导入 | `product:edit` |
| `GET /admin-api/link/links` | `product:view`；本人范围只能看自己名下的达人 |
| `POST /admin-api/link/index-rebuilds` | `SUPER_ADMIN` |
| `GET /admin-api/integration/weidian/shops` | `product:view` |
| 微店其余变更（应用、自用、授权、检查） | `SUPER_ADMIN`；OAuth 回调仍是公开接口 |
| 用户管理、操作日志、`GET /admin-api/system/permissions`、`GET/PUT .../users/{id}/permissions` | `SUPER_ADMIN` |
| `GET /admin-api/task/tasks/{id}` 与错误文件 | `SUPER_ADMIN` 或 `STAFF`；服务层仍是提交人或超管 |
| 登出、`/auth/me`、修改密码 | `PLATFORM_ADMIN`、`SUPER_ADMIN` 或 `STAFF` |
| 平台管理 | `PLATFORM_ADMIN` |

`/auth/me` 与用户列表的 `UserVO` 增加 `postTemplate`、`permissions`。超管的有效权限是枚举中的全部权限码，平台管理员是空数组，子账号是已授予且仍认识的码，顺序与枚举一致。

创建、编辑用户只接受 `SUPER_ADMIN` 或 `STAFF`。子账号必须带 `postTemplate`。`dataScope` 可省略，省略时用模板默认值（运营 `ALL`，商务 `OWN`）。创建时省略 `permissions` 按模板授予，带了则按给定集合授予。超管创建忽略传入的模板和权限；`OWN` 仍返回 422 `USER_INVALID_DATA_SCOPE`。编辑时子账号保持子账号不重写权限行；从其他角色改成子账号按模板授予；改成超管则删除权限行并清空 `post_template`。不认识的权限码返回 400 `USER_PERMISSION_INVALID`。对非子账号设置权限返回 400 `COMMON_VALIDATION_FAILED`。跨公司用户 ID 返回 404。

权限替换由独立的 `PermissionChangeApplier.apply` 加 `@AuditLog`，参数带修改前后的权限码和数据范围。控制器上的 PUT 不再加 `@AuditLog`，避免记两次。校验失败发生在调用之前，不写这条审计。

## 服务层改动

- `AccountDTO.ownScope()`：`STAFF` 且 `OWN`。`effectivePermissions()`：超管返回全部码，子账号返回已存储且认识的码，其他角色返回空。
- `AccountStoreService` 在读到用户后按 `user_id` 再查一次权限；用户不存在则不查。`CompanyTenantLineHandler` 不忽略 `sys_user_permission`。
- `StpInterface.getPermissionList`：仅 `admin` 登录类型走 `CurrentUserContext.permissionNames`，与账号读取共用请求缓存。其他登录类型返回空，不查库。停用、缺失、公司停用返回空。
- 达人、导入、链接、商品、对应关系里的 `OPERATOR` / `FINANCE` 判断已去掉。商品写入和对应关系导入不再拒绝本人范围。对应关系查询仍拒绝本人范围。更换商务在服务层对本人范围仍返回 403。
- `BdUserService` 不再拒绝本人范围调用方。可选商务是同公司、启用、`STAFF`、`OWN`、拥有 `kol:edit`。两次参数绑定查询，不用 `inSql`。
- `ProductImportService` 用当前用户 ID，不再依赖 `ProductService`。`MappingImportService` 不再依赖 `KolItemService`。

## 测试清单

- `ConfigurablePermissionsMigrationIT`：旧角色转换、删除行也转换、行号主键、无残留序列、唯一索引不含 `tenant_id`。
- `PermissionIT`：`kol:view`、`kol:edit`、`product:view`、`product:edit`、`product:status` 各有一条缺码 403 和一条有码 200；持有全部权限码的子账号访问超管专属接口仍 403；撤销后同一令牌下一次请求 403，审计参数含修改前的码；模板默认值、显式权限、非法码 400、对超管设权限 400、跨公司 404；本人范围在达人列表、对应关系、链接上的行为；平台管理员访问业务接口 403。
- `CurrentUserContextTest.shouldQueryStoreOnce` 同时调用 `permissionNames`，`getById` 仍为一次。
- `AccountStoreServiceTest` 断言已有用户查一次权限、用户不存在不查。
- `ArchitectureTest` 把 `@SaCheckPermission` 视为已声明，并用位于 `com.tcrm.fixtures` 的未声明接口夹具确认规则会失败。夹具不放在 `com.tcrm.admin`，避免被应用扫描注册成真实接口。
- 既有 `KolIT`、`SystemIT`、`TenantIsolationIT` 的创建体改为子账号加岗位模板，商务本人范围用例仍在。

## 因角色改名修改的断言

角色枚举从 `OPERATOR` / `FINANCE` 改为 `STAFF` 后，测试里的角色字面量一并改掉。下面这些不只是改名：

- `AdminMvcSupport.actAs`：`STAFF` + `ALL` 默认带运营模板再加 `kol:edit`，否则原来「运营可以新建达人」的切片测试会 403。`STAFF` + `OWN` 默认用商务模板。超管不存权限行，有效权限仍是全部码。
- 原来「财务只读所以写入 403」的控制器测试，改为缺少对应权限码的子账号，仍期望 403 且不进入服务。涉及达人写入、达人导入、商品编辑。
- `ProductControllerTest.shouldEdit_whenStaffOwnHasProductEdit`：本人范围加上 `product:edit` 时期望 200。原先本人范围编辑商品期望 403。
- `KolItemControllerTest`、`LinkControllerTest`：本人范围查询仍期望 403 或由服务拒绝。
- `KolImportServiceTest`：财务导入 403 改为 `STAFF` + `ALL` 可以提交。
- `KolServiceTest`：财务写入达人一律 403 的参数化测试删除。财务只读改由接口权限码保证。`STAFF` + `ALL` 不是本人范围，由既有的 `shouldChangeStatus_whenAdminDisablesKol` 覆盖。
- `BdUserServiceTest` / `BdUserControllerTest`：本人范围不再 403；没有 `kol:view` 的子账号 403。可选商务要求 `kol:edit`。
- `AuthControllerTest`：`/auth/me` 的角色为 `STAFF`，并断言 `permissions` 是数组。创建用户空请求的字段错误从 5 条变为 4 条，因为 `dataScope` 不再必填。
- `SecurityConfigurationTest`：角色列表为 `STAFF`；`admin` 类型读取权限，`kol` 类型不查库。
- `PlatformRequestValidationTest`：公司角色校验的合法值从 `FINANCE` 改为 `STAFF`。
- `SystemIT.shouldRejectProtectedLists_whenRoleIsStaff`：原先运营和财务各测一遍，两者都变成子账号后只保留一次，用户列表和操作日志仍期望 403。创建子账号带商务模板和 `OWN`。降级超管的请求从 `FINANCE` 改为 `STAFF` + 运营模板 + `ALL`。编辑请求从 `OPERATOR` + `OWN` 改为 `STAFF` + 商务模板 + `OWN`。至少保留一个超管的 200/422 断言未改。
- `SystemIT.shouldRequireTenantIdOnBusinessTables`：期望列表增加 `sys_user_permission:NO`（`tenant_id` 非空）。
- `TenantIsolationIT`：降级、跨公司编辑和用户名冲突的请求体改为子账号加岗位模板。`createUser` 仍不带模板，因为它创建的是超管。
- `KolIT.createBd`：`OPERATOR` + `OWN` 改为 `STAFF` + 商务模板 + `OWN`，创建出的账号仍有 `kol:edit`，可继续当负责商务。

## 偏离与遗留

- 规范 04 要求业务唯一索引包含 `tenant_id`。提示词明确要求唯一索引为 `(user_id, permission_code)`，按提示词实现，并加了 `(tenant_id, permission_code)` 非唯一索引。
- 提示词第 8 节禁止改 `admin-ui/`。第 4.5 节要求补错误码文案，否则 `admin-ui` 的错误码映射测试会失败。只改了 `zh-CN.ts` 与 `en-US.ts` 中的 `USER_PERMISSION_INVALID`（新增）、`USER_INVALID_DATA_SCOPE`、`KOL_INVALID_BD_USER`。
- 商品写入、对应关系导入不再因本人范围或财务角色拒绝。只读由权限码保证。
- 可选商务列表不再对本人范围返回 403。
- 管理端界面、尚未实现的新功能接口（注册链接、复制令牌、资金、看板）不在本任务。这些权限码已登记，没有对应接口。
- 两个岗位模板都不含 `commission:freeze`。
- 项目没有 OpenAPI，接口约定写在设计说明书 §2.2、§6.2 和本报告。
