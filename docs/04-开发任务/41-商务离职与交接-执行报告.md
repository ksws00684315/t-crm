## 需求落地

### 数据模型

新表 `sys_user_departure_plan`（`V202610221400__create_user_departure_plan.sql`）：

| 字段 | 说明 |
|---|---|
| `user_id` | 被标记的商务账号 |
| `plan_type` | `RESIGN` 离职 / `DISABLE` 停用 |
| `effective_at` | 生效时间（UTC），到点由定时任务执行 |
| `heir_user_id` | 继承商务；空表示达人生效后转为未分配 |
| `initiator` | `SELF` 本人 / `ADMIN` 管理员 |
| `reason` | 原因（≤ 255 字） |
| `status` | `SCHEDULED` / `DONE` / `CANCELLED` |
| `executed_at`、`result`、`result_message` | 执行时间与结果（`TRANSFERRED` / `UNASSIGNED` / `HEIR_INVALID`）与说明 |

索引：`uk_sys_user_departure_plan_scheduled (tenant_id, user_id) WHERE status = 'SCHEDULED'` 保证一个账号只有一条未执行计划（并发插入靠它兜底 409）；`idx_sys_user_departure_plan_due (effective_at, id) WHERE status = 'SCHEDULED'` 供任务取到期记录；`idx_sys_user_departure_plan_user` 供用户列表批量取最新计划。表与全部字段有中文注释。

`V202610221401__extend_notification_type_for_departure.sql` 把 `ck_crm_notification_type` 扩到两种新消息类型（原约束名以此为准，不是默认生成的 `crm_notification_type_check`）。

### 后端接口

本人（`STAFF` 登录态，`/admin-api/auth/resignation`）：`GET` 看自己的未执行计划、`POST {plannedLeaveAt, reason?}` 提交、`DELETE` 撤销；只有本人提交的计划能被本人撤销（管理员建的计划 403 `DEPARTURE_SELF_SUBMITTED_ONLY`）。

超管（`/admin-api/system/users`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/{id}/departure-plan` | 该账号未执行计划，没有则 `data` 为空 |
| POST | `/{id}/departure-plan` | `{type, effectiveAt?, heirUserId?, reason?}`；`effectiveAt` 空或已过则本请求内立即执行 |
| PUT | `/{id}/departure-plan` | 改继承商务、生效时间、原因 |
| DELETE | `/{id}/departure-plan` | 撤销 |
| GET | `/departure-heirs` | 可选继承商务（排除本人与已有计划的人） |

写操作都带 `@AuditLog`（`Schedule departure` / `Edit departure plan` / `Cancel departure plan`），本人提交与撤销记在 `Auth` 模块。新增错误码：`DEPARTURE_NOT_BD_ACCOUNT(422)`、`DEPARTURE_INVALID_TIME(422)`、`DEPARTURE_PLAN_EXISTS(409)`、`DEPARTURE_PLAN_NOT_SCHEDULED(409)`、`DEPARTURE_SELF_SUBMITTED_ONLY(403)`、`DEPARTURE_INVALID_HEIR(422)`。

### 继承商务校验

同一个方法 `heirProblem()` 供「建计划 / 改计划 / 执行」三处复用：不能是本人；必须启用、`STAFF`、数据范围 `OWN`、具备 `kol:edit`（`BdUserDTO.usable()`，与任务 16 的转移口径一致）；自己不能已有未执行计划。执行时再判一次，失效则**不转移但照常停用**，结果写 `HEIR_INVALID` 并在消息里说明原因。

### 到期执行

`DeparturePlanJob`（`@Scheduled(cron = "0 * * * * *", zone = "UTC")`，分布式锁 `system:departure-plan`）遍历启用公司，`TenantScope.runCompany` 内 `executeDueBatch()` 每批最多 200 条；每条独立事务：`FOR UPDATE` 锁计划行并重读状态（双实例不重复执行、重试不重复转移）→ 校验继承人 → 发布 `DepartureHandoverEvent`（`@TransactionalEventListener(BEFORE_COMMIT)`，由 `kol` 模块 `BdTransferService.handoverAll()` 转移仍属该商务的达人、写归属历史与 `DONE` 转移记录、取消这些达人原有的预约转移）→ `users.disableMembership()` 停用成员关系并发布 `StaffDisabledEvent` → 写 `DONE` + 结果 + 审计 → 发布 `DeparturePlanExecutedEvent`。整段回滚则计划保持 `SCHEDULED`，下一分钟重试。

顺序是关键：交接事件在提交前、且早于停用事件，所以「先转移、后停用」，`StaffDisabledEvent` 的原有兜底（达人转未分配）此时已无达人可处理，不会重复转移。

### 站内消息

`DEPARTURE_PLAN_SUBMITTED`（提交时提醒超管指定继承人）与 `DEPARTURE_PLAN_EXECUTED`（执行结果）。参数只放姓名、类型、生效时间、继承商务显示名与结果码，不含个人信息；`NotificationParamsCodec` 负责写读，`NotificationListener` 用 `AFTER_COMMIT` 并吞异常（消息失败不影响业务）。

- 用户管理列表新增「离职计划」列：未设置 / 「离职 · 2026-10-30 18:00 · → 张三」/ 「待指定继承人」/ 「已离职」「已停用」，原因与执行结果放悬停提示。
- 商务行（子账号且数据范围本人）的「更多」里新增「标记离职」（已有计划时「修改离职计划」）与「撤销离职计划」；对话框含类型、立即/指定时间、继承商务下拉（含「不指定（转为未分配）」）、原因，并注明浏览器时区。

## 不做与边界

- 提现、预付待办交接（属佣金结算，提示词第 5 节明确不做）；推广表商务名同步（推广表不入库，不适用）；商务业绩统计（看板任务 42 起）。
- 本人提交时不指定继承人，由超管在执行前补；执行时若仍无继承人，按现有规则转未分配。
- 停用复用现有 `disableMembership` 语义（结束本公司会话、不能再登录）；其他公司的成员关系与达人不受影响。
- 执行前若计划目标已不再是商务（例如被提升为超管），计划作废为 `CANCELLED` 并写明原因，不停用也不交接——计划只为商务而设，同时避免绕过「至少保留一个启用超管」的保护。
- `PUT /{id}/departure-plan` 是整体替换：请求里不带 `heirUserId` 会清空继承人；管理端对话框每次提交完整表单，直接调接口时需注意。
