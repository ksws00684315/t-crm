## 0. 本项目现状（对照文档与源码）

以下内容对照设计说明书 §3.4、ADR-014、ADR-018，以及源码中的租户组件（`CompanyTenantLineHandler`、`LoginTenantResolver`、`TenantScope`）。

| 维度 | 当前做法 |
|---|---|
| 隔离模型 | 共享库 + 业务表 `tenant_id`；MyBatis-Plus `TenantLineInnerInterceptor` + `CompanyTenantLineHandler` 自动过滤；取不到公司则抛 `MissingTenantException` |
| 租户上下文来源 | **只从登录态取**：管理员每次请求重读账号的 `tenant_id`（`LoginTenantResolver` → `CurrentUserContext`）；后台任务用 `TenantScope.openCompany` / `openSystem`；**接口不接受前端传入公司 ID** |
| 用户—公司关系 | 管理员账号只属于一家公司（`sys_user.tenant_id`）；用户名全系统唯一，登录页不选公司；同一人在多家公司工作则各开一个账号。平台管理员 `tenant_id` 为空，只能管公司本身 |
| 达人端 | 同一邮箱可在多家公司各有一行；登录时若匹配多家则选公司；换公司需重新登录（ADR-014 明确放弃「一个全局身份 + 登录后切换」） |
| 平台管理员 | 不进入业务数据；不能「冒充」某公司看业务 |
| 权限（ADR-018） | 公司内：`SUPER_ADMIN` + 可配置权限码的 `STAFF`；权限按**账号**授予，尚未按「成员关系 × 公司」建模 |

结论：本项目已具备「共享库字段隔离 + 登录态注入租户」的底座，但**管理端没有「一个账号属于多家公司 + 界面切换」**；达人端是「登录时选公司 / 换公司重登」。

## 2. 实现模式归纳（2～4 种）

### 模式 P1：账号单归属 + 登录态定租户（本项目现状）

- **做法**：一账号一公司；`tenant_id` 存在用户行；请求不接受公司 ID；插件从登录态取公司。
- **优点**：越权面最小；与 ADR-014「接口不接受公司 ID」一致；实现简单。
- **缺点**：一人多公司要多账号；管理端无法一键切换；达人已用「登录选公司」但管理端没有对等能力。
- **适用**：租户数少、同客户内强隔离、运维愿接受多账号（本项目当前前提）。

### 模式 P2：成员多归属 + 切换时换发「组织作用域」会话（IdP / 推荐演进）

- **做法**：全局用户 + `membership(user, tenant, roles/permissions)`；切换时服务端校验成员关系，**签发新令牌或更新服务端会话中的 currentTenantId**（Auth0/WorkOS/Clerk 同构）；客户端**不得**仅靠改 Header 改变租户。
- **优点**：一个登录身份；权限按公司独立；与主流 SaaS 一致；审计清晰（每次切换可记日志）。
- **缺点**：要改用户模型、登录/会话、权限加载；多标签页需约定（同会话共享当前租户，或每标签独立会话）。
- **适用**：同一自然人常跨多家公司办公，且希望「切一下就改数据范围」。

### 模式 P3：成员多归属 + 请求头传租户 + 后端校验归属（Jeecg / 部分国产框架）

- **做法**：前端每次带 `X-Tenant-Id`；后端校验「该用户是否属于该租户」后写入 ThreadLocal。
- **优点**：实现快；切换不必换 token。
- **缺点**：Header 易被篡改，**校验缺失即串租**；与本项目「接口不接受公司 ID」直接冲突；缓存/审计若未带租户更危险。
- **适用**：已有完善归属校验与网关加固的中后台；**不推荐**在未改安全原则时直接套到本项目。

### 模式 P4：平台「访问租户」（芋道 visit / RuoYi-Plus dynamic）

- **做法**：账号仍属原租户；额外权限允许临时把上下文切到目标租户（visit 头或 dynamic Redis）。
- **优点**：支持客服/平台运维进租户排查；与普通「员工多公司」可分开授权。
- **缺点**：写操作风险高；个人接口与 visit 冲突；审计与只读策略必须显式。
- **适用**：平台运维进客户租户；**对本项目「平台管理员看不到业务」是反向需求**，仅当负责人改变该原则时才考虑。

## 3. 对本项目的建议

### 3.1 是否需要「一个账号属于多家公司 + 界面切换」

| 端 | 建议 |
|---|---|
| **管理端** | **先向负责人确认真实痛点**：是否已有「同一运营/商务同时服务多家公司、且不愿维护多套账号密码」的诉求。若痛点不成立，**维持 P1** 成本最低，且与 ADR-014 一致。若痛点成立，再上 **P2（成员关系 + 换发/更新会话中的当前公司）**，不要上裸 Header（P3）。 |
| **达人端** | **维持现状**（登录选公司 / 换公司重登）。ADR-014 已论证：达人全局身份会导致 A 公司停用/改密牵连 B 公司。界面切换会削弱「各公司账号分开」的产品承诺。 |
| **平台管理员** | **继续禁止进入业务数据**（保持 ADR-014）。若将来要排障，单独做 **只读、强审计的 P4**，不要复用普通员工切换。 |

### 3.2 推荐模式（若管理端要做切换）

**推荐：模式 P2（成员多归属 + 服务端会话内 `currentTenantId`，切换时重载权限）**，技术上可对齐 RuoYi-Plus「动态租户」的「服务端权威」思路，但**不要**默认信任 `X-Tenant-Id`；更接近 WorkOS/Clerk「切换 = 更新组织作用域会话」。

不推荐：P3 裸 Header；不推荐把平台 visit（P4）做成日常切换。

### 3.3 若采用 P2，主要改动点（仅规划，本调研不改代码）

| 区域 | 改动要点 |
|---|---|
| 数据表 | 新增成员关系表，例如 `sys_user_tenant(user_id, tenant_id, …)`；权限表从「仅 user_id」扩展为「user_id + tenant_id」或「membership_id + permission_code」；`sys_user.tenant_id` 改为「默认/上次公司」或废弃单字段归属 |
| 登录与会话 | 登录成功后写入 `currentTenantId`（Sa-Token session / Token 扩展数据）；`/auth/me` 返回当前公司与可切换公司列表 |
| Sa-Token | 切换接口：校验成员关系 → 更新 session 中的 currentTenant → **按该公司重载权限码**（对接 ADR-018 的 `StpInterface`）；可选踢掉其它标签的旧上下文或广播 storage 事件 |
| 权限码 | 权限授予按公司；切公司后菜单/按钮随 `/auth/me` 变；超管专属仍按角色 |
| 管理端 UI | 顶栏公司下拉；切换后刷新路由/缓存；多标签约定（同浏览器同 session 则共享当前公司，避免一标签 A 公司、一标签 B 公司共用一个 token） |
| 定时任务与审计 | 继续用 `TenantScope`；操作日志必须记 `tenant_id` + 切换事件；禁止任务线程继承错误 ThreadLocal |
| 明确不做 | 业务 API 仍**不**接受 body/query 里的公司 ID；Header 若保留仅作调试且必须以 session 为准 |

### 3.4 与 ADR 的冲突（逐条）

#### 相对 ADR-014

| ADR-014 原文要点 | 冲突说明 |
|---|---|
| 「当前公司只从登录态取；任何接口都不接受前端传入公司 ID」 | P3（Header 租户）直接冲突。P2 若把「当前公司」放进**服务端会话**且切换接口只接受「目标公司 ID + 成员校验」，可解释为「仍从登录态取」，但需**修订 ADR 措辞**，明确允许「登录态内切换当前公司」。 |
| 「管理员按全系统唯一的用户名确定公司」 | 多归属后，用户名不再唯一映射公司；需改为「用户名定人，成员关系定可进入的公司」。 |
| 「同一个人为多家公司工作时，在每家各开一个账号」 | 管理端若合并为一账号，则**废除此条对管理端的约束**；达人端若保持多账号则这条仍成立。 |
| 「达人一个全局身份 + 登录后切换」被列为放弃方案 | 达人端引入界面切换会与该放弃理由冲突；**建议达人端不引入**。 |
| 「平台管理员看不到业务数据」 | P4 式「进入租户」冲突；日常切换也不应赋予平台管理员业务可见性。 |

#### 相对 ADR-018

| ADR-018 原文要点 | 冲突说明 |
|---|---|
| 子账号权限在 `sys_user_permission(user_id, permission_code)` | 一账号多公司时，同一权限码在不同公司可能不同，**必须改为按公司（或 membership）授权**，否则切公司后权限串用。 |
| 「每次请求重读账号，改权限立即生效」 | 仍可坚持，但重读时必须带 **currentTenantId** 过滤权限集。 |
| 岗位模板「运营/商务」预填 | 模板预填要按**目标公司**执行；跨公司复制权限需产品确认。 |
| 超管专属操作不可勾选 | 切到 B 公司后，是否仍是 B 的 `SUPER_ADMIN` 取决于成员角色建模；不能假设「全局超管」。 |

## 4. 风险与待负责人决定的问题

### 4.1 风险（若引入管理端切换）

1. **串租**：任何「客户端声明租户」路径（Header/本地缓存）在缺校验时都会串数据。
2. **权限串用**：权限表不带 `tenant_id` 时，A 公司勾选的码在 B 公司生效。
3. **缓存键**：Redis/本地缓存未带 `tenantId` 导致读到他家数据或脏配置。
4. **异步与定时任务**：线程池不继承 `TenantScope`（本项目已注明 holder 不继承）；切公司后投递的异步任务若捕获了旧公司会写错库。
5. **多标签页**：同一 token 下两标签各显示一家公司，实际以服务端 currentTenant 为准，易造成「界面撒谎」。
6. **审计与资金**：切公司后的打款/审批若审计未记 `tenant_id` + 切换轨迹，事后无法追责。
7. **达人产品承诺**：管理端合并账号容易被要求「达人也合并」，需坚持 ADR-014 对达人的放弃理由。

### 4.2 待负责人决定

1. 管理端是否存在「一人多公司、必须单账号切换」的真实需求？预计有多少人、多少公司？
2. 若需要：采用 **P2** 还是继续 **多账号（P1）**？
3. 达人端是否**明确永不做**登录后切换？（建议：永不做）
4. 平台管理员是否永远不能看业务？若将来要排障，是否接受「只读 + 全量审计」的临时进入（P4）？
5. 切换后是否允许写操作，还是仅浏览？
6. 多标签策略：强制单当前公司，还是允许每标签独立会话（实现成本高）？
7. 是否愿意修订 ADR-014 / ADR-018 及相关设计说明书章节后再开发？
8. 权限模型：一账号在不同公司是否可以分别是「超管 / 子账号」？

## 6. 一句话结论

**管理端若无强需求则保持「一账号一公司」；若有需求则采用「成员关系 + 服务端会话切换当前公司并重载按公司权限」（P2），达人端与平台管理员不引入业务侧切换；任何「只改请求头」的方案与现行 ADR-014 冲突且风险最高。**
