# Google 与微店 API 能力调研报告

> 调研日期：2026-09-30（同日补充：已查阅微店开放平台官方接口文档，见第八节。第一、四节中与第八节冲突的结论，以第八节为准）
> 方法：官方文档查阅 + 公开资料检索 + 对需求文档所附两份参考表格的链接实测分析
> 局限：微店开放平台的完整接口文档需登录开发者账号才能查看，本次只能依据公开信息判断。标注"推断"的结论需在拿到客户开发者账号后验证。

---

## 一、结论速览

| 客户想要的能力 | 可行性 | 一句话结论 |
|---|---|---|
| 自动为每位达人创建 Google 表格 | ✅ 可行 | 需要 Google Workspace 共享云端硬盘，或者让服务账号代表某个员工账号操作（域委派） |
| 每张表批量写入 2 万条链接 | ✅ 可行 | 单表约 10 次请求，100 张表约 15～20 分钟 |
| 表格公开分享 / 指定人可见 | ✅ 可行 | Drive API 标准能力 |
| 定时回写点击、订单数据到表格 | ✅ 可行 | 配额充足，每小时一轮没问题 |
| 系统中转链接 + 点击统计 | ✅ 可行 | 完全在自己系统内实现，不依赖第三方 |
| 通过微店 API 同步订单 | ⚠️ 有条件 | 只能读取**客户自己店铺**的订单；别人店铺的订单拿不到 |
| 调用微店接口批量生成达人专属链接 | ⚠️ 没有直接接口 | 推广员的分享链接也许可以按规则批量拼接，需要实测（见第八节） |
| 在微店链接上加 `kol_id`、`track_id`，并在订单中取回 | ❌ 不可行 | URL 上加的自定义参数不会写进微店订单 |
| 从微店订单中取回推广员（达人）身份 | ⚠️ 有条件可行 | 订单详情里有推广员字段，也可以通过粉丝接口查到买家绑定的推广员（见第八节） |
| 用达人专属优惠码归因 | ⚠️ 有条件可行 | 订单会返回优惠券 ID，也有创建优惠券的接口；前提是买家直接在微店下单 |
| **按达人准确归因订单** | ⚠️ **要换思路** | 真实交易发生在**代购平台**，归因应该依据代购平台的邀请码和订单数据 |

**最关键的发现**：需求文档假设"海外用户点链接 → 在微店下单"，但两份参考表格的链接显示，实际路径是"海外用户 → **代购平台**（Litbuy / Kakobuy）→ 代购平台再去微店下单"。这直接决定了订单归因方案怎么做，必须先跟客户确认。

## 二、关键发现：真实交易走的是代购平台

### 2.1 参考表格的链接实测

我们导出了需求文档附带的两份表格，统计了其中的全部超链接：

| 表格 | 链接总数 | 链接去向 | 链接格式 |
|---|---:|---|---|
| 参考达人 @cnmastair 的表格（标题"Best Litbuy spreadsheet"） | 1,243 | **100% 指向 Litbuy 代购平台** | `litbuy.com/product/weidian/{微店商品ID}?inviteCode=CNMASTAIR` |
| 客户自己的表格（East Maple） | 942 | **909 条指向 Kakobuy 代购平台**，33 条是微店直链 | `kakobuy.com/item/details?url={微店商品链接}`，其中 15 条带 `affcode=globereps` |

还有两个细节：

- 参考达人的 1,243 条链接中，有 **212 条带的是别人的邀请码（`WICK`）**。说明这类表格常常是从别人那里复制来的，推广码很容易串。这也正好是客户想用系统解决的痛点。
- 客户自己表格里的 Kakobuy 链接**大部分没有带推广码**，也就是说目前这些流量没有被归因。

### 2.2 为什么海外用户不在微店直接下单

公开资料显示：在微店购买需要中国手机号、支付宝账号和中国收货地址，不接受外国信用卡，也不发国际快递。海外买家只能通过代购平台购买，由代购平台在国内下单、收货、质检后再转运出国（来源：[KakoBuy 微店链接教程](https://kakoguide.com/guides/weidian-link-tutorial)）。

### 2.3 这对需求文档的影响

| 需求文档的设计 | 实际情况 |
|---|---|
| 优先级 1：订单里带达人 ID | 微店订单的买家是代购平台的采购账号，订单里没有达人信息 |
| 优先级 2：达人专属优惠码 | 海外用户在代购平台付款，接触不到微店优惠码 |
| 优先级 3：订单里带 track_id | URL 参数不会进入微店订单；而且代购平台下单时用的是它自己的链接 |
| 微店"推广员"分销模式 | 推广员按"买家账号"永久绑定（[微店说明](https://www.weidian.com/blog/details/472.html)）。代购平台只用少数几个采购账号下单，所有订单会绑到第一个推广员身上，无法区分达人（**推断**） |
| "微店商品不存在"报错 | 常见原因：商品已下架或换了 ID、短链没有展开，或者在海外/非微店环境下直接打开（[来源](https://kakoguide.com/guides/weidian-link-tutorial)）。走代购平台链接可以绕开这个问题 |

**结论：如果买家通过代购平台下单，在微店这一侧无法按达人准确归因，归因要放在代购平台那一侧做。如果买家直接在微店下单，可以用微店推广员功能归因（见第八节）。**

## 三、Google 能力详细评估

### 3.1 能力清单（均为官方 API 标准能力）

| 能力 | 接口 | 结论 |
|---|---|---|
| 复制模板表格（保留图片、格式、分类） | Drive API `files.copy` | ✅ |
| 批量写入链接 | Sheets API `values.batchUpdate` | ✅ |
| 公开只读分享 / 指定邮箱分享 | Drive API `permissions.create` | ✅ |
| 定时回写统计数据 | Sheets API `values.batchUpdate` | ✅ |
| 单表容量 | 上限 1000 万个单元格；2 万行 × 11 列约 22 万个 | ✅ 远低于上限 |

### 3.2 配额测算

官方配额（[Sheets API Limits](https://developers.google.com/workspace/sheets/api/limits)）：

- 每个项目每分钟 300 次读、300 次写
- 每个用户每个项目每分钟 60 次读、60 次写
- **没有每日上限**
- 建议每次请求不超过 2MB，单次请求 180 秒超时
- 超限返回 429，需要指数退避重试

| 场景 | 请求量 | 耗时 |
|---|---|---|
| 初始化 1 张表（2 万行，每 2000 行一批） | 约 10 次写 | 不到 1 分钟 |
| 初始化 100 张表 | 约 1000 次写 | 按"单用户每分钟 60 次"算，**约 17 分钟** |
| 每小时回写 100 张表的统计列 | 约 100～300 次 | 每轮 2～5 分钟 |

**注意**：服务账号算作一个"用户"，所以真正的瓶颈是每分钟 60 次写，而不是 300 次。系统要做全局限流队列。

### 3.3 必须注意的两个坑

**坑 1：服务账号没有存储空间**

服务账号自己的 Drive 存储配额通常是 0，直接用它建表会报错 "Service Accounts do not have storage quota"（[Fivetran 说明](https://fivetran.com/docs/activations/destinations/available-destinations/google-drive/troubleshooting/service-accounts-storage-quota)）。解决办法：

- **推荐**：开通 Google Workspace，建一个"共享云端硬盘"，把服务账号加为成员，表格建在共享云端硬盘里。Business Starter 套餐自 2024 年 9 月起已支持共享云端硬盘（[Google 官方公告](https://workspaceupdates.googleblog.com/2024/08/shared-drive-access-business-starter.html)）。
- 或者：配置域范围委派，让服务账号代表某个 Workspace 用户操作。
- 不推荐：用个人 Gmail 走 OAuth 授权。授权令牌会失效，需要人工重新授权，维护麻烦。

**坑 2：Google 内容政策风险（业务风险，技术上无法规避）**

Google 的滥用政策适用于 Drive / Sheets，明确禁止"销售或推广仿冒商品"。违规的后果包括限制文件访问、删除内容、限制或终止账号（[Google 滥用政策](https://support.google.com/docs/answer/148505?hl=en-GB)）。

参考表格中的商品含大量国际品牌名称，存在表格被 Google 限制访问、甚至整个 Workspace 账号被封的风险。一旦发生，100 张表会同时失效。

系统层面能做的是降低损失，但无法消除风险：

- 所有链接和数据以自己的数据库为准，表格只是展示载体，可以一键重建
- 表格里放的是自有域名的中转链接，表格被封后，只要换新表格，原来的链接依然有效
- 建议客户评估：是否把 Google 表格替换或补充为**自建的商品展示页**（自有域名，不受 Google 政策约束）

### 3.4 国内网络限制

国内服务器无法访问 Google API。本项目部署在美国服务器，这个问题**已经解决**。开发阶段在国内本地调试时，需要通过代理访问 Google。

## 四、微店能力详细评估

### 4.1 微店开放平台现状

| 项目 | 情况 | 来源 |
|---|---|---|
| 应用类型 | 自用型、服务型、移动型、官方型 | 公开资料 |
| 自用型权限 | **只能读写自己店铺的商品和订单**，不能为其他店铺服务 | 公开资料 |
| 申请方式 | 用微店账号登录开放平台 → 创建应用 → 填写 IP 白名单；需要订单推送的话还要配置回调地址 | 公开资料 |
| 订单接口 | 有，例如 `vdian.order.list.get`、`vdian.order.get` | [第三方 SDK](https://github.com/yanyingwang/weidian_open) |
| 优惠券接口 | 有：创建店铺优惠券、查询优惠券列表、查询使用报表 | 官方文档（见第八节） |
| 分销 / 推广员接口 | 有推广员查询接口（粉丝、关系链），**没有**生成推广链接的接口 | 官方文档（见第八节） |
| 从本机访问开放平台域名 | `open.weidian.com`、`api.vdian.com` 均可访问（HTTP 200，约 0.25 秒） | 实测 |

### 4.2 与客户需求逐条对照

| 需求 | 结论 | 说明 |
|---|---|---|
| 同步订单 | ⚠️ | 前提是**商品在客户自己的微店里**。客户表格里的链接分布在大量不同的店铺（`shopXXXX.v.weidian.com`），如果这些店铺不属于客户，就拿不到它们的订单 |
| 批量生成达人专属微店链接 | ❌ | 没有公开接口。需求文档提到的"微店复制工具"，可能是指分销的"铺货"功能（把供货商的商品上架到分销商自己的店铺）。如果是这个意思，就相当于给每位达人开一家分销店铺——100 家店、每家 2 万商品，而且每家店都要实名开店，运营成本很高 |
| 订单带回达人 ID | ❌ | 见第二节 |
| 优惠码归因 | ❌ | 见第二节 |

## 五、可行的归因方案

归因能否做准，取决于**客户能拿到哪一方的订单数据**。

| 方案 | 做法 | 准确度 | 前提 | 开发量变化 |
|---|---|---|---|---|
| **A. 代购平台邀请码归因（推荐）** | 每位达人在代购平台（Litbuy / Kakobuy 等）拥有自己的邀请码；表格链接 = 中转链接 → 代购平台商品页 + 达人邀请码；订单从代购平台后台导出（或通过其接口）导入系统，按邀请码归属 | 高 | 客户是代购平台本身，或与代购平台合作，能拿到**带邀请码的订单数据** | 与现有报价基本持平：微店接口换成代购平台数据导入 |
| B. 一位达人一家微店分销店铺 | 为每位达人开分销店铺并铺货，订单按店铺归属，通过微店接口拉单 | 高 | 能开 100 家实名店铺；铺货有接口或可批量操作；客户能授权访问这些店铺 | 大幅增加，而且运营成本很高 |
| C. 仅点击统计 + 人工对账 | 系统只统计各达人的点击量，订单由人工对账 | 低 | 无 | 最小 |

**我们的建议**：方案 A。从参考截图看（"Cooperative alliance" 后台里的子域名、跳转次数、合并包裹、达人提现、邀请数据等），这很可能就是某个代购平台的达人合作后台。客户的业务模式大概率是"代购平台 + 达人分销"，而不是"微店卖家 + 达人分销"。

无论选哪个方案，下面这些都与订单来源无关，可以照常开发：中转链接、点击统计、表格自动生成与回写、达人端、佣金结算。

## 六、需要客户立即回答的问题（决定方案）

1. **你们是什么角色？** 微店卖家、代购平台本身，还是代购平台的合作方（商务/渠道）？
2. **表格里的购买链接最终要跳到哪里？** 微店直链，还是某个代购平台（Litbuy / Kakobuy / 其他）？是否固定用一家？
3. **能否拿到代购平台的订单数据？** 能的话，是后台导出 Excel 还是 API？数据里是否包含邀请码或推广码（`inviteCode` / `affcode`）？
4. **2 万个商品是否都在你们自己的微店里？** 还是来自很多不同卖家的店铺？
5. **需求文档里说的"微店复制工具"具体是什么？** 能否录屏演示一次？
6. **参考截图（Cooperative alliance 后台）是哪个系统？** 你们是否有它的账号？它能否导出订单数据？
7. **是否了解 Google 内容政策的风险？** 是否考虑用自建商品展示页替代或补充 Google 表格？

- **Google 部分**：可行性已确认，报价和排期不变。

  - 如果需要对接代购平台接口，或者走方案 B：需要重新评估。

## 八、补充调研：微店订单里能否拿到"达人 ID"（官方接口文档）

> 背景：客户的做法是让达人把微店商品链接挂到 Ins / WhatsApp 上，并认为"微店返回的数据能看到这笔交易关联的是哪个达人"。
> 数据来源：微店开放平台官方接口文档（open.weidian.com 的公开文档接口，2026-09-30 查阅）。

### 8.1 结论

**能拿到，但拿到的是"微店推广员"的身份，不是我们自己定义的达人 ID。** 客户说的"微店能看到关联的达人"，对应的是微店自带的**推广员（分成推广）**功能：达人在微店注册成为店铺的推广员，买家通过达人分享的链接进店后，就与这位推广员绑定，之后的订单会记在这位推广员名下。

### 8.2 可用的接口与字段

| 途径 | 接口 | 能拿到什么 | 说明 |
|---|---|---|---|
| ① 订单详情直接带推广员 | `vdian.order.get` 2.0 | `fans1_id` / `fans2_id`（一级、二级推广员 ID），`fans1_money_total`（推广佣金），`items.total_fee`（分成推广佣金） | `fans1_id` 出现在官方返回示例中，但字段说明表里没有写，**需要实测确认含义** |
| ② 通过买家查绑定的推广员 | 订单里的 `buyer_info.buyer_id` → `fxmall.fans.get` | `sharerUid` / `sharerNick` / `sharerPhone`（推广员 ID、昵称、手机号），`bindTime`（绑定时间）、`invalidTime`（失效时间） | 文档字段清晰，可以作为主方案或兜底 |
| ③ 推广员关系链 | `fxmall.relation.get`、`fxmall.fans.list` | 粉丝与推广员的绑定关系列表 | 未打开推广员的推广开关时，不返回明细 |
| ④ 优惠码 | `create.shop.coupon` 创建优惠券；订单 `discount_list.couponIds` | 订单使用了哪张优惠券 | 可以作为"达人专属优惠码"的补充归因 |
| ✗ 自定义参数 | — | 订单字段中**没有**任何能带回自定义 URL 参数（`kol_id`、`track_id`）的字段 | 需求文档的优先级 1、3 仍然不可行 |

**系统里的做法**：每位达人录入系统时，登记他的"微店推广员 ID"。订单同步进来后，用 `fans1_id` 或 `sharerUid` 对应到系统里的达人 ID（KOL0001）。

### 8.3 前提条件（缺一不可）

1. **商品必须在客户自己的微店里。** 自用型应用只能读取自己店铺的订单。
2. **需要向微店申请接口权限。** 以上订单和推广员接口都是"加密接口"，官方文档写明要先联系微店开通调用权限；买家手机号、地址等敏感字段返回的是密文，要用官方 SDK 解密，且不允许解密后明文存储。
3. **每位达人都要成为该店铺的微店推广员**，也就是要有微店账号（推广员信息里有手机号字段，海外达人能否用海外手机号注册需要实测）。
4. **买家必须用自己的微店账号，直接在微店下单。** 如果买家是通过代购平台购买（第二节发现的情况），绑定的就是代购平台的采购账号，归因会全部失真。

### 8.4 这种归因方式的局限

- **按"买家绑定"归属，不是按"这次点的哪条链接"归属。** 订单记在买家当前绑定的推广员名下。在默认的"永久绑定、不允许抢客"设置下，买家第一次通过达人 A 的链接进店后就绑定 A，之后即使点达人 B 的链接下单，订单仍算 A 的。
  - 微店商家后台可以配置"是否永久绑定粉丝关系"和"是否允许粉丝间抢客"（[来源，2020 年](https://www.qudong.com/article/395380.html)，当前后台是否仍保留这两个选项需确认）。开启"允许抢客"、关闭永久绑定后，效果接近"按最近一次点击的链接归属"。
  - 这些规则由客户在微店后台设置，我们的系统无法改变微店的归属结果；我们的中转点击数据可以作为参考和人工复核的依据。
  - 如果开启了"允许抢客"，买家的绑定关系会变化。用 `fxmall.fans.get` 事后查到的是"查询时"的绑定人，不一定是"下单时"的绑定人，所以应以订单详情里的 `fans1_id` 为准（前提是实测确认它是下单时的快照）。
- **微店没有"批量生成推广员链接"的接口。** 推广员链接一般是达人在微店 App 里点"分享"生成的。如果分享链接里的推广员参数格式是固定的，系统就可以把这个参数拼接到 2 万条商品链接上，批量生成专属链接——**这需要实测**：让 1 位达人分享 1 个商品，分析链接参数，再换一个商品 ID 下单，看能否正确绑定。
- 推广员的部分进阶功能可能需要付费升级到微店商城版（[微店官方说明](https://www.weidian.com/blog/details/472.html)），需要客户确认店铺当前版本。

### 8.5 另一个值得问微店的渠道：跨境 CPS（买手业务）

微店开放平台有一组"买手业务（仅对买手业务开放）"接口，面向海外买手或代购：

- `vdian.cps.crossborder.batchGenerateLink`：批量生成**跨境 CPS 推广链接**，每次最多 50 个商品
- `channel.getOrderList`：按推广位 `pid` 获取渠道订单（T+1），包含渠道佣金
- `vdian.cps.popularize.getTunnel`：获取推广位 `pid`

如果客户能以渠道或买手身份和微店合作，并且**每位达人能分到一个独立的 pid**，就能同时解决"批量生成专属链接"和"订单按达人归属"两个问题，而且适用于海外流量。这需要客户去问微店商务，开发者无法自行开通。

### 8.6 更新后的归因方案建议

| 场景 | 推荐方案 |
|---|---|
| 买家直接在客户自己的微店下单 | **微店推广员归因**（第 8.2 节途径 ①② + 优惠券补充）；中转点击数据作参考 |
| 买家通过代购平台下单 | 代购平台邀请码归因（第五节方案 A） |
| 客户能拿到微店跨境 CPS 渠道资质 | 按 pid 归因（第 8.5 节） |

**需要追加确认的问题：**

1. 达人现在是否已经是客户微店的"推广员"？请在微店后台截一张推广员订单或业绩的截图。
2. 在 Ins / WhatsApp 上点链接的买家，是直接用自己的微店账号下单，还是通过代购平台下单？（第二节的表格分析显示大部分走代购平台。）
3. 商品是否都在客户自己的微店里？是否已开通微店开放平台开发者账号？
4. 客户是否与微店商务有联系，能否咨询跨境 CPS（买手业务）的合作？

## 九、最终确认的归因方案：按达人专属商品 ID 归因（2026-09-30）

客户确认：**每位达人有自己的专属商品副本，商品 ID 各不相同，由运营在微店中手动复制**。第五节和第八节中的推广员、优惠码、代购平台邀请码等方案都不再需要，归因方式改为：

```
运营在微店复制专属商品（每位达人一套，itemID 唯一）
  → 系统登记“专属商品 ID → 达人 + 原商品”对应表
  → 中转链接跳转到该达人的专属商品
  → 订单同步后，按订单里的商品 ID 查表，确定所属达人
```

| 项目 | 结论 |
|---|---|
| 准确度 | 高。一个商品 ID 只属于一位达人，与买家绑定、推广员设置无关 |
| 代购平台下单 | **同样适用**：代购平台按链接中的商品 ID 下单，微店订单里带的就是这个 ID |
| 用到的微店接口 | 订单：`vdian.order.list.get` / `vdian.order.get`（需申请加密接口权限）；对应关系：`vdian.item.list.get`、`weidian.cate.get.list` 读取商品和分类 |
| 系统不再需要 | 推广员接口、优惠码归因、微店链接批量生成 |

**仍需确认或注意：**

1. **对应关系如何标识**：建议每位达人的副本放在以达人编号命名的商品分类里，或者商家编码写成"原商品编码-达人编号"，这样系统可以通过接口自动读取对应表。
2. **规模**：100 × 2 万 = 200 万个商品，靠手动复制，工作量很大。需向微店确认单店商品上限，以及大量相同商品是否会被判定为重复铺货。
3. **副本同步**：原商品改价、改库存、下架后，100 份副本都要同步。本期由运营在微店处理；如需系统自动同步（可用 `vdian.item.update`、`vdian.item.stock.update`），需另行评估，且要考虑微店接口的每日调用次数限制。
4. **匹配不上的订单**：买家买了原商品，或买了尚未登记的副本，这类订单进入人工匹配池。
