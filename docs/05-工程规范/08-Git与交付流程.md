# 08 Git 与交付流程

## 1. 分支

【强制】`main` 是唯一长期分支，始终保持可构建、测试全部通过、可部署。
【强制】**禁止直接向 `main` 推送**；所有变更通过短期分支 + Pull Request 合并。
【例外】只修改过程文档时，项目负责人（或其明确指示的人）可以直接提交并推送到 `main`，不走 PR（见 ADR-011）。过程文档指 `docs/` 下除 `03-设计/`、`05-工程规范/`、`06-架构决策/` 之外的文件；一次提交同时改了其他任何文件时，不适用本例外。AI 编码代理执行开发任务时不适用本例外。
【强制】分支命名 `{类型}/{简短描述}`，类型同提交类型；对应开发任务时带任务编号：

| 示例 | 用途 |
|---|---|
| `task/02-engineering-baseline` | 执行 `docs/04-开发任务/` 中的任务 |
| `feat/order-attribution` | 新功能 |
| `fix/redis-blank-password` | 缺陷修复 |
| `docs/engineering-standards` | 文档 |

【强制】分支生命周期不超过一个任务；合并后删除。

## 2. 提交

【强制】提交信息遵循 Conventional Commits 1.0.0：

```
<type>(<scope>): <subject>

<body：为什么改、改了什么，可选>

<footer：关联任务、BREAKING CHANGE、署名>
```

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 不改变行为的重构 |
| `test` | 测试 |
| `docs` | 文档 |
| `chore` | 构建、依赖、配置 |
| `ci` | 持续集成 |
| `perf` | 性能 |

【强制】`scope` 使用工程或模块名：`backend`、`redirect`、`admin-ui`、`kol-portal`、`deploy`，或后台模块名 `order`、`commission` 等。
【强制】一个提交只做一件事，且提交后仍可构建；不把格式化、重构与功能修改混在同一个提交。
【强制】AI 代理产生的提交在末尾署名：Codex 为 `Co-Authored-By: Codex <noreply@openai.com>`，Claude 为 `Co-Authored-By: Claude <noreply@anthropic.com>`（以所用模型实际署名为准）。

## 3. Pull Request

【强制】PR 标题同提交格式；描述使用仓库的 PR 模板，包含：变更内容、关联任务、验证方式与结果、新增依赖说明、数据库变更说明、截图（涉及界面时）。
【强制】合并条件：
1. CI 全部通过（见第 4 节）；
2. 对照本规范完成审查（AI 代理提交的 PR 由项目负责人或 Claude 审查）；
3. 无未解决的审查意见。
【强制】合并方式使用 **Squash merge**，合并后的提交信息符合第 2 节格式。
【推荐】单个 PR 的改动不超过 800 行（不含锁文件、迁移脚本、自动生成文件）；超过时拆分。
【强制】一个 PR 只对应一个任务；业务功能与视觉统一、重构、依赖升级分开提 PR（规范 12 第 3 节）。

## 4. 持续集成（GitHub Actions）

【强制】每个 PR 与每次合并到 `main` 时运行：

| 工程 | 检查项 |
|---|---|
| backend | Spotless 格式校验、Checkstyle、编译、单元测试、ArchUnit、集成测试（`-Pdocker-it`，GitHub 托管机器自带 Docker）、JaCoCo 覆盖率门槛、依赖漏洞扫描 |
| redirect | 同上（无 ArchUnit 模块规则时只检查分层） |
| admin-ui / kol-portal | `pnpm install --frozen-lockfile`、ESLint、Prettier 校验、类型检查、Vitest、构建、`pnpm audit` |
| deploy | `docker compose config` 语法校验；`check-healthchecks.py`；`check-compose-env.py`（后台与跳转服务必需的环境变量都已传入，见规范 06 第 5 节） |

| 全仓库 | OSV-Scanner 依赖漏洞与许可证扫描（见规范 06 第 6 节） |

【强制】CI 失败的 PR 不得合并；不得为了通过而关闭检查或降低门槛（调整门槛须修改本规范）。
【临时】自 2026-10-18 起 GitHub Actions 暂停使用。暂停期间，代理不等待 `gh pr checks`，在执行报告中贴出本地全量检查结果；架构负责人合并前在临时工作树中把 PR 合并到最新 `main`，复跑上表全部检查，以复跑结果代替 CI（见规范 12 第 7 节）。恢复 CI 后删除本条。
【强制】工作流中引用的第三方 Action 必须固定到**完整的 40 位提交 SHA**，并在同一行注释标明对应版本号（如 `uses: actions/checkout@<sha> # v5.0.0`）；禁止只写版本标签或分支名。理由：标签可以被强行改指向，2026 年 3 月 trivy-action 的 76 个版本标签即被篡改为窃取 CI 密钥的恶意代码（见 ADR-004）。Dependabot 负责提示更新。

## 5. 完成标准（Definition of Done）

一个任务或 PR 只有同时满足以下条件才算完成：

- [ ] 功能符合需求原文（规范 12 第 1 节）、设计说明书与任务要求，未超出范围；执行报告含逐条复核表（规范 12 第 4 节）
- [ ] 符合本规范；自动检查全部通过
- [ ] 必测清单中相关项已有测试，覆盖率达标
- [ ] 数据库变更有迁移脚本，接口变更有 OpenAPI 描述，前端错误码映射已更新
- [ ] 设计说明书、README、`.env.example` 等受影响文档已同步
- [ ] 涉及界面的，已按规范 12 第 5 节完成浏览器验收并附截图；涉及配置或部署的，已用本地预览实际启动（规范 12 第 6 节）
- [ ] 无遗留调试代码、无未登记的 `TODO`
- [ ] 已通过 PR 合并到 `main`

## 6. 开发任务与执行报告

【强制】交给 AI 代理的开发任务写在 `docs/04-开发任务/{编号}-{名称}-Codex提示词.md`，代理完成后在同目录写 `{编号}-{名称}-执行报告.md`。
【强制】执行报告至少包含：结论、版本与环境、各步骤的验证命令与结果、偏离与原因、遗留事项、PR 链接。
【强制】任务完成的判定以 CI 结果与审查结论为准，不以执行报告的自述为准。

## 7. 架构决策记录（ADR）

【强制】以下决定须在 `docs/06-架构决策/ADR-{序号}-{标题}.md` 记录：技术选型、主版本升级、规范修改、偏离规范的例外、影响多个模块的设计取舍。
【强制】格式：背景、决定、备选方案及放弃原因、影响。已接受的 ADR 不修改，被推翻时新增 ADR 并标注替代关系。

## 8. 版本、发布与交付

【推荐】遵循语义化版本：上线首个版本为 `1.0.0`；发布时在 `main` 打标签 `v{版本}`，根据提交信息生成更新说明。

【强制】交付给客户的源代码包从发布标签生成，不直接打包工作目录：

```bash
git archive --format=tar.gz --prefix=t-crm/ -o t-crm-v{版本}-src.tar.gz v{版本}
```

【强制】`.gitattributes` 中标记为 `export-ignore` 的内容不进入交付包：AI 代理规则（`AGENTS.md`、`CLAUDE.md`），以及内部文档（需求原件、报价与合同、调研、开发任务、过程稿）。交付包保留：全部源代码、构建与部署配置、CI 工作流、`THIRD-PARTY-NOTICES`、设计说明书、工程规范、架构决策记录、README 与操作说明。
【强制】新增内部文档目录时，同步更新 `.gitattributes`。
【强制】生成交付包后检查清单：解压后不含上述排除内容；能按 README 完成构建；各工程 `THIRD-PARTY-NOTICES` 齐全。

## 9. 本地环境与 AI 代理协作

### 9.1 工作目录

【强制】主目录（仓库根目录，例如 `/Users/hh-mini/Public/dev/t-crm`）只供项目负责人和架构负责人使用。AI 代理执行任务时，只能在分配给它的工作树中读写文件：

- 本机任务的工作树放在 `.worktrees/{编号}-{名称}/`（已被 `.gitignore` 忽略），分支 `task/{编号}-{名称}`，由架构负责人从最新的 `main` 创建；
- 代理启动的每个子代理，输入中都必须写明工作目录的绝对路径，并要求先 `cd` 到该目录；
- 不得在主目录或其他工作树中创建、修改、删除文件，也不得在那里执行会写文件的命令（格式化、安装依赖、构建）。

【强制】架构负责人审查前检查主目录的 `git status`；发现任务代理写入的文件时，先存档为补丁，再恢复主目录，并在 PR 评论中指出。
【强制】派发任务的启动说明统一放在 `.worktrees/启动说明.md`（不提交），列出每个任务的工作目录、端口和联调方式；任务合并后删除对应段落和工作树。

### 9.2 共享中间件

自 2026-10-20（任务 35）起，负责人的本地预览、本地开发和所有代理的联调、浏览器验证，共用一套 PostgreSQL 和 Redis，也共用同一个数据库（Compose 项目 `tcrm-local`，端口 55432 / 46391，连接信息在主目录的 `deploy/.env.local`）。

【强制】派发任务前，架构负责人执行 `deploy/scripts/local-infra.sh backup`。
【强制】代理只读取 `deploy/.env.local`，不得修改；后台和 Vite 使用任务分配的端口，不得占用负责人的端口（以启动说明为准）。
【强制】测试账号和测试数据统一加任务前缀 `tNN_`（例如用户名 `t34_bd01`、邮箱 `t34_…@example.com`）；收尾时只删除自己创建的数据，并把改过的系统配置恢复默认。
【强制】不得停止、删除或重建共享中间件的容器和数据卷，不得执行 `down -v`，不得为任务另起 `docker-compose.dev.yml` 项目；不得重建负责人的预览（`tcrm-preview`），除非负责人明确要求。
【强制】任务自己创建的 Docker 资源（临时容器、镜像、网络）在收尾时删除，只删自己创建的，不执行 `docker system prune` 等全局清理；在执行报告中列出清理命令。
【强制】自动化集成测试仍使用 Testcontainers 临时容器，不连接共享中间件。
【强制】分支上的迁移会进入共享库。已在共享库执行过的迁移，在合并前被修改的，由架构负责人在合并后备份并修正 `flyway_schema_history` 的校验和；代理不得自行修改共享库的迁移记录。
