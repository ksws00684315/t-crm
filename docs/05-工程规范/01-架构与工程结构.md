# 01 架构与工程结构

## 1. 总体形态

【强制】后台 `crm-admin` 是**模块化单体**：一个可部署单元，内部按业务模块切分，模块之间只通过公开接口交互。跳转服务 `crm-redirect` 是独立进程，不与后台共享代码。

【强制】仓库目录：

```
t-crm/
├── backend/      crm-admin（Maven 单模块工程）
├── redirect/     crm-redirect（Maven 单模块工程）
├── admin-ui/     管理端（Vue 3）
├── kol-portal/   达人端（Vue 3）
├── deploy/       部署编排与配置模板
├── docs/         文档
├── AGENTS.md     AI 编码代理规则摘要
└── CLAUDE.md     指向 AGENTS.md
```

## 2. 后台模块划分

【强制】根包 `com.tcrm.admin`。**根包的每个直接子包是一个模块**（与 Spring Modulith 约定一致），业务模块不再嵌套在 `crm` 包下：

| 模块包 | 职责 | 类型 |
|---|---|---|
| `shared` | 统一响应、异常、分页、审计注解、通用配置、工具 | 共享内核，所有模块可依赖 |
| `security` | 登录、令牌、当前用户上下文、数据范围 | 基础模块 |
| `system` | 管理员用户、操作日志、业务配置 | 基础模块 |
| `kol` | 达人、商务归属、邀请 | 业务模块 |
| `product` | 原商品、店铺、专属商品对应关系 | 业务模块 |
| `link` | 中转链接、Redis 链接索引、点击消费 | 业务模块 |
| `sheet` | Google 表格 | 业务模块 |
| `order` | 订单同步、导入、归因、人工匹配 | 业务模块 |
| `commission` | 佣金明细、结算单、冻结 | 业务模块 |
| `stats` | 汇总表、看板、预警 | 业务模块 |
| `integration` | 微店、Google、邮件的外部客户端 | 适配器，只被业务模块调用 |
| `task` | 批量任务框架 | 基础模块 |

【强制】新增模块须先在本表登记（改规范走 PR）。

## 3. 模块内部分层

【强制】每个模块内部固定以下子包，不需要的可以不建：

```
com.tcrm.admin.<module>
├── api/          对其他模块公开的门面接口与跨模块 DTO（模块唯一的对外入口）
├── controller/   HTTP 接口；请求对象 *Request / *Query、响应对象 *VO
├── service/      业务逻辑
├── mapper/       MyBatis-Plus Mapper 接口
├── model/        *DO 实体、枚举、模块内值对象
├── job/          定时任务
└── config/       模块私有配置
```

【强制】调用方向（单向，禁止反向和跨层）：

```
controller → service → mapper
              ↓
         其他模块的 api
```

| 规则 | 说明 |
|---|---|
| controller 不能直接调用 mapper | 所有数据访问经过 service |
| service 不能依赖 controller 包的任何类 | 请求对象在 controller 层转换为 service 的入参 |
| 模块之间只能依赖对方的 `api` 包 | 禁止访问其他模块的 service、mapper、model |
| `shared` 不能依赖任何业务模块 | 共享内核保持纯净 |
| 模块之间禁止循环依赖 | 需要反向通知时使用 Spring 应用事件 |
| `integration` 只做外部协议转换 | 不含业务规则，业务规则留在调用它的模块 |

以上规则由 **ArchUnit 测试**在 CI 中强制检查（见 05）。

## 4. 对象模型

【强制】按《阿里巴巴 Java 开发手册》分层领域模型命名：

| 后缀 | 用途 | 所在包 | 形式 |
|---|---|---|---|
| `*DO` | 与数据表一一对应，字段与表字段一致 | `model` | 类：私有字段 + getter/setter |
| `*Request` | 写操作请求体 | `controller` | `record`，带校验注解 |
| `*Query` | 列表与查询条件（参数超过 2 个时必须封装） | `controller` | `record` |
| `*VO` | 返回前端的对象 | `controller` | `record` |
| `*DTO` | 跨模块传输对象、service 的复杂入参出参 | `api` 或 `service` | `record` |
| `*Command` | service 写操作入参（当 Request 需要转换时） | `service` | `record` |

【强制】`*DO` 不得出现在 controller 的入参和返回值中；不得直接序列化给前端。
【强制】禁止用 `Map` 传递业务数据（框架回调除外）。
【强制】不使用 Lombok；`record` 用于不可变对象，`*DO` 显式编写 getter/setter。理由：减少编译期代码生成，保证升级 JDK 时可控。

## 5. 跳转服务

【强制】`crm-redirect` 保持极简：只依赖 Web 与 Redis，不连接数据库，不引入与跳转无关的依赖。包结构：

```
com.tcrm.redirect
├── controller/
├── service/
└── config/
```

## 6. 前端工程结构

【强制】`admin-ui`、`kol-portal` 统一结构：

```
src/
├── api/          按后端模块划分的请求函数，带完整 TypeScript 类型（如 api/system/user.ts）
├── views/        页面，按模块分目录（views/system/user/index.vue）
├── components/   可复用组件
├── stores/       Pinia 状态
├── router/       路由与守卫；路由 meta.roles 声明可访问角色
├── utils/        工具函数
└── types/        共享类型定义
```

【强制】页面组件不得直接调用 axios，必须通过 `api/` 下的函数。
【强制】接口类型（请求、响应）在 `api/` 中定义，与后端 `*Request` / `*VO` 字段一一对应。
