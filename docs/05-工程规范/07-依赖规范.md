# 07 依赖规范

## 1. 版本

【强制】**直接依赖**（`pom.xml` 中直接声明的依赖与插件，`package.json` 的 `dependencies` / `devDependencies`）必须是正式稳定版，版本号写死；禁止 alpha、beta、RC、M、SNAPSHOT、`next`、版本范围、`latest`。
【强制】**传递依赖**中的预发布版本不作为阻断条件，不得为此强制覆盖版本或替换上游工具链；须在引入该依赖的 PR 中列出（包名、版本、引入路径）。
【强制】锁文件必须提交：前端 `pnpm-lock.yaml`；后端版本全部显式写在 `pom.xml` 或由 Spring Boot 父 POM 统一管理。
【强制】后端依赖的版本优先使用 Spring Boot 父 POM 管理的版本，不单独覆盖：**由 Spring Boot 管理的依赖与插件，在 `pom.xml` 中不写 `<version>`**，随 Spring Boot 版本一起升级；只有不受 Spring Boot 管理的依赖才写死版本。
【强制】Dependabot 只对不受 Spring Boot 管理的依赖、Spring Boot 父 POM 本身以及 GitHub Actions 提出升级；主版本升级被忽略，须按第 4 节手动处理；次版本与补丁升级按工程合并为一个 PR，CI 通过且审查后合并。
【强制】**安全修复例外**：Spring Boot 尚未发布包含修复的版本时，允许通过 Spring Boot 提供的版本属性（如 `tomcat.version`、`jackson-bom.version`）覆盖受漏洞影响的依赖，但只限**同一次版本内的补丁升级**；须在 `pom.xml` 该属性旁注释漏洞编号，并在 PR 中说明；Spring Boot 发布包含修复的版本后，升级 Spring Boot 并删除覆盖。

## 2. 新增依赖

【强制】新增依赖须在 PR 描述中说明：解决什么问题、为什么不用已有依赖或自己实现、许可证、维护活跃度（最近一次发布时间）。
【强制】能用 JDK、Spring 或已有依赖解决的问题，不引入新依赖。
【强制】不引入后台管理脚手架、代码生成框架、Lombok。
【强制】跳转服务只允许 Web、Redis、Actuator 及测试相关依赖。

## 3. 许可证

【强制】许可证规则按依赖是否**随交付物分发**区分：运行时依赖（打包进后台、跳转服务、前端产物，或随部署镜像交付的组件）适用下述白名单；只在构建与测试阶段使用的工具适用本节末尾的"构建与测试工具"规则。
【强制】运行时依赖的许可证白名单（SPDX 标识）：`MIT`、`MIT-0`、`Apache-2.0`、`BSD-2-Clause`、`BSD-3-Clause`、`ISC`、`EPL-1.0`、`EPL-2.0`、`CC0-1.0`、`Apache-1.1`、`0BSD`。白名单外的许可证一律视为违规，扩充白名单须修改本规范并记录 ADR。
【强制】**双重许可与元数据不规范的处理**：依赖以"A 或 B"双重许可发布、且其中一项在白名单内时，可选择白名单内的许可；依赖的许可证元数据不是标准 SPDX 标识（如写成 "Eclipse Public License - v 2.0"）时，可声明其对应的标准标识。两种情况都在仓库根目录 `osv-scanner.toml` 中按包逐条声明，每条必须写明：所选许可证、理由、官方许可证原文链接。禁止用此机制改写真实的非白名单许可证。
【强制】**组合许可（AND）**：依赖包内包含多个组件、许可证表达为"A AND B"时，**每一项都必须在白名单内**；在 `osv-scanner.toml` 中声明完整的许可证组合，不得只保留其中一项。
【强制】许可证以依赖 JAR 包（或 npm 包）内附的许可证原文为准；POM、`package.json` 中的元数据与原文不一致时，以原文为准。
【强制】禁止 GPL、AGPL、SSPL 等传染性或限制商用的许可证（交付给客户的源代码不能受其约束）。
【强制】**构建与测试工具**（Maven 插件及其依赖、测试框架与测试依赖、前端构建与检查工具等）同时满足以下条件时，可使用任何 OSI 认可的许可证，包括 LGPL 与带 Classpath 例外的 GPL：① 不打包进交付物；② 不修改其源码；③ 不以库的形式链接进业务代码。**AGPL、SSPL 以及非 OSI 认可的许可证仍然禁止**；例外：构建与测试工具附带的**数据文件包**（如许可证标识列表）可使用 `CC-BY-3.0`、`CC-BY-4.0`、`CC0-1.0`。 使用白名单外许可证的工具须在引入它的 PR 中列出（工具、版本、许可证、用途），见 ADR-007、ADR-010。在 `osv-scanner.toml` 中对这类包设置 `license.ignore` 时，每条 reason 必须写明：实际许可证、引入路径、不进入任何构建产物的依据。
【强制】引入模板或第三方源码时保留原 LICENSE 文件，并在对应目录 README 注明来源仓库、版本与获取日期。
【强制】**交付须附第三方许可声明**：每个工程（backend、redirect、admin-ui、kol-portal）由构建工具自动生成 `THIRD-PARTY-NOTICES`（列出全部运行时依赖的名称、版本、许可证，并附需要随附的版权声明与许可证原文，如 Apache-1.1 要求的致谢声明），生成文件提交到各工程根目录；CI 校验生成结果与已提交文件一致；部署包与交付给客户的源码中都必须包含该文件。

## 4. 升级

【推荐】每月检查一次依赖更新与安全公告；补丁版本随时升级，次版本升级单独开 PR 并跑完整测试，主版本升级需写架构决策记录。
