# ADR-017：管理端每次登录需要图形验证码

- 状态：已接受（2026-10-12）
- 决策人：项目负责人（选择"图形验证码，自己生成，每次登录都要"）
- 相关：[ADR-008](ADR-008-登录失败限流按用户名与来源IP分层.md)（失败计数与锁定，其"备选方案"中把验证码列为后续独立功能）、[ADR-009](ADR-009-可信代理与客户端IP解析.md)（来源 IP）

## 背景

管理端登录已有三层失败计数与锁定（ADR-008）和 Nginx 登录限速，但脚本仍能以每个 IP 每 15 分钟 4 次的速度持续撞库而不触发锁定，分布式来源更多。负责人要求登录页加验证码，并在三种方式（自生成图形验证码、行为验证码库、第三方云验证码）中选择了**自生成图形验证码**，触发时机选择**每次登录都要**（而不是失败 N 次后再出现）。

## 决定

1. **签发**：`POST /admin-api/auth/captchas`（显式公开，响应 `Cache-Control: no-store`）返回 `{enabled, captchaId, image, expiresIn}`。`image` 是 120×40 的 PNG data URL，由 `CaptchaImageGenerator` 只用 JDK `java.awt`（headless）绘制：4 个字符，取自去掉易混字符（0/O、1/I/L）的 31 个字符，随机字体、旋转、干扰点与干扰线；`SecureRandom`。不引入第三方库，也就没有新的许可声明。
2. **存储**：答案（大写）明文存 Redis `auth:captcha:{captchaId}`，有效期 3 分钟；`captchaId` 为随机 UUID。不做哈希：答案空间只有约 92 万种，能读 Redis 的人哈希也挡不住，反而让测试无法取答案。
3. **一次性**：校验用 GETDEL 原子地读取并删除，**无论对错**，一张图只能猜一次；用过、过期、不存在、格式不对的 `captchaId` 都按错误处理。比较不区分大小写，忽略首尾空格。
4. **校验顺序**：`AuthService.login` 先校验验证码，再检查锁定，再比对密码。验证码错误或过期返回 **HTTP 400 `AUTH_CAPTCHA_INVALID`**。
5. **不计入登录失败**：验证码错误时不调用 `LoginFailures.fail`，也不查询账号、不做 BCrypt。理由：
   - 验证码错误不说明攻击者在猜密码，计入只会让输错验证码的正常用户更快被锁；
   - 攻击者无法用错验证码锁别人的账号（否则等于给 ADR-008 新增一种低成本锁定手段）；
   - 锁定状态也要先通过验证码才能探测到。
   验证码正确、密码错误时，按 ADR-008 计数、锁定、返回 429，完全不变。
6. **状态码选 400 而不是 401**：管理端把 401 当作"登录态失效"处理（弹重新登录框）；400 只表示这次请求的输入不对。
7. **签发限速**：每个来源 IP（ADR-009 的解析结果，SHA-256 后作键）每分钟最多签发 120 张，超出返回 **429 `AUTH_CAPTCHA_RATE_LIMITED`**（Redis 固定窗口 `auth:captcha:rate:{ip}`）。上限由 `crm.auth.captcha.issue-per-minute` 配置（默认 120，最小 1）。初稿为 30 张且写死；负责人在 PR #35 评审中认为办公室共用出口时偏低，改为 120 并要求可配置（与 ADR-008 的"阈值写死"不同，这里是负责人明确要求）。生产 Nginx 另给该接口一个 `tcrm_captcha` 限速区（120r/m，burst 30）作为源站兜底；Cloudflare 频率限制规则（同一路径、每 IP 每分钟 120 次）是第一道防线，配置写在 `deploy/README.md`，**需负责人在 Cloudflare 控制台手工创建，尚未应用**。
8. **登录过期弹窗也要验证码**：重新登录弹窗调用的是同一个 `POST /admin-api/auth/login`，"每次登录都要"即包括它；设计文档没有与之冲突的条款。弹窗只在打开时才拉取验证码，不会在每个页面加载时请求。
9. **开关**：`crm.auth.captcha.enabled`，默认 `true`，生产不得关闭；只供本机开发或个别测试使用。关闭时签发接口返回 `enabled=false`，登录不校验验证码，管理端隐藏验证码输入框；`CaptchaService` 启动时打一条 WARN，避免误关后无人察觉。集成测试全部在开启状态下运行。
10. **到期前刷新**：管理端在拿到 `expiresIn` 后约提前 10 秒自动换一张（登录页与重新登录弹窗共用组件）；关闭弹窗或卸载组件时清掉定时器。点击图片仍可立刻换。
11. **达人端不变**：达人端登录目前是本地占位实现，没有后端登录接口，本决定只适用于管理端；达人登录任务实现时另行评估。

## 残余风险

- 图形验证码挡不住 OCR 或打码平台，只是提高了撞库成本；需要更强防护时再评估行为验证码或第三方服务（不改接口形态即可替换实现）。
- 同一出口 IP（办公室 NAT）的所有人共享每分钟 120 张的签发额度；以几十个内部用户的规模不会触及，必要时调整配置项。
- Redis 重启会让未使用的验证码失效，用户刷新一张即可。
- 验证码图片在深色主题下保持浅色底，作为图片本身的一部分，不随主题变化。

## 备选方案及放弃原因

| 方案 | 放弃原因 |
|---|---|
| 失败 N 次后才出现验证码 | 负责人选择每次都要 |
| 行为 / 滑块验证码库（如 AJ-Captcha） | 前后端都要多接一层，新增依赖；负责人选择图形验证码 |
| 第三方云验证码 | 需要密钥、外网、付费 |
| 第三方图形验证码库（EasyCaptcha、Kaptcha 等） | JDK 足以生成；这些库维护不活跃或依赖老旧组件，新增依赖须单独评估 |
| 验证码错误计入失败次数 | 见决定 5 |
| 只在前端校验 | 没有防护作用 |
