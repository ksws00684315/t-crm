# ADR-015 管理端与达人端支持中英文切换

- 状态：已接受（2026-10-11）
- 决策人：项目负责人

## 背景

签约范围与规范 02 原定"管理端中文、达人端英文"。2026-10-11 项目负责人要求两端都支持中英文切换。

现状：

- 管理端已有约 21 个页面，中文写在 45 个文件中；达人端只有登录页与框架。
- 后端错误已按 `errorCode` 由前端翻译，`msg` 为英文；参数校验提示固定按英文生成。
- 导入模板表头和逐行错误原因是写死在后端的中文。
- 操作日志的 `module` / `action` 是英文固定值。

## 决定

1. 两端都支持 `zh-CN` 与 `en-US`：管理端默认中文，达人端默认英文；用户的选择保存在浏览器本地，不存服务端。
2. 前端使用 **vue-i18n**（两端各新增一个直接依赖，MIT 许可，Vue 官方生态的国际化库；版本按规范 07 写死），并切换 Element Plus 的语言包。
3. 界面文字全部从语言包读取；后端错误仍按 `errorCode` 翻译，`msg` 保持英文、只用于排查。
4. 前端每个请求带 `Accept-Language`。后端用 Spring `MessageSource` 生成以下内容：参数校验提示、导入模板表头、错误文件中的说明。只识别两种语言，其他按英文处理。
5. 后台任务记录提交时的语言（`crm_task.locale`），错误文件按该语言生成。导入时中文和英文表头都能识别。
6. 业务数据不翻译。邮件同时包含中英文。Google 推广表格和跳转提示页保持英文。
7. 由任务 06d 实现，排在任务 06c 之后、M2 之前。之后每个新页面、新的后端文字都同时提供两种语言，两种语言的键必须一致（由测试检查）。

## 备选方案及放弃原因

| 方案 | 放弃原因 |
|---|---|
| 后端按语言返回翻译好的 `msg`，前端直接显示 | 违反规范 02"不直接展示后端 `msg`"；错误文案分散在前后端两处，容易不一致 |
| 语言偏好保存在用户资料（服务端） | 需要加字段和接口；浏览器本地保存已满足需求，达人端未登录的页面也能用 |
| 导入模板固定为中英双语表头（如"姓名 / Name"） | 实现更简单，但表头冗长，客户已有的单语模板无法直接使用 |
| 自行实现简单的翻译函数，不引入依赖 | 复数、插值、Element Plus 和 ECharts 的配合都要自己写，vue-i18n 是成熟做法 |

## 影响

- 规范 02 第 7 节的"界面文案"条款改为"界面文字从语言包读取"。规范 03 增加 `Accept-Language` 约定。
- 已有页面和导入模板需要一次改造，约 3～4 人天；后续每个页面的文案工作量约增加 10%～15%。
- 翻译质量（尤其是英文的业务术语）需要客户确认。术语表随任务 06d 一起提交，供客户审阅。
