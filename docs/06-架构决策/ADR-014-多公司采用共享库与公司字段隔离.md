# ADR-014 多公司采用共享库与公司字段隔离

- 状态：已接受（2026-10-11）；部分被 [ADR-022](ADR-022-管理员账号多公司成员关系与会话内切换.md) 修订（2026-10-17）
- 被 ADR-022 修订的条目（只涉及管理端账号，达人端不变）：
  - 「同一个人为多家公司工作时，在每家各开一个账号」改为「一个账号可属于多家公司」，账号与公司之间是成员关系（`sys_user_tenant`）；
  - 决定第 3 条「管理员按全系统唯一的用户名确定公司」改为「用户名定人，成员关系定可进入的公司；当前公司保存在登录会话中，可在本人的成员关系之间切换」，仍不接受前端传入的公司 ID 决定公司。
- 决策人：项目负责人

## 背景

签约范围按一家公司设计，设计说明书 §2.3 原写"不做多租户"。2026-10-11 客户提出：系统要支持客户旗下的多家公司，各公司只能看到自己的达人、店铺、商品和订单；同一个达人可能与多家公司合作，在每家公司各有一个账号，佣金分开计算。

客户确认的前提：

1. 公司都是客户自己的，目前只有 1 家；提出此需求是为了以后增加公司时系统不需要重构。
2. 不需要跨公司汇总。
3. 公司之间不共享店铺、商品等任何业务数据。
4. 同一达人在不同公司的账号与佣金分开。
5. 只用一个网址，不接受每家公司单独部署、单独网址。
6. 达人知道各公司之间的关系。

此时 M1（达人、商品、对应关系、链接、点击）已完成，M2（表格、订单、佣金、看板）尚未开始。

## 决定

1. **共享一个数据库，业务表加 `tenant_id`** 区分公司。新增 `sys_tenant` 公司表，迁移创建默认公司（`id = 1`），现有数据归入该公司。设计细节见设计说明书 §3.4。
2. **自动过滤**：使用 MyBatis-Plus `TenantLineInnerInterceptor`，所需的 `mybatis-plus-jsqlparser` 已在项目中，不新增依赖。取不到当前公司时报错，不放行。跨公司的后台维护和平台管理接口必须显式声明，并写明原因。
3. **当前公司只从登录态取**：管理员按全系统唯一的用户名确定公司；达人用邮箱 + 密码登录，邮箱属于多家公司且密码都匹配时，由达人选择公司。
4. **新增平台管理员角色**：只管理公司，看不到业务数据；初始平台管理员由原有初始化环境变量创建。
5. **不改的部分**：达人编号、微店店铺 ID、管理员用户名保持全系统唯一，因此跳转服务、Redis 链接索引与点击事件的结构不变。
6. **公司级凭证保存在数据库**：微店、Google 等第三方凭证按公司用 AES-256-GCM 加密入库，主密钥来自环境变量；**不引入配置中心**。
7. **数据库行级安全（RLS）本期不启用**。
8. 由任务 06c 实现，排在 M2 之前，使后续模块从一开始就按公司开发。

## 备选方案及放弃原因

| 方案 | 放弃原因 |
|---|---|
| 每家公司单独部署（独立库、独立网址） | 客户不接受多个网址；N 套环境的备份、升级、监控成本随公司数增加 |
| 每家公司一个 schema 或一个数据库 | 新建公司要执行迁移、管理多套连接；Flyway、分区维护、链接索引重建都要按公司循环。在"同一客户、规模小、不跨公司汇总"的前提下，隔离收益不抵复杂度 |
| 不做自动过滤，各 service 手写公司条件 | 漏写一处就是跨公司泄露，审查与测试难以穷尽；自动过滤加"取不到公司即报错"是默认安全的做法 |
| 同时启用 PostgreSQL 行级安全作为第二道防线 | 每条语句都要在事务内执行 `SET LOCAL` 设置公司，连接池复用连接时有残留风险；后台跨公司任务需要单独的数据库角色；Flyway 用表所有者执行，所有者默认不受 RLS 约束，需要额外配置。各公司同属一个客户，泄露的影响有限。表已有 `tenant_id`，以后需要时可以直接加策略，不改表结构 |
| 达人一个全局身份，加入多家公司并在登录后切换 | A 公司停用账号或重置密码会影响该达人在 B 公司的使用，违反"各公司账号分开" |
| 达人用达人编号登录 | 实现最简单，但海外达人难以记住编号；邮箱登录加必要时选择公司，体验更好 |
| 引入配置中心（Nacos、Apollo 等） | 公司级凭证是由各公司管理员维护、需要审计的业务数据，不是部署配置；单台服务器上只有两个服务，配置中心只会多一个需要运维和防护的组件 |

## 影响

- 新增迁移脚本：建 `sys_tenant`；给现有表加 `tenant_id`（先带默认值 1 填充，再去掉默认值）；调整唯一约束与按公司列表的索引。已合并的迁移不修改。
- 所有手写 SQL 都要经过多租户插件的解析，或者显式声明为系统范围。插件无法解析的 PostgreSQL 语法须改写，由任务 06c 逐条核对。
- 新增"跨公司隔离"集成测试，并检查每张业务表都有 `tenant_id`。之后每个新模块都要遵守（规范 04、05、06 相应条款）。
- 达人在多家公司使用相同密码时，登录响应耗时会多出几倍，可以据此推断"该邮箱属于多家公司"。达人知道各公司之间的关系，因此接受。
- 已在其他公司使用的达人编号、微店店铺 ID 或用户名会提示"已存在"。各公司同属一个客户，可以接受。
- 工作量：任务 06c 约 6～8 人天（改造 M1、平台管理、达人端多公司登录）；后续模块因按公司开发，约增加 3～5 人天。
