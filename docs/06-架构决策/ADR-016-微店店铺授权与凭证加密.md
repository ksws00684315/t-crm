# ADR-016：微店店铺授权与凭证加密

- 状态：已接受
- 日期：2026-10-12
- 背景：CRM 需要为后续订单、退款同步和商品复制准备微店接入底座；客户尚未确认应用类型，也没有可用于开发联调的真实账号。

## 决策

1. 同时支持微店自用型与服务型应用。自用型凭证按店铺保存，只能访问注册的商城版店铺；服务型应用按公司保存，并由每个店铺单独授权。授权回调中的 `openid` 必须与该 CRM 店铺的 `weidian_shop_id` 完全相同。
2. 第三方 secret 与访问 / 刷新令牌使用 `SecretCipher` 的 AES-256-GCM 加密，使用全局 `TCRM_SECRET_KEY`（Base64 32 字节）和每次随机的 12 字节 nonce，密文采用 `v1:` 前缀。环境变量必填；密钥丢失后需重新录入全部凭证。
3. OAuth `state` 为 32 位随机字母数字字符串，放在 Redis 并设置 10 分钟有效期。回调使用 GETDEL 一次性消费 state；拒绝、过期、重放、令牌交换失败和店铺身份不匹配都只返回固定原因码，不返回服务商响应或凭证。
4. 所有店铺令牌的获取与更新集中在 `WeidianTokenCenter`，并持有 `weidian:token:{shopId}` 分布式锁。每小时系统范围调度只枚举启用公司，再进入每家公司范围处理已启用店铺；到期 3 小时内续期。API 发现 access token 无效时最多被动刷新一次，同店铺 10 分钟防抖。
5. 外部 API 请求 POST 至官方网关，`public` 与 `param` 采用 form URL 编码。按 appkey 通过 Redisson 限制 QPS；暂时性错误与频率错误以 1、2、4 秒退避，最多重试 3 次。应用错误、无权限和授权错误不重试；买家个人信息不建模、不解密。

## 考虑过的方案

- 令牌和 secret 放在环境变量：拒绝。凭证按公司和店铺授权动态变化，环境变量不适合逐店管理，也无法安全展示状态。
- 明文存库：拒绝。数据库备份或只读访问会暴露可用凭证。
- 引入配置中心：拒绝。增加运行依赖与部署维护面；当前公司级配置存储和平台级密钥环境变量已满足需求。
- 只支持服务型或只支持自用型：拒绝。客户实际应用类型尚未确认，且两种类型的授权能力不同；按店铺选择可避免绑死接入方式。
- 每个调用方自行刷新令牌：拒绝。并发会消耗自用型每天 20 次取令牌配额，还可能让旧令牌覆盖新令牌。

## 后续核实

- 微店官方文档未说明 `refreshExpireTime` 表示绝对毫秒时间戳还是毫秒时长；实现按 `10^12` 阈值区分，并封顶授权后 30 天。M0 真实账号冒烟需核实。
- 官方订单详情 v2.0 示例缺少一个 JSON 逗号；测试夹具按相同数据修复该语法错误。`fans1_id` / `fans1_money_total` 出现在示例但没有字段说明，留在 `raw`。
- 官方退款列表 `add_time` 字段类型写作字符串，示例是 Unix 秒；退款详情 `refundFee` 文档单位为分。实现保留这些来源差异并分别解析。
- 店铺在时间窗口内没有退款时，`open.SellerQueryRefundList` 2.0 的响应根字段只有 `list`、没有 `totalNum`（任务 55 实测）；退款同步在该情况下按本页条数判断翻页结束，并设单窗口 200 页安全上限（任务 56）。
- M0 需核实服务型 `openid`、商品 `seller_id` 是否与系统 `weidian_shop_id` 使用相同标识空间。前者必须匹配才完成授权；后者仅作为状态警告。
- 任务 65 曾认为 `vdian.item.add` 1.5 成功返回的商品 ID 字段是 `itemid`，该字段名假设不成立。真正原因是解析器重复剥离了 `result`（任务 66 修复）。`vdian.item.add` 的真实商品 ID 字段名待修复后首次 M0 实测确认；解析仍兼容 `itemid` / `item_id` / `itemId`。任务 55 实测时店铺无商品，未覆盖该字段。
