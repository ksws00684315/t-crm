# ADR-007 构建与测试工具的许可证规则

- 状态：已接受（2026-10-05）
- 决策人：项目负责人

## 背景

任务 02 第三次续做时，Codex 发现代码检查工具 Checkstyle 的引擎 `com.puppycrawl.tools:checkstyle:14.3.0` 采用 LGPL-2.1-or-later（其 Maven 插件包装层为 Apache-2.0）。规范 07 的许可证白名单当时未区分运行时依赖与构建工具，Codex 按停止条件中止。

Checkstyle 只在构建时检查源码，不会被打包进交付给客户的程序。

## 决定

规范 07 按"是否随交付物分发"区分：

1. **运行时依赖**：继续适用白名单（MIT、Apache-2.0、BSD、EPL 等）。
2. **构建与测试工具**：不打包进交付物、不修改源码、不作为库链接进业务代码时，可使用任何 OSI 认可的许可证，包括 LGPL 与带 Classpath 例外的 GPL；AGPL、SSPL 及非 OSI 许可证仍禁止；白名单外的须在 PR 中列出。

保留 Checkstyle，并补充其规则（大括号、单行单语句等），弥补 google-java-format 不检查的 Google Java Style 条款。

## 理由

- 开源许可证的主要义务在**分发**时产生；只在开发过程中使用、不随产品交付的工具，不对交付代码产生许可证约束。这是业界区分"交付物许可证"与"工具许可证"的通行做法。
- AGPL 的义务由网络交互触发，SSPL 限制范围更广，即使只作为工具使用也存在争议，因此仍然禁止。

## 备选方案及放弃原因

| 方案 | 放弃原因 |
|---|---|
| 移除 Checkstyle | google-java-format 只做排版，不检查控制语句缺少大括号、通配符导入、`System.out` 等；审查发现已有约 17 处控制语句缺少大括号，需要工具拦截 |
| 为 Checkstyle 单独登记例外 | 构建工具是一类问题（测试框架、前端构建工具也会遇到），应在规则层面明确 |

## 影响

- 规范 07 第 3 节新增"构建与测试工具"规则。
- OSV-Scanner 的许可证检查仍针对项目依赖图；Maven 插件不在其扫描范围内，构建工具的许可证由 PR 审查把关。
