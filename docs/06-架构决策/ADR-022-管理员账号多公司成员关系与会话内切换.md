# ADR-022：管理员账号多公司成员关系与会话内切换

- 状态：已接受（2026-10-17）
- 决策人：项目负责人（2026-10-16 决定做「多公司账号与切换」，采用调研报告的 P2 模式）
- 相关：[ADR-014](ADR-014-多公司采用共享库与公司字段隔离.md)（部分修订）、[ADR-018](ADR-018-管理端改为超级管理员加可配置权限的子账号.md)（部分修订）、[ADR-017](ADR-017-管理端每次登录需要图形验证码.md)、[多租户切换方案调研](../02-调研/多租户切换方案调研.md)、任务 21a / 21b

## 背景

ADR-014 规定管理员账号只属于一家公司（`sys_user.tenant_id`），同一个人为多家公司工作时在每家各开一个账号，界面不能切换公司。ADR-018 的子账号权限码表 `sys_user_permission` 也只按账号授予。

负责人 2026-10-16 决定：同一个人用**一个账号**进入他所属的多家公司，在界面上切换当前公司；在各公司的角色与权限分别授予（例如在 A 公司是超级管理员、在 B 公司是商务）。达人端与平台管理员的规则不变。

调研报告第 2 节归纳了四种模式：P1 账号单归属（现状）、P2 成员多归属 + 服务端会话中的当前公司、P3 成员多归属 + 前端请求头自报公司、P4 平台「进入租户」。

## 决定

采用 **P2**。

### 1. 数据模型（迁移 `V202610172300__multi_company_membership.sql`）

1. `sys_user` 改为「人」：保留用户名（全系统唯一）、密码、姓名、邮箱、整个账号的启停（只有平台管理员能改）、凭据版本、最近登录时间。`role` 只区分 `PLATFORM_ADMIN` 与 `MEMBER`（公司账号）；`tenant_id` 改名为 `last_tenant_id`（上次所在的公司，只用于登录时选默认公司）；`data_scope`、`post_template` 迁到成员关系后删除。
2. 新表 `sys_user_tenant`（成员关系）：`user_id`、`tenant_id`、`role`（`SUPER_ADMIN` / `STAFF`）、`post_template`、`data_scope`、`status`（该公司内的启停）、`last_login_time` 与通用字段，`(user_id, tenant_id)` 在未删除行中唯一。原 `sys_user` 上关于角色与数据范围的 CHECK 搬到这里。
3. `sys_user_permission` 按公司授予：唯一键改为 `(user_id, tenant_id, permission_code)`，同一个人在不同公司的权限码互不影响。
4. 回填：每个现有公司账号生成一条成员关系（公司、角色、数据范围、岗位模板、状态取自原 `sys_user`）；权限码的公司取该账号原来的公司；平台管理员没有成员关系。迁移前的停用都是公司级的，已写入成员关系，因此公司账号的账号级 `status` 统一置为启用。
5. `sys_user` 加入 `CompanyTenantLineHandler` 的始终忽略列表。**理由**：账号不再属于任何公司，表上也没有 `tenant_id`；公司内的代码只能经由 `sys_user_tenant`（受公司过滤）找到账号，所有账号查询都与成员关系连接或按成员关系的结果取 ID。`sys_user_tenant`、`sys_user_permission` 都带 `tenant_id NOT NULL`，照常过滤。

### 2. 当前公司与会话

1. 当前公司保存在 Sa-Token **令牌会话**中（属性 `currentTenantId`，与 `credentialVersion` 放在一起）。同一浏览器的多个标签页共用一个令牌，因此共用当前公司。
2. 所有「当前公司」都从这里来：多租户插件的当前公司、`/me` 的 `tenantId`、角色与权限码（取该公司成员关系的角色与该公司的权限码）。
3. 每次请求校验：当前公司的成员关系启用、公司启用、账号启用；任一不满足即结束**这个令牌**并返回 401 `AUTH_ACCOUNT_DISABLED`，不踢掉同一个人在其他公司的令牌。
4. 上线前签发的令牌没有 `currentTenantId`：按账号的 `last_tenant_id`（即迁移前的公司）补上，不强制重新登录。

### 3. 登录与切换

1. 用户名、密码、验证码流程不变（ADR-017）。登录成功后，`last_tenant_id` 对应的成员关系仍可用就进入它，否则进入可用成员关系中公司名称排序第一的；一个可用的都没有时与密码错误一样返回 401 `AUTH_INVALID_CREDENTIALS`（同样计入登录失败），不签发令牌（PR #65 审查修订：不能让正确密码与错误密码的回答不同）。平台管理员登录不变，没有当前公司。
2. `POST /admin-api/auth/company {tenantId}`：只能切到本人可用成员关系所在的公司，否则 403 `AUTH_COMPANY_NOT_MEMBER`；平台管理员在角色检查处 403 `AUTH_FORBIDDEN`。成功后更新令牌会话的当前公司与 `last_tenant_id`，在**目标公司**写操作日志「切换公司」（参数为来源公司 ID），返回与 `/me` 相同的结构。

### 4. 防止「界面显示 A 公司，操作落在 B 公司」

管理端在每个请求上带 `X-Company-Id`（界面当前显示的公司）。后端拦截器在带了这个头、且与令牌会话中的当前公司不一致时返回 409 `AUTH_COMPANY_SWITCHED`，不执行业务。这个头**只用来核对，绝不用来决定公司**；没带时不校验；`/admin-api/auth/**`、平台接口、对外复制接口不校验。

### 5. 账号管理（公司超管）

1. 列表只有本公司成员，每行带 `companyCount`（这个人属于几家公司）。
2. 新建仍是新建账号 + 本公司成员关系；用户名已存在 409 `USER_USERNAME_EXISTS`。公司超管**不能**把其他公司已有的账号拉进本公司。
3. 角色、岗位模板、数据范围、启停、权限码只作用于本公司的成员关系；「至少保留一个启用的超管」按公司计算；停用 STAFF 时 `StaffDisabledEvent` 带本公司 ID，只把本公司内他名下的达人改为未分配；停用只结束他在本公司的令牌。
4. 姓名、邮箱、密码属于个人：`companyCount = 1` 时公司超管仍可修改；大于 1 时返回 422 `USER_MULTI_COMPANY_LOCKED`，由平台管理员修改。
5. 「可作为商务」按本公司成员关系判定：成员关系启用 + `STAFF` + `OWN` + 本公司权限码含 `kol:edit`，且账号启用。超管列表按本公司启用的 `SUPER_ADMIN` 成员（成员关系与账号都启用，查询只读本公司的 `sys_user_tenant`）。

### 6. 平台管理员

新增：按用户名**精确**查一个公司账号及其全部成员关系（不支持模糊搜索；查找结果含 `email`，无则 null）、把已有账号加入某公司（`STAFF` 按岗位模板预填权限码；已是成员 409 `USER_ALREADY_MEMBER`；成员关系与权限码在同一事务中写入）、修改公司账号的姓名邮箱、重置公司账号密码（所有令牌失效）、整个账号启停（停用时结束所有令牌）。平台管理员账号不在这些接口的范围内：查找返回空，修改、改密、启停返回 404 `COMMON_NOT_FOUND`（PR #65 审查修订）。原有「为公司创建超管、重置超管密码」保留。平台管理员仍**看不到任何业务数据**，不能进入公司。

## 备选方案及放弃原因

| 方案 | 放弃原因 |
|---|---|
| 维持 P1（每家公司各开一个账号） | 负责人已确认存在一人服务多家公司的需求；多套账号密码难管理，离职时也要逐个停用 |
| P3：前端在请求头里自报公司，后端校验成员关系 | 公司由客户端声明，任何一处漏校验即跨公司；与 ADR-014「当前公司只从登录态取」直接冲突；缓存、异步任务、审计都要额外防护 |
| P4：平台管理员「访问租户」 | 本项目要求平台管理员看不到业务数据，是反向需求；把它当作日常切换会扩大平台账号的风险 |
| P2 的变体：切换时签发新令牌、作废旧令牌 | 同一浏览器多个标签页会出现旧令牌失效、需重新登录的情况；更新令牌会话中的当前公司即可，配合 `X-Company-Id` 核对解决标签页显示不一致 |
| P2 的变体：每个标签页独立令牌、各自一个当前公司 | 管理端把令牌存在浏览器共享存储中，按标签页隔离要改造整个前端会话管理；收益不抵成本 |

## 后果

- **修订 ADR-014**：「同一个人为多家公司工作时，在每家各开一个账号」改为「一个账号可属于多家公司」；「管理员按全系统唯一的用户名确定公司」改为「用户名定人，成员关系定可进入的公司，当前公司保存在登录会话中，可在本人的成员关系之间切换」。达人端规则不变。
- **修订 ADR-018**：权限码改为按公司授予（`sys_user_permission` 带公司、唯一键含 `tenant_id`）；角色、数据范围、岗位模板存于成员关系；「至少保留一个超管」按公司计算。
- 每次请求多读一条成员关系；`sys_user` 不再受多租户插件过滤，读写账号的代码必须经由成员关系限定公司（全部集中在 `system` 模块）。
- 用户名仍全系统唯一，公司超管新建账号时遇到其他公司的同名账号只会得到「已存在」，需要请平台管理员把该账号加入本公司。
- 登录时若所有公司都不可用，返回与密码错误相同的 `AUTH_INVALID_CREDENTIALS`，并计入登录失败次数。正确密码与错误密码的回答因此相同，不会暴露「账号存在但无可用公司」（PR #65 审查修订，原先返回 `AUTH_ACCOUNT_DISABLED`）。
- 管理端（任务 21b）需要：顶栏公司切换、每个请求带 `X-Company-Id`、收到 409 `AUTH_COMPANY_SWITCHED` 时刷新到新公司。
