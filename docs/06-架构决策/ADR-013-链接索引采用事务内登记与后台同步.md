# ADR-013 链接索引采用事务内登记与后台同步

- 状态：已接受（2026-10-07）
- 决策人：项目负责人（任务 06b 提示词 §4.1）

## 背景

任务 06 在业务事务提交后（`AFTER_COMMIT`）直接写 Redis 链接索引，并每天 04:30（UTC）全量重建。PR #24 的审查指出三处因此失效的保证：

1. 全量重建先读出映射、写入暂存 key，再 `RENAME` 覆盖正式 key。重建读完之后才提交的映射会被这次覆盖抹掉。
2. 增量写 Redis 失败只打错误日志，没有重试，也没有积压告警，只能等下一次全量重建。
3. 停用店铺会在请求线程上刷新该店的全部链接，请求要等到 Redis 写完才返回。

## 决定

1. 映射、商品、店铺、达人的变更在提交前向 `crm_link_index_outbox` 插入一行，与业务变更同一事务。回滚则不会留下这一行。请求线程不写 Redis。
2. 后台工人空闲时每 2 秒领取一次到期行。有积压时在同一把分布式锁内按每批 200 行排空，直到没有到期行为止，避免大批导入要等满 1 分钟才能被索引。
3. 每个达人一把锁 `link:index:kol:{kolId}`。增量同步和全量重建都在持锁期间重新读取数据库，再写 Redis。两者可以同时跑，但同一个达人的写入串行。
4. 写入失败则 `attempts` 加 1，记下截断后的英文错误，并按 10 秒、30 秒、1 分钟、5 分钟、10 分钟退避，之后固定 10 分钟。行不丢弃，每次失败打 ERROR 日志。进程重启后继续处理剩余行。
5. 另一把锁上的监控每分钟看一次：最老未处理行等待超过 1 分钟记 WARN，超过 10 分钟记 ERROR；任一 `attempts >= 5` 的行记 ERROR，并带上范围和编号。

## 备选方案及放弃原因

| 方案 | 放弃原因 |
|---|---|
| 维持 `AFTER_COMMIT` 直接写 Redis | 停用店铺会堵住请求线程；失败没有可恢复的记录，只能等每日重建；重建的 `RENAME` 仍会盖掉读取之后写入的映射 |
| 事务同步回调里写 Redis | 仍然发生在请求线程上，回调失败后没有持久化的重试队列 |
| 数据库事务与 Redis 用两阶段提交绑在一起 | 跳转服务依赖 `RENAME` 做整键替换，Redis 无法加入数据库事务；失败语义比发件箱更难解释 |

## 影响

- 链接索引在事务提交后数秒内更新，不再与请求同时完成。管理端界面不变。
- 索引遗漏或陈旧由本机制在数秒到数分钟内修正，每日全量重建仍保留，用于修复漏网和删除多余 key。
- 发件箱积压和反复失败由监控日志暴露；在引入站内通知之前，运维看日志。
