# ADR-018：管理端改为超级管理员 + 可配置权限的子账号

- 状态：已接受（2026-10-16）；部分被 [ADR-022](ADR-022-管理员账号多公司成员关系与会话内切换.md) 修订（2026-10-17）
- 被 ADR-022 修订的条目：
  - 权限码改为按公司授予：`sys_user_permission` 的唯一键为 `(user_id, tenant_id, permission_code)`，同一个人在不同公司的权限码互不影响；
  - 角色、数据范围、岗位模板存于成员关系 `sys_user_tenant`，按公司分别设置；「至少保留一个启用的超管」按公司计算。
- 决策人：项目负责人（采纳 2026-10-14 客户会议结论）
- 相关：[ADR-014](ADR-014-多公司采用共享库与公司字段隔离.md)（多公司）、设计说明书 §1.3、§3.1、§3.2

## 背景

现有实现按固定角色授权：`PLATFORM_ADMIN`、`SUPER_ADMIN`、`OPERATOR`、`FINANCE`，商务 = `OPERATOR` + 数据范围 `OWN`。每个接口用 `@SaCheckRole` 写死允许的角色（当前约 35 处）。

2026-10-14 客户会议改为：

- 每家公司只有三种人：**超级管理员**（兼财务）、**运营**（商品上架下架，能看全部达人）、**商务**（管理自己名下达人的全部信息，只能看自己的达人）；
- 不再需要财务角色，财务工作由超级管理员完成；
- 我方提议「像千牛那样，主账号给子账号逐项勾选可用功能」，客户同意。

需求补充文档的需求 3 另写明：运营可以查看全部达人但不能修改，商务编辑自己名下的达人，商品权限单独划分。

## 决定

1. **账号类型**：
   - 平台管理员：不变，`PLATFORM_ADMIN`。
   - 公司主账号：`SUPER_ADMIN`，拥有本公司全部权限，权限不可配置。
   - 子账号：`STAFF`，权限由超级管理员逐项勾选。
   - `OPERATOR`、`FINANCE` 不再作为角色存在。
2. **权限码**：功能权限用固定的权限码表示，例如 `kol:view`、`kol:edit`、`product:status`、`payout-account:review`，完整清单见设计说明书 §3.1。
   - 权限码在代码中集中定义（一个枚举），不存数据库字典表。
   - 新增功能时在枚举中加码，并补中英文名称。
3. **授予方式**：子账号的权限保存在 `sys_user_permission`（`user_id`、`permission_code`），超级管理员在用户管理页勾选。
   - 新建子账号时选择**岗位模板**「运营」「商务」或「财务」，自动勾上该岗位的默认权限，之后可以逐项增减。
   - 模板只是预填，不与账号绑定；修改模板不影响已有账号。
4. **数据范围**：保留现有 `data_scope`（`ALL` / `OWN`）。
   - 商务模板默认 `OWN`，运营、财务模板默认 `ALL`；
   - 超级管理员可按账号修改；
   - `OWN` 的过滤规则不变（设计说明书 §3.2）。
5. **超管专属**：以下操作只允许 `SUPER_ADMIN`，不出现在可勾选清单中：
   - 用户与权限管理、系统配置、接口参数（微店、Google）、操作日志；
   - 审批预付、把提现申请标记为已打款；
   - 转移商务名下的达人。

   理由：这些是资金和账号安全的最后一道关，客户明确由超级管理员本人负责。
6. **接口声明**：
   - 业务接口一律改用 `@SaCheckPermission("权限码")`；
   - 超管专属接口用 `@SaCheckRole("SUPER_ADMIN")`；
   - 平台接口仍用 `@SaCheckRole("PLATFORM_ADMIN")`。
   - Sa-Token 的 `StpInterface` 从请求级账号缓存返回权限列表：超级管理员返回全部权限码，子账号返回已授予的码。
   - 仍然每次请求重读账号（设计说明书 §3.3），改权限立即生效，不需要重新登录。
7. **前端**：菜单和按钮按 `/auth/me` 返回的权限码显示，不再按角色名判断；没有权限的菜单不显示，直接访问路由时进入 403 页面。
8. **迁移**：
   - 新增 Flyway 脚本：把已有 `OPERATOR` / `FINANCE` 账号改为 `STAFF`，按原角色授予对应的默认权限；
   - `FINANCE` 账号授予原财务可见的只读权限，资金类操作由超级管理员完成；
   - 生产尚无真实数据，迁移只需保证测试环境与开发库可升级；
   - 已合并的迁移脚本不改。
9. **审计**：授予、撤销权限与修改数据范围写入操作日志，并记录修改前后的权限码集合。

## 影响

- 约 35 处 `@SaCheckRole` 需要替换。管理端路由、菜单、按钮的权限判断随之改动。
- 越权测试从「换一个角色访问」改为「缺少某个权限码访问」，每个权限码至少一条拒绝用例。
- 「商务 = 运营 + OWN」的说法作废，改为「商务模板 = 若干权限码 + OWN」。

## 备选方案及放弃原因

| 方案 | 放弃原因 |
|---|---|
| 保留固定角色，只删除财务角色 | 客户同意可配置；固定角色以后每次调整都要改代码 |
| 完整 RBAC（自定义角色 → 权限，账号挂多个角色） | 一家公司只有几十个账号，「岗位模板 + 逐账号勾选」已经够用，少一层角色表与界面 |
| 权限码存数据库字典表 | 权限码与代码中的接口一一对应，存库反而要处理代码与数据不一致 |
| 动态菜单（菜单存数据库） | 菜单随代码版本发布即可，按权限码显隐已满足需求 |
| 资金审批也可授予子账号 | 客户明确由超级管理员负责；以后需要时把对应操作改为可勾选的权限码即可 |

## 修订记录

### 2026-10-22 修订：新增 FINANCE 模板

依据负责人提供的《CRM权限与数据范围-27项精简版-20261022》。在「运营 / 商务」两种岗位模板之外，新增可配置子账号模板 `FINANCE`（财务）：默认数据范围 `ALL`，授予达人 / 商品 / 订单 / 收入只读、收款账户与提现审核、三个看板与导出等权限码，不含商品或订单写操作。

与本文「2026-10-16 取消财务角色」的关系：财务**不再是固定角色**（`FINANCE` 角色已废除，见上文决定第 1 条），但可以作为**可配置的子账号岗位模板**存在。超级管理员仍兼资金类最后一道关（审批预付、标记提现已打款等，见上文决定第 5 条）。
